## 第二部分：18 条可以直接借鉴的具体设计点

以下 18 条设计点均源自对参考仓库正文的实际阅读，具有极高的工程实战价值。

### 1. 通讯平台群聊「线路规程（Line Discipline）」与防抢话防抖机制
- **参考出处**：`18-通讯平台.md` 第三节、第六节（线路规程）
- **解决问题**：在外部群聊场景中，AI 极易在连续消息涌入时过度插话、抢话、在短时间内重复触发多个昂贵回合，造成刷屏和 Token 浪费。
- **落脚 GQYv2**：`docs/designs/16-连接器与外部平台.md` 第 9 节（聊天室），新增 9.1 小节「线路规程与防抖状态机」。
- **改动内容**：引入进站防抖缓冲（500ms–1500ms 动态聚合连续发言）、发言冷却时间（Cooldown）、@提及强制激活与群聊被动倾听模式。
- **成本**：中。

### 2. 通讯平台驱动 Quirk 表（平台特异性声明与补偿）
- **参考出处**：`18-通讯平台.md` 第十一节（驱动的 quirk 表）
- **解决问题**：不同外部通讯平台（QQ、Telegram、Discord、iMessage）在单条文本长度上限、图片内联方式、Markdown 支持度、撤回时效上差异巨大，平台分支代码容易散落腐化。
- **落脚 GQYv2**：`docs/designs/16-连接器与外部平台.md` 第 3.3 节（能力声明），补充「驱动 Quirk 规格表」。
- **改动内容**：在 Connector 协议中增加 `DriverQuirks` 声明（如 `max_text_bytes`, `supports_markdown`, `rate_limit_interval_ms`），网关根据声明自动完成长消息分段与降级转义。
- **成本**：小。

### 3. 提示词「四去处（Four Destinations）」分类与化石区指令清理规范
- **参考出处**：`26-提示词.md` 第一节、第二节
- **解决问题**：工具返回结果中常夹带临时指令（如“请根据以上内容回复用户”），多轮对话后沉淀为化石历史，污染上下文并降低模型遵循主指令的能力。
- **落脚 GQYv2**：`docs/designs/04-前缀缓存账本.md` 第 4 节与 `05-上下文与压缩.md` 第 3 节。
- **改动内容**：明确将模型输入划分为：稳定系统指令、本轮动态事实、历史化石事件、工具返回纯数据。落库前自动过滤工具输出中的指令性文本。
- **成本**：小。

### 4. 工具加载三态（Full / Stub / Off）与按组动态按需加载
- **参考出处**：`25-工具加载.md` 第一节至第三节
- **解决问题**：工具数量膨胀导致 System Prompt 占用过高，增加首字延迟并提高模型误用工具的概率。
- **落脚 GQYv2**：`docs/designs/07-工具系统.md` 第 4 节（加载与生命周期）及 `04-前缀缓存账本.md` 第 6 节。
- **改动内容**：将工具划分为多个逻辑组（代码组、搜索组、任务组），支持全量（Full）、存根（Stub）与关闭（Off）三态。模型初次调用 Stub 时动态提升为 Full 并通知前端。
- **成本**：中。

### 5. 模型用途四档划分（Cheap / Fast / Smart / Auxiliary）与降级池
- **参考出处**：`15-模型与供应商.md` 第四节、第五节
- **解决问题**：入群判断、记忆抽取、对话摘要等辅助小任务调用主力大模型成本高且浪费算力；单点供应商故障导致任务卡死。
- **落脚 GQYv2**：`docs/designs/06-模型供应商适配.md` 第 5 节（模型调度与故障切换）。
- **改动内容**：在配置中显式区分 4 个档位，为 Auxiliary 任务指定专用小模型（如 cheap 档），并配置备用 Provider 动态故障转移池。
- **成本**：中。

### 6. 配置系统：Schema 驱动生成验证器、TUI 表单与 Web 设置
- **参考出处**：`14-配置.md` 第二节（一份清单，处处推导）
- **解决问题**：新增配置项时，需要手动修改 Rust 结构体、TOML 示例、TUI 输入框、Web 设置页和文档，极易遗漏脱节。
- **落脚 GQYv2**：`docs/designs/12-人格配置与场所.md` 第 3 节与 `15-Web控制台与桌面.md` 第 6 节。
- **改动内容**：引入 `schemars` 通过 `cargo xtask` 生成 JSON Schema，Web 控制台与 TUI 直接由 Schema 驱动生成表单校验与 UI。
- **成本**：中。

### 7. 人格与预设正交解耦（Persona vs Preset）
- **参考出处**：`16-人格与预设.md` 第一节、第二节
- **解决问题**：角色人设（语气、性格、身份）与运行时开关（启用的工具组、权限级别、模型档位）绑定过紧，导致切换场景时人设丢失或权限错乱。
- **落脚 GQYv2**：`docs/designs/12-人格配置与场所.md` 第 5 节（persona）新增 5.7 小节「Preset 预设矩阵」。
- **改动内容**：Persona 只定义角色提示词与风格；Preset 定义工具面、权限和模型档位。会话可在同一 Persona 下自由切换 Preset。
- **成本**：中。

### 8. 交互协议中的「抽屉（Drawer）」机制（审批、提问、选择正规化）
- **参考出处**：`04-核心协议.md` 第五节、`13-终端界面.md` 第四节
- **解决问题**：权限审批、多选确认、用户提问混在普通流式文本中，前端无法以结构化表单或模态卡片进行渲染。
- **落脚 GQYv2**：`docs/designs/13-网关与API协议.md` 第 6.2 节（事件目录）与 `14-TUI.md` 第 7 节。
- **改动内容**：定义独立的 `DrawerEvent`（包含 Approval, Question, Choice 三种形态），带唯一 `drawer_id`，前端统一弹出抽屉控件响应并回传。
- **成本**：小。

### 9. 上下文压缩检查点（Checkpoint）关键事实萃取清单
- **参考出处**：`09-压缩.md` 第三节、第四节
- **解决问题**：长会话压缩时若完全依赖大模型自由发挥，极易丢失任务待办清单、已修改文件路径及未决设计决策。
- **落脚 GQYv2**：`docs/designs/05-上下文与压缩.md` 第 5 节（压缩算法与提示词）。
- **改动内容**：在压缩 Prompt 中强约束结构化提取 4 类资产：(1) 待办列表与进度；(2) 本会话已修改文件及摘要；(3) 核心设计决策；(4) 仍待确认的问题。
- **成本**：小。

### 10. TUI 界面宽窄屏自适应与底栏 Token 溢出显示降级策略
- **参考出处**：`13-终端界面.md` 第二节、第八节
- **解决问题**：在小尺寸终端（<100列）下，状态栏多项数据挤占折行，破坏 TUI 界面美观。
- **落脚 GQYv2**：`docs/designs/14-TUI.md` 第 4.2 节（布局模式与尺寸）。

### 11. 纯逻辑内核（Pure-Logic Reducer）状态推进解耦
- **参考出处**：`02-内核.md` 第四节（纯逻辑内核）
- **解决问题**：回合引擎直接在异步循环中混合调用网络与文件 I/O，导致状态机难以编写确定性的无 mock 纯内存单测。

## 第三部分：6 条不建议照搬的设计点（结合定位与实测差异）

以下设计点因产品定位、技术哲学及历史实测数据的根本不同，明确**不建议**在 GQYv2 中照搬：

### 1. 完全废弃 SQLite、改用纯文件系统 JSONL 段文件存储
- **参考主张**：`07-存储.md` 主张放弃关系型数据库，采用纯文件目录树 + 分段 JSONL 文件 + 内存索引，声称以此彻底规避 Schema 迁移痛点。
- **为什么不照搬**：
  1. **复杂查询性能低下**：GQYv2 需要频繁进行记忆多维检索（FTS5全文检索/向量检索）、账本条目回溯、多任务树关联查询。在纯 JSONL 文件系统上重写查询引擎是巨大的倒退与重复造轮子。
  2. **ACID 事务与崩溃安全性**：SQLite WAL 模式经过数十年工业级验证，支持高并发零锁竞争读取与原子写入；自建分段索引在意外断电或系统崩溃时极易产生元数据与正文不一致。
  3. **GQY 已有成熟迁移体系**：GQY 团队在 v1 实践中已经成功验证了 37 版增量迁移流程，具备极高工程可控性。

### 2. 引入 Linux 式多租户体系（UID / GID / 权限位 / 组管理）
- **参考主张**：`06-多用户与身份.md` 仿照 Linux 构建了完整的用户、用户组、文件所有权（owner/group/others）、chmod/chown 以及多租户用量配额。
- **为什么不照搬**：
  1. **定位错位**：GQYv2 定位为个人专属的私人伴侣与开发 Agent，核心诉求是单人私有、极致安全与本地化。
  2. **过度设计**：引入 UID/GID 会导致所有数据表和 API 增加多租户隔离字段，带来巨大的心智负担和复杂度，完全脱离了个人端侧使用场景。

### 3. 将基础文件与搜索工具全部拆为外部扩展包与动态包管理器
- **参考主张**：`10-自带软件.md`、`12-进程形态与分发.md` 主张内核极致空心化，连读写文件、grep、glob 都要做成独立包（.mpk）由用户空间动态安装管理。
- **为什么不照搬**：
  1. **违背单一自包含二进制原则**：GQYv2 的核心原则是「零外部运行时依赖」与「单二进制分发」。基础文件与搜索工具内置在主程序中，调用零 IPC 开销且永不损坏。
  2. **过度碎片化**：将基础工具外部化会增加跨进程 IPC 延迟、包依赖冲突及安装失败率。

### 4. 废弃中心化网关而采用纯 Unix Stdio/RPC 管道架构
- **参考主张**：`04-核心协议.md`、`22-命令行.md` 深度绑定基于 Stdio/UDS 的轻量 Unix RPC 协议。
- **为什么不照搬**：
  1. **无法支撑现代化多端形态**：GQYv2 拥有内嵌 Web 控制台、TUI、可选 Tauri 桌面、外部 IM 连接器以及点对点设备共享网络。
  2. **标准生态兼容**：Axum（HTTP/SSE/WebSocket）不仅天然支持浏览器与桌面端，还能通过 UDS 提供同等高效的本地 IPC。

### 5. 纯文本文件系统承载记忆与知识库索引
- **参考主张**：`17-记忆.md`、`19-知识库.md` 试图在纯文本 Markdown/JSON 文件上建立简易记忆与倒排索引。
- **为什么不照搬**：
  1. **无法支撑长时记忆代数**：GQYv2 的记忆系统包含强度衰减、遗忘曲线、聊后复盘与四个 Reset 代数命令，需要 SQLite 强类型表提供事务保障。
  2. **向量与全文检索集成**：SQLite 原生支持 FTS5 和向量扩展，能无缝实现混合检索，纯文件自建索引极易腐化。

### 6. 极端无头隔离导致的双重状态序列化开销
- **参考主张**：`01-架构.md`、`02-内核.md` 要求前端与内核绝对隔离，所有状态必须经由序列化/反序列化和 IPC 信道传递。
- **为什么不照搬**：
  1. GQYv2 在 TUI 或内嵌桌面模式下，前端与内核在同一进程内运行。强制进行全量 JSON 序列化和跨进程传输会造成不必要的内存拷贝与 CPU 开销。GQYv2 允许在进程内使用高效的 Rust 内存 Channel 进行零拷贝通信。

## 第五部分：决策点（Claude 自主决策并留痕，待项目主人事后复核）（附推荐选项）

以下整理出 7 项需要项目主人拍板的顶层设计决策：

### 开放问题 1：是否将 Persona 与 Preset（预设）在配置模型中正交解耦？
- **背景**：参考仓库将 Persona（性格、口吻、设定）与 Preset（启用的工具组、权限级别、模型档位）彻底拆分为两个正交维度；GQYv2 目前将部分工具与权限配置混在 Persona/Venue 中。
- **推荐选项**：**推荐解耦（采纳）**。允许同一 Persona（如“顾清影”）在“专注编码预设”、“日常闲聊预设”、“免审批自动化预设”之间任意组合切换。

### 开放问题 2：是否引入工具三态（Full / Stub / Off）与按组动态按需加载机制？
- **背景**：随着内置工具与 MCP 工具增多，全量注入会严重消耗 System Prompt 预算；参考仓库提出了按组动态提升机制。
- **推荐选项**：**推荐采纳**。将工具按领域分组，默认仅全量加载基础代码组，其他组以 Stub 形式常驻，模型首次调用时自动提升为 Full。

### 开放问题 3：是否在连接器中引入群聊「线路规程（Line Discipline）」与防抢话防抖机制？
- **背景**：v1 在 QQ/微信群聊中存在高频连续消息打断 AI 或 AI 过于活跃插话的问题。
- **推荐选项**：**推荐采纳**。在 `16-连接器与外部平台.md` 中增加线路规程状态机，引入 500ms–1500ms 智能聚合防抖与冷却时间控制。

### 开放问题 4：是否将回合引擎核心重构为「纯逻辑 Reducer」形态？
- **背景**：参考仓库坚持内核为纯同步状态机，输入 Event 输出 State+Effects，不含任何 async I/O。
- **推荐选项**：**推荐采纳**。将状态流转逻辑抽离为纯同步函数，由外层 Supervisor 执行 I/O，大幅提升单测确定性与测试速度。

### 开放问题 5：是否引入 Schema 驱动代码生成（Schema-Driven UI & Config）？
- **背景**：参考仓库主张由统一 Schema 自动生成 Web 表单、TUI 菜单和 CLI 校验，消除多端不同步。
- **推荐选项**：**推荐采纳**。利用 `schemars` 配合 `cargo xtask` 在编译期生成 TypeScript 类型与 UI 配置元数据。

### 开放问题 6：是否在上下文压缩算法中强制结构化保留 4 类核心资产？
- **背景**：长会话压缩时，无格式约束的总结容易丢失待办事项与已修改文件清单。
- **推荐选项**：**推荐采纳**。在压缩 Prompt 中强约束必须输出 `todos`, `modified_files`, `decisions`, `pending_questions` 四个固定段落。

### 开放问题 7：是否在设计文档中建立统一的「性能预算靶子表」？
- **背景**：目前性能目标散落各处，缺少全局可验证的量化基线。
- **推荐选项**：**推荐采纳**。在 `19-可观测性与测试.md` 中建立统一指标表（冷启动首帧 <50ms、可交互 <150ms、空载内存 PSS <30MB、120k 上下文 TTFT <1.2s）。
