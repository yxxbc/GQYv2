> 本文件只管 `docs/` 目录。共同工作规范以仓库根 [`../AGENTS.md`](../AGENTS.md) 为准，仓库级工程护栏以 [`../scripts/CLAUDE.md`](../scripts/CLAUDE.md) 为准；本文件只补这两份没写、又只在文档目录成立的部分。三者冲突时，以根 `AGENTS.md` 与 `scripts/CLAUDE.md` 为准，并指出冲突。
>
> 创建：AI 助手（deepseek-flash 会话），2026-09-28；同日 Cline 会话补记：§7 预期断链范围更新（P00、P01 目录已建）。改动本文件时，按根 `AGENTS.md` 规矩 7 更新这一行：写清谁改的、什么时候改的。

## 1 目录里有什么，谁是真相源

| 路径 | 是什么 | 真相源口径 |

| `construction/00-施工总纲.md` | 阶段划分、施工单规范与模板、全局完成定义 | 施工组织的真相源：“按什么顺序、怎么验收地造出来” |

| `construction/施工图.html` | 进度的可视化（`plan-data` + 架构拼图 + 每一步的图） | `plan-data` 必须与施工单文件头一致，`PIECES` 必须与块和单的对应关系一致 |

## 2 在 docs/ 里的通用规矩

1. **先改上游，再改下游。** 设计文档没写到的细节，先补设计文档再写施工单；施工单没写到的，先补施工单再写代码。
2. **不把规划写成现状。** 未实现的能力一律标【规划】并按“将来会怎样”描述；仓库当前没有 `Cargo.toml` 与运行时代码（P00 完成后再回来改这句话）。
3. **一个事实只有一处成文。** 同一规则、表格、清单只保留一个正文位置，其他位置只放链接与一句话，不复制内容。
4. **文件不删、编号不复用。** 废弃的施工单保留文件并把状态改成“已废弃”；过时内容就地标「已过时（日期 + 原因）」，保留原文，等项目主人确认后再清理。
5. **开头写清状态与作者。** 每篇文档第一屏要有状态（形如 `> 状态：【规划】。`）与最后更新日期；改动较大时补一行说明改了什么、谁改的（根 `AGENTS.md` 规矩 7）。
6. **只动本次范围。** 范围外的发现记进所在阶段 README 的「遗留与发现」，不顺手动别的文档。
7. **文字面向人，术语面向机器。** 正文用中文短句、先结论后依据、不堆没人问的分析；要给模型看或要进提示词的字用英文短句。

## 3 改 designs/

- 新增、改名、删除设计文档时同步三处：`designs/00-设计理念.md` 的「阅读顺序」表、文末的「相关文档」、所有指向它的链接（用 `grep -rn "文件名" docs/` 找全）。
- 编号 00–20 已定；新文档往后排号，不插队，不复用已废弃的编号。
- 待定决策：00 §6 是全局待定清单，每篇文末的「待定问题」是局部项。拍板后把该条从待定处移走，并改所有引用它的地方。
- 涉及接口、架构、兼容性、数据或安全边界的改动，先取得项目主人确认再落笔（根 `AGENTS.md`「协作」）。
- 只写设计文档里已经成立的结论；拿不准的写进「待定问题」，不要用含糊措辞糊过去。

## 4 改 construction/

**新单、调整单：**

- 位置与编号按 00-施工总纲 §3.1（`Pxx-NN-<短名>.md`）；结构照 §3.2 模板写，不自创章节，`cargo` / `xtask` 尚不存在时不要写成现成命令。
- 一张单会牵动四处，别漏：① 阶段 `README.md` 的清单（只写链接 + 一句话，不写状态）；② 施工图 `plan-data` 里对应的条目；③ 施工图的 `PIECES`（块与单的归属变了才改）；④ 00-施工总纲 §2 的阶段表、依赖图与里程碑口径（阶段/依赖/里程碑变了才改）。

**状态：**

- 只写 未开始 / 进行中 / 待验收 / 已完成 / 已废弃；施工单文件头是唯一真相源，改状态必须同步 `plan-data`（P00-02 之后由 `cargo xtask plan` 校验一致，目前靠手工对齐）。
- 一张单合入 main 时，在施工图「每一步的图」补一节：做完以后仓库长成什么样、新加了什么、怎么验收的。
- 标“待验收”之前，先把 00-施工总纲 §3.3 的全局完成定义逐条过一遍；本单判据要能一条条勾，测试要有区分能力（去掉实现会红）。

## 5 改 reviews/

- 这里的文档是**面向 AI 助手**的，不是给人看的汇报；文件顶部那段“面向对象 / 优先级 / 工作方式”是自己的操作说明，保留它。
- 定时任务会话没人可问：遇到不确定自己拍板——先选可逆的，再选改动面小的，最后选与 `designs/` 现有决定一致的——并就地留痕：选了哪条、依据、影响面、怎么回滚、日期，再标「待项目主人事后复核」。
- 外部参考材料（如 miyu-agent-remake、claude-code-system-prompts）只作索引：要确切结论就读原文，不引用本目录的转述。
- 失效内容标「已过时（日期 + 原因）」并保留原文，等项目主人确认后再清理，不直接删除。

## 6 白皮书、技术栈与发布文档

- 白皮书是**对外叙述**：改它不等于改设计；它写的能力必须与仓库实际一致，现在整体仍是【规划】。
- 图片素材在仓库 `assets/pics/`，引用用相对路径（如 `../assets/pics/gqy-logo.png`）。
- `tech-stack.md` 改动选型时，同步 `designs/01-总体架构.md` 及相关设计文档里的选型表述。
- 版本号与发布说明由 Release Please 生成，不手工改。`release-versioning.md` 是详细规范，`CONTRIBUTING.md` 是给贡献者的摘要；两者冲突时以规范为准并修摘要。

## 7 改完自查

交付前至少做三件事：

1. **相对链接可达。** 改过的文件里每个 `](x.md)` 都能在对应目录找到目标。已知预期断链：`construction/00-施工总纲.md` 里指向尚未创建的 `P02…P16` 阶段目录的链接——阶段目录随阶段开工才建（P00、P01 目录已建）。
2. **交叉一致。** 状态、编号、依赖在施工单文件头、阶段 README、施工图 `plan-data` 三处对齐；`designs/` 的编号在 00 的索引表里都在。
3. **不与共同规范重复或冲突。** 根 `AGENTS.md` 与 `scripts/CLAUDE.md` 已写的规矩，本目录只引用，不重写第二遍。

链接检查目前靠手工（`grep` 加肉眼）或一次性脚本；要固化成工具时，按 `../scripts/CLAUDE.md` 把检查放进 `scripts/`，并向项目主人说明原因后取得同意。

## 8 交付口径

- 用中文说明：改了什么、为什么这样改、跑了哪些检查、还有什么要项目主人拍板。
- 交付前像审别人的文档一样读一遍自己的改动：有没有漏掉的引用、有没有夹带无关改动、有没有把“计划”写成“已完成”。
- 纯文档维护一般不写 `CHANGELOG.md`；确实改变了读者能看到的东西（例如新增施工单改变对外说明）时，才按 Keep a Changelog 写进 `[Unreleased]`。
