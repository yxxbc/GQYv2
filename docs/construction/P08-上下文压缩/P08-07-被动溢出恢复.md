## 目标

撞窗之后能恢复一次：溢出错误与两种「无报错溢出」都被识别；前提满足时强制压缩（绕过闸 1/3/4、闸 2 仍有效）、开 `OverflowRecovery` 纪元、重新规划发送；恢复后再溢出如实失败（`Failed(ContextOverflow)`，原错误原文落库）。做完之后：`Too many tokens, please wait` 等限流文案不再被误判（v1 教训回归）；已开始输出的回答不会被恢复流程打断。

## 范围

- 做：
  - 识别两层：供应商错误走 06 §8.3 的 `is_overflow()`（P02 已实现；核对特征表与限流排除的现状，缺口在 PR 说明）；加上两种无报错溢出——`finish_reason = length` 且 `output = 0` 且 `input_total ≥ 0.99 × window`（服务端截断输入）、`finish_reason = stop` 且 `input_total > window`（静默溢出），基于归一化用量判定（`malformed` 用量不参与）。
  - 前提（§9 第 2 条）：本回合尚未恢复过（`ctx.overflow_barrier` 一次屏障，P04-04 的语义接真）且本次请求**尚未产出任何 assistant 内容**（已开始输出就不恢复，避免丢半截回答或重复副作用）。
  - 动作：强制压缩（`Trigger::Overflow`；绕过闸 1、闸 3、闸 4；**闸 2 仍有效**——无可折叠时直接失败）；只走 Isolated 或 Placeholder（不走 Fork——其输入本身会溢出）；开新纪元（原因 `OverflowRecovery`）；重新规划并发送。
  - 恢复后的请求再次溢出：运行 `Failed(ContextOverflow)`，原错误原文落库并展示。
  - 新用户回合复位屏障（屏障挂运行，`TurnEvent` 复位路径接线）。
  - 事件与日志：`context.compact_started{trigger: overflow, …}`；恢复成功 / 失败的事件字段；`context_rewrite reason=overflow_recovery` 行。
  - 发送前硬检查的消费：`total + max_output_tokens > window` 在发送前与强制档同判（P08-01 的类型），作为溢出前的最后一道预防——本单接线到 `needs_compaction` 的调用点。
- 不做：
  - 水位计量与四档线（P08-01）、提交管线（P08-02）、摘要路径本体（P08-03/04）。
  - 供应商侧特征表与重试策略（P02 已有；本单只消费与核对）；退避（06 §8.2）。

## 实施步骤

1. `classify_overflow` 纯函数 + 表驱动（含限流文案回归：`Too many tokens, please wait`、`Throttling` 不判溢出）。
2. 屏障语义接线（`try_take` 一次；新回合复位）；「已出内容不恢复」的判据。
3. 强制路径（绕闸 1/3/4、闸 2 失败即 `ContextOverflow`）；只走 Isolated/Placeholder。
4. 再溢出与原文落库；事件与 `context_rewrite` 行。
5. 与 04 §12.3 门禁场景「溢出恢复」联测；发送前硬检查接 `needs_compaction` 调用点。
6. `cargo xtask check --fast`、`cargo test -p gqy-engine -p gqy-provider`；提交：`feat(context): 被动溢出恢复`。

## 测试与守护

- **识别**：两种静默各一例（伪造归一化用量）；限流文案（`rate limit`/`too many requests`/`Throttling`/Bedrock 的 `Too many tokens`）不误判（去掉排除测试红）。
- **前提**：已产出内容 → 不恢复、直接失败；第二次溢出 → `Failed(ContextOverflow)` 且原文在库（去掉护栏测试红）。
- **屏障**：同一回合第二次溢出不恢复；新回合复位后允许。
- **闸 2 仍有效**：无可折叠时强制压缩失败 → 原子错误；构造闩锁状态再溢出 → 仍恢复（闸 1/3/4 被绕过）。
- **只走 Isolated/Placeholder**：断言未发 Fork 请求（mock 请求取证）。
- **换纪元**：`context_rewrite reason=overflow_recovery` 一条；04 §12.3 场景接真。
- 先红后绿对照（PR 贴输出）：去掉限流排除、把屏障改成无限次各一次。

## 风险与回退

- **静默溢出的误判面**：`stop + input > window` 可能来自供应商计数口径差异——先核对 06 §14 的归一化口径；要收紧阈值时先改 06 再改代码。
- **恢复成本**：溢出恢复 = 一次计划内冷启动；不因恢复而跳过闸 2（避免空转重压）。
- **回退**：`overflow.rs` 删除；主循环回到 P04-04 的屏障路径（假压缩器），行为仍为「一次后 `Failed(ContextOverflow)`」。
