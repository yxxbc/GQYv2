## 目标

`gqy-ledger`（L2，纯逻辑）在 P02-01 的类型之上长出**行为**：条目的三通道写入规则、payload 的规范编码与 blob 阈值、追加时的前置检查、以及纪元视图的读取（含 `Checkpoint` 排序规则）。做完之后，账本是"发什么"的唯一来源，且它的一切输出都是纯函数。

## 范围

- 做：
  - `gqy-ledger` crate 骨架（L2，依赖 `gqy-core`、`gqy-store`、`gqy-config`；**不碰 IO**）。
  - 条目规则：
    - `EntryKind × Channel` 合法矩阵（04 §4.2/§5：`Context` 只承载模型可见条目；`Display`/`Raw` 各归各的读者；`Legacy` 只由导入器写）；非法组合报错并写清期望与实际。
    - `enc(e)`：条目的**逻辑内容规范 JSON**（04 §10 的链与夹具共用；不依赖任何协议）。
    - payload 落位：`payload` 行内 BLOB 与 `payload_blob` 二选一（`store.blob_inline_max`，默认 8 KiB；阈值边界有测试）；大 payload 先经 `BlobStore::put`（P01-07），引用随行写入。
    - 三通道写入：一次用户输入最多三条（同 `turn_seq`、不同 channel，04 §5）；工具输出 `Raw`=全文 blob、`Context`=接收已处理的文本（写入期截断在 P06）。
  - `LedgerRepo`（`gqy-store` 侧，按列名读）：`append`（序号分配 + 前置检查 + 返回 `seq`）、`freeze(seq 集合)`、`view(session)`（纪元视图：最新水位之后的条目 + `Checkpoint`/`Rehydrate` 渲染在最前的**唯一非 seq 排序**，04 §9.1）、`by_channel(session, channel)`（分区读；接口上强制 channel 参数，防串读）。
  - 追加前置检查（参考 miyu 1-7）：序号连续（与库约束一致）、`kind×channel` 合法、payload 二选一合法；**不校验** `_at` 时间先后（时钟可能回拨）——写进模块文档。
  - xtask 扫描器加两条规则：`gqy-ledger` 不得依赖 IO crate（`tokio::fs`、`std::fs`、`reqwest` 等，04 §7）；`gqy-ledger` 与 `gqy-provider` 源码**禁 `HashMap`/`HashSet`**（04 §7、06 §6.2；先例：miyu 1-7“纯逻辑层禁止 HashMap”）。
- 不做：
  - 请求规划（P03-02）、冻结事务（P03-03）、工具面（P03-04）、链与记录（P03-05）。
  - 压缩/撤销压缩对水位的**写入**（05、P08）：本单只按 04 §9.1 **读**已有水位；测试用合成的水位行。
  - v1 `Legacy` 条目的构造（P20 导入器）；本单只定义种类与回放读法。

## 接口草案

草案，以实现为准。

```rust
// gqy-ledger/src/entry.rs
/// 条目的逻辑内容规范 JSON（链、夹具共用；与协议无关）。
pub fn canonical_entry_bytes(e: &LedgerEntry) -> Result<Vec<u8>, LedgerError>;
/// 校验 kind×channel 与 payload 落位；错误写清期望与实际。
pub fn validate(e: &LedgerEntry) -> Result<(), LedgerError>;

// gqy-ledger/src/repo.rs
pub struct LedgerRepo;
impl LedgerRepo {
    pub async fn append(store: &Store, e: &NewEntry) -> Result<EntrySeq, LedgerError>;
    pub async fn freeze(store: &Store, session: &SessionId, seqs: &[EntrySeq]) -> Result<(), LedgerError>;
    /// 纪元视图：最新水位之后的 Context 条目 + Checkpoint/Rehydrate 前置排序（04 §9.1）。
    pub async fn view(store: &Store, session: &SessionId) -> Result<LedgerView, LedgerError>;
    pub async fn by_channel(store: &Store, session: &SessionId, channel: Channel) -> Result<Vec<LedgerEntry>, LedgerError>;
}
```

## 实施步骤

1. crate 骨架与两条扫描规则（先 fixture 红、再实现）。
2. `entry.rs`：矩阵与 `enc(e)`；先写规则用例（每栏一格）。
3. payload 落位：阈值边界（等于 8 KiB、8 KiB±1）与 blob 引用往返。
4. `repo.rs`：append（序号、前置检查、事件行）、freeze、view（重点：`Checkpoint` 排序规则的夹具）、by_channel。
5. `cargo xtask check --fast`、`cargo test -p gqy-ledger -p xtask`；提交：`feat(ledger): 条目模型与三通道`。

## 测试与守护

- **矩阵**：`kind×channel` 每格一例（合法通过、非法拒绝并检查报错文案）。
- **`enc(e)` 确定性**：同一 entry 两次编码相同；改变字段顺序构造仍相同；夹具落 `tests/fixtures/entries/*.json`。
- **payload**：`blob_inline_max` 左右边界；大 payload 先落 blob（`tmp/` 清空）再写行；读回逐字节。
- **视图**：合成水位行 + 条目 → `Checkpoint` 即使 `seq` 更大也渲染在最前（去掉该规则必红）；水位之前条目不可见；水位为空的会话视图 = 全量条目。
- **三通道**：同 `turn_seq` 三条的写入；`by_channel` 只回本通道（去掉 channel 参数化则测试无法编译——接口层面防串读）。
- **不校验时间**：构造 `_at` 回退（时钟回拨）的追加序列，照样成功。
- 先红后绿对照（PR 贴输出）：去掉 `Checkpoint` 前置排序、把 blob 阈值判断改为 `<` 各一次。

## 风险与回退

- **与 P02-01 类型的接口**：`NewEntry` 是写入侧视图；若发现类型需调整，先改 04 的草案再动（设计先行）。
- **`view` 的成本**：长会话上每次规划都读全量条目会慢；本单先正确（后续性能问题在 P08 的计量与 P03-02 的接缝里优化，不提前调优）。
- **回退**：新 crate，revert 即可；表已在 P01-06，未动。
