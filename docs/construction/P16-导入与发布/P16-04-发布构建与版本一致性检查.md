## 目标

发布构建与版本一致性检查成立：workspace release profile 固化（LTO / 符号与体积策略写进 `Cargo.toml`，与 01 §6 一致，体积前后数值记入 PR）；构建期注入构建 ID（`<version>+<git 短 SHA>`，无 git 时 `+dev` 如实标注），`gqy --version` 与 `GET /api/v1/info` 的构建 ID 同源；`cargo xtask version` 检查四处一致——`version.txt` == `.release-please-manifest.json`（根包）== `Cargo.toml`（workspace 版本，形态按复核第 3 条拍板）== `CHANGELOG.md` 最新发布标题的版本；不一致时门禁红并列出期望与实际；`docs/release-versioning.md` 更新「新增 Cargo 后」的口径（唯一来源、同步方式、检查命令）。

## 范围

- 做：
  - release profile；构建 ID 注入与 `/info` / `--version` 同源。
  - `cargo xtask version` 一致性检查与违规样例测试。
  - `release-please-config.json` 的 `extra-files`（复核第 3 条拍板后）；`docs/release-versioning.md` 修改。
  - `cargo build --release` 三平台可构建（Windows 只要求编译通过）。
- 不做：
  - 制品矩阵与上传（P16-05）；桌面打包（P16-06）；自动更新（15 §10.3 不在第一版）。

## 接口草案

草案，以实现为准。

```rust
/// 唯一构建信息来源（gqy-core）；由构建脚本在编译期写入。
pub const VERSION: &str = env!("CARGO_PKG_VERSION");
pub const BUILD_ID: &str = concat!(env!("CARGO_PKG_VERSION"), "+", env!("GQY_GIT_SHA"));
/// xtask：四处版本读数与比对；不通过则列出 (来源, 期望, 实际)。
pub fn check_versions(root: &Path) -> Result<VersionReport, VersionError>;
```

## 实施步骤

1. release profile 与 `--version`（先写「无 git 时输出 `+dev`、不 panic」）。
2. 构建 ID 注入与 `/info` 接线（同源断言）。
3. `cargo xtask version` 四处检查 + 违规样例测试。
4. 复核第 3 条拍板后改 `release-please-config.json` 与 `release-versioning.md`。
5. `cargo xtask check`；提交：`feat(build): 发布构建与版本一致性检查`。

## 测试与守护

- **一致性**：逐处篡改 `version.txt` / manifest / Cargo / changelog 标题之一 → 检查红并指名来源与期望实际（去掉任一处比对，红）。
- **同源**：`gqy --version` 与 `/info` 的构建 ID 相同；`protocol` 仍是 `gqy-protocol` 的值（不混）。
- **无 git / 浅克隆**：BUILD_ID 取 `+dev` 或短 SHA，不 panic、不吞错。
- **release 构建**：`cargo build --release` 三平台绿（Windows 只要求编译）。
- 先红后绿对照（PR 贴输出）：去掉 changelog 标题比对一次。

## 验收流程

```sh
cargo xtask check
cargo xtask version            # 或 cargo xtask check 内含（复核第 3 条定）
cargo build --release -p gqy
./target/release/gqy --version # 期望：<version.txt>+<短SHA>
# 违规样例：临时改 version.txt 再跑 cargo xtask version → 红；随后恢复
# /info 对照（daemon 运行中）：curl -s localhost:8310/api/v1/info | jq .build_id
```

## 风险与回退

- **Release Please 同步 Cargo 失败**：发布 PR 与 `cargo xtask version` 双重把关；若 `extra-files` 方案失效，退到「检查 + 人工同步」并在 release-versioning.md 写明（复核第 3 条）。
- **体积变化**：release profile 影响二进制体积（19 §3.7 是参考不是承诺）；记录前后数值到 PR。
- **回退**：回滚本单提交；版本来源保持单点，不引入第二个版本文件。
