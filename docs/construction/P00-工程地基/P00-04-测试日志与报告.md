## 目标

落地 `cargo xtask test`：运行 `cargo test`（`--no-fail-fast`）、解析 libtest 文本输出、终端打印可读摘要（每个 crate 一行、失败清单含文件行号与期望/实际、复跑命令）、写 JSON 与 Markdown 报告到 `target/gqy-test-report/`，并执行**测试计数门禁**（实际执行数 ≥ 平台基线，降低报红）。做完之后，“每次测试都能看出哪些地方出错需要修复和改进”成为默认体验，且删测试躲失败会被机器拦住。

## 范围

- 做：
  - `cargo xtask test [--workspace | -p <crate>] [--filter <pat>] [--include-ignored[=<tag>]] [--unit] [--no-count-gate]`（19 §5.1 的形态；`--unit` 供 Windows 作业跑 `--lib --bins`）。**`=<tag>` 的映射机制已定**（19 §4.1）：扫描测试源码里 `#[ignore = "needs:<tag>"]` 的属性行建立“用例 → 标签”映射（扫描器有单测），运行时把其它 ignored 用例列入 `--skip`；出现名字子串冲突时逐用例运行并提示改名。
  - libtest 解析器：`test <name> ... ok|FAILED|ignored`、`test result:`、`---- <name> stdout ----`、`panicked at <file>:<line>:<col>:`、doc 测试行。
  - 终端摘要（照 19 §5.2 的版式）、失败定位（期望/实际来自断言输出、复跑命令）、最慢 5 个用例、门禁行。
  - `target/gqy-test-report/report.json`（19 §5.3 的 schema 1）与 `report.md`。
  - 测试计数门禁与基线：`xtask/baselines/test-count.<os>.txt`（linux / macos / windows 三份，首版写入当时实测值；§6.2 的按平台原因）。
  - 退出码：任一失败或门禁不过 → 1；解析失败 → 2（报告指出无法解析的行）。
  - 解析器夹具测试与计数门禁的纯函数测试。
- 不做：
  - 真实 needs 用例本身（首个出现在 P02-03）。
  - 基准（criterion）报告 `bench.json`（P03 起随基准加入）。
  - CI 接线（P00-06）。

## 接口草案

草案，以实现为准。

```rust
// xtask/src/test/parse.rs

/// 一个测试二进制的解析结果。
pub struct SuiteResult {
    pub name: String,        // 例如 "gqy-core" 或 "unittests src/lib.rs"
    pub passed: usize,
    pub failed: usize,
    pub ignored: usize,
    pub elapsed_ms: u64,
}

/// 一个失败用例的定位信息。
pub struct Failure {
    pub name: String,        // 完整测试名
    pub file: Option<String>,   // 来自 "panicked at <file>:<line>:<col>:"
    pub line: Option<u32>,
    pub message: String,     // 断言输出原文（期望/实际在里面）
    pub rerun: String,       // 可直接复制的复跑命令
}

/// 解析一行；流式解析器内部用。
/// `parse_stream` 是所有解析逻辑的入口，纯函数：输入行序列，输出结构化结果。
pub fn parse_stream(lines: &[String]) -> ParseOutcome;

pub enum ParseOutcome {
    Parsed { suites: Vec<SuiteResult>, failures: Vec<Failure> },
    /// 解析遇到无法识别的关键行：整次运行按“解析失败”处理（退出码 2），
    /// 报告里写明是哪一行。
    Unrecognized { line: String, at: usize },
}
```

```rust
// xtask/src/test/count_gate.rs

/// 计数门禁：executed = passed + failed（不含 ignored，19 §6.1 第 11 项）。
/// `baseline` 为 `xtask/baselines/test-count.<os>.txt` 的当前值。
/// 返回 Ok(Warning) 表示高于基线（提示同提交更新基线）；
/// 返回 Err 表示低于基线（红）。
pub fn check_count_gate(executed: usize, baseline: usize) -> Result<GateVerdict, Violation>;

pub enum GateVerdict { Equal, Higher { executed: usize, baseline: usize } }
```

## 实施步骤

1. 建 `test` 子命令骨架：调用 `cargo test --no-fail-fast`（透传 stdout/stderr、逐行捕获），先只打印原始输出。
2. 写解析器 `parse_stream`（纯函数）与其夹具测试（先写样本与期望、确认解析器未实现时红）。
3. 组装摘要输出；接上失败定位与复跑命令。
4. 写 `TestReport`（schema 1）与 Markdown 渲染；输出到 `target/gqy-test-report/`。
5. 计数门禁：基线文件格式（一行整数）+ 三个平台的初始值（linux / macos 先跑实测定值；windows 在 P00-06 CI 首次运行后回填——本单先写 `0` 并在 P00-06 更新为实测值，PR 里注明）。
6. 退出码整理：失败 1、解析失败 2、通过 0；`--no-count-gate` 跳过第 11 项。
7. 提交：`feat(xtask): 测试运行器与报告`。

## 测试与守护

- **解析器夹具**（`xtask/tests/parse_libtest.rs`）：内置样本覆盖——
  1. 全通过；2. 含 `FAILED` 与 `panicked at` 定位；3. 含 `ignored`；4. doc 测试行（`src/lib.rs - foo (line 3) ... ok`）；5. `should_panic`；6. 编译失败的输出（无 `test result` 行 → `Unrecognized`）；7. 多二进制输出拼接。每份样本配期望的结构化结果。
- **计数门禁**（`xtask/tests/count_gate.rs`）：等于基线 → 通过；高于 → 警告；低于 → 红。另测 `--no-count-gate` 路径。
- **端到端手工对照**（进验收流程，PR 贴输出）：临时在 `gqy-core` 加一个失败测试 → `cargo xtask test` 输出失败定位与复跑命令、退出 1、报告 JSON 含该失败；删除后重跑绿。
- **标签筛选**：源码扫描器的单测覆盖固定属性形态（合规 / 形态错误不误吞）；临时造两个 ignored 用例（`needs:alpha`、`needs:beta`）→ `--include-ignored=alpha` 只跑 alpha 与全部常规用例；不带 `=` 时全跑。
- **区分能力**：把 `parse_stream` 里对 `FAILED` 行的处理删掉 → 夹具 2 必红；把计数门禁的比较改成 `>=` 恒真 → 计数门禁测试必红。
- **首版基线**：写基线时同步把当前执行数记录到 PR；基线只增（设计 §6.2）。

## 风险与回退

- **libtest 输出格式变化**：解析失败按退出码 2 上报（不把“解析失败”当“通过”），并在报告里指出行；如需换 nextest 见 Q-19-1（未拍板，不擅自换）。
- **doc 测试与集成测试的输出差异**：用夹具覆盖，先于真实仓库验证。
- **基线起点低**：当前仓库测试数很少（fixture 测试为主），基线按实测写；后续每张单执行数增长会自动触发“高于基线”提示，需同提交更新基线（工作量小）。
- **回退**：revert 即可；不影响运行时与数据。
