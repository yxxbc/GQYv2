## 目标

备份与恢复从设计变成库能力：`VACUUM INTO` 出一致快照、`integrity_check` 验收、blob 增量复制（不可变、可 reflink）、`manifest.json` 记账；`restore` 按 10 §9.1 的三步替换；`quick_check` / `integrity_check + foreign_key_check` / blob 重算哈希三件套做完整性检查。做完之后，P05-05 的 `gqy backup/restore` 子命令与 P11-05 的 `gqy doctor` 只是接线。

## 范围

- 做：
  - `backup`：`backup(store, blobs, dest_dir, now, app_version) -> BackupManifest`（在一条读连接上 `VACUUM INTO`；对产物 `integrity_check`；blob 目录增量复制——按文件名跳过已有、优先 `clonefile`/`FICLONE`、退化普通复制；写 `manifest.json`：版本、schema 版本、blob 数、总字节、库文件 blake3）。
  - `restore`：`restore(data_dir, backup_dir)`（要求调用方保证 daemon 已停止：先把当前三件套移到 `backups/replaced-<ts>/`，再放入备份库，校验 `integrity_check` 与 `application_id`）。
  - `integrity`：`quick_check`、`integrity_check_plus_fk`、`verify_blob`（重算哈希，报告损坏清单，不删）。
  - 测试：备份期间写者活跃、manifest 正确、恢复往返、拒绝非 GQY2 库、blob 复制跳过已有。
- 不做：
  - `gqy backup` / `gqy restore` 子命令与启动检查的接线（P05-05）；周检作业（P13-02）；`doctor --deep/--blobs`（P11-05）。
  - 备份保留策略的**调度**（7 日 + 4 周在 10 §9.1；执行方是 P13-02 的保留作业；本单不做删除逻辑）。
  - 导出包 `gqy export`（10 §11，P16 起）。

## 接口草案

草案，以实现为准。

```rust
// gqy-store/src/backup.rs

/// 备份清单（写入备份目录的 manifest.json）。
#[derive(Serialize, Deserialize)]
pub struct BackupManifest {
    pub schema: u32,               // 1
    pub app_version: String,
    pub schema_version: u32,       // 迁移最高版本
    pub created_at_ms: i64,
    pub db_blake3: String,
    pub blob_count: u64,
    pub blob_bytes: u64,
}

/// 一条读连接上的 VACUUM INTO + 完整性验收 + blob 增量复制 + manifest。
///
/// 不阻塞写者（WAL 下一读写不互斥，10 §9.1）；产物不通过 `integrity_check` 时报错并
/// 保留产物供取证（不静默删除）。
pub async fn backup(
    store: &Store, blobs: &BlobStore, dest_dir: &Path,
    now_ms: i64, app_version: &str,
) -> Result<BackupManifest, BackupError>;

/// 恢复（调用方保证 daemon 已停止；10 §9.1 三步）。
///
/// # Errors
/// 备份缺件、`integrity_check` 不过、`application_id` 不符时返回错误；
/// 替换前先原样保存当前三件套到 `backups/replaced-<ts>/`。
pub fn restore(data_dir: &Path, backup_dir: &Path, backups_dir: &Path) -> Result<(), BackupError>;
```

```rust
// gqy-store/src/integrity.rs

/// 启动路径用：轻量检查（10 §9.2 的 quick_check 行）。
pub fn quick_check(conn: &ReadConn) -> Result<(), IntegrityError>;
/// 周检与 doctor --deep 用：全量 + 外键。
pub fn integrity_check_plus_fk(conn: &ReadConn) -> Result<(), IntegrityError>;
```

## 实施步骤

1. `backup` 最短路径：`VACUUM INTO` + `integrity_check`；先测“备份产物能全量读回”。
2. blob 增量复制（跳过已有；`clonefile`/`FICLONE` 尝试 + 普通复制回退）与 manifest。
3. `restore` 三步（保存三件套 → 放入 → 校验）；错误路径全部回退到“原库不动”。
4. `integrity` 三件套。
5. 测试矩阵（见下），关键负例先红后绿。
6. `cargo xtask check --fast`、`cargo test -p gqy-store`；提交：`feat(store): 备份、恢复与完整性检查`。

## 测试与守护

1. **备份**：有数据（含 blob 引用、多字节文本）的库 → `backup` 成功；产物 `integrity_check` 通过；manifest 的 `db_blake3`/`blob_count`/`blob_bytes` 与实际相符。
2. **写者活跃**：备份期间持续 `Store::write`（另一个任务）→ 备份成功、写入不被阻塞（WAL）；备份期间不许出现锁错误。
3. **增量 blob**：备份目录已有部分 blob → 只复制缺的（用文件计数与 mtime 断言“已有未被重写”）。
4. **恢复往返**：改造库（加数据、删 blob 文件）→ `restore` → 数据与备份时一致；当前库被移到 `replaced-<ts>/`。
5. **拒绝外来库**：把 `application_id` 改成别的 SQLite 文件的目录当备份 → `restore` 拒绝，且**不动当前库**。
6. **损坏检测**：手动改坏 blob → `verify_blob` 报 `BlobIssue`（含 hash 与路径），文件不动；`quick_check` 对正常库通过。
7. **rename 平台差异**：Windows 上“文件被占用”的等价情形在测试里用关闭句柄规避；`replaced-<ts>/` 的移动在 Unix/Windows 都跑。
8. **区分能力**：把备份改成 `fs::copy` 活库（v1 的坏做法）→ 测试能发现不一致（在写者活跃用例里红）；去掉恢复前的 `integrity_check` → 用例 5 红。

## 完成判据

- [ ] 全局完成定义（施工总纲 §3.3）全部满足

- [ ] 接线时点写在单里：`gqy backup/restore` → P05-05；启动 `quick_check` → P05-05；周检 → P13-02；doctor → P11-05

## 风险与回退

- **`clonefile`/`FICLONE` 跨平台**：`cfg` 分支实现；不支持或失败即回退普通复制（行为一致，只是慢）——不做“假装成功”。
- **`restore` 的“daemon 已停止”**：本单只在文档与参数上要求（函数不检测锁；P05-05 接线时用 `run/daemon.lock` 检查并拒绝）。
- **manifest 的 schema 版本**：取迁移链最高版本（P01-05 的结果）；将来导入器（P16）会读它，字段保持向后兼容（只加不改）。
- **回退**：新增模块，revert 即可；备份产物是普通文件，用户可自行保留或删除。
