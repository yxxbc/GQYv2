## 目标

迁移从“注释里的规矩”变成机器守护：`NNNN_<name>.sql` 迁移文件按编号连续、`include_str!` 编进二进制、每个迁移在一个事务里执行并登记 `schema_migrations`（含 checksum）；校验和改动即拒绝启动；库比二进制新时拒绝写入；迁移前自动 `VACUUM INTO` 备份（保留 3 份）。同时落地**只增守护**：静态扫描（`DROP`/`RENAME`/`DELETE`/`ALTER…DROP` 直接违规；`UPDATE` 只许碰本迁移新建的列与表）+ `cargo xtask migrations` 门禁（CHECKSUMS 清单不可变）+ schema 差分与行级不变两个测试装置（P01-06 起对真实迁移链运行）。

## 范围

- 做：
  - `migrations`：迁移注册表（宏 + `include_str!`）、`apply(&Store)`（`BEGIN IMMEDIATE` + 逐文件执行 + 登记行）、启动校验（checksum、库版本高于二进制 → 拒绝写入）、迁移前 `VACUUM INTO backups/pre-migrate-<from>-<to>-<ts>.db` 且保留最近 3 份。
  - `cargo xtask migrations`：编号连续性；词法扫描（忽略注释与字符串）——`DROP`/`RENAME`/`DELETE FROM`/`ALTER TABLE … DROP` 违规；`UPDATE` 的表与 `SET` 列必须出自本文件的新建（10 §8.3.1）；`migrations/CHECKSUMS` 中已登记的文件的 blake3 必须不变（`--refresh` 在发布流程里更新，P16-05）。
  - 守护测试装置（gqy-store `tests/`）：
    - **schema 差分**：对每一对 (k−1, k)，在 k−1 状态上执行迁移 k，比较 `pragma_table_info` / `pragma_index_list` / `sqlite_master`——旧表旧列原样存在（10 §8.3.2）；
    - **行级不变**：迁移前后旧表按主键的旧列值 blake3 相等（10 §8.3.3）。
    - 装置对“迁移列表”泛型化：测试里可喂合成迁移（含故意违规的），不依赖真实迁移链的长度。
- 不做：
  - 第一个真实迁移 `0001_core.sql`（P01-06）。
  - 夹具链生成 `cargo xtask fixtures store`（10 §8.3.4，发布时启用；本单只把测试装置留好接缝）。
  - 保留期清理的调度（P13-02）；`gqy doctor` 的迁移报告（P11-05）。

## 接口草案

草案，以实现为准。

```rust
// gqy-store/src/migrations/mod.rs

/// 一个迁移：SQL 文本编译期入库，checksum = blake3(sql)。
pub struct Migration {
    pub version: u32,          // 0001 → 1
    pub name: &'static str,
    pub sql: &'static str,     // include_str!
    pub checksum: [u8; 32],
}

/// 把库迁移到二进制已知的最新版本。
///
/// - 已应用迁移的 checksum 必须与二进制一致，否则 `MigrationTampered { version }`；
/// - 库版本高于二进制 → `DatabaseTooNew`（拒绝写入，只读可开）；
/// - 申请迁移前若库非空：`VACUUM INTO backups/pre-migrate-…`（保留 3 份）。
pub async fn migrate(store: &Store, backups_dir: &Path, app_version: &str)
    -> Result<MigrationReport, MigrationError>;

/// 测试接缝：对任意迁移列表跑的同一套逻辑（合成迁移用）。
pub async fn migrate_with(store: &Store, list: &[Migration], /* … */)
    -> Result<MigrationReport, MigrationError>;
```

```text
# xtask
cargo xtask migrations             # 校验（编号连续、词法扫描、CHECKSUMS 不可变）
cargo xtask migrations --refresh   # 发布流程用：把新增迁移写入 CHECKSUMS（P16-05 调用）
```

## 实施步骤

1. 迁移注册表与 `apply` 最小版：空列表也能跑（建 `schema_migrations` 在哪里？**框架自己建**：`0001` 之前由框架保证该表存在——写进 10 的实现注记，PR 里说明）。
2. 启动校验（checksum、`DatabaseTooNew`）与迁移前备份（保留 3 份）。
3. `cargo xtask migrations`：先写 fixture（违规 `DROP INDEX`、`UPDATE` 旧列、编号断档、CHECKSUMS 被改）确认全红，再实现扫描器。
4. 守护测试装置：schema 差分与行级不变，先对合成迁移链跑通；违规样例（迁移 k 里 `DROP`、改旧列值）必须让装置红——这就是 10 §8.3.5 要求的验收演示。
5. `cargo xtask check --fast`、`cargo test -p gqy-store`、`cargo test -p xtask`；提交：`feat(store): 迁移框架与只增守护`。

## 测试与守护

1. **校验和**：应用迁移后手动篡改 `schema_migrations.checksum` → 再 `migrate` 拒绝（`MigrationTampered`，错误带版本号）；**区分**：去掉校验 → 测试红。
2. **库太新**：把库迁到合成版本 2，再用只有版本 1 的列表打开 → 拒绝写入；只读查询仍可用。
3. **迁移前备份**：非空库迁移前生成 `pre-migrate-*` 文件；连续 4 次迁移只保留最近 3 份。
4. **编号与词法**（xtask）：断档、重复、`DROP TABLE`/`DROP INDEX`/`RENAME`/`DELETE FROM`/`ALTER … DROP` 各自断红；`UPDATE` 写本文件新建的列（合规）与写旧列（违规）各一例。
5. **CHECKSUMS**：登记文件被改动 → 红；新增未登记文件 → 允许（并由 `--refresh` 登记）；`--refresh` 后再次校验 → 绿。
6. **schema 差分**：合成链 1→2（加列、加索引）绿；合成链里删列/改默认值 → 红，错误指出表与列。
7. **行级不变**：合成迁移 2 里 `UPDATE` 旧表旧列 → 红（对应 v1 v36 的 `UPDATE … SET workspace = NULL` 教训，10 §2）。
8. **幂等**：同一列表跑两次；第二次不做任何写入（`schema_migrations` 行数不变、mtime 不变）。

## 验收流程

```sh
cargo test -p gqy-store          # 合成迁移测试全绿
cargo test -p xtask              # 门禁 fixture 全绿
cargo xtask migrations           # 校验绿（仓库里还没有迁移文件，输出“0 个迁移”）
# 先红后绿对照（PR 贴输出）：
#   1) 临时加一条含 DROP INDEX 的迁移 → cargo xtask migrations 红 → 删除
#   2) 把合成迁移里的 UPDATE 改成写旧列 → 装置红 → 恢复
```

## 风险与回退

- **词法扫描的边界**：它是“防手滑”不是安全边界；SQL 里的间接写法（动态拼接）在迁移文件里被禁止（迁移是静态 SQL 文件），PR 评审兜底。
- **`migrate_with` 测试接缝**：生产路径不得用它；文档注明，且注册表列表只有一处（宏生成）。
- **备份目录参数**：由调用方传入（P05-05 用 `GqyPaths::backups_dir()`）；本单不引入对 `gqy-config` 的依赖（同层）。
- **回退**：新增模块与工具，revert 即可；已生成的 `pre-migrate` 文件留给用户自行删除（不动）。
