## 施工单 8-22：模型默认温度

状态：已完成（2026-10-05 完成，项目主人确认开工）。

### 目的

人能给每个模型配置默认的采样温度（`temperature`，0.0 到 2.0），写在 `[providers.<id>.models."<model>"]` 里。经路由一直通到三个驱动（`openai-chat`、`anthropic`、`openai-responses`）；没配的不发，照供应商的默认；不支持温度的模型（如 Anthropic 开启思考时、OpenAI Responses 开启思考档位时）由驱动抑制不发，避免 API 报错。`model.list` 每一项带出 `temperature` 资料格和 `key`，供界面读取与直接配置。

### 蓝图改哪几节

1. `models.md`：

   - 「协议」`model.list` 的 `facts` 加 `temperature`（带 `key`，照 `effort` 的办法）；
   - 「驱动要守的约定」加第 14 条（温度的写法与抑制约定）；

2. `drivers/openai-chat.md`、`drivers/anthropic.md`、`drivers/openai-responses.md`：

施工时定的（已定项，项目主人批准）：

| # | 定了什么 | 为什么 | 别的选法 |
|---|---|---|---|
| 1 | 配置键名 `providers.<id>.models."<model>".temperature`，取值 `0.0..=2.0`（`float [0, 2]`），系统和个人两层，`next_turn` 生效 | 照 `effort` 与 `window` 的做法，每个模型单独配置；数值范围覆盖主流大模型（0.0 严谨到 2.0 创意） | 放在 provider 级（不同模型对温度支持和敏感度差异大，不够细） |
| 2 | 不支持温度的模型或状态：驱动抑制不发，不报错（例如 Anthropic/Responses 开启思考时） | 保证用户体验丝滑，换思考强度或切换模型时不因残留温度参数导致 API 请求失败 | 报错打断请求；或者配置时拦截（无法覆盖动态思考开关） |
| 3 | 不做会话内动态温度命令（如 `/temperature`），温度只随配置两层（系统兜底、个人设置覆盖） | 保持与 8-18（补）理念一致：配置层已足够，界面可直接写个人设置；避免会话状态膨胀 | 做 `/temperature` 会话内命令（违背 8-18 补已确立的无状态简化原则） |
| 4 | `model.list` 每个模型的 `facts` 带出 `temperature`，并带完整键名 `key`（如 `providers.dev.models."deepseek-chat".temperature`） | 头照抄 `key` 发 `config.set`，与 `effort`、`name` 一致，前端容易接 | 头自己拼键名（容易出引号转义 bug） |
| 5 | `Call` 中使用 `Option<Real>`：保持 `Call: Eq`，浮点数由 `Real` 精确比对与序列化 | `Call` 需派生 `Eq`，标准 `f64` 无法 `Eq`，`Real` 已经在内核稳定使用 | 使用 `Number` 或手写 `Eq`（`Real` 现成且统一） |

### 不做什么

- 不加会话内动态改温度的命令（如 `/temperature`）及协议方法。
- 不增加全局默认温度（温度与具体模型特性强相关，模型未配置时交由服务商 API 自带默认处理）。
