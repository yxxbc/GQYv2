## 目标

`gqy-memory` 的地基落地：`memory_scopes`、`memories`、`memory_tags`、`memory_subjects`、`memory_sources`、`memory_recalls`、`memory_postings`、`memory_doc_stats`、`session_reviews` 九表经迁移只增建好；repo 的每个查询都带 `AccessScope` + “是否群聊”，可见性谓词只有一处实现；写入可见性由代码按场所裁决，模型改不动。做完之后：可见性矩阵测试红绿分明（成员 A 看不到成员 B 与 owner 的私有记忆；群聊里的 owner 也只读 `public` + 本人 `principal`）；改 `memories.content` 会触发数据库拒绝；不带 `AccessScope` 的 `pub fn list_*` 被 xtask 规则报红。

## 范围

- 做：
  - 迁移（10 §8 只增、blake3 清单）：11 §3.3 九表的 DDL（先按 README 复核清单第 4 条补齐进 10 §7.6）；按查询需要建索引（例如 `memories(persona_id, status, kind)`、`memory_postings` 的主键即索引）。
  - 触发器与受控更新（10 §4.4）：`memories` 的 `content` / `visibility` / `owner_principal` / `kind` 拒 UPDATE（正文修改 = 新行 + `superseded_by`）；`memory_recalls` 拒 UPDATE；允许原地更新的标量列（`strength`、`status`、`last_decay_at`、`expires_at`、`consolidated_at`、`superseded_by`）登记进 10 §4.4 名单；DELETE 侧在当前阶段只允许后续 reset / 清理作业的登记路径（P12-05 / P12-08 接上）。
  - `MemoryRepo`（在 `gqy-memory` 内，经 `Store::read/write` 访问，不自己开连接）：`insert`、`get`、`update_scalars`、`mark_forgotten`、`mark_superseded`、标签与主题子表写入；全部方法接收 `AccessScope`（10 §10），不提供“全部行”方法。
  - 可见性谓词唯一实现 `visibility_predicate(scope, in_group)` 与查询过滤：`public`；`principal` 且 `owner_principal = scope.principal`；`privileged` 且 `trust == Owner` 且非群聊。Internal（作业、复盘、子代理）继承创建者 scope。
  - 写入默认裁决唯一实现 `write_visibility(venue, requested)`：Owner 私有场所默认 `privileged`（owner 显式要求时可放宽为 `public`）；Member / External 私聊与群聊默认 `principal`；Internal 继承创建者；非 Owner 场所把传入的放宽请求强制收窄。
  - `memory_scopes` 行的创建时机（persona 启用 memory 时；组装侧调用，P12-02 / P12-04 接线）。
  - 纪律核对：按列名读、无 `SELECT *`（xtask 既有扫描）；时间列 `_at` 毫秒 UTC；`mem_` 前缀 ULID；`StoreBusy` 语义照 10 §4.2（写队列满不静默丢写）。
- 不做：
  - 工具（P12-02）、检索与倒排维护（P12-03）、钩子与注入（P12-04）、整理与日记（P12-05）、复盘（P12-06）、kb 两表（P12-07）、reset 命令与代数变更（P12-08；本单只落代数存储与读取）。

## 接口草案

草案，以实现为准。

```rust
pub struct AccessScope { pub principal: Principal, pub trust: Trust }  // 10 §10 现状核对
pub enum Visibility { Public, Principal, Privileged }

impl MemoryRepo {
    /// 可见性谓词是唯一实现；群聊再多一条“只读 public + 本人 principal”。
    pub fn visible_where(scope: &AccessScope, in_group: bool) -> VisibleWhere;
    pub async fn get(&self, id: &MemoryId, scope: &AccessScope, in_group: bool)
        -> Result<Option<MemoryRow>, MemoryError>;
    pub async fn insert(&self, tx: &mut WriteTx, row: &NewMemory, gen: MemoryGeneration)
        -> Result<MemoryId, MemoryError>;   // 代数比对在写作业第一步
}

/// 写入可见性的代码裁决；requested 来自模型参数，非 Owner 场所只可能被收窄。
pub fn write_visibility(venue: &Venue, requested: Option<Visibility>) -> Visibility;
```

## 测试与守护

- **可见性矩阵**：owner、成员 A、成员 B、群聊中的 A 四种 scope × 三种可见性 × 两个 owner 的记忆交叉，断言查询与（后续）召回的结果集；去掉 SQL 谓词，红。
- **写入收窄**：群聊场所模型传 `visibility="public"`，落库仍为 `principal`；去掉收窄，红。
- **成员隔离（10 §10 守护）**：以成员 A 的 scope 调用每个列举 / 读取 API，断言看不到成员 B 与 owner 的数据。
- **不可变列**：UPDATE `content` / `visibility` / `owner_principal` 被触发器拒绝；`memory_recalls` 的 UPDATE 被拒。
- **xtask 规则**：新增一个不带 `AccessScope` 的 `pub fn list_*` 或整数字面量 `row.get` → 报红；去掉规则，样例测试红。
- **迁移只增**：`cargo xtask migrations` 通过；改动已发布迁移文件 → 红。
- 先红后绿对照（PR 贴输出）：去掉可见性谓词的 `privileged` 条件、去掉写入收窄各一次。
