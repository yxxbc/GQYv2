## 目标

停机与恢复成为可测试的协议步骤：`Shutdown { deadline }` 广播 → 运行以 `CancelReason::Shutdown` 取消 → 宽限期内等待终态 → store 写队列排空 + WAL checkpoint；启动时**一次**恢复例程把非终态运行收成 `Interrupted`、关闭问题、标 `Lost` 作业、按场所重建队列、补跑/标记定时器，并留下摘要日志一行。做完之后，「重启后会话可以继续」（M1 验收口径）在引擎侧成立。

## 范围

- 做：
  - `ShutdownCoordinator`：广播 `SessionCmd::Shutdown{deadline}` → 运行取消（P04-05 的树，原因 `Shutdown`）→ 宽限（`engine.shutdown_grace` 默认 10 s、上限 60 s）内等待终态 → 超时对剩余子进程强制终止（sys 接缝）→ 调用 store 的写队列排空与 WAL checkpoint（接口归 P01-04）；返回 `ShutdownOutcome { forced, pending_runs }`；发 `daemon.stopping{deadline_ms}`（13 §6.2）。
  - **不做**（边界写清）：信号安装、`run/daemon.lock` 的释放、`run/daemon.json` 的删除与退出码——全部归 P05-05；本单交付引擎侧接口与语义。
  - `recover(deps, now) -> RecoverySummary`：只在 daemon 启动、网关接受请求之前执行一次（02 §9），照 03 §13 七步：
    1. 非终态运行（planning/compacting/streaming/awaiting_approval/executing_tools）→ `interrupted`；按 03 §3.3 收尾：合成工具结果按两档文案（`ReadOnly`/`Presentation` vs `Writes`/`Exec`/`Network`，03 §13.1 表）、`TurnAborted` 注记、partial 文本只进 `Display`。
    2. 回合内压缩中断 → 记 `context.compact_failed{reason: "interrupted"}`（压缩事务未提交即等于没发生；P08 前用假压缩器路径验证语义）。
    3. 待回答问题 → `closed{reason: expired}`。
    4. `Running` 作业：`pid_start` 与存活进程匹配才终止整个进程组；统一 `Lost` 并发 `job.finished{state: Lost}`；**不接管**孤儿进程输出（v2 首版明确不做，03 §14）。
    5. 队列：交互式场所（Tui/Web/Cli）一律丢弃 + `queue.dropped{reason: restart}`；非交互在 `queue_restart_ttl` 内按原序重新准入（调用 P04-03 的 `rebuild_after_restart`）——**待用户确认（Q-03-3）**，确认前按推荐口径。
    6. 定时器：`next_due < now` 按 `CatchUp` 补跑一次（`timer.fired{late_by}`）或记 `timer.missed`；周期定时器随后按 03 §10.2 计算下一次。调度器本体在 P13-02/03，本单只做恢复语义与事件。
    7. 摘要日志一行：`recovery interrupted_runs=… lost_jobs=… requeued=… dropped=… timers_fired=… timers_missed=…`（19 §3.2 的格式）。
  - 幂等：重复调用 `recover` 不再有副作用（以终态行过滤）。
- 不做：
  - 进程生命周期（P05-05）、定时器/作业调度器本体（P13）、压缩实现（P08）、v1 导入的续跑（P16/P20）、网关侧的 `daemon.stopping` 分发（P05-02；本单只发事件）。

## 接口草案

草案，以实现为准。

```rust
// gqy-engine/src/shutdown.rs
pub struct ShutdownCoordinator { /* supervisor handle, terminator, store */ }
impl ShutdownCoordinator {
    /// 广播 → 等宽限 → 必要时强制终止 → store 排空与 WAL checkpoint。
    pub async fn shutdown(&self, deadline: Instant) -> ShutdownOutcome;
}
pub struct ShutdownOutcome { pub forced: bool, pub pending_runs: u32 }

// gqy-engine/src/recovery.rs
pub struct RecoverySummary {
    pub interrupted_runs: u32, pub lost_jobs: u32, pub requeued: u32,
    pub dropped: u32, pub timers_fired: u32, pub timers_missed: u32,
}
pub async fn recover(deps: RecoveryDeps<'_>, now: Timestamp) -> Result<RecoverySummary, RecoveryError>;
```

## 实施步骤

1. 停机广播与宽限（fake terminator；先写“宽限内终态则 forced=false”的测试）。
2. `recover` 第 1–3 步（运行收尾、压缩中断、问题关闭）。
3. 第 4 步作业 `Lost`（fake pid 探测两分支）。
4. 第 5–6 步队列与定时器重建。
5. 摘要日志与幂等；`cargo xtask check --fast`、`cargo test -p gqy-engine -p gqy-store`；提交：`feat(engine): 停机与启动恢复`。

## 测试与守护

- **停机中重启**（02 §10、03 §16）：在 `ExecutingTools` 处构造「未写终态即中断」（重建 store 句柄模拟崩溃），重启后运行 `Interrupted`、`tool_call` 配对完整；`Writes` 类合成结果含 “may have partially taken effect”；去掉 `Interrupted` 标记必红。
- **队列恢复**：交互式三场所丢弃并解释；非交互 TTL 内原序重排、超 TTL 丢弃并计数（TestClock ±1 s 边界）。
- **作业 `Lost`**：fake 探测两分支（存活 → 终止序列；不存活 → 直接 `Lost`）；`job.finished{state: Lost}` 字段齐全。
- **定时器**：`RunOnceIfWithin` 窗口边界（内补跑一次、外记 `missed`）；周期定时器积压 5 次只补 1 次（03 §16）。
- **partial 文本**：只进 `Display` 且 `partial=true`，不进 `Context`（对照 04 §3 的不变量）。
- **幂等**：连调 `recover` 两次，第二次全零且无新行/事件。
- 先红后绿对照（PR 贴输出）：去掉 `Interrupted` 标记、把 `Lost` 作业改成 `Cancelled` 各一次。

## 风险与回退

- **与 P05-05 的边界**：本单不做进程、锁、退出码；若组装处需要更多信息，`ShutdownOutcome` 字段**只增**。
- **依赖 P13 的定时器调度**：本单先落恢复语义；联调在 P13-02（调度器接入时复用同一 `CatchUp` 函数，避免两处实现）。
- **崩溃测试的确定性**：用「构造未写终态」而不是真 SIGKILL 时序，保证可复现。
- **回退**：`shutdown.rs`/`recovery.rs` 是新文件，revert 即可；配置默认值一并回退。
