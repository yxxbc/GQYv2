# 00 · 施工总纲

> 状态：【规划】。本目录把 `docs/designs/` 的设计拆成按顺序执行、可逐张验收的施工单。设计是“是什么”，施工单是“怎么造、怎么证明造对了”。二者冲突时，先修设计文档，再改施工单。

## 1 施工原则

1. **垂直闭环优先。** 尽早打通“输入 → 模型 → 落库 → 显示”这一条完整链路（里程碑 M1），然后逐层加厚，不要先把某一层横向铺满。
2. **一张施工单对应一个 PR。** 工作量 1–3 天，可以独立审查、独立验收、独立回退。超过 3 天的单子必须拆开。
3. **守护与功能同单交付。** 每张单子的测试必须具备区分能力：去掉实现后会红（铁律 10）。
4. **不越单施工。** 施工中发现范围外的问题，先记入所在阶段 README 的“遗留与发现”，再由用户决定是否另开单。
5. **按用户规则收尾。** 功能完成后，给出可照做的验收流程；用户验证通过后才能提交（commit）。用户可见的改动写进 `CHANGELOG.md` 的 `[Unreleased]`。

### 里程碑验收口径

- **M1 最小闭环**：在干净的临时数据目录下，`gqy daemon start` → `gqy ask "你好"` 通过 mock 供应商和真实供应商都能流式返回并落库；重启 daemon 后会话可以继续；`gqy`（TUI）能对话。
- **M2 可日用编码**：TUI 中可以完成读文件、改文件、跑命令、审批、取消、压缩的完整编码回合；Linux 上沙盒生效，macOS 上走“审批后无沙盒执行”路径；在 mock 长会话上，字节前缀门禁与缓存用量日志都成立。
- **M3 Web**：同一个二进制内嵌 Web 控制台，局域网外默认不可访问；TUI 与 Web 同时观察同一会话，事件一致。
- **M4 伴侣回归**：persona、记忆、QQ 与 iMessage 连接器可用；外部输入全部按不可信处理。
- **M5 多设备**：两台设备配对，能委派能力，能按用户选择同步会话；跨设备继续时哈希链校验通过，或按计划冷启动。
- **M6 首个正式发布**：Release Please 产出制品；v1 数据导入可预演、可核对、可回退。

## 3 施工单规范

### 3.1 编号与位置

- 阶段目录：`docs/construction/Pxx-<阶段名>/`。每个阶段有一份 `README.md`，写阶段目标、进入条件、退出条件、施工单清单与依赖、遗留与发现。
- 施工单：`Pxx-NN-<短名>.md`，例如 `P03-02-请求规划.md`。编号一旦发布就不再复用；废弃的单子保留文件，并把状态标为“已废弃”。
- 状态以施工单文件头为唯一真相源。阶段 README 的清单只写链接和一句话，不重复写状态。
- [施工图](施工图.html) 是进度的可视化：`plan-data` 里的状态与施工单文件头一致，架构拼图按状态自动点亮。P00-02 起由 `cargo xtask plan` 校验两者一致；每张单合入 main 时在施工图的“每一步的图”里补一节（见 `AGENTS.md`）。

### 3.2 模板

````markdown
# Pxx-NN · 标题

| 项 | 值 |
| --- | --- |
| 状态 | 未开始 / 进行中 / 待验收 / 已完成 / 已废弃 |
| 依赖 | Pxx-NN、… |
| 设计依据 | designs/NN-文档名.md §x.y |
| 规模 | S（≤1 天）/ M（1–2 天）/ L（2–3 天） |
| 涉及 crate / 目录 | crates/gqy-xxx、… |

## 目标
一段话：做完之后，系统多了什么可以验证的能力。

## 范围
- 做：…
- 不做：…（写明归属哪张单）

## 改动清单
按文件或模块列出要新增 / 修改的内容。

## 接口草案
关键类型与函数签名（Rust 代码块），标注“草案，以实现为准”。

## 实施步骤
1. …

## 测试与守护
- 单元 / 集成 / 属性测试列表；
- 区分能力要求：说明去掉哪段实现后，哪条测试会红。

## 验收流程
可照做的命令与期望输出，用户按此验收。

## 完成判据
- [ ] 全局完成定义（§3.3）全部满足
- [ ] 本单特有判据……

## 风险与回退
````

### 3.3 全局完成定义（Definition of Done）

每张施工单在“待验收”之前必须全部满足：

- [ ] `cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace` 全部通过；
- [ ] `cargo xtask arch`（层序）与 `cargo xtask size`（文件体积）通过；
- [ ] 以上适用的代码检查均由 GitHub Actions 在 PR 中执行，并配置为必需状态检查；仅在本地通过不构成合并门槛；
- [ ] 新增测试具有区分能力，已按“先红后绿”验证，并在 PR 描述中写明验证方式；
- [ ] 测试失败时输出可读的定位信息，包括期望值、实际值和相关 ID（19）；
- [ ] 公开 API、数据库迁移、配置字段、协议字段的变更，已同步到对应设计文档；
- [ ] 用户可见的变化已写入 `CHANGELOG.md` 的 `[Unreleased]`；
- [ ] 没有新增非测试代码中的 `unwrap`/`expect`/`panic!`，没有无界通道，没有无超时等待；
- [ ] 给出可照做的验收流程，用户验收通过后才能提交。

P00 完成之前，上述 cargo 与 xtask 检查尚不存在。P00 的各单以本单交付的检查为准，逐步收紧。

## 4 执行方式建议

- 每张单交给一个执行者（人或 AI）。执行前先读单中列出的设计依据章节；执行中如需偏离设计，先停下来提出，不要自行改变设计。
- 每张单在独立工作树 `.worktrees/Pxx-NN-<短名>/` 上施工，分支为 `step/Pxx-NN-<短名>`。验收通过后整理提交，再经 PR 合入 main；细则见仓库根的 `AGENTS.md`。
- 平台口径（00 §5）：Linux 与 macOS 做完整验收；Windows 只验收编译和单元测试。
- 规模为 L 的单子，实施步骤中的每一步都应能单独编译通过，方便中途检查。
- 需要真实供应商、真实平台账号或特定操作系统的验收步骤，在单中标注“需用户环境”，并同时提供 mock 版本的替代验收。
