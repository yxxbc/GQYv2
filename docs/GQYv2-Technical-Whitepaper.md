## 摘要

GQY v2（下称 GQYv2）要解决的是一个本地问题：个人的 AI 能力如何长期驻留在自己的机器上——行为可预测、边界可审计、升级不丢记录。

这个项目从本地 gqy-agent 的实践中生长出来：一个已经跑了数月的本地 Agent 系统（终端、网页、QQ、iMessage、语音多个入口），它验证了长会话下的前缀缓存工程、内核级沙盒与数据迁移，也暴露了跨语言胶水层、外部运行时依赖与架构熵增的代价。GQYv2 的答案是一次"纯血化"重构：Rust 为体，Web 为面，C 为径；核心产物是单一自包含可执行文件，零外部解释型运行时依赖。它对设备共享的回答同样朴素：每一个 app 既是客户端，也是服务端——不依赖中心服务器，设备之间点对点地互相提供能力（见第 3 章）。

本白皮书记录 GQYv2 的工程判断与长期方向。我们关心的是：当模型、提示词、工具规划与交互形态持续变化时，用户在本机积累的会话、任务、数据与授权能否稳定延续。为此，模型适配与执行循环保持可替换，而系统边界、持久化记录、缓存契约与用户控制被当作长期地基维护。

GQYv2 目前处于脚手架阶段。本文以 2026-09-26 的仓库快照与本地 gqy-agent 仓库为工程基线，严格区分两类陈述：

- **【现状】**：仓库中可直接核对的既有事实（文档、脚本、CI、历史项目的实测与架构记录）；
- **【规划】**：尚未实现的设计方向。GQYv2 当前没有构建清单（Cargo manifest）与任何应用实现，所有目标章节均为规划，目录、接口与数据格式都可能随重构改变。

文献引用只用于解释设计取舍，不构成性能评测或行业对比。

## 1 起点与问题重构

### 1.1 本地 gqy-agent 的历史【现状】

GQYv2 的起点是本地 gqy-agent 项目。它的历史不长，但提交、版本与文档记录完整、可核对：

| 时间 | 事件 |
| --- | --- |
| 2026-04-24 | 仓库首个提交；项目以 Miyu 之名从上游 miyu-agent 分叉起步 |
| 2026-06-28 | 发布 v0.1.0 |
| 2026-06 至 08 | 0.1.x–0.4.x 快速迭代：子代理、文件编辑工具、脚本接口、剪贴板与并行会话陆续成形 |
| 2026-09-06 / 09-17 / 09-24 | v0.5.0 → v0.6.0 → v0.7.0；至 2026-09-26 共 36 个版本 tag、1281 次提交 |
| 2026-09-14 | 全面改名 GQY / 顾清影：命令 `miyu`→`gqy`、数据目录 `~/.miyu`→`~/.gqy`、环境变量 `MIYU_*`→`GQY_*`、MCP 服务名与默认人格；并决定与上游独立分叉、不再合并 |

它的工程形态（来自其架构模型说明书，as-built）：

- 六种进程形态：CLI、常驻 daemon、语音前端，以及渲染 / 嵌入 / 闹钟 worker；除语音前端独立构建外，其余角色共用同一个二进制，以不同 argv 与环境长出；
- daemon 是唯一执行回合的地方：HTTP/SSE + 反向 WebSocket + unix socket，单 actor 负责准入；
- 向上接终端、浏览器、QQ、iMessage、麦克风；横向接 MCP 服务器与多家模型供应商；
- 每身份一份 `conversation.db`（37 版迁移）、每 persona 独立记忆库；提示词、工具描述与 Web 静态资源在编译期进入二进制。

它留下的四份工程资产，是 GQYv2 的直接前提：

1. **前缀缓存工程**：缓存按字节（更准确地说，按 token 块）匹配，"前缀即契约、append-only、化石化、stub 工具面"被写进项目正典并实测——连续两轮请求共享 84% 字节；stub 工具面把工具循环的轮内命中从 0% 拉到 95%–99.8%；116k token 上下文实测命中 99.9%。
2. **内核级沙盒**：Linux 用 Landlock 做无特权访问控制；非 Linux 平台带策略时"失败关闭"（拒绝创建子进程），而不是降级裸奔；并明文登记"沙盒只管文件系统，网络不受限"这一边界。
3. **数据即历史**：库内 37 版迁移、改名时的全量数据迁移脚本与"预演 → 核对 → 应用"流程，证明了"用户的会话与记忆不能被静默丢失"是可施工的要求。
4. **架构门禁**：8 层 44 个顶层模块的层序检查，加一份"只许变小不许变大"的反向依赖白名单，把架构现状变成可执行的登记，而不是口号。

### 1.2 问题重构：从"能用的伴侣"到"可长期运行的运行时"

gqy-agent 的背景负载决定了它的工程难题与一次性工具完全不同：会话以天计、上下文以十万 token 计、每轮都要把历史整体重发一次。v1 证明了这条路可行；也把下一阶段的问题暴露成清晰的工程命题【现状→规划】：

- **分发与环境负担**：跨语言胶水层与外部运行时依赖，让"装在哪、跑在哪"变成用户问题；
- **长期运行的可预测性**：内存、延迟与缓存命中必须在数天到数周尺度上保持稳定；
- **能力边界与硬限制**：系统能力必须可审计、可收敛，不能靠提示词或应用内开关承担；
- **入口与内核**：TUI、网页、桌面应当共享同一运行时，而不是三套各自演化的半成品。

GQYv2 的三条工程主张由此确定【规划，来源：docs/tech-stack.md】：

1. **纯血化**：以 Rust 与 C 为绝对核心语言，杜绝 Python / Node.js 等解释型运行时的强依赖；
2. **零运行时依赖**：核心产物为单一自包含可执行文件，开箱即用；
3. **强类型与可预测延迟**：以所有权模型与无 GC 特性，支撑长时运行与高并发多轮对话。

一句话定位：GQYv2 不是 v1 的功能重写，而是把 v1 已验证的运行时经验（缓存契约、沙盒、数据迁移、架构门禁）提炼为一份可施工的纯血实现。

### 1.3 范围与非目标【规划】

**范围**：个人用户在自己的设备上使用；TUI 与内嵌 Web 控制台作为主要交互入口，可选 Tauri 桌面宿主；执行发生在设备本机，设备之间按"每个 app 都是客户端 + 服务端"的点对点模型互相提供能力（见第 3 章）。

**非目标**（明确不做，避免范围漂移）：

- 设备共享不引入"必须依赖"的中心服务器：服务器角色是可选的设备角色，任何设备都可以回到"客户端 + 服务端一体"（见第 3 章）；也不引入节点空间、绑定与持久化同步一类的问题域；
- 不引入 Flutter / Dart 等额外运行时栈，也不做 JavaScript 桥一类的胶水层；
- 不承诺平台支持清单：平台能力以 FFI 与沙盒的真实实现为准，文档不预支承诺。

## 2 运行时构成：单一二进制与多入口【规划】

### 2.1 概念与边界

GQYv2 的目标形态是"一个二进制、一颗内核、多个入口"。核心概念与必须守住的边界如下（判据来自 docs/tech-stack.md）：

| 概念 | 在 GQYv2 中的角色 | 必须守住的边界 |
| --- | --- | --- |
| Harness 引擎 | 智能体运行时的主体：状态机与执行循环，把用户输入推进为可核对的工具事实 | 同一会话同一时刻只有一个推进者；中断与取消必须可传播 |
| Perception Matrix | 把"模型看到什么"拆成 Host / Workspace / Origin / Context 四个正交维度 | 感知是显式的、可审计的；不靠隐式全局状态 |
| Prefix Cache Ledger | 逐字节可复现的 append-only 前缀账本（Append-only / Fossilize） | 只追加；压缩是唯一的、单调的例外 |
| 存储层 | SQLite（WAL）承载会话、任务与账本记录 | 单机文件即事实来源；演进只走增量迁移 |
| Host / FFI | 系统能力边界：PTY、信号、文件系统、进程、OS 探测与沙盒 | 能力来自本机真实权限；应用内开关不能创造系统没有的能力 |
| 入口（TUI / Web / Desktop） | 三种交互形态共享同一运行时 | 入口不持有业务事实，不各自演化为独立实现 |

### 2.2 目标分层

图 1 是目标分层（对应 docs/tech-stack.md 的全景矩阵）：

```text
┌───────────────────────────────────────────────────────────────┐
│                  入口层：共享同一运行时                          │
│  TUI（ratatui + crossterm）                                    │
│  Web 控制台（TypeScript，编译期内嵌进二进制）                     │
│  Desktop（可选，Tauri v2：Rust 宿主 + WebView）                  │
├───────────────────────────────────────────────────────────────┤
│              GQY v2 Harness 引擎（tokio 异步核心）               │
│  Perception Matrix（Host / Workspace / Origin / Context）       │
│  State Machine & Execution Loop                                │
│  Byte-Pure Prefix Cache Ledger（Append-only / Fossilize）       │
├───────────────────────────────────────────────────────────────┤
│                    存储、IPC 与网关                             │
│  SQLite（rusqlite，WAL） · Axum（HTTP / SSE / WebSocket）       │
│  本机 IPC：Unix Domain Sockets                                  │
├───────────────────────────────────────────────────────────────┤
│                 系统原语与沙盒（C FFI）                          │
│  PTY · POSIX 信号 · OS 探测 · Landlock / 平台级工作区隔离        │
└───────────────────────────────────────────────────────────────┘
```

*图 1：GQY v2 目标分层（规划）。*

三条构成原则：

- **单一产物**：核心是一个自包含二进制；Web 控制台在编译期内嵌，不需要独立部署 Node 服务；
- **单一内核**：TUI 与 Web 不是两套实现，而是同一运行时的两种门面；
- **单一事实来源**：数据落在本机文件（SQLite）；版本与发布由仓库根的单一版本文件管理（见第 10 章）。

## 3 设备共享：每个 app 都是客户端 + 服务端【规划】

设备共享的理念只有一句话：**每一个 app 都是一个客户端，也是一个服务端。** 这个项目没有独立的"服务端产品"：前端与后端一起封装在 app 里；谁扮演服务器，是配置出来的角色，而不是另一种安装包。app独立使用的时候不走网关，网关只是连接三方平台使用

### 3.1 拓扑：服务器角色与自动降级

- 默认形态：每个 app 实例（TUI / Web / 桌面）既向用户与其它设备**提供**本机能力，也可以**使用**其它设备提供的能力；
- 可选形态：把其中一台设备**设置为服务器**，由它集中承担服务角色；
- **自动降级**：被指定的服务器不在运行时，当前设备自动降级为"客户端 + 服务器"一体——功能不因服务器缺席而瘫痪；
- 没有服务器时，也可以选择使用自身客户端内置的后端。

```text
默认：每个 app 都是客户端 + 服务端（局域网内互相服务）
  设备 A（app） ⇄ 设备 B（app） ⇄ 设备 C（app）

可选：指定一台设备（B）为服务器
  设备 B（服务器） ⇐ 设备 A（客户端）    设备 C（客户端）

服务器不在运行时：
  设备 A 自动降级为「客户端 + 服务器」一体（本机后端兜底）
```

*图 2：设备共享的拓扑与自动降级（规划）。*

### 3.2 发现、配对与信任

- **局域网自动发现**；发现后，新设备加入需要**全部设备同意**，而不是单一管理员拍板；
- **无须账户体系**；信任通过**密码**建立；设备授权**长期有效**，撤销是显式动作；
- **撤销之后**：该设备降级为"客户端 + 本地服务器"，退回本地自用；重新联网后仍可再次合并（见 3.3）。

### 3.3 同步与合并

- **共享范围是全部**：会话、任务记录、能力、文件、记忆 / 知识库与模型接入都可以共享；
- 重新加入或重连时，可以**询问用户是否同步合并**——合并由用户决定，系统不静默替用户做；
- 传输采用 **HTTPS**。

### 3.4 版本与一致性

- **每次更新时统一版本号管理**：全设备在同一版本体系内升级；
- 版本不一致时如何处置（拒绝服务、降级或提示统一升级）尚未定义，本版不虚构。

### 3.5 研究课题：跨设备的前缀契约

GQYv2 的硬约束是"逐字节相同的前缀"（第 5 章）。任务从设备 A 继续到设备 B 时，B 发出的请求必须与 A 的历史请求前缀逐字节一致，前缀缓存才会命中。供应商侧前缀缓存以内容前缀（token 块哈希）为键复用[8][11]：同一账号下，不同设备发出的相同前缀请求理论上命中同一份缓存，但"跨客户端是否共享缓存池"需按供应商实测确认。

由此，跨设备继续**原则上可行**，真正的要求是"字节可重建"。本版给出研究框架（候选方案，未定；验证结果将回写本文）：

1. **账本随任务走**：共享范围是全部（3.3），B 从同一份 append-only 账本重建请求；重建路径必须唯一，不允许存在会产出不同字节的第二条渲染路径；
2. **序列化与工具面恒定**：stub 工具面常驻（第 5 章），配合统一版本号管理（3.4），保证"换设备不换字节"；
3. **注入冻结**：任何注入（时间、环境、探测结果）在写入账本时被冻结，换设备重放同一份冻结值；
4. **链式哈希校验**：为每个请求前缀记录哈希，交接时校验重建结果；不一致就执行"计划内冷启动"并向用户明示，不允许静默失配；
5. **模型在局域网内提供时**：命中还取决于请求是否被路由到持有该前缀 KV 的实例——服务端需要缓存感知路由；SGLang、vLLM 的服务部署组件已提供这类路由（选型时单独评估）。

待验证项：供应商缓存的 TTL 与写入计价差异（v1 已观测到热窗口随负载浮动【现状】）、跨设备交接的时间窗、模型接入同步后的凭据与配额归属。本版不承诺结果。

## 4 工程架构【规划】


### 4.1 核心引擎与异步模型

- 语言与版本：Rust 2024 Edition / 1.85+；
- 异步运行时：tokio——多线程核心驱动 + 单线程 local task 隔离，把"共享状态"与"会话内状态"分槽放置；
- 序列化与数据模型：serde / serde_json，数据结构先行，能力以 trait 暴露；
- 结构化日志与追踪：tracing / tracing-subscriber，作为长期运行的可观测地基。

### 4.2 存储与状态持久化

- 嵌入式数据库：SQLite（rusqlite 绑定），开启 WAL，读写分离，零锁竞争；
- 数据演进：纯增量 migration，历史会话数据向前兼容，不用重建库来换取新功能；
- 先例【现状】：v1 的 `conversation.db` 经历 37 版迁移仍在服役，证明"增量演进"是本地 Agent 的可行路线。

### 4.3 入口与网关

- TUI：ratatui + crossterm；目标是毫秒级首屏、平滑滚动、多会话切换与任务面板，无 Python / curses 外部依赖；
- Web 控制台：TypeScript + 现代 Web 标准（HTML5 / CSS3 / ES Modules）；编译期经 rust-embed 或 include_dir 打入二进制，浏览器访问即用；
- HTTP / RPC 网关：axum，支持 SSE 流式传输与 WebSocket 实时双工；
- 本机进程间：Unix Domain Sockets，供同机其他进程与工具复用同一运行时；
- 桌面（可选）：Tauri v2（Rust 核心宿主 + 系统 WebView）；docs/tech-stack.md 给出的量级预期是打包体积通常小于 15MB、运行时常驻内存约 30MB。

### 4.4 系统交互与沙盒

- 语言边界：Rust + C / libc FFI；libc 与 nix 承担系统调用与进程管理；
- 伪终端：portable-pty 或原生 PTY 封装，支持流式输入输出与信号传递——终端会话是 Agent 的一等公民，不是拼接字符串的假终端；
- 沙盒：Linux 走 Landlock 内核级权限收敛；macOS 走系统级资源隔离与工作区作用域限制；
- 硬限制优先：宁可失败关闭，也不静默降级（v1 在非 Linux 平台"带策略即拒绝执行"是同类先例【现状】）。

### 4.5 分层与依赖方向

- 低层只通过数据结构与 trait 暴露能力，上层负责组装实现，降低平台适配、模型接入与前端形态之间的耦合；
- 依赖方向与边界必须可检查：v1 用层序检查与"只减不增"的反向依赖白名单，把架构现状变成可执行登记【现状】；GQYv2 规划沿用这一思路；
- 模块化、可复用，避免单文件膨胀为"上帝文件"（仓库工程约定）。

## 5 会话、执行与上下文连续性

### 5.1 回合与执行循环【规划】

一次"回合"= 用户输入 → 组装请求 → 模型流式响应 → 工具调用与执行 → 结果回填 → 下一请求。核心约束：

- **执行归属唯一**：同一会话同一时刻只有一个推进者，避免"多处输入同时改写同一段上下文"；
- **可中断**：取消必须从入口一直传播到工具进程与模型请求；
- **事实可核对**：工具参数、执行环境、结果与错误都是记录，不只是界面上的动画。

```text
用户输入 ─▶ 组装请求（前缀 = 上轮请求的逐字节延续）
             │
             ▼
      模型流式响应 ──▶ 工具调用 ──▶ 本机执行（沙盒内）
             │                          │
             └────────── 结果回填 ◀──────┘
             ▼
      账本追加：请求、响应与工具事实逐字节落库（append-only）
```

*图 3：回合与账本（规划）。*

### 5.2 字节纯净的前缀缓存账本【规划，v1 实测佐证】

长会话的成本不是由"上下文有多大"决定的，而是由"每轮有多少字节与上轮相同"决定的。LLM API 是无状态的：每轮都要重放系统提示词、工具定义与全部历史；供应商的前缀缓存复用"逐字节相同"的前缀，价格通常是全价的十分之一、速度快一个数量级[12]。于是设计目标被压缩成一条可检验的契约：

- **前缀即契约**：相同的会话状态，必须产生逐字节相同的请求前缀。所有非确定性内容（时间、随机数、探测结果）要么不进前缀，要么在进入的瞬间被冻结；
- **append-only**：追加不插入；已发送的内容落库后逐字节回放，永不删除（化石化）。压缩是唯一的例外，且必须单调；
- **工具面稳定**：工具以"真名 + 一行摘要 + 宽松参数壳"常驻，tools 数组在会话内字节恒定；完整参数契约按需以工具结果的形式获取，落在对话尾部，不碰前缀；
- **多通道分离**：用户原文、界面展示与工程附加物（运行时上下文、来源元数据）走不同通道，缓存工程不污染记忆与展示。

实测依据【现状，来自 v1 在特定供应商上的测量，不是 GQYv2 的承诺】：连续两轮请求共享 84% 字节；stub 工具面把工具循环的轮内命中从 0% 提到 95%–99.8%；116k token 上下文实测命中 99.9%。v1 的经验同样表明：不同供应商的缓存语义差异巨大（有契约型、尽力而为型、按次计费型），因此 GQYv2 规划把"把自己的字节做纯"作为普适层默认开启，把依赖供应商行为的策略（如保温请求、写入宽限）作为可配置项，并写清适用条件。

### 5.3 上下文分层与预算【规划】

- 模型上下文是稀缺的工作空间，不是个人数字生活的唯一容器；
- 分层：热工作状态（当前回合）/ 任务事实（工具轨迹、结果、错误、产物引用）/ 语义历史（摘要、用户意图、下一步）/ 本地敏感（凭据与临时句柄，仅存本机、不进入模型可见文本）；
- 压缩（compact）是账本的"翻页"：水位线只能向前推进，压缩产物一旦写下也进入账本，不许中段改写；
- GQYv2 不自称解决模型内生的长期记忆问题；它维护的是模型之外的连续性基础：工作状态、持久记录、权限与数据归属。

## 6 感知矩阵与能力边界

### 6.1 四维骨架【规划】

Perception Matrix 是 GQYv2 规划的感知骨架，把"系统知道什么"与"模型看到什么"分隔开。docs/tech-stack.md 明确列出 Host / Workspace / Origin / Context 四个维度；本文不虚构其字段级契约：

| 维度 | 回答的问题 | v1 中的同类先例【现状】 |
| --- | --- | --- |
| Host | 这台机器现在真正能做什么？ | 系统能力经 FFI 暴露；OS 探测；沙盒按代码路径登记 |
| Workspace | 当前工作区在哪里、读写边界到哪？ | 工作区作用域与沙盒策略分离 |
| Origin | 这条内容从哪来、可信级别是什么？ | 外部消息按不可信输入处理；权限在代码层判定，不由提示词承担 |
| Context | 当前任务需要模型看到什么？ | 原文 / 展示 / 工程附加物三通道分离；化石尾部固定 |

### 6.2 沙盒与硬限制【规划】

- Linux：Landlock 内核级权限收敛，权限集按需收紧；
- macOS：系统级资源隔离与工作区作用域限制；
- 失败关闭：策略无法生效时拒绝执行，而不是降级裸奔（v1 先例【现状】）；
- 边界诚实：沙盒的覆盖面必须在文档里写明（v1 明文登记"只管文件系统、网络不受限"），不夸大隔离能力；
- 硬限制服务健壮性：限制的目的是让代码保持可维护、行为可预测，而不是制造仪式感。

### 6.3 平台能力的表述方式【规划】

GQYv2 不在文档里承诺"支持哪些平台"，而是以能力描述为准：某平台上暴露哪些 Host 能力、沙盒以什么形式生效、缺哪些能力时如何失败。这样平台清单可以增长，而文档不需要预支承诺。

## 7 权限与用户主权【规划】

本地 Agent 的核心不是替用户做所有决定，而是让用户能看见、理解并决定重要的边界。规划的权限层级自上而下：

| 层级 | 责任 | 对用户的意义 |
| --- | --- | --- |
| 系统与账户 | 操作系统与部署环境真实授予的权限 | 这台机器和这个账户真的能做什么 |
| 沙盒与工作区 | 进程 / 文件边界收敛（Landlock、工作区作用域） | 她实际能读到、写到哪里 |
| AI 能力模式 | 运行时档位：只读 / 工作区读写 / 完全 | 此刻允许模型与工具做什么 |
| 单次工具审批 | 对一次有后果的调用做确认 | 哪个动作将在哪里发生、是否授权 |

两条原则：

- **下层只能收紧，不能绕过上层**；应用内开关不能创造系统没有的能力；
- **用户可见性**：确认、拒绝与解释应当是入口（TUI / Web）里的自然交互，而不是命令行负担；
- **能力不随共享漂移**：设备之间互相使用能力时，权限判定仍由提供能力的那台设备完成（见第 3 章）。

docs/tech-stack.md §四 已记录三类必须长期考虑的议题【现状】：破坏性变更、补丁更新、以强有力的硬限制保持代码健壮性与可维护性。本文把它们落成规划要求：破坏性变更必须附带迁移说明与恢复路径；补丁与更新不得静默改变用户数据的语义。

## 8 可扩展性与演进路径

### 8.1 现状【现状】

- 仓库为入口预留 `apps/`（`tui/`、`web-console/src/`、`desktop/src-tauri/` 均为规划占位），为扩展预留 `plugins/` 目录；
- 这些目录目前没有任何契约、接口或实现；apps/README.md 明确声明"当前目录是规划占位，不代表这些应用已经实现"。

### 8.2 v1 的扩展经验【现状】

- **persona 即配置单位**：一个目录承载提示词、关系档案与启用集，扩展面随配置组合生长；
- **多样扩展面**：技能、脚本工具、MCP 服务器与包管理在 v1 已长期运行；
- **连接器协议**：把平台 I/O 放进独立连接器进程（可用任意语言编写），主程序不因新增平台而重新编译；
- **契约式治理**：架构反向依赖白名单"只许变小不许变大"，是比口头约定更硬的契约形态。

### 8.3 v2 的立场【规划】

- 先立边界，后扩能力：FFI、沙盒、存储与缓存账本是先决条件，扩展接口排在后面；
- 扩展契约在有真实实现之前不写进本白皮书——不虚构 SDK，也不预支兼容承诺；
- 任何扩展都必须能被"能力边界"约束（第 6、7 章），不允许以全权限兜底。

## 9 研究背景与技术定位

### 9.1 执行循环与可核对的工具事实

ReAct 展示了把推理轨迹与外部动作交错，可以让模型维持任务计划、让过程比最终答案更可理解[3]。GQYv2 不把模型的隐藏推理当作需要无限记录的对象，而是承认"任务过程需要可核对的外部事实"：工具调用、输入、结果、错误、产物与执行环境在系统层面是一等公民。这与第 5 章的账本设计一致。

### 9.2 分层记忆与上下文预算

MemGPT 把有限上下文窗口与分层记忆管理联系起来，指出长对话与大文档需要跨存储层选择信息[4]。这类工作启发了 GQYv2 把模型上下文视为稀缺工作空间：账本、摘要与原始记录分层存放，按当前任务供给上下文，而不是把一切灌进请求。GQYv2 不自称解决模型内生的长期记忆问题——它维护的是模型之外的连续性基础。

### 9.3 前缀缓存的工程现实

服务端推理引擎的前缀复用（SGLang 的 RadixAttention[5]、vLLM 的 PagedAttention[6]）让"缓存命中"成为可设计的工程目标；而供应商 API 的缓存语义差异（写入计价、TTL 承诺、尽力而为[8]）意味着客户端唯一可控的变量，是把字节做纯。v1 的实测【现状】验证了这一点：语义等价的两种上下文，只要字节不同，命中即为零。这就是"前缀即契约"被当作硬约束的原因。

### 9.4 权限收敛的内核基础

Landlock 让无特权进程也能对自己施加访问控制[7]，这正是本地 Agent 沙盒需要的形态：不依赖 root、不依赖容器，把能力收敛到工作区。GQYv2 的 Linux 沙盒路线以它为基座。

### 9.5 技术定位

模型越强，应用侧的固定脚手架越可能被替换；但"任务在本机执行"这一事实不会消失，它要求系统记录可访问资源、授权范围、任务结果与恢复路径。GQYv2 选择维护这些"模型之外"的运行时地基：长时运行、清晰边界、缓存契约、单一二进制分发。

## 10 可靠性、迁移与阶段演进


### 10.1 长时运行的质量清单【规划】

- 内存占用在数天到数周尺度上稳定；无 GC 不等于无资源问题，生命周期必须显式管理；
- 取消传播、背压与流终止是协议的一部分，不是异常处理；
- 结构化日志与追踪（tracing）作为可观测地基；
- 测试内生化：单元、集成、Mock 与基准全部用 Rust 原生编写（cargo test、wiremock、tempfile、criterion），淘汰外挂式探针；v1 的实践【现状】已经证明"每次测试都有反馈"是长时系统的必要习惯。

### 10.2 数据与文件演进【规划】

- SQLite WAL + 纯增量 migration；历史会话与账本向前兼容；
- 迁移必须可核对：预演、计数校验、备份，与 v1 改名迁移的流程同构【现状】；
- 发布产物与版本必须一致：包版本、Git tag 与 changelog 标题同源；仓库当前以 `version.txt` 为版本文件，`Cargo.toml` 的 `[workspace.package].version` 由发布 PR 同步【现状】。

### 10.3 版本与发布治理【现状，本仓库已落地】

GQYv2 在写第一行运行时代码之前，先落地了可执行的治理：

| 机制 | 实现 |
| --- | --- |
| 提交与 PR 规范 | Conventional Commits；本地 commit-msg hook 与 CI 共用同一校验器（scripts/check-commit-subject.sh） |
| PR 标准检查 | pr-standards：PR 标题、提交范围与 changelog 条目一致性（scripts/check-pr-standards.sh） |
| 供应链与工作流安全 | zizmor 工作流审查（中危及以上阻断）；dependency-review 阻断高危及以上依赖 |
| 发布 | Release Please：version.txt / Cargo.toml / manifest / changelog 同源（`extra-files` 同步 Cargo 版本）；0.x 阶段按 minor 承接破坏性变更；Git tag 不可变 |
| 变更日志 | Keep a Changelog：面向用户的变更进入 `[Unreleased]`，纯文档与内部维护可豁免 |

### 10.4 阶段声明【现状】

仓库当前仍处于脚手架阶段：没有构建清单、没有应用实现，运行时只存在于文档与规划中。本文的一切目标章节都是规划；当实现落地时，本文应同步更新——文档与代码不一致时，以代码、命令行帮助与运行结果为准。

## 11 实施优先级与结语【规划】

下一步的重点是让用户能在自己的机器上启动、观察、批准、继续并迁移 Agent 的工作，而不是继续堆文档。优先级如下：

| 优先级 | 要解决的真实问题 | 期望的地基 |
| --- | --- | --- |
| 最小可运行闭环 | 目前没有构建清单与应用实现 | 建立 Rust workspace 与第一个垂直回路：TUI ↔ 网关 ↔ SQLite 跑通一轮对话 |
| 能力与沙盒 | 系统能力不可审计、边界不可收敛 | C FFI（PTY、信号、OS 探测）与 Linux Landlock / macOS 工作区隔离落地 |
| 缓存契约与账本 | 长会话成本与延迟不可预测 | Byte-Pure Prefix Cache Ledger 落地；测试内生化覆盖缓存契约 |
| 干净分发 | 装到什么机器就得先配什么环境 | 单一自包含二进制 + 内嵌 Web 控制台；构建、测试、基准进入 CI |
| 设备共享 | 多台设备的能力无法互相使用 | "每个 app 都是客户端 + 服务端"的最小互联：配对、授权与能力委派（见第 3 章） |
| 发布基线 | 版本与制品不可核对 | Cargo manifest 接入版本一致性检查与依赖审查；产出首个可发布制品 |

我们希望的终局很朴素：一台机器、一颗二进制，就能承载长期的陪伴与工作——聊天、记事、编码、跑任务，记录留在本机，边界写在明处，升级不丢过去。GQYv2 会继续经历必要的重构；我们选择把成本花在清晰的边界、可靠的记录与可恢复的迁移上。
