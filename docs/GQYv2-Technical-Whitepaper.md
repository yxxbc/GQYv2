## 摘要

GQY v2（下称 GQYv2）要解决的是一个本地问题：个人的 AI 能力如何长期驻留在自己的机器上——行为可预测、边界可审计、升级不丢记录。

这个项目从本地 gqy-agent 的实践中生长出来：一个已经跑了数月的本地 Agent 系统（终端、网页、QQ、iMessage、语音多个入口），它验证了长会话下的前缀缓存工程、内核级沙盒与数据迁移，也暴露了跨语言胶水层、外部运行时依赖与架构熵增的代价。GQYv2 的答案是一次"纯血化"重构：Rust 为体，Web 为面，C 为径；核心产物是单一自包含可执行文件，零外部解释型运行时依赖。它对设备共享的回答同样朴素：每一个 app 既是客户端，也是服务端——不依赖中心服务器，设备之间点对点地互相提供能力（见第 3 章）。

本白皮书记录 GQYv2 的工程判断与落地架构。我们关心的是：当模型、提示词、工具规划与交互形态持续变化时，用户在本机积累的会话、任务、数据与授权能否稳定延续。为此，模型适配与执行循环保持可替换，而系统边界、持久化记录、缓存契约与用户控制被当作长期地基维护。

GQYv2 目前已全面进入多 Crate 模块化实现与蓝图落地阶段。本文以 2026-10 的工程仓库快照与本地 `docs/blueprint/`、`docs/designs/` 为工程基线，严格区分两类陈述：

- **【现状】**：仓库中可直接核对的既有事实（Rust 2024 Workspace、核心 Crates 实现、文档蓝图、设计决策、三平台 CI 矩阵与真实提交）；
- **【规划】**：尚未完全收尾或规划中演进的设计方向（如跨设备点对点完全互联、更高级的扩展生态等）。

文献引用只用于解释设计取舍，不构成性能评测或行业对比。

## 1 起点与问题重构

### 1.1 本地 gqy-agent 的历史【现状】

GQYv2 的起点是本地 gqy-agent 项目。它的历史不长，但提交、版本与文档记录完整、可核对：

| 时间 | 事件 |
| --- | --- |
| 2026-04-24 | 仓库首个提交；项目从上游 Agent 分叉起步 |
| 2026-06-28 | 发布 v0.1.0 |
| 2026-06 至 08 | 0.1.x–0.4.x 快速迭代：子代理、文件编辑工具、脚本接口、剪贴板与并行会话陆续成形 |
| 2026-09-06 / 09-17 / 09-24 | v0.5.0 → v0.6.0 → v0.7.0；共 36 个版本 tag、1281 次提交 |
| 2026-09-14 | 全面改名 GQY / 顾清影：命令 `gqy`、数据目录 `~/.gqy`、环境变量 `GQY_*`、MCP 服务名与默认人格；并决定独立演进 |
| 2026-09-26 至 10-05 | 全面启动 GQYv2 纯血重构：分拆 20+ 个核心 Crates，推进两百张原子施工单，三端 CI 覆盖 |

它留下的四份工程资产，是 GQYv2 的直接前提：

1. **前缀缓存工程**：缓存按字节匹配，"前缀即契约、append-only、化石化、stub 工具面"被写进项目正典并实测——连续两轮请求共享 84% 字节；stub 工具面把工具循环的轮内命中从 0% 拉到 95%–99.8%；116k token 上下文实测命中 99.9%。
2. **内核级沙盒**：Linux 用 Landlock 做无特权访问控制；macOS 基于作用域隔离；非特权环境下"失败关闭"，而不是降级裸奔。
3. **数据即历史**：事件溯源（Event Sourcing）设计，状态是事件日志的投影，确保可回滚（Undo）、可重做（Redo）与跨版本无损迁移。
4. **架构门禁**：Rust 2024 Workspace，全局禁用 `unsafe_code`（个别 OS 原语严格限定并注释），禁用直接 unwrap，禁止静默吞错。

### 1.2 问题重构：从"能用的伴侣"到"可长期运行的运行时"

gqy-agent 的背景负载决定了它的工程难题与一次性工具完全不同：会话以天计、上下文以十万 token 计、每轮都要把历史整体重发一次。v1 证明了这条路可行；也把下一阶段的问题暴露成清晰的工程命题：

- **分发与环境负担**：跨语言胶水层与外部运行时依赖，让"装在哪、跑在哪"变成用户问题；
- **长期运行的可预测性**：内存、延迟与缓存命中必须在数天到数周尺度上保持稳定；
- **能力边界与硬限制**：系统能力必须可审计、可收敛，不能靠提示词或应用内开关承担；
- **入口与内核**：TUI、网页、桌面应当共享同一运行时，而不是三套各自演化的半成品。

GQYv2 的三条工程主张【现状】：

1. **纯血化**：以 Rust 为绝对核心语言，杜绝 Python / Node.js 等解释型运行时的强依赖；
2. **零运行时依赖**：核心产物为自包含可执行文件，开箱即用；
3. **强类型与可预测延迟**：以所有权模型与无 GC 特性，支撑长时运行与高并发多轮对话。

### 1.3 范围与非目标

**范围**：个人用户在自己的设备上使用；CLI、TUI 与内嵌 Web 控制台作为主要交互入口；执行发生在设备本机，设备之间按点对点模型互相提供能力（见第 3 章）。

**非目标**：
- 不引入"必须依赖"的中心云控服务器；
- 不引入解释型运行时或重量级跨语言胶水层；
- 不预支无根据的平台承诺，一切能力以沙盒与底层系统真实实现为准。

## 2 运行时构成：单一二进制与多入口【现状】

### 2.1 概念与边界

GQYv2 采用"微内核 + 可插拔入口"设计。核心概念与边界如下：

| 概念 | 对应落地模块 | 在 GQYv2 中的角色与约束 |
| --- | --- | --- |
| 核心守护（Daemon） | `crates/gqy-core` | 无界面纯逻辑内核，空闲超时自动退出，单执行回路 |
| 协议与 IPC | `crates/gqy-ipc` | 本机通信层，标准 JSON-RPC 2.0，Unix Domain Socket / Windows 管道 |
| 命令行前端（CLI） | `crates/gqy-cli` | 极薄的交互门面，参数解析、命令分发、安全终端回显控制 |
| 模型驱动 | `crates/gqy-models` | 供应商目录、多协议端点接入、认证与上下文计量 |
| 事件与投影 | `crates/gqy-kernel` / `gqy-store` | 状态机核心；一切会话状态皆为 append-only 事件日志的投影 |
| 沙盒与环境 | `crates/gqy-sandbox` | 系统隔离层；对文件系统读写进行严格约束 |
| Web 与渲染 | `crates/gqy-web` / `gqy-mermaid` | 内嵌 Web 服务与可视化图表渲染支持 |

### 2.2 架构分层

```text
┌───────────────────────────────────────────────────────────────┐
│                  交互入口（共享同一核心）                       │
│  CLI（gqy ask / redo / undo / setup / config）                │
│  TUI（终端全屏界面） · Web 控制台（内嵌 Web 服务）              │
├───────────────────────────────────────────────────────────────┤
│                  IPC 通信层（gqy-ipc）                         │
│  JSON-RPC 2.0 · Unix Domain Socket / Windows Named Pipe       │
├───────────────────────────────────────────────────────────────┤
│              GQY v2 核心守护（gqy-core / gqy-session）         │
│  会话 Actor · 状态机 · 事件溯源（Event Sourcing）              │
│  Byte-Pure Prefix Cache Ledger · 任务与多代理协调 (Subagent)    │
├───────────────────────────────────────────────────────────────┤
│               模型接入与工具执行（gqy-models / gqy-tool）       │
│  流式累积 · 出错重试 · 工具调度 · 本地沙盒（gqy-sandbox）       │
├───────────────────────────────────────────────────────────────┤
│                    存储与持久化（gqy-store）                   │
│  数据根 · 会话日志 · 密钥与配置管理（settings.toml / secrets）  │
└───────────────────────────────────────────────────────────────┘
```

## 3 设备共享：每个 app 都是客户端 + 服务端【现状与规划】

设备共享的理念只有一句话：**每一个 app 既是客户端，也是服务端。** 这个项目没有独立的"专用云端服务"：前端与后端封装在一体化程序中；谁扮演服务器，是配置出来的角色。

### 3.1 拓扑：服务器角色与自动降级

- **默认形态**：每个 app 实例（CLI / TUI / Web）既向用户与其它设备提供本机能力，也可以使用其它设备提供的能力；
- **可选形态**：把其中一台设备设置为常驻服务节点，由它承担中枢角色；
- **自动降级**：当外部节点离线时，当前设备自动降级为本机核心自闭环运行；
- 独立单机使用时完全无需公网连接，仅在需要跨平台联动或多端协同调用时开放端口。

### 3.2 发现、配对与信任

- 局域网基于安全握手自动发现与配对；
- 信任通过显式授权建立，授权凭证安全隔离在本地 Secret 存储中；
- 跨端权限严格继承本地主机的安全策略，绝无越权提权通道。

## 4 工程架构【现状】

### 4.1 核心语言与规范

- 语言与版本：**Rust 2024 Edition / 1.97+**；
- 异步运行时：tokio，多线程调度与本地安全隔离结合；
- 序列化与数据协议：serde / serde_json，数据结构先行；
- 极高代码门禁：
  - `unsafe_code = "deny"`（除底层 OS 终端控制必要处外严格阻断）；
  - `unwrap_used = "deny"`，禁止不可控 panic；
  - `unused_result_ok = "deny"`，禁止丢弃未处理的错误。

### 4.2 存储与状态持久化

- 会话状态完全由 **事件日志（Append-only Event Log）** 驱动；
- 配置管理分层覆盖：系统级、用户个人设置（`settings.toml`）、项目专属配置与加密密钥管理（`secrets`）；
- 每次会话变动可无损复现，支持 `undo` 文件回滚和上下文单调压缩。

### 4.3 系统交互与沙盒

- C FFI 原语支持、PTY 原生终端环境接管；
- 沙盒与隔离（`gqy-sandbox`）：针对 Linux Landlock、macOS 资源作用域、Windows 用户策略进行针对性收敛；
- 严格遵循硬限制：宁可失败拒绝执行，绝不静默裸奔。

## 5 会话、执行与上下文连续性【现状】

### 5.1 回合与执行循环

一次回合流转：
```text
用户输入（CLI/Web） ─▶ IPC 发送到 gqy-core ─▶ 会话 Actor 调度
                             │
                             ▼
              模型请求流式响应 ──▶ 工具调用与参数解析
                             │            │
                             ▼            ▼
                     实时累积与通知 ◀── gqy-sandbox 沙盒隔离执行
                             │
                             ▼
              事件落库 ──▶ 状态投影 ──▶ 生成最终回答 / 产物回填
```

- **单推进者原则**：同一会话严格保证单一写入线程，规避状态竞争；
- **多级撤销保障**：通过事件反向重放与工作区差异记录，支持一键撤销（`gqy undo`）并还原被修改文件。

### 5.2 字节纯净的前缀缓存账本

长会话的核心是成本与延迟可控：
- **前缀即契约**：严格保证请求前缀的字节级稳定性，极大拉高大模型供应商侧 KV Cache 的命中率；
- **Append-only & 化石化**：历史记录只增不改，确保连续对话在推理端的预填充（Prefill）耗时降低 80%~90%；
- **模型资料与用量监控**：实时记录 Prompt Tokens、Completion Tokens 及缓存命中占比。

## 6 感知矩阵与能力边界【现状】

| 维度 | 责任与边界 | 对应工程机制 |
| --- | --- | --- |
| Host | 本机系统环境与能力检测 | 核心环境探测、跨平台 OS 原生支持 |
| Workspace | 当前工程目录与代码边界 | 沙盒作用域限制、只读/读写模式切换 |
| Origin | 外部输入的来源可信度 | 权限模型（只读 / 读写 / 询问确认） |
| Context | 上下文投影与压缩 | 上下文自动/手动压缩（`gqy compact`）、Token 限额预算 |

## 7 权限与用户主权【现状】

- **运行时权限档位**：支持只读模式（`start_read_only`）、交互确认模式与完全授权模式；
- **敏感凭证防泄漏**：输入 API Key 时终端自动关闭回显，密钥文件权限严格设为 `0600`，绝不随运行日志泄露；
- **随时中断与撤回**：支持 `Ctrl+C` 平滑中断任务推进，支持会话回退与重做。

## 8 可扩展性与演进路径【规划】

- **模型与驱动插拔**：已内置支持 DeepSeek、OpenAI、Anthropic、本地服务等多套标准化驱动；
- **子代理体系（Subagents）**：支持父子会话派工与后台异步任务调度（Job 系统）；
- **跨平台界面统一**：逐步落地全功能 TUI 与现代化 Web 交互界面。

## 9 实施优先级与结语【现状】

GQYv2 已成功完成核心地基的建设：微内核架构、IPC 协议层、事件日志系统、沙盒环境与多模型接入已全部落地并验证。

下一步演进重点：
1. **完善全屏终端界面（TUI）与内嵌 Web 前端**，提供更加优雅的交互体验；
2. **拓展多设备间点对点能力互联**；
3. **沉淀成熟的一键式跨平台分发打包（Release Artifacts）**。

一台机器、一颗自包含二进制，让个人的数据、任务与历史长期稳健驻留于本地。
