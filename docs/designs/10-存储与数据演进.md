# 10 · 存储与数据演进

> 状态：【规划】。前置阅读：[00 设计理念](00-设计理念.md)、[01 总体架构](01-总体架构.md)、[02 运行时与并发模型](02-运行时与并发模型.md)。本文定义数据目录、主库 `gqy.db`、内容寻址 blob、写者线程与读连接池、核心表草案、迁移纪律、备份与保留策略。账本条目的语义见 04，记忆表细节见 11，配置文件见 12，v1 数据导入见 20。

## 1 目标

1. 一个数据目录承载一个用户的全部数据：一个主库加一个 blob 目录，外加少量人类可编辑的文件（配置、persona、知识库文档、扩展）。
2. 写入只有一条路径：单写者线程。读走只读连接池。异步代码里不出现同步 SQLite 调用（02 §2）。
3. 迁移只增不删，由测试钉住；每个发布版本都留一份夹具库，新版本必须能迁移所有旧夹具。
4. 备份只用 `VACUUM INTO`；库文件三件套（`-wal`、`-shm`）同进同退。
5. 数据有明确的保留策略；过期清理本身是可审计的作业，不是散落的 `DELETE`。

## 2 v1 教训

- **碎片化**：【v1 实测】同一用户的数据分布在每身份一份 `home/<user>/conversation.db`、每 persona 一份 `memory.db` 与 `evicted_context.db`、`data/kb/` 两个库、记账 `ledger.db`、平台 `message_history/history.sqlite3`，以及 `state/` 下 20 多个 JSON/JSONL 文件。v1 的导出清单 `transfer/registry.rs` 列了约 60 个路径单元。跨库没有事务，也没有统一备份。
- **“只追加”没守住**：conversation.db 共 39 版迁移（`LATEST_VERSION = 39`），其中 v2、v29 整表重建后 `DROP TABLE`，v24 `DROP TABLE goals`，v36 `UPDATE sessions SET workspace = NULL`，v21 批量改名，v5 回填 `display_content`。规则写在注释里，没有测试。
- **位置索引**：turns 表一度 22 列按位置读取，列清单复制 7 遍；加列即错位。
- **JSON 数组读改写**：`turns.tool_reports` 每追加一条都要读整列、解析、push、写回。【v1 实测】80 条 2 KB 报告，理想写入 160 KB，实际 6.5 MB（40.5×），耗时 210.7 ms。v25 才改成子表。
- **活库直接复制**：08-21 用 `fs::copy` 复制活库，丢了 POSIX 锁，库损坏。
- **时间类型混用**：TEXT RFC3339、REAL 秒、INTEGER 秒三种并存。
- **日志不轮转**：`usage-history.jsonl` 不轮转，每次统计全量读。

## 3 数据目录

根目录默认 `~/.gqy2`，可由 `GQY2_HOME` 覆盖（**D-01 待定**）。所有路径只由 `gqy_config::GqyPaths` 计算，其他 crate 不得拼接路径字符串（xtask 规则：`gqy-config` 之外出现 `".gqy2"` 字面量即报红）。

```text
~/.gqy2/                          0700
├── .gqy2-root                         数据根标记（layout 1；认根用，无数据）
├── config/                       0700
│   ├── gqy.toml                  0600  主配置（12，D-07 待定）
│   ├── secrets.toml              0600  密钥（12 Q-12-1 待定）
│   └── .lock                           配置写锁（daemon 未运行时 CLI 用）
├── personas/<persona_id>/              persona 目录（12）
├── extensions/{skills,scripts,mcp,packages}/   扩展（18）
├── extensions-data/<name>/             扩展自有数据（18 §7.3）；不受迁移纪律约束，备份一并打包
├── kb/<domain>/                        知识库文档，人类可编辑（11）
├── files/                              用户托管文件（导入的 pictures/documents、分享快照）
├── data/                         0700
│   ├── gqy.db  gqy.db-wal  gqy.db-shm  0600  主库
│   └── blobs/                    0700  内容寻址存储
│       ├── tmp/                        写入暂存
│       └── ab/cd/<64 hex>        0600
├── mesh/                         0700  device.key（0600，设备身份私钥，17 §5.1；永不同步、不进导出）
├── run/                          0700  daemon.lock、daemon.json、gqy.sock、local.token（0600，每次启动重生成，13 §8.1）、tmp/<session>/（08 §6.2）
├── logs/                         0700  daemon.YYYY-MM-DD.jsonl、requests.YYYY-MM-DD.jsonl（19 §3.2）
├── backups/                      0700  VACUUM INTO 产物
├── cache/                                可随时整个删除的派生数据（FST 词典、模型目录缓存）
└── import/v1-<ts>/                       导入报告（20）
```

规则：

- 启动时设置进程 `umask(0o077)`。`GqyPaths::ensure()` 创建缺失目录，并检查已有目录权限：比 0700 宽时收紧并记 `warn`（只处理本目录树内、非符号链接的条目；遇到符号链接指向树外时拒绝启动，错误 `PathEscapes`）。
- **只认自己的数据根**：`ensure()` 动手前先检查——目标根已存在、非空、且没有 `.gqy2-root` 标记文件时，报 `NotOurs { root }` 并**什么都不建**；根不存在或为空目录时创建骨架，并写入 `.gqy2-root`（内容一行 `This directory is a GQYv2 data root (layout 1).`，创建后同步目录）。理由：`GQY2_HOME` 可以指向任何目录，宁可停下报错，不往别人的目录里建东西（参考 miyu 施工单 3-1 补/再补 的语义；2026-09-28 定，00 §5）。
- `cache/` 的任何内容删除后都必须能重建，重建失败不得影响正确性。有测试：删除 `cache/` 后跑完整 e2e 套件。
- **平台**（00 §5：Linux 与 macOS 完整支持，Windows 只要求编译与单元测试通过）：路径一律由 `GqyPaths` 解析，代码中不硬编码 `~`、`/` 分隔符或 `$HOME` 拼接。Linux/macOS 默认根为 `$HOME/.gqy2`；Windows 默认根为 `%LOCALAPPDATA%\gqy2`，仅保证能编译与跑单元测试。权限位（0700/0600）、`umask`、`flock` 放在 `#[cfg(unix)]` 分支；Windows 分支不做权限收紧，`gqy doctor` 明确报告“未收紧权限”，不假装已隔离（铁律 8）。
- **测试隔离**：所有测试（单元、集成、e2e）的数据目录都来自测试夹具 `TestHome::new()`：它创建 `tempfile` 临时目录，并直接用该目录构造 `GqyPaths`（`GqyPaths::at(root)`），不读取数据目录环境变量（`GQY2_HOME`，名称随 D-01 定），因此环境变量是否设置都不影响测试。`GqyPaths::from_env()` 遵守非测试代码不 panic 的规矩：返回 `Result<GqyPaths, PathsError>`；环境变量未设置时回落到默认根，在 `cfg(test)` 构建中若解析出的根不在系统临时目录内则返回 `Err(PathsError::NotIsolated { root })`，调用方如实上报，绝不写到用户真实数据。
- 多 profile 就是多个数据目录（`GQY2_HOME=... gqy`）。同一数据目录只允许一个 daemon（`run/daemon.lock`）。
- `data/` 是唯一需要一致性快照的子树；其余是普通文件，按文件粒度复制即可。

### 4.2 写者线程

```rust
// 草案，以实现为准
pub struct Store { tx: mpsc::Sender<WriteJob>, bg_tx: mpsc::Sender<WriteJob>, readers: ReadPool }

pub enum Lane { Interactive, Background }

impl Store {
    /// 唯一写入口。闭包在写者线程内、一个 SAVEPOINT 中执行。
    pub async fn write<R: Send + 'static>(
        &self, lane: Lane, label: &'static str,
        f: impl FnOnce(&WriteTx<'_>) -> Result<R, StoreError> + Send + 'static,
    ) -> Result<R, StoreError>;

    /// 在 blocking 池执行只读查询。
    pub async fn read<R: Send + 'static>(
        &self, label: &'static str,
        f: impl FnOnce(&ReadConn) -> Result<R, StoreError> + Send + 'static,
    ) -> Result<R, StoreError>;
}
```

- **两条车道**：交互车道（回合、账本、事件、审批）容量 4096（02 §7）；后台车道（记忆整理、GC、保留清理、导入）容量 256。写者线程每批优先取交互车道；交互车道非空时，每批最多夹带 1 个后台作业，保证回合不被后台写饿死。
- **分组提交**：写者线程取到第一个作业后，最多再等 `group_commit_ms`（默认 5 ms），或凑够 256 个作业，然后在一个 `BEGIN IMMEDIATE` 事务中逐个执行。每个作业包在 `SAVEPOINT` 里：单个作业失败只回滚它自己，然后把错误回给该作业的调用方。`COMMIT` 成功后，才统一回复本批所有调用方。因此调用方拿到 `Ok` 就意味着数据已持久化。
- **超时**：调用方等待入队 5 s（上限 30 s，02 §6），超时返回 `StoreBusy`。作业执行时间超过 1 s 记 `warn`，带 `label`。
- **禁止**：闭包内做网络 IO、文件 IO（blob 写入在 §6 的调用方先完成）、等待其他异步结果。闭包类型是同步 `FnOnce`，在类型上就做不到 await。
- **COMMIT 失败**：整批回复 `StoreError::CommitFailed`，写者线程执行 `quick_check`；检查不通过时进入只读降级：拒绝所有写入，daemon 广播 `store.degraded`，回合失败并给出明确原因（铁律 8：不假装写成功）。

### 4.3 读连接池

- 默认 4 条只读连接（02 §2），在 blocking 池执行。WAL 下读不阻塞写。
- 写入回复在 COMMIT 之后发出，所以“先写后读”在同一调用链上总能读到自己的写入。
- 读查询超过 2 s 记 `warn`。池耗尽时等待，超过 5 s 返回 `StoreBusy`。

### 4.4 仓储（repo）与读写纪律

- `gqy-store` 按领域提供 repo：`SessionRepo`、`LedgerRepo`、`RunRepo`、`QueueRepo`、`ToolCallRepo`、`QuestionRepo`、`GrantRepo`、`JobRepo`、`WorkRepo`、`TimerRepo`、`EventRepo`、`RequestRepo`（`llm_requests` + `usage_records`）、`AuditRepo`、`BlobRepo`。记忆与知识库的 repo 在 `gqy-memory` 内，经 `Store::write/read` 访问，不自己开连接。
- **按列名读**：所有 `row.get` 使用列名。`cargo xtask arch` 扫描 `gqy-store` 与 `gqy-memory`，出现 `row.get(<整数字面量>)` 或 `SELECT *` 即报红。
- **追加型数据放子表**：“一个实体的多条记录”一律建子表（`INTEGER PRIMARY KEY` 自增即顺序），禁止 JSON 数组列追加。
- **JSON 列两种可变性**，在 schema 注册表中逐列声明：
  - `WriteOnce`：只在 INSERT 时写入（冻结的快照，例如 `sessions.venue_json`）。迁移为每个 `WriteOnce` 列创建 `BEFORE UPDATE OF <col>` 触发器，执行 `RAISE(ABORT, 'write-once column')`。
  - `ReplaceWhole { max_bytes }`：只允许不读旧值、整体覆盖，大小不超过上限（默认 4 KiB）。repo 里对这些列的 UPDATE 语句不能引用该列本身（xtask 检查 `SET x_json = json_set(x_json` 一类形式）。
- **不可变表**：`ledger_entries`、`ledger_watermarks`、`events`、`memory_recalls`、`audit_log`、`auth_events`、`mesh_membership` 等追加表创建 `BEFORE UPDATE` 触发器直接拒绝。删除只有两条路径，均由触发器的 `WHEN` 条件钉住：①“会话清除”（§9.3）：触发器检查 `sessions.purge_state = 'purging'`；②§9.3 表中明文登记的保留期删除（例如 `events` 只允许删除 `type IN ('assistant.delta','reasoning.delta','tool.output')` 的行，`audit_log` 只允许删除早于保留期的行）。其余 DELETE 一律拒绝。
- **时间**：全部为 `INTEGER` Unix 毫秒 UTC，列名以 `_at` 结尾。持续时长用 `_ms`。
- **ID**：`gqy-core` 定义带前缀的 ULID 文本，例如 `ses_01J…`、`run_…`、`q_…`、`job_…`、`call_…`。ULID 保证跨设备生成不冲突（17）。供应商返回的工具调用 id 另存为 `provider_call_id`。
- **Principal**：沿用 v1 的编码，以保证导入后记忆归属不变：`blake3( len_le_u64(platform) ‖ platform ‖ len_le_u64(account_id) ‖ account_id ‖ len_le_u64(user_id) ‖ user_id )` 取前 24 位 hex，文本形式为 `principal:<24hex>`（v1 `platform_types.rs::stable_key`）。有固定测试向量钉住。

## 5 事务与一致性边界

- **一次回合步骤一次事务**：账本条目、对应的事件、工具调用状态变化在同一个写作业里提交。否则崩溃后可能出现“事件说完成了，账本里没有”。
- **事件先落库再广播**（02 §7）：写作业返回分配好的 `EventSeq` 之后，事件总线才广播。
- **流式增量**：`assistant.delta` 不逐条写库。回合任务按 50 ms 或 4 KiB 合并成一个 `assistant.delta` 事件落库；最终文本以账本条目为准。
- **恢复**：启动时唯一一次恢复（02 §9）是一个写作业：把非终态的 `runs` 标记为 `interrupted`，为未配对的 `tool_calls` 补写 `cancelled` 结果条目。

## 6 内容寻址 blob

### 6.1 何时用 blob

- 字节数 ≥ `blob_inline_max`（默认 8 KiB）的载荷：账本条目载荷、工具输出原文、附件、图片、artifact 版本、导入的 v1 附件。
- 小于阈值的载荷直接存在行内（`payload BLOB` 列）。行内与 blob 二选一，由 `CHECK` 约束保证。

### 6.2 布局与写入

- 哈希：`blake3(raw bytes)`，64 位小写 hex。路径 `data/blobs/<h[0..2]>/<h[2..4]>/<h>`。首版不压缩；是否对文本载荷加 zstd 见 Q-10-3。
- 写入顺序（在 blocking 池执行，不在写者线程）：
  1. 流式写入 `blobs/tmp/<ulid>`，边写边算哈希；
  2. `fsync` 文件；
  3. 目标已存在时：比对大小，一致则**把目标的 mtime 刷成现在并删除临时文件**（去重；刷 mtime 是给 §6.3 的 GC 宽限期用的——刚被重新引用的旧文件不该被当成陈旧垃圾）；不一致则报 `BlobCorrupt` 并保留两份以便取证；
  4. 目标不存在时：`rename` 到目标路径，再 `fsync` 父目录；
  5. 然后才提交引用它的数据库行（`blobs` 表登记加业务行引用），这一步走写者线程。
- 读取：每次读取都校验 blake3（速度在 GB/s 量级，对账本字节契约来说值得）。不一致时返回 `BlobCorrupt { hash, path }`，回合失败，不静默替换。

### 6.3 回收：标记—清除

不存储引用计数（计数器本身就是读改写，崩溃即漂移）。引用就是业务行里的 `*_blob` 列。

- **引用列注册表**：`gqy-store` 中一张常量表列出所有 blob 引用列，例如 `(ledger_entries, payload_blob)`、`(attachments, blob)`。测试遍历 `sqlite_master`：凡是名字以 `_blob` 结尾的列都必须在注册表里，否则失败。新增引用列却忘了登记会导致误删，这个测试就是防这个的。
- **GC 作业**（后台车道，默认每 24 h 一次，或 `gqy doctor --gc`）：
  1. 标记：在一个读快照内，对注册表里的所有列做 `SELECT DISTINCT`，得到存活集合；
  2. 清除：遍历 `blobs/` 目录，删除不在存活集合中、且 mtime 早于 `blob_gc_grace`（默认 24 h）的文件。宽限期覆盖“文件已写、行未提交”的在途写入；
  3. 删除 `blobs` 登记表中无文件或无引用的行；
  4. 结果写入 `gc_runs`（扫描数、删除数、释放字节数）。
- 删除顺序永远是先删行，再由 GC 删文件，绝不反过来。

## 7 核心表草案

> 草案，以实现为准。列类型均为 SQLite 类型亲和性；未写 `NOT NULL` 的列可空。所有表都有 `STRICT`。

### 7.1 元数据

### 7.3 回合、运行、账本

## 8 迁移纪律

### 8.1 机制

- 迁移是 `gqy-store/migrations/NNNN_<name>.sql` 文件，编号连续，通过 `include_str!` 编进二进制。每个迁移在 `BEGIN IMMEDIATE` 事务中执行，并在同一事务里写入 `schema_migrations`。
- 启动时比对：已应用迁移的 `checksum` 必须等于二进制内同编号迁移的 checksum，不等就拒绝启动（`MigrationTampered { version }`）。仓库另有 `migrations/CHECKSUMS` 文件，CI 校验：已发布版本的迁移内容一旦改动即报红。
- 库的版本高于二进制已知的最大版本时：拒绝写入并提示升级；`gqy doctor` 仍可只读打开。
- 执行迁移前，若库非空，自动 `VACUUM INTO backups/pre-migrate-<from>-<to>-<ts>.db`，保留最近 3 份。

### 8.2 只增规则

允许：`CREATE TABLE`、`CREATE INDEX`、`CREATE TRIGGER`、`CREATE VIEW`、`ALTER TABLE … ADD COLUMN`（可空，或带常量默认值）。

禁止：`DROP`（任何对象）、`RENAME`、`ALTER TABLE … DROP COLUMN`、修改已有列的 `UPDATE`、`DELETE`、整表重建。

回填：只允许写入**同一迁移中新建的列或表**，且必须幂等。需要改变语义时，加新列、新表，旧列保留并在 repo 中停止写入（标记 `deprecated_since`）。

### 8.3 守护

1. **静态扫描**：测试对每个迁移文件做词法扫描，出现 `DROP`、`RENAME`、`DELETE FROM`、`ALTER TABLE … DROP` 即失败；对 `UPDATE` 语句，检查其 `SET` 的列是否都在本迁移新建。
2. **schema 差分**：对每个编号 k，在夹具库 k−1 上执行迁移 k，比较前后 `pragma_table_info`、`pragma_index_list`、`sqlite_master`：旧的每张表、每列（类型、`notnull`、默认值、主键位）、每个索引必须原样存在。
3. **行级不变**：同一测试对所有旧表按主键计算“旧列值”的 blake3，迁移前后必须相等。v1 v36 那种 `UPDATE … SET workspace = NULL` 会让它变红。
4. **夹具链**：每次发布时由 `cargo xtask fixtures store` 生成 `gqy-store/tests/fixtures/schema-<version>.db`，内含每张表的代表行（含边界值：空串、最大长度、NULL、多字节文本）。夹具一旦提交就不再重新生成（CI 校验其哈希清单只增）。测试把**每一份**历史夹具迁移到最新版本，然后跑 repo 读取冒烟测试与 `integrity_check`。
5. **区分能力**：在测试分支上故意加入一条 `DROP INDEX` 迁移，守护 1、2 必须变红（施工单 P01 验收时演示）。

## 9 备份、完整性与清理

### 9.1 备份

- `gqy backup [--to <dir>]`：在一条读连接上执行 `VACUUM INTO '<dir>/gqy-<ts>.db'`（WAL 下是一致快照，不阻塞写）；然后对产物做 `PRAGMA integrity_check`；再增量复制 `blobs/`（blob 不可变，按文件名跳过已存在的，能用 reflink/clonefile 时优先使用）；最后写 `manifest.json`（版本、schema 版本、blob 数、总字节、库文件 blake3）。
- 自动备份：每日一次（默认 03:00 本地时间，daemon 运行时），保留最近 7 份日备份与 4 份周备份。
- **禁止**对活库 `fs::copy`。确实需要手工复制时，必须在 daemon 停止后同时复制 `gqy.db`、`gqy.db-wal`、`gqy.db-shm` 三个文件。`gqy doctor` 检测到数据目录中存在孤立的 `-wal`/`-shm` 或 `*.db.bak` 时给出提示。
- `gqy restore <backup>`：要求 daemon 已停止；先把当前三件套一起移到 `backups/replaced-<ts>/`，再放入备份库，最后校验 `integrity_check` 与 `application_id`。

### 9.2 完整性检查

| 检查 | 时机 | 失败处理 |
| --- | --- | --- |
| `PRAGMA quick_check` | 启动时（上次未干净停机时必做；否则每 7 天一次） | 拒绝启动，提示从备份恢复；`gqy doctor` 输出细节 |
| `PRAGMA integrity_check` + `foreign_key_check` | 每周一次后台作业；`gqy doctor --deep` | 发 `store.integrity_failed` 事件，进入只读降级 |
| blob 重算哈希 | `gqy doctor --blobs`；读取时实时校验 | 报告损坏清单，不自动删除 |
| 干净停机标记 | `meta` 之外的 `run/clean-shutdown` 文件 | 缺失则触发启动 quick_check |

### 9.3 保留策略

这是**唯一**允许按时间自动删除数据的清单（铁律 9 的落地）。不在表中的数据没有自动过期；新增一行必须改本文并说明为什么被删的数据可重建、已汇总，或属于日志 / 审计 / 短期运行态。

| 数据 | 默认 | 机制 | 为什么允许删除 |
| --- | --- | --- | --- |
| `logs/` tracing 日志 | 14 天 | 按日轮转，启动与每日清理（19 §3.2） | 日志，非用户数据 |
| `usage_records` 明细 | 90 天 | 每日作业先汇总进 `usage_daily`，再删除明细；`usage_daily` 永久保留 | 已汇总 |
| `events` 中的 `assistant.delta`、`reasoning.delta`、`tool.output` | 所属运行结束后 7 天（`retention.stream_event_days`） | 触发器只放行这三种类型；被删区间的补拉返回 `resync_required{purged}`（13 §6.3） | 完整内容在账本与 `assistant.message` / `tool.finished` 中，可重建 |
| `audit_log` | 180 天（`audit.retention_days`，08 §9.1） | 只删早于保留期的整日数据 | 审计日志，保留期是明文策略 |
| `auth_events` | 180 天（`auth.retention_days`，13 §8.6） | 只删早于保留期的整日数据 | 鉴权审计，保留期是明文策略 |
| `auth_sessions`、`auth_tokens` | 过期或吊销后 30 天 | 每日作业删除终态行 | 凭据行；审计事实在 `auth_events` |
| `connector_inbound` | 7 天 | 只用于去重窗口 | 短期运行态，原文在账本 |
| 已删除会话（`deleted_at`，用户显式删除） | 30 天后清除 | `purge_state='purging'` 后级联删除（含该会话的 `ledger_entries`、`events`、`llm_requests`、`compactions` 及转录 blob 引用） | 用户显式操作 + 宽限期 |
| 子代理审计会话 | 7 天（`subagent.trace_days`，03 §9.3） | 同上；用户固定的除外；发 `session.expired` | 父账本保留工具结果；v1 同为 7 天 |
| `jobs`、`work_items` 终态行 | 30 天 | `job_events` 一并删除 | 运行态记录，结果已进账本 |
| 自动备份 | 7 日 + 4 周 | §9.1 | 备份副本 |
| blob | 无引用且超过 24 h 宽限期 | §6.3 | 无引用 |

所有清理都是 `work_items` 中 `kind = 'retention'` / `'gc.blobs'` 的后台车道作业，每次执行写一行 `gc_runs`，保证可审计。用户数据（账本、记忆、附件、`llm_requests`）不设自动过期；删除只来自用户的显式操作（铁律 9）。

## 10 多身份：从“每身份一库”到“一库多 principal”

- v1：每个 Web 账号一个 `home/<user>/`，内含独立的 `conversation.db`、artifacts、ledger 等；管理员看不到成员会话，靠的是文件隔离。
- v2：一个数据目录只有一个 `gqy.db`。所有归属数据带 `principal` 列（`sessions.principal`、`memories.owner_principal`、`jobs.principal`、`work_items.principal`、`timers.principal`、`session_grants.principal`）。
- **访问由 repo 强制**：repo 的查询方法必须接收 `AccessScope { principal, trust }` 参数，不提供“全部行”的公开方法。`Trust::Owner` 可以看到全部；`Member` 只能看到自己 principal 的数据；`External` 不能列举会话。`Internal`（定时器、作业）继承创建者的 scope。
- 本机 owner principal 固定为 `principal("local", install_id, "owner")`；owner 的 Web 账号在 `accounts.principal` 中指向同一个值，因此 TUI、Web、CLI 看到同一批会话。
- 守护：集成测试以成员 A 的 scope 调用每一个会话、记忆、作业的列举与读取 API，断言看不到成员 B 与 owner 的数据；repo 中新增一个不带 `AccessScope` 的 `pub fn list_*` 时，xtask 规则报红。

## 11 导出与导入包

- `gqy export -o <file>.gqy2.tar [--sessions <id…>] [--include memory,kb,personas,config]`：
  - `manifest.json`：格式版本 `1`、应用版本、schema 版本、导出时间、每个文件的 blake3；
  - `db/gqy.db`：完整导出时是 `VACUUM INTO` 快照；部分导出时建一个同 schema 的新库，经 `ATTACH` 只复制选中会话及其引用的行；
  - `blobs/`：只包含被引用的 blob；
  - `personas/`、`kb/`、`config/gqy.toml`（按选项）。**永不包含 `secrets.toml`、`accounts.password_hash`、`run/`、`cache/`、`mesh/device.key`。**
- `gqy import <file>`：首版只支持导入到空数据目录（等同恢复）。合并导入到已有目录见 Q-10-4；它与设备同步（17）共用 ID 不冲突的前提。
- 导出物可以用 `gqy export --canonical` 生成去除时间戳的规范化转储，供测试比较两次导入结果是否一致（20 §8）。

## 13 测试与守护

- **写者隔离**：交互车道持续写入的同时，后台车道塞满 256 个慢作业（每个 50 ms），交互写入 p99 < 100 ms。去掉车道优先级后该测试变红。
- **分组提交语义**：一批 3 个作业，中间一个返回错误，另外两个的写入可见、失败作业的写入不可见。去掉 SAVEPOINT 后变红。
- **持久化确认**：`write` 返回 `Ok` 后立即 `kill -9` 子进程（测试夹具），重开库后数据存在。
- **按列名读 / 禁止 `SELECT *`**：xtask 规则，附一个故意违规的夹具文件证明规则会报红。
- **不可变触发器**：对 `ledger_entries` 执行 UPDATE 必须失败；非清除状态下 DELETE 必须失败。
- **blob**：写入后篡改文件一个字节，读取返回 `BlobCorrupt`；GC 不删除宽限期内的未引用文件，删除超期的；未登记的 `*_blob` 列使注册表测试失败。
- **迁移守护**：§8.3 的五项。
- **备份**：写入过程中执行备份，备份库 `integrity_check` 通过且包含备份开始前已提交的全部行。
- **权限**（`cfg(unix)`）：新建数据目录后逐个检查模式位：目录 0700，库与配置 0600。
- **测试不碰真实目录**：在 `cfg(test)` 下把 `GQY2_HOME` 指向非临时目录，`GqyPaths::from_env()` 必须返回 `Err(PathsError::NotIsolated)`（不 panic）；不设置该变量时 `TestHome::new()` 照常得到临时目录；CI 另以只读挂载的假 `$HOME` 运行全套测试，任何写入都会失败。
- **Windows 编译**：CI 在 Windows 上执行 `cargo build` 与 `gqy-store`、`gqy-config` 的单元测试（路径解析、迁移守护），不跑依赖 unix 权限的测试。
- **多 principal 隔离**：§10。
