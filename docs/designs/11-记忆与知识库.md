# 11 · 记忆与知识库

> 状态：【规划】。前置阅读：00、01、02、[10 存储与数据演进](10-存储与数据演进.md)。账本与化石化见 04，人格与场所见 12，工具系统见 07，持久化工作队列 `work_items` 与定时器表见 10 §7.4（03 的 `jobs` 是另一种东西：用户可见的后台命令 / 子代理作业）。本文描述 `gqy-memory` crate：记忆的分类、可见性、写入与召回、整理、遗忘、聊后复盘、reset 语义，以及知识库（kb）。

## 1 目标

1. 记忆是**模型之外的连续性**（00 §4），不是提示词技巧。它由代码决定谁能读到什么；提示词不承担鉴权（铁律 7）。
2. 召回结果只追加在回合尾部，并化石化，不破坏前缀契约（铁律 1）。
3. 所有后台写入（整理、衰减、复盘）都是持久化作业：可重试、有退避、重启不丢，并且 reset 之后不会“复活”。
4. 第一版只做关键词检索，零运行时外部依赖；向量检索是可选扩展（D-05）。
5. 记忆作为子系统挂载：只通过 `Tool` 与 `SubsystemHooks` 接入引擎。persona 没启用记忆时，不建索引、不注入、不写日记（12 §5：决定构造什么，而不是装上再关）。

## 2 v1 教训

- 【v1 实测】记忆按 persona 分库：每个 persona 一个 `memory.db` 加一个 `evicted_context.db`，外加早期残留的 `data/memory.db`。跨库不能事务，reset 要分别处理多个库。
- v1 的 `facts.subjects`、`tags`、`source_episode_ids` 都是 JSON 数组列，更新要读改写（10 §2 同一类问题）。
- 整理器按 14 条触发、召回 3 次长期化、失败退避 2 s→300 s、每次最多 4×20。这组参数经过实际使用，v2 保留为默认值。
- 联想召回用 jieba 分词 + FST 关键词，加上向量两路 RRF 融合。向量依赖外置 ONNX Runtime 动态库与独立 worker 进程，违反零运行时依赖（D-05）。
- 聊后复盘：闲置 900 s（下限 300）回看 12 轮、产出不超过 3 条，结果放在 **system 提示词最末尾**。v1 自己在注释里承认“复盘结果改 system 侧，缓存还热着就换会作废整段历史缓存”，所以才设了 300 s 下限。v2 把它改为尾部追加（§8），从结构上消除这次前缀改写。
- 六种 reset 语义（`/clear`、`/reset`、`/reset all`、`/reset-memory`、`/reset-all-memory`、`/wipe`）容易混淆；“记忆代数”用来防止后台整理器在 reset 之后把旧结果写回。v2 保留代数机制，并把 reset 收敛成四个命令（§9）。
- 知识库 v1 有两个：用户 kb（`data/kb/files` + `kb_meta.db` + `semantic_index.db`）与内置默认 kb（`data/default-kb`）。上传闸门曾按正文关键词拦截，误伤正常资料（09-09），后来改为只按路径与技能标记判断。

## 3 记忆模型

### 3.1 种类

| kind | 来源 | 生命周期 | 召回 |
| --- | --- | --- | --- |
| `short_term` | 每个完成的交互回合由 `after_turn` 写一条日记 | `expires_at = created + 14 d`；被有效召回时续期；整理成功后才物理删除 | 参与，低权重 |
| `long_term` | 整理器从短期日记提炼的“值得回溯的经历” | 按强度衰减，低于阈值标记 `forgotten`，不删除 | 参与 |
| `fact` | 整理器提炼，或模型调用 `remember` | 同上 | 参与 |
| `correction` | 用户纠正时模型调用 `remember(kind="correction", reason=…)`，importance 固定为 5 | 同上 | 参与，复盘时额外参考 |

记忆正文保存对话中的原始语言，不强制英文；英文规则只约束包裹它的模型可见外壳（12 §9）。日记正文只从 `Channel::Raw` 取（04），不含化石、XML 外壳和运行时噪声。

### 3.2 可见性

| visibility | 可以读到的场景 |
| --- | --- |
| `public` | 该 persona 的所有场景 |
| `principal` | 只有 `owner_principal` 等于当前请求 principal 的场景 |
| `privileged` | 只有 `Trust::Owner` 的场景（本机 TUI/Web/CLI/桌面、owner 账号），以及 owner 在连接器上的**私聊** |

- 读取过滤写在 SQL 的 `WHERE` 里，由 `AccessScope`（10 §10）加场所是否群聊共同决定。群聊中即使发送者是 owner，也只读 `public` 加本人的 `principal` 记忆，因为群里所有人都能看到回复。
- 写入可见性由代码按场所决定默认值。非 Owner 场所中模型不能改变它；只有 Owner 场所可以把 `privileged` 放宽为 `public`（这是 owner 本人的决定，不会泄露他人信息）：

| 场所 | 默认写入可见性 | 模型可改为 |
| --- | --- | --- |
| Owner 私有场所 | `privileged` | `public`（owner 显式要求“所有场景都可以知道”时） |
| Member / External 私聊 | `principal`（owner = 发送者） | 无 |
| 群聊 | `principal`（owner = 发送者） | 无 |
| Internal（作业、复盘、子代理） | 继承创建者 scope | 无 |

### 3.3 表（草案，以实现为准）

记忆表都在主库 `gqy.db` 中（10 §7.6），遵守 10 §4.4 的全部纪律。

```sql
CREATE TABLE memory_scopes (        -- 每个 persona 一行；generation 即“记忆代数”
  persona_id TEXT PRIMARY KEY, generation INTEGER NOT NULL DEFAULT 0,
  last_reset_at INTEGER, last_reset_kind TEXT
) STRICT;
CREATE TABLE memories (
  memory_id TEXT PRIMARY KEY, persona_id TEXT NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('short_term','long_term','fact','correction')),
  content TEXT NOT NULL,            -- 不可变；修改 = 新行 + superseded_by
  reason TEXT,                      -- correction 的原因
  visibility TEXT NOT NULL CHECK (visibility IN ('public','principal','privileged')),
  owner_principal TEXT NOT NULL,
  importance INTEGER NOT NULL CHECK (importance BETWEEN 1 AND 5),
  confidence REAL NOT NULL, truth_status TEXT NOT NULL,   -- reported|confirmed|disputed|retracted
  status TEXT NOT NULL CHECK (status IN ('active','forgotten','superseded')),
  superseded_by TEXT, strength REAL NOT NULL, last_decay_at INTEGER NOT NULL,
  expires_at INTEGER, consolidated_at INTEGER,            -- short_term 专用
  source_key TEXT,                  -- 去重键，UNIQUE(persona_id, source_key)
  origin_session_id TEXT, origin_run_id TEXT, origin_turn_seq INTEGER,
  origin_venue_kind TEXT NOT NULL, written_generation INTEGER NOT NULL,
  imported_recall_count INTEGER NOT NULL DEFAULT 0,       -- 20：v1 历史召回次数
  created_at INTEGER NOT NULL
) STRICT;
CREATE TABLE memory_tags     (memory_id TEXT NOT NULL, tag TEXT NOT NULL, PRIMARY KEY (memory_id, tag)) STRICT;
CREATE TABLE memory_subjects (memory_id TEXT NOT NULL, subject TEXT NOT NULL, PRIMARY KEY (memory_id, subject)) STRICT;
CREATE TABLE memory_sources  (memory_id TEXT NOT NULL, source_memory_id TEXT NOT NULL,
  PRIMARY KEY (memory_id, source_memory_id)) STRICT;       -- 整理产物来自哪些短期日记
CREATE TABLE memory_recalls (       -- 追加型；召回次数 = COUNT，最近召回 = MAX(at)
  id INTEGER PRIMARY KEY, memory_id TEXT NOT NULL, session_id TEXT NOT NULL,
  run_id TEXT NOT NULL, entry_seq INTEGER, content_hash TEXT NOT NULL,
  rank INTEGER NOT NULL, via TEXT NOT NULL,                -- auto|tool
  at INTEGER NOT NULL
) STRICT;
CREATE TABLE memory_postings (      -- 关键词倒排；corpus 区分记忆、被逐出上下文、kb
  corpus TEXT NOT NULL, term TEXT NOT NULL, doc_id TEXT NOT NULL, tf INTEGER NOT NULL,
  PRIMARY KEY (corpus, term, doc_id)
) STRICT, WITHOUT ROWID;
CREATE TABLE memory_doc_stats (corpus TEXT NOT NULL, doc_id TEXT NOT NULL, len INTEGER NOT NULL,
  PRIMARY KEY (corpus, doc_id)) STRICT;
CREATE TABLE session_reviews (      -- 聊后复盘，追加型
  review_id INTEGER PRIMARY KEY, session_id TEXT NOT NULL, last_turn_seq INTEGER NOT NULL,
  notes_json TEXT NOT NULL,         -- WriteOnce，≤ 3 条
  delivered_entry_seq INTEGER, created_at INTEGER NOT NULL
) STRICT;
```

`strength`、`status`、`last_decay_at`、`expires_at`、`consolidated_at` 是允许原地更新的标量列；正文、可见性、归属一经写入不再改变。修改正文 = 插入新行并把旧行标为 `superseded`，形成可追溯的修订链。

## 4 工具

工具以 `Tool` trait 实现（07），名字与 schema 在 persona 启用 `memory` 子系统时才进入工具面；stub 形态下只有真名加一行摘要（07）。

| 工具 | 参数 | 效果类别 | 说明 |
| --- | --- | --- | --- |
| `remember` | `content`, `kind: fact\|correction`, `reason?`, `importance?`, `visibility?`, `tags?` | `Writes`（内部存储，见 Q-11-4） | `correction` 必须带 `reason`；可见性按 §3.2 由代码裁决 |
| `recall_memories` | `query?`, `id?`, `limit ≤ 10`, `include_forgotten?` | `ReadOnly` | `include_forgotten` 只在 Owner 场所有效 |
| `forget_memory` | `id`, `reason` | `Writes` | 标记 `forgotten`（不删除）；只能作用于当前 scope 可见的记忆 |
| `search_evicted_context` | `query`, `limit ≤ 10` | `ReadOnly` | 检索本会话水位以下的账本原文（§6.5） |
| `kb_search` / `kb_read` / `kb_write` | 见 §10 | `ReadOnly` / `Writes` | 知识库 |

所有工具返回给模型的文本、错误信息一律用英文短句，并说明期望值与实际值（00 §3），例如 `"id not found or not visible in this conversation: mem_01J…"`。

## 5 子系统挂载

```rust
// 草案，以实现为准。SubsystemHooks 的正式定义见 18 §3.1（trait 位于 gqy-core，00 §5）；下面只写记忆子系统的行为。
// 子系统自己持有 Store 句柄（组装处注入），HookCx 不携带 store。
pub struct MemorySubsystem { store: Store, index: Arc<KeywordIndex>, cfg: Arc<MemoryConfig>, clock: Arc<dyn Clock> }

impl SubsystemHooks for MemorySubsystem {
    fn id(&self) -> &'static str { "memory" }
    /// 引擎在每个请求前调用；记忆只在回合第一个请求（RequestView.request_index == 0）检索，
    /// 其余请求直接返回空。返回的块 once_per_turn = true，由账本追加并化石化（04），本子系统不直接写账本。
    fn before_request<'a>(&'a self, cx: &'a HookCx, req: &'a RequestView) -> BoxFuture<'a, Result<Vec<TailBlock>, HookError>>;
    /// 回合终态之后调用：写短期日记、登记召回、按需入队整理工作项、安排复盘。
    fn after_turn<'a>(&'a self, cx: &'a HookCx, turn: &'a TurnDigest) -> BoxFuture<'a, Result<(), HookError>>;
    /// 压缩提交后调用（被折叠条目推到水位以下）：为 search_evicted_context 建索引。
    fn on_evict<'a>(&'a self, cx: &'a HookCx, span: &'a EvictedSpan) -> BoxFuture<'a, Result<(), HookError>>;
}
```

- 钩子都有超时：召回自身预算 `recall.timeout_ms` 默认 500 ms（在 18 §3.3 所有钩子共享的 1.5 s 时限之内），超时就跳过本回合召回并记 `memory.recall_skipped { reason: "timeout" }`。跳过是安全的：化石化只记录实际发出的字节，没发就没有化石。`after_turn` 与 `on_evict` 只做入队或轻量写入（后台车道），实际工作放到作业中。
- 场所过滤：`Venue.kind` 为 `Subagent`、`Review`、`Job`、`Timer` 的回合不写日记，也不做自动召回（它们是 Internal 流量，不是和人的交流）。

## 6 召回流水线（第一版）

### 6.1 分词与索引

- 分词：`jieba-rs`（内置词典，编译期嵌入），搜索模式切词，统一小写与全半角，去停用词（中英停用词表编译期嵌入）。ASCII 词按 Unicode 单词边界切分。
- 索引：`memory_postings` 存词项与词频；`memory_doc_stats` 存文档长度。写入记忆时同一写作业内更新倒排，保证“写入即可召回”。
- 词典 FST：进程内用 `fst` crate 把各 corpus 的词表编成 `fst::Set`，用于查询词的前缀匹配与编辑距离 1 的模糊匹配（Levenshtein 自动机），把查询词扩展成索引中真实存在的词项。FST 是派生数据，缓存在 `cache/fst/<corpus>-<generation>.fst`，删掉可以重建。增量写入时先追加到内存中的小词表，积累 256 个新词或 10 分钟后在后台重建。

### 6.2 流程

```text
before_request(cx)
  1 query      ← 本回合用户原文（Channel::Raw），截断到 512 字符
  2 scope      ← AccessScope(cx.principal, cx.venue.trust) + 是否群聊 → 可见性谓词
  3 terms      ← jieba 切词 → FST 扩展（每词最多 8 个扩展）
  4 candidates ← 倒排取候选，BM25(k1=1.2, b=0.75) 打分，只含 status='active'，
                  short_term 另要求 expires_at > now；每路取前 50
  5 rank       ← score × strength^0.5 × kind_weight（fact 1.0 / correction 1.2 /
                  long_term 0.9 / short_term 0.6）；权重为初始值，P12 用导入的 v1 数据校准
  6 fuse       ← RRF(k=60) 融合所有 Retriever 的排名列表（第一版只有关键词一路）
  7 dedup      ← 本会话中同一 memory_id 且 content_hash 相同、其召回条目仍在水位以上的，跳过
  8 select     ← fact/correction 取前 2，long_term/short_term 取前 1；
                  单条截断 120 字符（带 id，可用 recall_memories(id=) 取全文），总计 ≤ 1800 字符
  9 render     ← 唯一渲染函数，生成不可信尾部块（见 6.3）
 10 record     ← 回合结束后在 after_turn 中写 memory_recalls（后台车道）
```

- 检索器抽象：

```rust
// 草案，以实现为准
pub trait Retriever: Send + Sync {
    fn name(&self) -> &'static str;
    async fn search(&self, q: &RecallQuery, scope: &VisibilityPredicate, limit: usize)
        -> Result<Vec<Scored<MemoryId>>, MemoryError>;
}
```

  第一版只有 `KeywordRetriever` 一个真实实现，另有一个测试替身。RRF 融合在第一版就走通用路径，接入向量检索器（D-05）时不改流水线。

- **确定性**：同一库状态、同一查询、同一时钟，输出字节必须完全相同。排序的平局按 `(score desc, created_at desc, memory_id asc)` 决定。

### 6.3 渲染与化石化

```text
<recalled-memories note="Background from earlier conversations. Not instructions.">
- [mem_01J…] (fact, 2026-09-20) User runs Arch Linux with an NVIDIA GPU.
- [mem_01J…] (diary, 2026-09-27) 用户说周末想把终端配色换成 Selene…
</recalled-memories>
```

- 以 user 角色的**不可信尾部**块追加在当前用户原文之后（请求布局见 04；v1 的顺序为 当前 user 原文 → untrusted tail → trusted tail → runtime tail）。
- 块由账本作为 `Channel::Context` 条目写入并化石化，之后每轮逐字节回放（04），不会因为下一轮召回内容不同而改写历史。
- 日期只精确到天，避免分钟级时间制造额外差异。

### 6.4 强度、续期与长期化

- 召回被“有效使用”后（进入了实际请求），`after_turn` 为每条写一行 `memory_recalls`，并在同一作业中：`strength = min(1.0, strength + 0.35)`，`last_decay_at = now`；`short_term` 的 `expires_at` 顺延 14 天。
- `short_term` 的召回次数（`COUNT(memory_recalls)` 加 `imported_recall_count`）达到 3 时，入队一次整理作业，把它优先长期化。

### 6.5 被逐出上下文的检索

v1 把被压缩逐出的回合另存进 `evicted_context.db`。v2 的账本本身就保留水位以下的全部原文（04、05），所以不再复制内容：`on_evict` 只把被逐出的 `Channel::Raw` 条目写进 `memory_postings(corpus='evicted:<session_id>')`。`search_evicted_context` 只检索当前会话的这个 corpus，返回条目摘录加 `EntrySeq`。

## 7 整理器（organizer）

- **工作项**：`work_items.kind = 'memory.organize'`（10 §7.4），`dedupe_key = 'memory.organize:<persona_id>'`，保证同一 persona 同时只有一个待办整理工作项。
- **触发**：未整理的 `short_term`（`consolidated_at IS NULL`）累计 ≥ 14 条；或某条短期日记召回达到 3 次；或 daemon 启动时发现积压。
- **执行**：每次最多 4 批、每批最多 20 条。每批发起一次辅助请求：角色 `organizer`、档位 standard（06），缓存与会话状态独立，超时 120 s。输出必须是符合 JSON Schema 的对象 `{ facts: [...], long_term: [...], corrections: [...] }`；解析失败按失败处理，原始输出存为 blob 以便取证。
- **写回**：一个写作业内完成：插入新记忆（`written_generation = 作业开始时读到的代数`）、`memory_sources` 关联、给来源短期日记设置 `consolidated_at`。写作业的第一句是 `SELECT generation FROM memory_scopes WHERE persona_id = ?`，与作业携带的代数不相等时整批放弃，并返回 `StaleGeneration`（§9.2）。
- **退避**：失败后 `next_run_at = now + min(300 s, 2 s × 2^attempt) × 抖动(0.8–1.2)`；`max_attempts = 10`，超过则进入 `dead`，`gqy doctor` 列出，并发出 `work.dead` 事件（13 §6.2）。成功后 `attempt` 清零。
- **物理删除**：已整理且过期的 `short_term` 由每日清理作业删除（它的来源原文仍在账本中）；尚未整理的过期日记不参与自动召回，但保留到整理成功为止。

## 8 遗忘与聊后复盘

### 8.1 遗忘

- 每日工作项 `memory.decay`：对 `long_term`、`fact`、`correction` 计算 `strength = strength × 0.5^(Δt / half_life)`，其中 `Δt = now − last_decay_at`，`half_life = 7 d`；然后更新 `last_decay_at`。
- `strength < 0.15` 时，`status` 改为 `forgotten`。遗忘不是删除：`recall_memories(include_forgotten=true)` 在 Owner 场所仍能找到；再次被显式找回时，强度重置为 0.5，状态恢复为 `active`。
- 所有计算使用注入的 `Clock`（02 §10），可在测试中快进。

### 8.2 聊后复盘

- 条件：Owner 交互场所（TUI、Web、桌面、CLI 交互模式）的回合完成后，会话闲置满 `review_idle_seconds`（默认 900，下限 300，0 为关闭）。
- 实现：`after_turn` 写入或更新一个 `timers` 行（`action = 'work'`、`catch_up = 'skip'`，10 §7.4），到期时入队 `memory.review` 工作项（不提交回合）。作业携带当时的 `last_turn_seq`；执行前与写回前都检查会话的最新 `turn_seq`，若已有新回合则放弃（新回合会重新安排）。
- 请求：辅助角色 `review`，档位 standard，回看最近 12 个回合的 `Channel::Raw` 内容与最近 5 条 correction，输出最多 3 条英文“下次注意什么”，写入 `session_reviews`。
- **投递方式（与 v1 不同）**：结果**不再修改 system 提示词**。下一个用户回合的第一个请求由 `before_request` 读取尚未投递的复盘，以**可信尾部**块（system 角色，位于尾部）追加一次：

```text
<self-review source="post-chat review">
- Confirm the target distro before giving package commands.
</self-review>
```

  追加后回填 `delivered_entry_seq`，之后随账本化石化回放。这样复盘不再是前缀改写点，v1 的“300 s 下限防止作废热缓存”也就不需要了；下限保留只是为了控制辅助请求成本。

## 9 Reset 语义与记忆代数

### 9.1 命令（收敛为四个）

| 命令 | 作用 | 会话账本 | 记忆 | 确认 |
| --- | --- | --- | --- | --- |
| `/clear` | 只清客户端屏幕 | 不动 | 不动 | 否 |
| `/new` | 归档当前会话并新开一个（同一场所绑定改指新会话）。取代 v1 的 `/reset` | 旧会话保留、可查阅 | 不动 | 否 |
| `/forget-session` | 删除**本会话**产生的记忆（`origin_session_id` 匹配），代数 +1 | 不动 | 删除匹配行及其倒排、召回记录 | 是 |
| `/forget-all` | 删除当前 persona 的全部记忆，代数 +1 | 不动 | 全部删除 | 是（需输入 persona 名） |

v1 的 `/wipe`（会话、记忆、群聊上下文全抹）不作为斜杠命令提供，改为 `gqy data wipe --persona <id>` 命令行操作，执行前自动做一次备份（10 §9.1）。

### 9.2 代数守护

- `memory_scopes.generation` 在 reset 的同一个写事务中 +1，同时删除相应行。
- 所有**异步产生**的记忆写入（整理、复盘、召回登记、`after_turn` 日记）都在作业或回合开始时读取代数，并随写作业携带；写作业内先比对，不一致就整批放弃并记 `memory.write_rejected { reason: "stale_generation" }`。
- 模型在回合内同步调用的 `remember` 同样携带回合开始时的代数：如果回合进行中用户在另一个入口执行了 reset，这次写入也会被拒绝，并返回给模型英文说明。
- 删除是物理删除（reset 是用户的显式意图；见 Q-11-3）。删除覆盖 `memories`、`memory_tags`、`memory_subjects`、`memory_sources`、`memory_recalls`、`memory_postings` 中对应的行。已经化石化进账本的召回块不受影响：账本是对话历史，属于会话数据，需要删除时走会话删除。

## 10 知识库（kb）

### 10.1 定位与域

知识库存放**参考资料**，与记忆（关于人和事的连续性）分开。按域（domain）组织：

| 域 | 来源 | 可写 | 位置 |
| --- | --- | --- | --- |
| `manual` | 内置使用手册，编译期嵌入二进制，版本随程序 | 否 | 二进制内 |
| `user` | 用户与模型写入的文档 | 是 | `kb/user/` |
| `<自定义>` | 用户新建的域（例如 `arch`、`work`） | 是 | `kb/<domain>/` |

- 文档是普通 Markdown/文本文件，人可以直接编辑。库中只存索引：`kb_documents(domain, path, content_hash, size, mtime, indexed_at)`、`kb_chunks(domain, path, chunk_idx, start, end)` 与 `memory_postings(corpus='kb:<domain>')`。
- 索引更新：daemon 启动时与每 60 s 扫描一次 mtime 与大小，有变化时重算 blake3；哈希变了才重建该文档的分块与倒排（后台车道）。分块按标题与空行切分，每块目标 800 字符。
- 上传闸门沿用 v1 最终版的做法：只看落点路径是否为 GQY 自己的资产目录（`config/`、`personas/`、`extensions/`、`data/`），以及正文是否带技能文件标记。**不**按正文关键词拦截。

### 10.2 工具

| 工具 | 参数 | 说明 |
| --- | --- | --- |
| `kb_search` | `query`, `domain?`, `limit ≤ 10` | 复用 §6 的关键词检索器，返回 `kb:<domain>/<path>#chunk` 与摘录 |
| `kb_read` | `path`（`kb:<domain>/<path>`）, `offset?`, `limit?` | 与文件读取工具同一套分页上限（07） |
| `kb_write` | 统一补丁格式（`*** Begin Patch`，存储域前缀 `kb:`，07） | 只能写可写域；`manual` 域返回错误 |

### 10.3 与 system 提示词的关系

- system 中的 `kb-index` 节（12 §8）列出启用的域名与每个域的文档数、最多 20 个标题，在**会话创建时**渲染并冻结。会话进行中 kb 的变化不改 system；新文档通过 `kb_search` 可见。
- `manual` 域随程序升级而变化；已有会话的 system 不变，下一次压缩（05）或新会话时才更新。

## 12 边界与失败模式

| 情形 | 行为 |
| --- | --- |
| 召回超时或出错 | 跳过本回合召回，记 `memory.recall_skipped`；回合照常 |
| 整理器输出不合 schema | 本次作业失败，按退避重试；原始输出存 blob |
| 整理期间发生 reset | 写回时代数不符，整批放弃；作业标记成功（无事可做），不重试 |
| 写队列满（`StoreBusy`） | 日记写入失败不重试、不补写（原文仍在账本中）；必须记 `warn` 并累加计数器 `memory.diary_dropped`，供 19 的指标告警 |
| FST 缓存损坏 | 删除后重建；重建期间只做精确词匹配 |
| kb 文件被外部删除 | 下次扫描删除索引行；`kb_read` 返回 `not found` |
| persona 未启用 memory | 不注册工具、不挂钩子、不建 `memory_scopes` 行；已有数据保留不动 |

## 13 测试与守护

- **可见性矩阵**：构造 owner、成员 A、成员 B、群聊中的 A 四种 scope，与三种可见性、两个 owner 的记忆交叉，断言召回与 `recall_memories` 的结果集。去掉 SQL 可见性谓词后测试变红。
- **写入收窄**：群聊场所中模型传 `visibility="public"`，落库仍为 `principal`。
- **代数守护**：整理作业读到代数 0 → 执行 reset（代数变 1）→ 作业写回，断言无新行、记录 `stale_generation`。去掉代数比对后测试变红（v1 “清完又复活”的回归）。
- **召回确定性与化石化**：同一状态连续两次 `before_request` 输出字节相同；mock 供应商断言第 N+1 轮请求中第 N 轮的召回块逐字节保留（接入 04 的前缀门禁）。
- **复盘不改前缀**：复盘写入后，下一轮请求是上一轮请求的字节前缀延伸（04 门禁），且 `<self-review>` 只出现一次。按 v1 做法把复盘放进 system 时测试变红。
- **复盘放弃**：复盘作业执行前插入新回合，断言不写 `session_reviews`。
- **遗忘数学**：注入时钟快进 7 天，强度减半；快进到阈值以下，状态变为 `forgotten`，显式找回后恢复。
- **整理退避**：mock 供应商连续失败，`next_run_at` 序列符合 2、4、8…300 s（容许抖动区间），第 10 次失败后进入 `dead`。
- **重启不丢**：整理作业执行中 kill daemon，重启后作业被重新领取并完成，结果不重复（`source_key` 唯一约束）。
- **kb**：外部修改文件后 60 s 内可被 `kb_search` 检到；`manual` 域写入被拒绝；会话 system 中的 kb 索引在 kb 变化后保持字节不变。
