# 17 · 设备共享

> 状态：【规划】，其中标注【研究项】的部分连候选方案都未验证。前置阅读：[00 设计理念](00-设计理念.md)、[01 总体架构](01-总体架构.md)（`gqy-mesh`）、[02 运行时与并发模型](02-运行时与并发模型.md)、[13 网关与 API 协议](13-网关与API协议.md)。本文把[技术白皮书](../GQYv2-Technical-Whitepaper.md)第 3 章的理念展开为设计；前缀字节契约见 04，权限判定见 08。

## 1 目标

1. **每个 app 都是客户端，也是服务端。** 没有独立的“服务端产品”；谁扮演服务器是配置出来的角色（白皮书 §3）。
2. **服务器缺席不瘫痪。** 指定的服务器不可达时，本机自动降级为“客户端 + 服务器”一体。
3. **无账户体系。** 信任靠配对密码建立，**新设备加入需全部设备同意**；授权长期有效，撤销是显式动作。
4. **能力可委派，裁决留在提供方。** 设备 B 把自己的文件、命令、模型接入借给设备 A 使用，但是否允许由 B 的权限引擎判定。
5. **合并由用户决定。** 重新连上时询问是否同步合并，系统不静默替用户做；append-only 账本让合并退化为并集，冲突变成分叉。
6. **传输只用 HTTPS**，证书按公钥钉扎。

非目标：跨用户共享（mesh 内所有设备属于同一个人）；公网穿透与中继（第一版只在局域网或用户自备的 VPN 内工作）；工作区文件的实时同步。

## 2 背景与 v1 对照

v1 没有设备共享。相关的 v1 事实只有：网关默认 `0.0.0.0:8300`；成员账号靠邀请码注册；授权索引有进程内缓存，跨进程吊销要重启才生效【v1 实测】。v2 的设计从零开始，因此本文比其它文档有更多待定项。

白皮书 §3 有一句“app 独立使用的时候不走网关，网关只是连接三方平台使用”，与 01 的“所有入口都是网关的客户端（TUI 经 UDS）”表述不一致。本文按 01 理解：**单机使用时不启用 mesh 监听**，本机入口仍经 UDS 上的同一 API；设备间流量才走 mesh 的 HTTPS 监听（见报告中的冲突说明）。

## 3 概念与角色

| 概念 | 定义 |
| --- | --- |
| 设备（Device） | 一个数据目录 + 一个运行中的 host（daemon 或内嵌模式的桌面宿主）。`DeviceId` = 设备身份公钥 SPKI 的 blake3 前 16 字节（32 hex） |
| 网格（Mesh） | 一组互相信任的设备；由成员账本（§5.4）定义 |
| host | 执行回合、持有账本写权的角色（即 01 中的 daemon） |
| 会话主场（home） | 每个会话有且只有一个主场设备，只有主场设备推进该会话（铁律 2 的跨设备版本） |
| 服务器角色 | 被用户指定为“集中承担服务”的设备；其它设备优先把新会话建在它上面并通过它访问 |

### 3.1 角色配置

```toml
# 草案，以实现为准（config/gqy.toml，D-07 待定）
[mesh]
enabled = false            # 默认关（D-03）
role = "auto"              # auto | server | client
server = ""                # 指定服务器的 DeviceId；role=client/auto 时使用
listen = "0.0.0.0:8443"    # 仅 enabled=true 时监听
```

| `role` | 行为 |
| --- | --- |
| `auto`（默认） | 本机 host 始终运行；若配置了 `server` 且可达，新会话默认建在服务器上，本机会话仍在本机 |
| `server` | 同 auto，并对其它设备广播“我是服务器” |
| `client` | 优先把 UI 连到服务器；服务器不可达时自动降级（§4），本机 host 接管新会话 |

### 3.2 自动降级

```text
client 设备启动 / 运行中
  └─ 探测服务器：mesh HTTPS GET /api/v1/mesh/ping，超时 2 s，连续 3 次失败
       ├─ 可达 → UI 连接服务器（远程会话），本机 host 仍运行（服务本机能力委派）
       └─ 不可达 → 降级：UI 切到本机 host；状态条显示 “server offline — working locally”
             服务器恢复 → 提示用户：切回服务器？是否同步本地期间的新会话？（§7，用户决定）
```

- 降级不迁移会话：主场在服务器上的会话在降级期间**只读**（来自上次同步的副本）。用户在降级期间继续某个服务器会话时，本机以该副本为起点创建一个**本机分叉**（`session.forked`，13 §6.2），而不是冒充服务器写同一会话。这保证任何时刻每个会话只有一个推进者。
- 探测间隔 30 秒；降级/恢复都记录日志并发 `notice`。

## 4 发现

- 仅当 `mesh.enabled = true` 时启用。使用 mDNS/DNS-SD，服务类型 `_gqy._tcp.local`，端口为 `mesh.listen`。
- TXT 记录：`id=<DeviceId>`、`name=<用户起的设备名>`、`mesh=<网格 id 前 8 hex 或空>`、`proto=gqy-mesh/1`、`ver=<应用版本>`、`pair=0|1`（是否正在接受配对）。
- TXT 内容视为不可信，只用于在界面上列出候选；身份以 TLS 握手中的公钥为准。
- 无法使用组播的网络（企业 Wi-Fi、部分 VPN）：支持手动输入 `host:port`。
- crate 选型：纯 Rust mDNS 实现（如 `mdns-sd`），P15 评估。

## 5 配对与信任

### 5.1 设备身份

- 首次启用 mesh 时，设备生成 Ed25519 身份密钥，私钥存 `<data>/mesh/device.key`（0600，10 §3），不参与任何同步、不进导出。
- TLS 证书由身份密钥自签发，有效期 10 年；**信任对象是公钥而不是证书**，证书重签不影响信任。

### 5.2 建网与密码

- 第一台设备“创建网格”：生成网格 id（随机 128 bit）与成员账本创世条目，用户设置网格密码（≥ 12 字符，强度提示）。密码不落盘，只在配对时由用户输入。
- 密码的作用是**配对时的相互认证**，不是长期凭据。长期凭据是成员账本中的公钥。

### 5.3 配对流程（全员同意）

```text
新设备 N                          已有成员 A（任一在线成员）            其它成员 B、C…
  │  发现 A 或手动输入地址               │                                   │
  │── TLS（不校验证书，仅加密）──────────▶│                                   │
  │  PAKE（CPace/SPAKE2，口令 = 网格密码）│                                   │
  │  双方把各自 TLS 公钥指纹绑定进 PAKE 记录（防中间人）                        │
  │◀──── PAKE 成功：双方互证知道密码 ─────│                                   │
  │  N 提交 JoinRequest{device_id, pubkey, name, ver}                        │
  │                                      │── 广播 JoinRequest（mesh 通道）──▶│
  │                                      │  每台成员设备在本机 UI 弹出确认：    │
  │                                      │  “设备 N（指纹词 ×4）请求加入”     │
  │                                      │◀── Approve / Reject（签名）───────│
  │  全部成员批准 → A 写入 Join 条目（附全部签名）并分发成员账本                 │
  │◀──── 成员账本 ──────────────────────│                                   │
```

- **PAKE**：用口令认证密钥交换，而不是把密码发过去比对；中间人无法离线猜测密码。每个 JoinRequest 限 5 次口令尝试，失败后该来源锁定 15 分钟。
- **指纹词**：双方界面显示 4 个由公钥指纹派生的单词，供用户肉眼核对（可选步骤）。
- **离线成员**：白皮书要求“全部设备同意”。离线成员无法当场同意。本文推荐：JoinRequest 挂起，等所有成员上线逐一批准，最长 7 天后过期；若某成员长期不在线，用户可先在其它设备上撤销它（§5.5），再完成加入。这一点需要用户确认（Q-17-1）。
- 任一成员 Reject → 请求作废，N 收到拒绝。

### 5.4 成员账本

```rust
// 草案，以实现为准（gqy-mesh）
pub enum MembershipOp {
    Genesis { mesh_id: MeshId, founder: DevicePubKey, name: String },
    Join    { device: DevicePubKey, name: String, approvals: Vec<(DeviceId, Signature)> },
    Revoke  { device: DeviceId, reason: String },
    Rename  { device: DeviceId, name: String },
}
pub struct MembershipEntry { seq: u64, prev_hash: [u8; 32], op: MembershipOp, author: DeviceId, sig: Signature }
```

- 只追加、哈希链接、每条由作者设备签名。每台设备独立校验整条链：`Join` 必须带当时全部未撤销成员的签名；`Revoke` 的作者必须是当时的成员。
- 两台设备在断网期间各自追加导致分叉时：`Revoke` 条目取并集（撤销优先，安全侧），`Join` 在合并后重新校验签名集合是否覆盖合并后的成员集，不覆盖则该 `Join` 挂起重新征求同意。
- 成员账本存在主库 `mesh_membership` 表（10 §7.6），是设备间信任的唯一事实来源；TLS 校验器每次握手都查它（按请求查库，02 §8），撤销立即生效。

### 5.5 撤销

- 任一成员可以撤销任一其它成员，也可以撤销自己（“离开网格”）。推荐这一宽松规则：丢失设备时，用户手边的任何一台设备都应能立刻切断它（Q-17-2）。
- 撤销后：其它设备立即拒绝该设备的 TLS 连接；被撤销设备收到（或下次连接时得知）撤销后，降级为“客户端 + 本地服务器”，本机数据保留、可继续本地使用。
- 重新加入需要重新走完整配对（新的 Join 条目）；之后可以按 §7 合并。

### 5.6 TLS

- mesh 监听只接受双向 TLS（rustls）。自定义 `ServerCertVerifier` / `ClientCertVerifier`：取对端证书的 SPKI，计算 `DeviceId`，在成员账本中查找且未撤销才接受；证书链、主机名一律不看。
- 配对阶段（§5.3）使用单独的路由 `/api/v1/mesh/pair/*`，允许未知证书，只能执行 PAKE 与提交 JoinRequest。
- **浏览器**不直接访问其它设备的 mesh 监听（自签证书会触发警告，且浏览器无法做钉扎）；浏览器只访问本机网关，由本机 host 代理远程请求。

## 6 能力委派

### 6.1 模型

设备 B 对网格声明可委派的能力；设备 A 上的会话把它们作为工具使用，执行发生在 B。

| 能力类别 | 例子 | 在 A 的工具面上的形态 |
| --- | --- | --- |
| 文件与命令 | B 上的工作区读写、命令执行 | 远程工具 `device_<name>.<tool>`，stub 形态（07），会话创建时冻结进工具面 |
| 模型接入 | B 的供应商配额或局域网模型 | A 的 `ModelBinding` 指向 `Mesh{device}` 供应商代理 |
| 记忆 / 知识库 | B 上的知识库检索 | 远程只读工具 |
| 硬件 | B 的摄像头、打印机（扩展提供） | 远程工具 |

- **工具面冻结**：远程工具是否出现在工具面，在会话创建时按“当时的委派表”快照（12、07）。B 之后下线，工具仍在面上（字节恒定，前缀契约），调用时返回 `device_offline` 错误（模型可见英文短句）。

### 6.2 裁决留在提供方

```text
A 的回合调用 device_B.run_command(args)
  A：本机策略先判“这个会话能否使用委派能力”（08，只能收紧不能放宽）
  A → B：POST /api/v1/mesh/invoke { capability, tool, args, origin: { device: A, session, principal, venue } }
  B：以 Venue{ kind: Mesh{device: A}, trust: 来自 B 的 mesh_grants 配置 } 构造 ToolContext
     B 的权限引擎（08）判定：允许 / 拒绝 / 需要审批
     需要审批 → B 生成 Question，推送到 A 的会话流（A 的 UI 显示“来自设备 B 的审批”）
               同时在 B 本机 UI 显示；任一端回答，答案由 B 校验回答者身份（同一用户的已配对设备或 B 本机 Owner）
     执行在 B 的沙盒内 → ToolOutcome 返回 A
```

- **A 不能替 B 做决定**：A 只能在本机侧额外拒绝（收紧），不能把 B 的“需要审批”变成“允许”。B 的 `mesh_grants`：按对端设备、能力类别配置 `CapabilityMode`（默认 `ReadOnly`，08）。
- 审计：B 的审计日志记录发起设备、会话、principal、工具与参数哈希；A 的账本记录调用与结果（化石化，04）。
- 取消传播：A 取消运行时向 B 发 `POST /api/v1/mesh/invoke/{id}/cancel`；B 按 02 §6 终止子进程。网络中断时 B 在 `invoke_timeout`（默认同工具超时）后自行终止。

## 7 同步与合并

### 7.1 范围

白皮书：共享范围是全部——会话、任务记录、能力、文件、记忆/知识库、模型接入。本文细化默认值：

| 数据 | 默认同步 | 合并方式 | 备注 |
| --- | --- | --- | --- |
| 会话账本 | 是 | 并集，冲突 = 分叉（§7.3） | |
| blob | 按需（被同步的账本引用时） | 内容寻址，天然并集 | |
| 作业记录 | 是 | 并集（按 `(device, job_id)`） | 作业本身不迁移执行 |
| 记忆 | 是 | 并集；遗忘为墓碑标记（11 的“标记遗忘不删”） | |
| 知识库 | 是 | 文档级并集，同名不同内容保留两份并提示 | |
| persona | 询问 | 按 generation 取较新者，另一份保留为历史版本 | |
| 配置 | 否 | — | 各设备独立 |
| 模型接入凭据 | **否，逐项选择** | — | 凭据跨设备复制风险高，见 Q-17-4 |
| 工作区文件 | 否 | — | 非目标 |

### 7.2 协议

```text
1. 交换摘要：GET /api/v1/mesh/sync/heads → [(session, home_device, last_seq, last_prefix_hash, last_entry_hash)]
2. 本机计算差异：对方有而我没有的会话 / 对方更长的会话 / 同 seq 不同哈希（冲突）
3. 向用户展示计划：“新会话 N 个、延长 M 个、冲突 K 个（将分叉）、记忆 +X 条” → 用户确认
4. 分页拉取：GET /api/v1/mesh/sync/entries?session=&after_seq=&limit=500
5. 校验：逐条验证哈希链（04 的 prefix_hash / 条目哈希）；任何断链 → 该会话中止并报告
6. 经 store 单写者应用；进度可断点续传（记录每个会话已应用的 seq）
```

- 拉取方向由用户选择（双向 / 只拉 / 只推）。所有同步只追加，不修改本机已有条目（铁律 9）。

### 7.3 合并即并集，冲突即分叉

- 账本条目以 `(session, seq)` 为键、带内容哈希。两台设备的同一会话：
  - 一方是另一方的前缀 → 追加缺少的尾部；
  - 在某个 seq 处内容哈希不同 → 找到最后公共 seq `p`，本机保持原会话不变，对方从 `p+1` 起的条目写成一个**新会话**（`session.forked { from_session, from_seq: p }`），标题标注来源设备。
- 由于 §3.2 规定每个会话只有主场设备推进，正常情况下不会冲突；冲突只来自降级期间或撤销后的离线使用，分叉如实反映“两台设备各自继续了对话”。
- 分叉后不自动合并内容；用户可以手动在任一分支继续。

## 8 跨设备前缀交接【研究项】

目标：会话主场从 A 迁到 B（或在 B 上继续 A 的会话副本）时，B 发出的请求前缀与 A 的历史请求逐字节一致，使供应商前缀缓存继续命中。以下是研究框架，**不是已定设计**，结论写回本节与白皮书 §3.5。

| 要素 | 设计假设 | 需要验证 |
| --- | --- | --- |
| 账本随会话走 | B 从同步来的账本重建 `RequestPlan`；重建路径唯一（04） | — |
| 序列化与工具面恒定 | 工具面在会话中冻结并入账本（`surface_hash`）；序列化器由 `layout_version` + `encoding_version` 标识（04 §9.3） | 不同应用版本的序列化器是否产出相同字节；版本号策略 §9 |
| 注入冻结 | 时间、感知值、联想记忆在写入账本时化石化，B 重放同一冻结值（04、09） | B 的新回合使用 B 的感知值，只影响新尾部 |
| 哈希链校验 | A 在每次请求记录 `prefix_hash`；B 重建后计算并比对 | 比对失败率 |
| 计划内冷启动 | 比对失败时，B 明确告知用户“本次交接将导致缓存冷启动”，并记录 `context_rewrite reason=device_handoff`（仅日志类别，不改写账本） | — |
| 供应商缓存是否跨客户端共享 | 同一账号下，相同前缀理论上命中同一缓存 | 按供应商实测：Anthropic、OpenAI、DeepSeek；TTL、写入计价 |
| 局域网模型的缓存感知路由 | 请求需路由到持有该前缀 KV 的实例（SGLang / vLLM 路由组件） | 选型时单独评估 |
| 凭据与配额归属 | B 使用谁的 API 密钥？若不同账号，缓存一定不共享 | 与 Q-17-4 一起决定 |
| 交接时间窗 | 供应商缓存 TTL（v1 观测 DeepSeek 热窗口晚高峰 < 25 s、深夜 > 5 min） | 交接能否在 TTL 内完成 |

主场迁移流程（候选）：A 停止接受新回合 → 等待当前运行终态 → 同步到 B 并校验哈希链 → 成员双方签名的 `HomeTransfer{session, from, to, at_seq}` 记录 → B 成为主场。任何一步失败则主场不变。

## 9 版本与一致性

白皮书 §3.4：“每次更新时统一版本号管理”；版本不一致时如何处置**尚未定义**。本文列出需要一致的维度，并给出推荐（待用户确认，Q-17-3）。

| 维度 | 说明 | 推荐的不一致策略 |
| --- | --- | --- |
| 应用版本 | `version.txt`，全网格同一发布体系 | 允许不同；在设备列表中高亮版本落后的设备，提示升级 |
| `gqy-mesh` 协议大版本 | 配对、同步、委派的线上格式 | 大版本不同 → 拒绝连接（只能本地使用），提示统一升级 |
| API 协议 `/api/v1` 小版本 | 13 §4 | 按能力位降级 |
| 账本格式版本 | 条目编码与哈希算法 | 不同 → 同步只能从旧到新（新版本能读旧格式），反向拒绝 |
| `layout_version` / `encoding_version` | 请求字节的渲染与编码版本（04 §9.3） | 不同 → 交接一律计划内冷启动（§8） |

握手时交换以上全部版本号；不兼容时的错误说明期望与实际（00 §3）。

## 10 安全边界

- mesh 内所有设备视为同一用户。一台设备被攻破 = 攻击者获得该设备在网格中的全部授权；缓解靠撤销（§5.5）与提供方裁决（§6.2）。
- 身份私钥不同步；凭据默认不同步。
- 局域网被动监听：全部流量 TLS；配对用 PAKE，密码不上线。
- mDNS 信息泄露：TXT 只含设备名与版本；用户可关闭广播改为手动地址。
- 不防护：同一用户账号下的本机恶意进程（它可以直接读 `device.key`，与读数据目录同级）。

## 12 测试与守护

- **配对**：两个临时数据目录的 daemon 完成 PAKE；错误密码 5 次后锁定；中间人代理替换证书时 PAKE 失败（指纹绑定生效，去掉绑定后此测试必红）。
- **全员同意**：三设备网格，C 拒绝 → N 未加入；C 离线 → 请求挂起，C 上线批准后才加入。
- **成员账本校验**：伪造缺签名的 Join、非成员作者的 Revoke、断链，全部被拒；分叉合并时 Revoke 取并集。
- **撤销即时生效**：撤销后 1 秒内被撤销设备的新 TLS 握手失败、已有连接被关闭。
- **委派裁决**：A 请求 B 执行 `Exec` 类工具，B 的授权为 `ReadOnly` → 拒绝；A 侧任何配置都不能让其通过。
- **同步并集**：构造前缀关系、冲突关系两种会话，断言前者追加、后者分叉且 `from_seq` 正确；同步不修改本机已有条目（比对同步前后已有条目的哈希）。
- **降级**：停掉服务器，client 在 3 次探测后降级；在服务器会话上继续时产生本机分叉而非直接写入。
- **跨设备前缀（研究）**：同一版本两台设备，从同步账本重建的第 N 轮请求字节与原设备记录的 `prefix_hash` 相同；`layout_version` 或 `encoding_version` 不同时显式冷启动并记日志。
