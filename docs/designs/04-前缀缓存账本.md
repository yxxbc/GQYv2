# 04 · 前缀缓存账本

> 状态：【规划】。前置阅读：[00 设计理念](00-设计理念.md)（铁律 1、6、9）、[01 总体架构](01-总体架构.md) §3.1、[02 运行时与并发模型](02-运行时与并发模型.md)、[03 回合引擎](03-回合引擎.md)。配套：[05 上下文与压缩](05-上下文与压缩.md)（唯一的前缀改写点）、[06 模型供应商适配](06-模型供应商适配.md)（字节编码）。

## 1 目标

把铁律 1“前缀即契约”变成可执行、可检验的结构：

1. **相同的会话状态产生逐字节相同的请求前缀。** 同一会话的第 N 次请求，是第 N−1 次请求的字节前缀延伸，除非两者之间发生了**计划内冷启动**（§9）。
2. **职责切分。** 账本（`gqy-ledger`）决定“发什么、按什么顺序”，产出 `RequestPlan`；供应商适配器（`gqy-provider`，06）决定“怎么编码成字节”。两者都是纯函数、确定性输出，组合起来才构成字节契约（01 §3.1）。
3. **缓存工程不污染语义。** 用户原文、界面展示、工程附加物分通道存放（§5），记忆与界面只读自己的通道。
4. **退化会被机器发现。** 字节纯度被破坏时“毫无症状”（v1 理念 §八），所以必须有 mock 供应商上的 CI 门禁（§12）与每请求一行的绝对值用量账（§14）。

## 2 v1 教训

- 【v1 实测】DeepSeek 上只改 tools 数组第一个工具描述中的一句话，其余几万 token 不变，命中为 0，连排在前面的 system 也一起失效：服务端模板把工具渲染在很靠前的位置。**tools 数组是前缀里最危险的部分。**
- 【v1 实测】`<runtime now=…>` 最初放在当前 user 消息之前，下一轮回放时被丢弃，导致每轮都在 user 消息处分叉；挪到 user 之后才修好。
- 【v1 实测】化石化上线后，连续两轮请求共享 84% 字节，第一个分叉点落在上一轮 prompt 末尾；每轮必然 miss 约 1.3k token（本轮输入 + 本轮化石尾 + 上轮回复重渲染），40k 上下文命中约 97%，116k 实测 99.9%。
- 【v1 实测】hybrid 懒加载时工具循环轮内命中 0%；stub 常驻时 95%–99.8%。
- v1 persona 指纹变化时曾删除历史（缺陷 C1）。修法是指纹拆分为 `persona_compatibility_id` 与 `wire_prompt_hash`，指纹变化只算一次计划内冷启动。
- v1 的“序列化路径必须唯一”靠自觉；`WirePrefixShape`、`llm_requests` 表、Anthropic `cache_control` 断点、mock 字节门禁多为未实施项。v2 把它们作为 P03 的交付物。

## 3 不变量

以下不变量每条都对应 §12、§13 中至少一个守护测试。

| 编号 | 不变量 |
| --- | --- |
| I-1 | **append-only**：`Context` 通道条目一旦写入，其 `payload` 永不修改、永不删除。唯一例外是压缩推进视图（§9、05），而压缩也不删除条目，只改变视图起点。 |
| I-2 | **前缀延伸**：同一纪元（epoch，§9）内，请求 N 的编码字节去掉收尾后缀后，是请求 N+1 编码字节的前缀（精确定义见 §12.1）。 |
| I-3 | **先落库后发送**：请求中出现的每个条目在发送前已持久化且 `frozen = true`。发送失败不回滚条目。 |
| I-4 | **瞬态必化石**：任何只在“这一次”有意义的内容（时间、感知值、联想记忆、来源元数据）一经发送就作为条目存下，之后逐字节回放（§6）。 |
| I-5 | **冻结后不重算**：注入内容在进入账本的那一刻计算一次，存储的是结果文本，不是生成它的参数（§7）。 |
| I-6 | **工具面会话内恒定**：同一纪元内 `surface_hash` 不变；每个逻辑回合至多一次工具面变更，且变更即开启新纪元（§8）。 |
| I-7 | **单一编码路径**：每种条目只有一个渲染函数、每种协议只有一个编码函数；编码只依赖 `(条目, ProviderProfile, layout_version)`（06 §6）。 |
| I-8 | **不进 msg[0]**：易变内容（时间、cwd、感知值）永远不出现在 system 区段或第一条消息里。 |
| I-9 | **辅助请求不碰会话链**：标题、判定、整理、视觉、隔离式摘要等请求使用独立的链与缓存标识（§11）。 |
| I-10 | **每次改写可解释**：任何导致前缀不延伸的事件都产生一行 `context_rewrite reason=…` 日志和一个新纪元（§9、§14）。 |

## 4 请求布局

### 4.1 区段

```text
┌─[S] 稳定区段（纪元内字节恒定）────────────────────────────────┐
│ tools：ToolSurface（按名排序、规范 JSON，§8）                 │
│ system：persona_core → audience_policy → platform_policy     │
│         → active_tool_guidelines → kb / skills 索引           │
└──────────────────────────────────────────────────────────────┘
┌─[A] 历史区段（append-only，已化石）───────────────────────────┐
│ [checkpoint]（若本纪元由压缩开启，05 §7）                      │
│ [rehydrate]（压后回灌，05 §7）                                 │
│ 回合 k：user 原文 → 不可信尾巴 → 可信尾巴 → 运行时尾巴           │
│        → assistant 信封 → tool 结果… → 插话… → assistant 信封 … │
│ 回合 k+1 …                                                    │
└──────────────────────────────────────────────────────────────┘
┌─[E] 本回合新增（发送前落库，发送后即成为 [A] 的一部分）─────────┐
│ user 原文                   （user 角色）                       │
│ 不可信尾巴：昵称、群历史、联想记忆…（user 角色，XML 外壳）         │
│ 可信尾巴：principal 摘要、审核结果、模式更新（system-late 角色）   │
│ 运行时尾巴：<runtime now="…分钟级" cwd="…"/>（system-late 角色） │
└──────────────────────────────────────────────────────────────┘
```

- `[E]` 的顺序固定为：user 原文 → 不可信尾巴 → 可信尾巴 → 运行时尾巴。运行时尾巴在 user 原文**之后**（v1 教训），这样本回合的大块 user 内容（例如群聊记录）进入下一回合可复用的前缀。
- 运行时尾巴**每个逻辑回合一条**，只在回合的第一次请求前生成；工具循环中的后续请求不追加新的运行时尾巴。时间粒度为分钟，时区取 `PerceptionFrame`（09）。
- 工具循环中两次请求之间新增的条目只有：assistant 信封、tool 结果、插话（03 §5.4）、system-late 通知（作业完成、`<turn-aborted>`、`<persona-update>`）。它们都追加在尾部。

### 4.2 条目种类

```rust
// 草案，以实现为准
pub enum EntryKind {
    StableSection,      // [S]，每纪元一条：surface_hash + system 块文本
    UserMessage,        // 用户原文（Context 通道版本）
    UntrustedTail,      // 不可信上下文，user 角色
    TrustedTail,        // 可信上下文，system-late 角色
    RuntimeTail,        // 运行时尾巴
    AssistantEnvelope,  // 供应商原生信封（06 §5），含工具调用
    ToolResult,         // 工具结果（已按 05 §10 写入期截断）
    Steer,              // 插话，user 角色
    Notice,             // system-late 通知：persona-update / memory-update / job-finished / turn-aborted
    Checkpoint,         // 压缩摘要（05 §7）
    Rehydrate,          // 压后回灌文件（05 §7）
    Display(DisplayKind), Raw(RawKind),   // 非 Context 通道条目，§5
    Legacy(LegacyKind), // 20 导入的 v1 条目：Fossil（context_messages 原样字节）/ ToolReport / AssistantMessage 等；只由导入器写入
}
```

### 4.3 条目结构

```rust
// 草案，以实现为准
pub struct LedgerEntry {
    pub seq: EntrySeq,            // 会话内单调递增
    pub turn_seq: u32,            // 账本内回合序号
    pub run: RunId,
    pub kind: EntryKind,
    pub channel: Channel,         // Raw | Display | Context
    pub payload: Payload,         // 逻辑内容（规范 JSON）；达到 10 §6.1 的 `store.blob_inline_max`（默认 8 KiB）时存 blob，存引用
    pub frozen: bool,             // 已随请求发出；为 true 后 payload 不可变
    pub epoch: u32,               // 写入时所在纪元
    pub chain: Option<[u8; 32]>,  // 仅 Context 条目：截至本条的前缀哈希（§10）
}

pub enum WireRole { User, Assistant, Tool, SystemLate }
pub struct ContextPayload { pub role: WireRole, pub parts: Vec<ContentPart> }  // ContentPart 定义在 gqy-core
```

`payload` 存的是**逻辑内容**（角色 + 内容片段），不是某个协议的线上字节。线上字节由适配器从逻辑内容确定性地编码得到（06 §6）。这样同一个会话在编码版本不变时，重新编码得到的字节与当初发送的完全相同；编码版本变化则是一次计划内冷启动（§9）。

### 4.4 system-late 角色

可信尾巴、运行时尾巴、通知都用逻辑角色 `SystemLate`。它映射成什么由适配器按 `ProviderProfile.late_system_role` 决定（06 §4）：支持时编码为对话中段的 `system`（或 `developer`）消息；不支持时（例如 Anthropic Messages API 只有顶层 system）编码为 `user` 消息，内容包在 `<system-context>…</system-context>` 中。无论哪种编码，它**都不承担鉴权**（铁律 7），只是给模型的信息。

### 4.5 RequestPlan

`RequestPlan` 是账本交给适配器的全部输入。适配器看不到 `TurnContext`、工具注册表或回合状态（01 §3.1）。

```rust
// 草案，以实现为准
pub struct RequestPlan {
    pub session: SessionId,
    pub run: RunId,
    pub request_seq: u32,
    pub epoch: u32,
    pub purpose: RequestPurpose,                 // §11
    pub binding: ModelBinding,                   // 06 §10；纪元内不变
    pub stable: Arc<StableSection>,              // tools（已规范化）+ system 块文本
    pub entries: Vec<Arc<LedgerEntry>>,          // 纪元视图中的 Context 条目，已按 §9.1 排好序
    pub params: SamplingParams,                  // max_tokens、temperature、thinking 等；纪元内不变
    pub cache: CacheHints,                       // 会话缓存键、上一次请求的条目边界（供 06 §11 放断点）
    pub expect_parent: Option<[u8; 32]>,         // 同纪元上一次请求的 prefix_hash（§10 自检）
}

pub struct CacheHints {
    pub session_key: Option<String>,             // 由 SessionId 派生的稳定字符串；Auxiliary 为 None
    pub prev_request_end: Option<EntrySeq>,      // 上一次主链请求覆盖到的最后条目
}
```

**类型归属**（00 §5 已定，01 §3）：`gqy-ledger` 与 `gqy-provider` 同属 L2，按 01 §3 不得互相依赖。因此 `RequestPlan`、`LedgerEntry`、`StableSection`、`ContextPayload`、`ModelBinding`、`ProviderProfile` 这些**数据类型**定义在 `gqy-core`；`gqy-ledger` 只实现规划与化石化逻辑，`gqy-provider` 只实现编码与传输。

`SamplingParams` 在纪元内不变是 §12.1 第 1 条的前提：`max_tokens`、温度、推理强度等来自 `ModelBinding` 与会话设置，用户中途修改它们等同换模型（`ModelBindingChange`）。

## 5 三通道

| 通道 | 内容 | 读者 | 对应 v1 |
| --- | --- | --- | --- |
| `Raw` | 用户原话、附件原件、工具输出全文（blob） | 记忆、联想检索、日记、导出 | `raw_content` |
| `Display` | 界面展示文本：渲染后的回复、带 `partial` 标记的中断输出、插话标记 | TUI、Web、连接器投递 | `display_content` |
| `Context` | 模型实际看到的字节来源 | 仅 `RequestPlan` | `context_messages` |

- 一次用户输入产生最多三条条目（同一 `turn_seq`、不同 `channel`）。`RequestPlan` 只读 `Context`；记忆子系统只读 `Raw`；界面只读 `Display`。三者之间没有“从一个推导另一个”的读路径，避免 v1 那种“缓存工程改了字节、记忆里混进 XML 与时间戳”。
- 工具输出：`Raw` 存全文 blob 引用；`Context` 存写入期截断后的文本（05 §10）。
- 不可信文本（连接器正文、昵称）进入 `Context` 前经 `safe_prompt_field` 处理（16），`Raw` 保留原文。

## 6 化石化

**定义**：发送给模型的每一段内容都作为 `Context` 条目持久化，`frozen = true`，之后每一次请求逐字节回放它。

执行时机（03 §6.1 的 `fossilize_pending`）：

1. 规划器产出 `RequestPlan`，其中尾部若干条目处于“待冻结”状态（本回合的 `[E]`、上一批工具结果、插话）。
2. 在**同一个 store 事务**里：把待冻结条目写为 `frozen = true`，计算并写入它们的 `chain` 哈希，写入请求记录（`request_seq`、`epoch`、`prefix_hash`，§10）。
3. 事务提交成功后，才把请求交给适配器发送。事务失败 → 请求不发送，运行失败为 `StoreUnavailable`。

由此得到：

- 崩溃发生在发送之后、响应落库之前：条目已存在，下次请求照常回放；缺失的只是那次响应，由 03 §3.3 的收尾逻辑处理。
- 发送失败（网络错误）后重试（06 §8）：重试发送的是同一份字节，账本不变。

成本：化石是常数级的（每回合一二百 token），换来整段前缀的连续性。**任何“为节省 token 删除已发送瞬态内容”的改动都违反 I-1，被 §12 的门禁拦截。**

## 7 冻结注入

所有“从外部状态计算出来再塞进上下文”的内容，都遵守同一规则：**在注入点计算一次，存结果文本，之后不再重算。**

| 注入物 | 注入位置 | 冻结点 | 说明 |
| --- | --- | --- | --- |
| 运行时尾巴（时间、cwd） | `[E]` 末尾 | 回合第一次请求前 | 分钟粒度 |
| 感知值（09 的 Context 维度） | 可信尾巴 | 回合开始时的 `PerceptionFrame` | 回合内不变（02 §4） |
| 联想记忆（11） | 不可信尾巴 | 回合开始时检索一次 | 以 `<recalled-memories>` 包裹 |
| 来源元数据（发送者、群名） | 不可信尾巴 | 准入时 | 可信字段（principal 摘要）走可信尾巴 |
| persona 兼容编辑 | `Notice`（`<persona-update>`） | 下一个逻辑回合开始 | §9.2 |
| 记忆写入提示 | `Notice`（`<memory-update>`） | 下一个逻辑回合开始 | 11 |
| 作业完成 | `Notice`（`<job-finished>`） | 作业结束时 | 03 §10.1 |
| `load_tools` 返回的完整 schema | `ToolResult` | 工具执行时 | 07；不改变 tools 数组 |

禁止的写法：在渲染函数里读时钟、读配置、读文件系统、读随机数、遍历 `HashMap`。`gqy-ledger` 的渲染函数签名只接收条目与冻结的快照参数，不接收 `Clock` 或任何 IO 句柄；由 `cargo xtask arch` 检查 `gqy-ledger` 不依赖 IO crate（`tokio::fs`、`std::fs`、`reqwest`）。

## 8 工具面规范化

工具面的编译归 07；本节规定它对字节契约必须满足的性质。

1. **排序**：`tools` 数组按工具真名的字节序排序（`name` 升序），与注册顺序无关。
2. **规范 JSON**：每个 `ToolSpec` 编码为规范 JSON（`gqy_core::canonical_json`）：对象键按字节序排序、无多余空白、数字最短往返表示、字符串不做 Unicode 规范化、非 ASCII 字符原样输出不转义。适配器按协议外壳包装（06 §6），但 schema 内部字节来自这一步。
3. **stub 形态**（`LoadingMode::Stub`，默认）：`name` 为真名；`description` 为 ≤ 60 字符的一行摘要；参数壳固定为 `{"type":"object","properties":{"arguments":{"type":"object"}}}`。完整 description 与 JSON Schema 通过 `load_tools` 以工具结果返回，落在对话尾部，不改变 tools 数组。
4. **`surface_hash`** = `blake3(canonical_json(sorted_tool_specs))`，取 32 字节，展示时取前 16 hex。它写入 `StableSection` 条目与每条请求记录。
5. **会话冻结**：工具面在会话创建时由 persona 启用集与场所决定（12），之后每个逻辑回合开始时重新扫描注册表并冻结“注册表代际”（registry generation）。扫描结果的 `surface_hash` 与当前纪元相同则什么都不发生；不同则按下一条处理。
6. **每回合至多一次工具面变更**：变更只在逻辑回合开始时生效，并开启新纪元（§9，原因 `SurfaceChange`）。回合进行中出现的变更（例如 MCP 服务器上线了新工具）推迟到下一个回合开始。`LoadingMode::Hybrid` 下，一个回合内多次 `load_tools` 请求的完整 schema 合并为一次变更，在下一个回合开始时生效；`Full` 模式下工具面按启用集一次展开，不存在回合内变更。
7. **形状夹具**：每个预设工具面（按 persona × 场所组合）逐工具计算 `sha256(canonical_json(spec))`，与 `crates/gqy-tools/tests/fixtures/shapes/<surface>.json` 比对（§13、07 §12.1）。

三角约束（v1 继承）：没有供应商配合时，“严格原生调用、稳定前缀、真正按需加载”三者只能取其二。默认 `Stub` 放弃的是参数的语法层校验（enum、pattern 降级为 description 文本），由注册表分发处的参数收口补回（07）。

## 9 纪元与计划内冷启动

### 9.1 纪元

纪元（epoch）是“一段满足 I-2 的连续请求”。纪元号在会话内单调递增。开启新纪元的原因是封闭枚举：

```rust
// 草案，以实现为准
pub enum ColdStartReason {
    Compaction,          // 05：压缩推进视图
    CompactionUndo,      // 05 §11：撤销压缩，以新纪元恢复旧视图
    SurfaceChange,       // §8
    PersonaGeneration,   // §9.2 不兼容编辑
    ModelBindingChange,  // 用户换模型或供应商（06 §10）
    LayoutVersion,       // 渲染或编码版本升级（§9.3）
    DeviceHandoff,       // 17：跨设备继续且哈希链校验失败
    OverflowRecovery,    // 05 §9：溢出恢复触发的强制压缩
    V1Import,            // 20 §7.1：v1 导入会话在 v2 的第一个请求
}
```

纪元模型（00 铁律 1）：水位与纪元记录只追加；压缩与撤销压缩都开启新纪元，撤销以新纪元恢复旧视图，不删除、不改写任何已写条目或水位记录（05 §7、§11）。

每个纪元开始时写一条 `StableSection` 条目（记录 `surface_hash`、`wire_prompt_hash`、`persona_generation`、`layout_version`、`profile_hash`、原因），并打一行 `context_rewrite reason=<snake_case> epoch=<n> …`。**纪元切换之外的任何前缀不延伸都是缺陷**，由 §12 门禁判定。

纪元视图：请求 = 本纪元的 `StableSection` + 视图起点（05 的水位）之后的 `Context` 条目，按下述顺序：`Checkpoint`、`Rehydrate`（若本纪元由压缩开启）在前，其余条目按 `seq` 升序。`Checkpoint` 的 `seq` 大于被保留的尾巴条目，但规定渲染在纪元开头；这条排序规则是 `plan()` 中唯一的非 `seq` 排序，并被夹具测试钉住。

### 9.2 persona 代际

`PersonaSnapshot` 带 `generation`，并计算两个指纹：

- `persona_compatibility_id`：由启用集、工具面相关配置、受众策略等“结构性”字段计算；
- `wire_prompt_hash`：由最终渲染的 system 文本计算。

热编辑 persona（12）时：

| 情况 | 行为 | 冷启动 |
| --- | --- | --- |
| 当前回合进行中 | 当前回合继续用旧快照（02 §4 快照语义） | 否 |
| 兼容编辑（`compatibility_id` 不变，只有文本变化） | 下一个逻辑回合开始时追加一条 `<persona-update>` 通知，说明变化要点；`[S]` 不变。新 system 文本在下一次**因其他原因**开启纪元时（通常是压缩）才写入 `StableSection` | 否 |
| 不兼容编辑（启用集、受众策略变化） | 下一个逻辑回合开始时原子切换代际，开启新纪元（`PersonaGeneration`），历史条目全部保留 | 是，一次 |

**绝不删除历史**（v1 缺陷 C1）。`<persona-update>` 的正文由 persona 编辑者提供的变更说明或自动 diff 摘要生成，一经生成即冻结。是否需要“立即强制刷新 [S]”的手动命令（`/persona reload`，12 §5.5）见 Q-04-2。

> **跨文档冲突（待拍板）**：12 §5.5 推荐的生效时机与上表不同——12 让所有 persona 编辑（含不兼容编辑）都等到下一次压缩或显式 `/persona reload` 才进入已有会话，不在“下一个逻辑回合”自动切换代际，也不注入 `<persona-update>`。两者只能实现一套，统一由 Q-12-2 决定（Q-04-2 随之合并），拍板前不得实现。

### 9.3 版本升级

`layout_version`（`gqy-ledger` 渲染）与 `encoding_version`（`gqy-provider` 编码，06 §6）是代码常量。任何改变已存在条目渲染字节的代码修改都必须升级对应版本号，形状夹具与 §12 门禁会在忘记升级时变红。版本升级后，每个会话在下一次请求时开启新纪元（`LayoutVersion`）。

## 10 前缀哈希链

每个 `Context` 条目在冻结时计算链哈希：

```text
chain(e_0) = blake3( "gqy-prefix-v1" ‖ epoch ‖ stable_hash ‖ enc(e_0) )
chain(e_i) = blake3( chain(e_{i-1}) ‖ enc(e_i) )
```

其中 `enc(e)` 是条目的**逻辑内容**的规范 JSON（不是某协议的线上字节），`stable_hash` 是本纪元 `StableSection` 的哈希。每条请求记录保存：

```rust
// 草案，以实现为准
pub struct RequestRecord {
    pub session: SessionId, pub run: RunId, pub request_seq: u32, pub epoch: u32,
    pub purpose: RequestPurpose,            // §11
    pub prefix_hash: [u8; 32],              // 最后一个条目的 chain
    pub entry_range: (EntrySeq, EntrySeq),
    pub parent_prefix: Option<[u8; 32]>,    // 同纪元上一次请求的 prefix_hash
    pub wire_hash: [u8; 32],                // 适配器最终请求体的 blake3（06 §6）
    pub surface_hash: [u8; 32], pub profile_hash: [u8; 32],
}
```

用途：

1. **自检**：规划时断言“上一次请求的 `prefix_hash` 出现在本次请求的链上”；不成立且没有冷启动原因时，开发构建 panic（测试中），发布构建记录 `prefix_violation` 错误日志并照常发送（不因缓存问题拒绝服务）。
2. **跨设备交接**（17）：接手设备比对链头，一致则继续；不一致按 `DeviceHandoff` 冷启动。
3. **CLI 中转续传**（06 §12，后续扩展）：以 `prefix_hash` 作为续传键，失配时整段重放。

## 11 辅助请求隔离

```rust
pub enum RequestPurpose { Main, CompactFork, Auxiliary(AuxKind) }
pub enum AuxKind { CompactIsolated, Title, Judge, Organizer, Review, Vision, Selection, Keepalive }
```

- `Main`：会话主链。进入账本、更新链、携带会话缓存标识（06 §9 的 session header / `prompt_cache_key`）。
- `CompactFork`（05 §6）：前缀字节与主链某次请求的前缀完全相同，只在尾部追加摘要指令。它**读**主链、复用缓存，但追加的指令与返回的摘要**不写入**主链 `Context` 条目（摘要以 `Checkpoint` 的形式在新纪元中出现）。请求记录的 `parent_prefix` 指向被复用的主链请求。
- `Auxiliary`：不带会话缓存标识，不参与粘性路由，不读写会话账本，有自己独立的 `RequestRecord`（`epoch = 0`，`parent_prefix = None`）。它们的 system 文本与 tools 是常量字节，自成一条可缓存的短链。`Keepalive`（06 §9.3）是特例：它原样复用主链最后一次请求的前缀字节，但同样不写账本。

## 12 字节前缀门禁

### 12.1 判定

适配器输出的请求体布局约定（06 §6）：**所有非消息字段在前，消息数组（`messages` / `input`）是 JSON 对象的最后一个键**。于是请求体可以写成：

```text
body = head ‖ "[" ‖ item_1 ‖ "," ‖ … ‖ item_n ‖ "]" ‖ "}"
```

门禁断言，对同一纪元内的相邻主链请求 N−1 与 N：

1. `head(N−1) == head(N)`（同一会话主链的采样参数、tools、system 在纪元内不变）；
2. `body(N−1)` 去掉末尾的 `"]}"` 之后，是 `body(N)` 的字节前缀；
3. 链哈希：`prefix_hash(N−1)` 出现在请求 N 的条目链上；
4. 纪元号变化时，`context_rewrite` 日志行存在且原因属于 §9.1 枚举；压缩引起的纪元，新纪元第一条历史条目必须是 `Checkpoint`。

Anthropic 的 `cache_control` 标记是编码层叠加物（06 §11），会随断点移动而出现在不同消息上。门禁对 Anthropic 协议先剥离所有 `cache_control` 键再做第 2 条比较，并另行断言断点位置符合 06 §11 的规划。`CompactFork` 请求只做第 3 条与“消息项逐项前缀”比较，因为它的 head（`max_tokens`、`tool_choice`）合法地不同。

### 12.2 mock 供应商

门禁运行在 06 §13 的 mock 供应商上：它实现三种协议的 HTTP 端点，逐字节记录收到的请求体，按脚本返回流式响应（文本、工具调用、`finish_reason`、用量、故障）。测试用临时数据目录启动完整引擎（不经网关），驱动场景，最后对记录的请求序列执行 §12.1 判定。

### 12.3 场景矩阵

每个场景在 `openai-chat`、`openai-responses`、`anthropic` 三种协议上各跑一遍：

| 场景 | 期望 |
| --- | --- |
| 10 回合纯对话 | 全部同纪元，逐次延伸 |
| 工具循环（单调用、并行 3 调用、`[read, write, read]` 屏障） | 同上；工具结果按规范顺序 |
| 插话、打断、取消、流中断、`finish_reason=length` | 同上；中断输出不进入下一请求 |
| 冻结注入（运行时尾巴跨分钟、联想记忆、作业通知） | 同上；旧时间戳原样回放 |
| persona 兼容编辑 / 不兼容编辑 | 前者不换纪元；后者恰好换一次 |
| `load_tools`（Stub）/ Hybrid 合并加载 | Stub 不换纪元；Hybrid 下一回合恰好换一次 |
| 自动压缩、强制压缩、溢出恢复、撤销压缩 | 每次恰好换一次纪元，新纪元以 `Checkpoint` 开头（撤销除外） |
| daemon 重启后继续会话 | 同纪元延伸（重新编码与当初字节相同） |
| 子代理 | 父链与子链各自延伸，互不干扰 |
| 辅助请求穿插（标题、判定） | 主链不受影响；辅助请求不带会话缓存标识 |

区分能力要求：每个场景都要有一个“变异版本”证明门禁会红，例如在渲染函数里加入当前秒数、把运行时尾巴移到 user 之前、删除一条已发送的通知、对 tools 不排序。变异版本作为 `#[should_panic]` 或断言失败的反例测试一起提交。

## 13 形状夹具

- 位置：`crates/gqy-tools/tests/fixtures/shapes/<surface>.json`（工具逐个的 `sha256` 与 `surface_hash`，07 §12.1）、`tests/fixtures/request-shapes/<protocol>/<scenario>.body`（代表性请求体全文）。

## 14 缓存用量账与改写日志

每个请求一行（target `gqy::usage`，JSON 行格式与完整字段表以 19 §3.3 为准；同一个值同时写入主库 `llm_requests` / `usage_records`，10 §7.5；正文不记录），刻意用**绝对值**而不是百分比。下例只展示本文负责的派生字段（`epoch`、`purpose`、`prev_input_total`、`shared_prefix_bytes`、`expected_read_floor`、`miss_suspect`）的含义，示意为 key=value 形式：

```text
prompt_cache_accounting session=… run=… req=17 epoch=3 purpose=main provider=… model=…
  input_total=41230 cache_read=40960 cache_write=0 input_uncached=270 output=512
  prev_input_total=40480 shared_prefix_bytes=162311 expected_read_floor=40448 miss_suspect=false
```

- 用量桶的定义与归一化归 06 §14；本行只消费结果。
- `expected_read_floor` = 同纪元上一次请求的 `input_total` 向下取整到供应商缓存块粒度（`ProviderProfile.cache_block_tokens`，默认 64，06 §4）。
- `miss_suspect = (min(prev_input_total, input_total) − cache_read) > noise_floor`，其中 `noise_floor` 按缓存语义类别取值：`Contract` 为 1 块，`BestEffort` 为 4096 token（DeepSeek 会话链每请求只多持久化约 1k，热窗口随负载浮动，【v1 实测】），`PerRequest` 不判定。`miss_suspect=true` 只打日志与计数，不告警到界面。
- 纪元第一次请求的 `prev_input_total` 为空，不判定（计划内冷启动的成本由改写日志解释）。
- `context_rewrite` 日志：`context_rewrite reason=compaction epoch=4 folded_entries=… before_tokens=… after_tokens=…`。命中率下跌时，用这两类日志并排归因。

保留：日志文件按日轮转（超 256 MiB 再滚动），默认保留 14 天（19 §3.2）；主库 `llm_requests` / `usage_records` 的保留策略见 10 §9.3。

## 15 边界与失败模式

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| 渲染非确定性（`HashMap` 迭代、浮点格式、时钟） | 门禁红 | 渲染层禁止 IO 与 `HashMap`（clippy `disallowed_types` 限定在 `gqy-ledger`） |
| Unicode 规范化、尾部空白修剪 | 用户原文字节变化 | 永不规范化、永不修剪；原样存储 |
| 服务端模板变化 | 命中下跌但门禁绿 | 只能从用量账观察；不属于客户端缺陷 |
| 供应商按块缓存（64 token） | 尾部不足一块不命中 | 预期内，`expected_read_floor` 已按块取整 |
| 多密钥轮转跨账号 | 缓存不共享 | 06 §8 默认会话粘性选钥 |
| 会话换模型或协议 | 原生信封无法跨协议回放 | 计划内冷启动；跨协议时按 06 §5.3 降级回放 |
| 落库失败 | 不能发送 | 回合失败 `StoreUnavailable`，不“先发再补” |
| 大条目 | 主库膨胀 | payload 达到 `store.blob_inline_max`（默认 8 KiB，10 §6.1）存 blob；链哈希按内容计算，与存储位置无关 |
