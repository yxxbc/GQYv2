## 1 目标

1. **权限由代码判定**：提示词里的任何文字都不参与鉴权（铁律 7）。判定输入只有 principal、场所、能力档位、调用评估、授权记录。
2. **交互式审批**：v1 没有审批，护栏只有“只拒不放”。v2 让用户在 TUI / Web 中对有后果的调用做“同意一次 / 本会话同意 / 拒绝”。
3. **失败关闭、边界诚实**：沙盒不能生效时拒绝执行；沙盒不覆盖的范围（网络）明文写出（铁律 8）。
4. **可审计**：每一次判定和每一次子进程执行都有记录；密钥永远不出现在模型可见文本里。

## 2 v1 教训

| v1 事实 | 数字 / 证据 | v2 的回答 |
| --- | --- | --- |
| 无交互式审批 | guard 只拒不放；TUI 无 Question 消费者（backlog） | §5 审批流程 + Question 事件 |
| 命令黑名单是子串匹配 | `command_deny` 子串；绕过只需加引号或空格 | 先分词再匹配，并明确“黑名单不是安全边界”（§5.4） |

| 属主不套沙盒 | Owner 默认无沙盒；成员回合强制 Landlock | Owner 默认 `Workspace` 档位，Exec 在沙盒内；需要时切 `Full` 宿主直跑（00 §5 已定，原 Q-08-1） |

| 授权缓存不失效 | `PLATFORM_ACCESS_INDEXES` 进程内缓存，撤销要重启才生效 | 授权按请求查库（02 §8） |
| 游客限流 | guest 2 次 / 600 s；群聊非管理员永远拿不到宿主工具 | 保留，归入场所信任映射（§7） |

## 3 四层权限

下层只能收紧，不能绕过上层；应用内开关不能创造系统没有的能力。

| 层 | 由谁决定 | 判定内容 | 失败时 |
| --- | --- | --- | --- |
| L1 系统与账户 | 操作系统、运行 daemon 的 OS 用户 | daemon 进程本身能做什么 | OS 报错（`EACCES` 等），原样报告 |
| L2 沙盒与工作区 | `WorkspaceScope` + `SandboxPolicy` | 路径读写边界；子进程的文件系统视图 | 路径守卫拒绝；沙盒不可用则失败关闭 |
| L3 能力档位 | `CapabilityMode`，按会话设置，受场所上限约束 | 此刻允许哪些效果类别 | `error[denied] layer=capability` |
| L4 单次审批 | 自动策略 + 会话授权 + 用户回答 | 这次调用是否执行 | `error[denied] layer=approval` |

另有一个**前置闸**：工具是否在本会话工具面中（07 §5）。External 场所的工具面里根本没有宿主工具，这比任何运行时判定都硬。

## 4 判定函数

```rust
// 草案，以实现为准 —— gqy-tools::permission，纯函数、无 IO
pub fn decide(input: &DecisionInput) -> Decision;

pub struct DecisionInput<'a> {
    pub venue: &'a Venue,              // trust、interactive
    pub principal: &'a Principal,
    pub mode: CapabilityMode,          // 会话当前档位（已按场所上限钳制）
    pub assessment: &'a Assessment,    // 07 §3.2：effect、targets、approval_key、risk
    pub scope: &'a WorkspaceScope,     // 读写根
    pub sandbox: SandboxAvailability,  // Available{backend, abi} | Unavailable{reason}
    pub grants: &'a GrantSet,          // 本会话授权（§5.3）
    pub policy: &'a ApprovalPolicy,    // 自动策略（§5.2），来自 ConfigSnapshot
}

pub enum Decision {
    Allow { by: RuleId },
    Ask(QuestionSpec),
    Deny { layer: Layer, rule: RuleId, message: String },
}
```

判定顺序（先命中者生效，每一步的 `RuleId` 写入审计）：

1. **命令策略拒绝**（§5.4 deny 规则、trash 拒绝目标）→ `Deny`。
2. **能力档位**（下表）不允许该效果或目标 → `Deny`。
3. **沙盒可用性**：`Exec` 在 `Workspace` 档位下、`sandbox == Unavailable` 时：Member / External / Internal（继承非 Owner）→ `Deny{layer: Sandbox}`（失败关闭）；Owner → 标记为无沙盒执行，审批键加 `unsandboxed:` 前缀（沙盒内得到的会话授权不会延伸到无沙盒执行）后继续第 4–6 步；第 6 步按 `exec_unsandboxed`（只接受 `ask | deny`），所以未命中会话授权时必然 `Ask`，卡片醒目标注 unsandboxed 并提供“本会话同意”（§4.1，00 §5 已定）。`Full` 档位不经过这一步（宿主直跑）。
4. **风险**：`risk == Dangerous` → `Ask`，不受会话授权与自动策略影响。
5. **会话授权** `grants` 匹配 `approval_key` → `Allow`。
6. **自动策略**：按效果类别和允许清单 → `Allow` 或 `Ask`。
7. `Ask` 且 `venue.interactive == false` → 按 §5.5 处理（通常是 `Deny`）。

### 4.1 能力档位

| 效果 \ 档位 | `ReadOnly` | `Workspace` | `Full` |
| --- | --- | --- | --- |
| `ReadOnly`（读） | 读根内允许 | 读根内允许 | 除保护路径外允许 |
| `Presentation` | 允许 | 允许 | 允许 |
| `Writes` | 拒绝 | 写根（工作区）内允许；写根外拒绝 | 除保护路径外允许 |
| `Exec` | 拒绝 | 有沙盒后端：在沙盒内允许（写根 = 工作区），按自动策略审批；无沙盒后端：仅 Owner 可无沙盒执行，每次先审批（可“本会话同意”），Member / External 拒绝 | 仅 Owner：直接在宿主运行（Linux / macOS，不套沙盒），只有 Dangerous 命令需审批 |
| `Network` | 拒绝（Q-08-3） | 允许 | 允许 |

- **默认档位（00 §5 已定，原 Q-08-1）**：Owner 本机会话默认 `Workspace`：Linux 上 Exec 由 Landlock 限制在工作区内；需要系统级操作时 Owner 用 `/mode full` 切到 `Full`，在宿主上直接执行，只有 Dangerous 命令（§5.4）需要审批。沙盒不会因此被移除；Member / External 场所永远拿不到宿主 Exec（`Full` 仅 Owner）。
- **无沙盒后端的平台（00 §5 已定，原 Q-08-2）**：当前 macOS（Seatbelt 落地前，D-02），以及探测到 Landlock 不可用的 Linux 内核同理（代码只问 `HostCap::SandboxFs`，不问平台）：Owner 的 `Workspace` 档位 Exec 在宿主上无沙盒运行，但每次都需审批，审批卡片醒目标注 unsandboxed，提供“本会话同意”；Member / External 一律拒绝。一旦后端可用（探测结果变为 Available / Degraded），自动改为沙盒内执行，不需要用户操作。`Full` 档位在 Linux / macOS 上始终宿主直跑。Windows 维持 §6.5：第一版拒绝全部 Exec。
- **边界诚实**：无沙盒执行（`Full` 档位，或无后端平台上 Owner 批准的 `Workspace` Exec）等价于 Owner 本人在终端执行，能读到 `run/local.token`，不在 13 §8.1 本地令牌的防护范围内；审批卡片、`gqy doctor` 与用户文档都写明这一点（铁律 8）。
- **读根**：`Workspace` 与 `ReadOnly` 档位下 = 工作区 + 系统只读目录 + 配置的 `extra_read_roots`。Owner 场所可配置 `read_anywhere = true`（默认 true），Member 永远 false。
- **保护路径**（任何档位都拒绝模型经文件工具读写）：GQYv2 数据目录（`~/.gqy2`，D-01 待定）中除存储域外的全部内容（`gqy.db`、`blobs/`、`config/`、`run/`、`logs/`）、`~/.ssh`、`~/.gnupg`、`~/.aws`、`~/.config/gh`、`~/.netrc`，以及配置中追加的 `protected_paths`。保护路径是路径守卫规则（§6.1），对 `Full` 同样生效；需要处理这些文件时用户自己动手。
- 档位切换：用户经 TUI `/mode`、Web 设置或 API 切换，事件 `session.mode_changed`；切换**不改变工具面字节**（07 §5.1）。模型可见的只有一条化石化的尾部通知 `<mode-update mode="workspace"/>`（04 trusted tail）。

## 5 审批

### 5.1 流程

```text
Dispatcher::prepare → Decision::Ask(spec)
  engine：QuestionId 生成；落库 questions 表（status=pending，10 §7.4）→ 事件 question.asked
          运行状态 AwaitingApproval（02 §6：无超时、可取消、不占全局回合配额）
  客户端（TUI/Web/桌面/gqy ask --approve=prompt）展示审批卡片
  POST /api/v1/questions/{qid}/answer  { Approval: { decision, note? } }（13 §5.3.2）
  gateway：校验回答者身份（§5.6）→ SessionCmd::Answer（02 §3.2）
  engine：先到先得；落库 status=answered；事件 question.answered（广播给其他客户端收起卡片）
     AllowOnce       → 执行本次
     AllowForSession → 写入会话授权（§5.3）后执行
     Deny            → 工具结果 error[denied]，附用户备注（若有）
  运行取消 → 未答问题 status=closed，事件 question.closed{reason: run_ended}
```

`question.asked` 的数据（字段只加不改，13）：

```rust
// 草案，以实现为准
pub struct QuestionAsked {
    pub question: QuestionId,
    pub kind: QuestionKind,            // Approval | Ask（ask_user，07 §10）
    pub run: RunId,
    pub call: Option<CallId>,
    pub origin_run: Option<RunId>,     // 子代理冒泡时的发起运行
    pub tool: String,
    pub effect: EffectClass,
    pub summary: String,               // 一行英文摘要（Assessment.summary）
    pub targets: Vec<TargetView>,      // 路径（域 + 相对路径）、命令 argv、URL
    pub diff: Option<BlobRef>,         // Writes 的补丁预览（07 §9.2）
    pub sandbox: SandboxView,          // backend、abi、写根、"network: not restricted"
    pub risk: Risk,
    pub choices: Vec<Choice>,          // AllowOnce | AllowForSession | Deny；Dangerous 时不含 AllowForSession
    pub session_key_preview: Option<String>, // “本会话同意”将覆盖的范围，如 `run_command: cargo test *`
}
```

- 审批界面必须显示 `sandbox` 与 `session_key_preview`：用户要知道“同意本会话”到底同意了什么，以及网络不受限。
- 一个回合内同时至多一个待答审批：组内需要审批的调用按规范顺序逐个提问，前一个回答后才发下一个（03 §6.2 第 3 条）。
- 用户备注（`note`）以 **trusted** 文本进入工具结果：`error[denied]: user denied run_command "rm -rf build": note: "use cargo clean instead"`。备注只来自已通过 §5.6 身份校验的回答者。

### 5.2 自动策略

```toml
# 草案；默认值唯一来源在 gqy-config
[approval]
read            = "allow"   # ReadOnly
presentation    = "allow"
writes_in_scope = "allow"   # 写根内的 Writes；写根外由档位直接拒绝
exec_sandboxed  = "ask"     # 在可用沙盒内的 Exec
exec_unsandboxed = "ask"    # 无后端平台上 Owner 的 Workspace Exec（§4.1）；只接受 ask | deny；"本会话同意"可覆盖
exec_full       = "allow"   # Full 档位宿主直跑；Dangerous 仍强制 Ask（§4 第 4 步）
network         = "ask"
auto_allow_commands = ["git status", "git diff", "git log", "ls", "cargo check", "cargo test", "cargo clippy", "cargo fmt --check"]
```

- 值域 `allow | ask | deny`。`exec_unsandboxed` 只接受 `ask | deny`，配置为 `allow` 时校验报错（配置加载失败并指出字段）。
- `auto_allow_commands`：按 argv 前缀匹配（§5.3 的同一匹配器），只在沙盒可用时生效。
- persona 可以把策略**收紧**，不能放宽超过全局配置（12）。

### 5.3 会话授权与审批键

`AllowForSession` 写入 `session_grants` 表（会话级，随会话持久化，重启后仍有效；`/grants` 命令查看与撤销；表草案见 10 §7.4）。匹配键由工具的 `assess` 给出：

| 工具 | `approval_key` | 例 |
| --- | --- | --- |
| `run_command` | 分词后的 `argv[0]` + 第一个非选项子命令，前缀匹配 | `cargo test`（覆盖 `cargo test -p x`） |
| `run_command`（含 shell 元字符 `\| ; & $ \` > < ( )` 或 here-doc） | 完整命令字符串精确匹配 | `make 2>&1 \| tee log` |
| `write`/`edit`/`apply_patch`（写根外，仅 Full 档位） | 目标文件的父目录 | `/etc/nginx/` |
| `web_fetch` | URL 的 scheme + host | `https://docs.rs` |
| `pty_open` | 同 run_command | `htop` |
| MCP / 脚本工具 | 工具真名 | `mcp_github_create_issue` |

- 分词用 POSIX shell 词法（引号、转义），失败则退回精确匹配。
- 授权不跨会话、不跨 principal；子代理继承父会话的授权（只读快照）。
- 撤销：`DELETE /api/v1/sessions/{id}/grants/{grant}`，立即生效（按请求查库，02 §8）。

### 5.4 命令策略、危险识别与回收站

**deny 规则**（`command_policy.deny`，匹配分词后的 argv；默认集合）：

| 规则 id | 匹配 | 说明 |
| --- | --- | --- |
| `deny.rm_root` | `rm` 带 `-r`/`-R`/`--recursive` 且任一目标规范化后为保护目标（下表） | 递归删除系统或根目录 |
| `deny.mkfs` | `mkfs`、`mkfs.*`、`wipefs` | 格式化 |
| `deny.dd_dev` | `dd` 且 `of=/dev/*` | 写块设备 |
| `deny.power` | `shutdown`、`reboot`、`poweroff`、`halt`、`systemctl poweroff/reboot` | 关机重启 |
| `deny.forkbomb` | 字面量 `:(){ :\|:& };:` | fork 炸弹 |
| `deny.chmod_root` | `chmod`/`chown` 带 `-R` 且目标为保护目标 | 递归改权限 |

**危险（强制 Ask，不受授权影响）**：`rm` 带递归或通配符、`git push --force`/`-f`、`git reset --hard`、`git clean -f*`、`sudo`/`doas`、管道到 shell（`curl … | sh`、`wget … | bash`）、写 `~/.bashrc` 等 shell 启动文件。

诚实声明：**命令策略是减速带，不是安全边界**。shell 足够灵活，任何黑名单都能被绕过（变量拼接、`eval`、脚本文件）。真正的边界是能力档位与沙盒；命令策略只防“模型顺手打错”和提升审批时的可见性。

**回收站**（`trash` 工具与补丁 `Delete`）：拒绝目标为规范化后等于以下任一路径——`/`、`/bin`、`/boot`、`/dev`、`/etc`、`/home`、`/opt`、`/proc`、`/root`、`/run`、`/sbin`、`/sys`、`/tmp`、`/usr`、`/var`（v1 的 15 项），加上 macOS 的 `/System`、`/Library`、`/Applications`、`/Users`、`/private`，以及工作区根、家目录、回收站目录本身（Linux `~/.local/share/Trash`、macOS `~/.Trash`）、GQYv2 数据目录。回收站后端不可用（无桌面回收站规范、跨设备卷）时，**不退化为删除**，返回 `error[unsupported]` 并说明原因。

### 5.5 非交互场所

| 场所 | 需要 Ask 时 |
| --- | --- |
| `Timer`、`Job` | 只使用创建时写入任务的**预授权集**（创建者在交互场所中确认过的效果类别与审批键）；不在集内 → `Deny`，结果 `error[denied]: approval required but venue is non-interactive (timer)`，并发 `question.unanswerable` 通知事件供 UI 提醒 |
| `Subagent` | 冒泡给父运行：`question.asked` 带 `origin_run`，由父会话的交互客户端回答；父场所也非交互时按父场所规则 |
| `Cli`（`gqy ask`） | 默认非交互（12 §6.2）：`--approve=never`（默认）→ Deny；`--approve=policy` 只用自动策略；`--approve=prompt` 需要 TTY，等同 `--interactive`，场所变为交互式并逐次询问。退出码见 13 §9 |
| `Connector{..}` | External 场所工具面中无需要审批的宿主工具；Owner 通过连接器私聊时，审批以“回复 1/2/3”文本交互（16），回答者身份按平台真实 ID 校验 |
| `Review`（聊后复盘） | 只有 `ReadOnly`/`Presentation` 与记忆工具，不产生审批 |

### 5.6 谁能回答

- 回答者的 principal 必须等于会话 principal，或是 Owner（本机账户）。Member 只能回答自己会话的问题。
- External 永远不能回答审批。连接器转来的文本即使内容是“同意”也不构成回答——回答只经 `SessionCmd::Answer`，而连接器入口不产生 Approval 的 Answer，除非 §5.5 的 Owner 私聊路径并校验平台 ID。
- 模型输出永远不能回答问题（回答不是账本条目的解析结果）。

## 6 沙盒与路径守卫

### 6.1 进程内路径守卫

内置文件工具在 daemon 进程内执行，Landlock 无法只约束某次调用（它约束整个线程/进程），所以文件工具靠路径守卫：

1. 拒绝含 NUL 的路径；相对路径相对工作区根解析。
2. 规范化：对已存在的最长前缀做 `realpath`（解析符号链接），再拼接剩余部分，拒绝剩余部分中的 `..`。
3. 与 `WorkspaceScope` 的读根 / 写根、保护路径比较（按路径组件比较，不按字符串前缀——`/work2` 不属于 `/work`）。
4. 打开文件：Linux 5.6+ 有 `openat2` 时用 `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS` 相对根目录 fd 打开，关闭“检查与使用之间”的符号链接竞争；没有时退回“规范化 + 打开后 `fstat` 比对 dev/ino”，并在 `gqy doctor` 标注“路径守卫存在 TOCTOU 窗口”。
5. 写入：同目录临时文件 + `rename`（07 §9.2）；不跟随目标本身是符号链接的情况（写符号链接指向的文件需要该文件本身在写根内）。

守卫实现只有一份（`gqy-tools::guard`），存储域 `artifact:`、`kb:` 不走文件系统守卫而由域自身按 principal 隔离（07 §9）。

### 6.2 Linux：Landlock 后端

实现在 `gqy-sys::sandbox::landlock`（01 §3，唯一允许 unsafe 的 crate）。

- **ABI 探测**：daemon 启动时调用 `landlock_create_ruleset(NULL, 0, LANDLOCK_CREATE_RULESET_VERSION)`；返回值 ≤ 0（内核未编译、被 LSM 列表禁用、seccomp 拦截）→ `Unavailable{reason}`。结果进入 Host 感知（09），每 10 分钟与 `gqy doctor` 时复测。
- **访问位按 ABI 取**：ABI 1 基础文件访问；ABI 2 加 `REFER`（跨目录 rename/link）；ABI 3 加 `TRUNCATE`；ABI 5 加 `IOCTL_DEV`。v2 **要求 ABI ≥ 1**，并对需要的位使用“硬要求”模式（`landlock` crate 的 `CompatLevel::HardRequirement`）：某个声明的位在当前 ABI 不存在时，降低 handled 集合而不是报错，但必须在 `SandboxView` 中列出“未受控的访问类型”（例如 ABI 1 下跨目录 rename 不受控）。
- **规则集**：

| 路径 | 访问 |
| --- | --- |
| 工作区根（写根） | 读、写、执行、建删 |
| 会话私有临时目录 `<data>/run/tmp/<session>/`，经 `TMPDIR` 传入 | 读写；会话卸载时清理 |
| `/dev/null`、`/dev/zero`、`/dev/urandom`、`/dev/tty`（PTY 时） | 读写 |
| `/usr`、`/bin`、`/sbin`、`/lib*`、`/etc`、`/opt`、`/nix/store`（存在者） | 读、执行 |
| `extra_read_roots`（配置，如 `~/.cargo`、`~/.rustup`） | 读、执行 |
| `extra_write_roots`（配置，如 `~/.cargo/registry`） | 读写；审批界面显示 |

  不存在的根先剔除（Landlock 对打不开的根是失败关闭）；但**写根不存在时整体失败**，不静默丢掉写根。
- **不在规则集中**：数据目录（含 `run/gqy.sock`、`run/local.token`、`config/`、`gqy.db`）、`$HOME` 其余部分、`/tmp`（改用私有临时目录）。
- **硬规则（00 §5 已定）**：任何沙盒后端的策略都必须拒绝读取数据目录下的 `run/` 与 `config/`（本地令牌与密钥所在），`extra_read_roots` / `extra_write_roots` 配置若覆盖这两个目录，配置校验失败。沙盒内进程即使能 `connect()` 到 `gqy.sock`，也拿不到本地令牌，UDS 请求一律 401（13 §8.1）。守护：沙盒内 `cat <data>/run/local.token` 与 `cat <data>/config/secrets.toml` 必须失败，去掉该规则测试变红。
- **施加时机**：`Command::pre_exec` 中，fork 后 exec 前：建规则集 → 逐条 `add_rule` → `prctl(PR_SET_NO_NEW_PRIVS)` → `landlock_restrict_self`。路径在 fork 前转为 `CString` 并打开 fd，`pre_exec` 中不分配内存。任一步失败 → 子进程 `_exit(126)` 并经管道回报 errno，父进程报告 `error[sandbox_unavailable]: landlock_restrict_self failed: EPERM`。
- 同时施加的资源限制：`RLIMIT_CORE = 0`，`RLIMIT_NOFILE = 4096`，可选 `RLIMIT_AS`（默认不设，避免误伤 JIT 运行时）。
- **不覆盖（明文）**：
  - **网络**：不限制。Landlock ABI 4 能限制 TCP bind/connect，但不管 UDP、DNS、Unix socket，只做一半会给出错误的安全感，第一版不用（Q-08-3）。
  - 已继承的文件描述符：子进程只继承 stdin/stdout/stderr（与 PTY），其余 fd 一律 `CLOEXEC`，由测试钉住。
  - 进程间信号与抽象 Unix socket：ABI 6 起才有作用域限制，探测到则启用，否则在 `SandboxView` 标注。
  - 读取系统只读目录中的敏感文件（如 `/etc/shadow` 由 L1 的文件权限保护，不由沙盒保护）。

### 6.3 子进程环境

- 命令用 `sh -c`，不使用 login shell（v1 用 `sh -lc`，会加载用户 profile，把 profile 中导出的密钥带进子进程）。
- 环境变量白名单：`PATH`、`HOME`（工作区根或真实家目录，按档位）、`LANG`、`LC_*`、`TERM`、`TZ`、`USER`、`SHELL`、`TMPDIR`（私有临时目录）、`COLUMNS`/`LINES`（PTY），加配置 `exec.env_passthrough`。**其余全部清除**，包括供应商密钥与所有 `GQY*` 变量。
- 独立进程组；超时与取消按 02 §6 整组终止。

### 6.4 macOS（D-02 待定）

- **现在**：没有沙盒后端，`SandboxAvailability = Unavailable{reason: "no sandbox backend on macos"}`。按 §4 第 3 步与 §4.1（00 §5 已定）：Member / External 场所在 macOS 上没有 `Exec`；Owner 的 `Workspace` 档位 Exec 无沙盒运行、每次审批（卡片标注 unsandboxed，可“本会话同意”）；`Full` 档位宿主直跑。Seatbelt 落地后自动切为沙盒内执行。
- 路径守卫（§6.1）在 macOS 上照常生效（它不依赖内核沙盒）；`openat2` 不存在，走退回路径并标注 TOCTOU。
- **Seatbelt 研究项**（D-02 推荐：单独验证后再决定；若采用，配置文件同样必须拒绝读取 `run/` 与 `config/`，§6.2 硬规则）：用 `sandbox-exec -p <profile>` 启动子进程，配置文件形如 `(version 1)(deny default)(allow process-exec process-fork)(allow file-read* (subpath "/usr") …)(allow file-write* (subpath "<workspace>"))`。验证清单：① 在当前 macOS 版本上仍可用、弃用警告的实际影响；② 对 `/dev/tty`、PTY、`xcrun` 工具链的兼容性；③ Seatbelt **能**限制网络（`(deny network*)`），这是 Landlock 没有的，若采用需在文档里写清两平台的差异；④ 失败时的错误形态与探测方法；⑤ 与 App Sandbox（桌面宿主签名分发时）的关系。研究结论写回本节并由用户确认。

### 6.5 Windows 与其他平台

平台范围已定（00 §5，2026-09-28）：Linux 与 macOS 完整成立；Windows 要求能编译、能跑单元测试，缺失的能力失败关闭。本节只规定 Windows 上的失败方式，不设计 Windows 支持。

- **沙盒**：Windows 没有后端，`SandboxAvailability = Unavailable{reason: "no sandbox backend on this platform"}`。凡策略要求沙盒的 `Exec` 一律拒绝（§4 第 3 步），错误文本 `error[sandbox_unavailable]: command execution refused: no sandbox backend available`。§4.1 的“无后端平台上 Owner 无沙盒 Exec + 审批”规则**不适用于 Windows**：Windows 上连进程组终止、PTY 这些 02 §6 依赖的原语也没有实现（见下），第一版一律拒绝 Exec，`Full` 档位同样拒绝。
- **子进程原语**：进程组整组终止、SIGTERM/SIGKILL 宽限流程、PTY 都由 `gqy-sys` 暴露为能力（`HostCap::ProcessGroup`、`HostCap::Pty`，09 §4.1）。能力缺失时，依赖它们的工具在编译期被排除（07 §5.1），运行期的调用点也按能力判断，不以 `cfg!(target_os)` 分支业务逻辑。
- **路径守卫**：守卫的组件比较与保护路径在 Windows 上也要编译通过；Windows 路径语义（盘符、UNC、大小写不敏感、`\\?\` 前缀）的完整处理不在第一版范围。只读与写入文件工具在 Windows 上是否开放取决于守卫能否证明路径在根内——不能证明时拒绝（失败关闭）。
- **回收站**：Windows 回收站后端未实现 → `HostCap::Trash = Missing`，`trash` 工具不编译，补丁 `Delete` 返回 `error[unsupported]`（§5.4，不退化为删除）。
- **单元测试**：判定函数（§4）、命令策略分词、审批键匹配、脱敏都是纯函数，必须在 Windows CI 上运行；Landlock 实测与进程组测试在 Windows 上以 `cfg` 排除，并在测试日志中打印“因平台能力缺失跳过”。

其他平台（BSD 等）同理：无后端即 `Unavailable`，行为同 macOS 现状，只在 `gqy doctor` 描述能力（09）。

**代码约束**：业务 crate（`gqy-tools`、`gqy-engine` 等）不出现 `cfg(target_os = …)`；平台差异只在 `gqy-sys` 内部，由 `cargo xtask arch` 扫描 `target_os` 出现位置钉住（测试代码与 `gqy-sys` 除外）。业务代码问“这里能不能做 X”（`HostFacts::has(HostCap::…)`），不问“这是不是 macOS”。

## 7 场所信任映射

| 信任级 | 典型场所 | 档位上限 | 宿主工具（host） | 沙盒 | 可回答审批 |
| --- | --- | --- | --- | --- | --- |
| `Owner` | Tui、Web（本机 owner 账户）、Cli、Desktop、Owner 私聊连接器 | `Full`（默认 `Workspace`） | 有 | `Workspace`：有后端则沙盒内，无后端则无沙盒 + 审批（§4.1）；`Full`：宿主直跑 | 是 |
| `Member` | Web 成员账户 | `Workspace` | 有，限本人工作区 | **强制**；无后端则无 Exec | 本人会话 |
| `External` | Connector 群聊 / 陌生人私聊 | `ReadOnly`，且工具面中无 host 工具 | **永不** | 不涉及 | 否 |
| `Internal` | Timer、Job、Subagent、Review | 继承创建者，且不超过父运行当前档位 | 继承 | 继承 | 冒泡或预授权（§5.5） |

- External 的工具面由 07 §5.1 第 2 步在编译期剔除宿主工具；即使模型“知道”工具名，调用也只会得到 `unknown_tool`。v1 “群聊非管理员永远拿不到宿主工具”在 v2 由类型与编译保证。
- 身份只信平台真实 ID，不信昵称；principal 随会话冻结（12、16），编码为 10 §4.4 的 v1 兼容形式 `principal:<24hex>`。
- External 的限流（v1 游客 2 次 / 600 s）属于准入层（03、16），不在本文判定函数中。

## 8 边界与失败模式

| 情形 | 行为 |
| --- | --- |
| Landlock 在 daemon 启动后变为不可用 | 下次探测更新 Host；已有会话下一次 Exec 判定即拒绝；UI 显示横幅 |
| 写根被删除 | Exec 失败关闭并报写根不存在；文件工具报 `not_found` |
| 审批等待期间 daemon 停机 | 重启恢复时问题标 `closed{expired}`，运行按 02 §9 恢复为 `Interrupted`（03 §13） |
| 两个客户端同时回答 | 先到先得，后到者收到 `409 question_already_answered` |
| 会话授权命中但沙盒不可用 | 非 Owner：第 3 步先拒绝，授权不能绕过失败关闭；Owner：只有带 `unsandboxed:` 前缀的授权（在无沙盒审批卡片上给出）才会命中 |
| 配置 `exec_unsandboxed = "allow"` | 配置校验失败，daemon 拒绝加载该配置，保留旧快照（12） |
| 模型在参数里伪造 `approved: true` | 无效：审批不读参数；未知字段按 07 §7.2 处理 |

## 9 审计与密钥

### 9.1 审计记录

`audit_log` 表（gqy.db，只追加，迁移纪律见 10）每条对应一次判定或一次执行：

| 字段 | 说明 |
| --- | --- |
| `seq`、`ts` | 全局序号与时间 |
| `session`、`run`、`call`、`question` | 关联 ID |
| `principal`、`venue_kind`、`trust` | 身份 |
| `tool`、`effect`、`mode` | 调用与当时档位 |
| `decision`、`layer`、`rule_id`、`decided_by` | `allow/ask/deny`；`decided_by` = `policy:<id>` / `grant:<id>` / `user:<principal>` / `auto` |
| `args_digest`、`args_summary` | 原始参数的 blake3 与脱敏后的摘要（原文在账本 Raw 通道，07 §7.2） |
| `sandbox` | backend、abi、策略哈希、未受控访问类型 |
| `exit`、`duration_ms`、`bytes_out`、`truncated` | 执行结果 |

- 保留期默认 180 天（`audit.retention_days`）。到期删除是 10 §9.3 明文登记的保留作业之一：只删超过保留期的整日数据，每次执行写一行 `gc_runs`；除此之外 `audit_log` 不可 UPDATE、不可 DELETE（10 §4.4 触发器）。
- 查询：`GET /api/v1/audit?session=&since=`（仅 Owner），TUI `/audit`。

### 9.2 事件

`permission.decided`（仅 deny 与 ask 发给 UI）、`question.asked|answered|closed|unanswerable`、`session.mode_changed`、`sandbox.unavailable`。全部登记在 13 §6.2。

### 9.3 密钥不进模型可见文本

- 密钥（供应商 key、连接器 token、MCP env 中标记为 secret 的值）只存在于配置与 OS 钥匙串（12），`ConfigSnapshot` 中以 `Secret<String>` 类型持有，`Debug`/`Serialize` 输出 `[REDACTED]`。
- 任何进入账本的文本（工具结果、错误信息、感知块、钩子输出）在写入前经 `redact_known_secrets`：按当前全部已知密钥值做**精确匹配**替换为 `[REDACTED:<name>]`。这只能挡住已知值，不能识别任意“看起来像密钥”的字符串——文档与 UI 不宣称更多。
- 子进程环境不含密钥（§6.3）；`gqy doctor` 与日志中的配置输出也走同一脱敏函数。
- 守护：测试中配置一个假密钥，让工具输出包含它，断言账本、事件、审计、日志四处都找不到原值。

```toml

[command_policy]
```

## 11 测试与守护

- **判定表测试**：以 (trust × mode × effect × sandbox × grant × interactive) 做笛卡尔表驱动测试，期望表与 §4、§4.1、§7 一一对应；删掉 §4 任何一步，至少一行变红。
- **失败关闭**：注入 `SandboxAvailability::Unavailable`，断言 Exec 被拒且子进程从未 spawn（用 spawn 计数器）；移除第 3 步后测试变红。
- **Landlock 实测**（Linux CI，需要内核支持；不支持时测试以“跳过并打印原因”结束，CI 另有一台保证支持的 runner）：沙盒内 `touch $HOME/x` 失败、`touch $WORKSPACE/x` 成功、`cat <data>/run/daemon.json` 与 `cat <data>/run/local.token` 失败、`cat <data>/config/gqy.toml` 失败、`nc -U gqy.sock` 失败或无令牌被 401、`ls /proc/self/fd` 只有 0/1/2。
- **路径守卫**：符号链接逃逸（工作区内链接指向 `/etc`）、`..` 逃逸、`/work2` 对 `/work` 前缀混淆、大小写不敏感文件系统（macOS）上的 `WORKSPACE/../Workspace` 各一例。
- **审批流程**：mock 供应商触发 `run_command`，测试客户端收到 `question.asked` 后分别回答三种选择，断言工具结果、授权表、审计；会话授权后同前缀命令不再提问，Dangerous 命令仍提问。
- **非交互**：Timer 场所无预授权时 Exec 被拒且回合不挂起（在 1 s 内得到结果）。
- **Windows 失败关闭**：Windows CI 上以 `SandboxAvailability::Unavailable` 构造判定输入（真实探测结果），断言 Owner/Full 下 `run_command` 被拒且未 spawn；§4 判定表测试整体在 Windows CI 运行。
- **平台分支扫描**：`cargo xtask arch` 断言 `gqy-sys` 之外的非测试代码中没有 `target_os`。
- **External 场所**：连接器场所的工具面快照中不存在任何 `host: true` 工具（形状夹具 `chat.external.connector.stub`，07 §12.1）。
- **密钥**：§9.3 守护。
