# 12 · 人格、配置与场所

> 状态：【规划】。前置阅读：00、01、02、[10 存储与数据演进](10-存储与数据演进.md)。本文定义配置文件、默认值的唯一来源、保存与热加载、密钥、persona（提示词 + 启用集）与代际、场所（Venue）注册表、会话创建时的 Surface 快照、system 段的组装顺序，以及模型可见文本的语言规则。工具面编译见 07，请求布局与字节契约见 04，权限判定见 08。

## 1 目标

1. **一个概念一个真相源。** 配置默认值只在 `gqy-config` 定义一次；persona 是唯一的配置单位，不存在另一套“模式”（00 §1.3）。
2. **决定构造什么，而不是装上再关。** persona 启用集与场所共同决定会话的工具面和子系统，在会话创建时快照并冻结。
3. **配置可热加载，但不破坏前缀。** 新配置在下一回合生效；会影响前缀字节的内容只在计划内的时机生效（新会话、压缩、显式重载）。
4. **保存只有一个写者。** 任何入口保存配置都走同一条原子写入路径，secret 不会被并发保存回滚。

## 2 v1 教训

- 【v1 实测】`AgentMode`（normal/dev）与 persona 清单两个真相源并存：`AgentMode` 有 336 处引用、分布在 61 个文件；迁移停在一半，因为一动就改变提示词字节。`AgentTurnControl` 同时持有 `normal_tools` 与 `dev_tools` 两份注册表。
- `update_config` 并发保存时互相静默回滚 secret；配置、密钥在同一个 JSONC 文件中。
- 前端的配置默认值是从 Rust 手抄过去的，schema 分布在 3 个文件、共 3.2k 行。
- `ProviderConfig` 全字段 `serde(default)`，新增供应商不改代码。这一点做对了，v2 保留。
- v1 的 persona 目录只有 `persona.toml`（启用集）与记忆库，提示词却在 `data/prompts/*.md` 与配置项 `system_prompt_file` 里，靠名字关联。`persona.toml` 中 `subsystems.persona_reminder`、`subsystems.emotion` 是否真的被读取，v1 架构说明书列为待验证（U4）。
- 入口表之外还有 5 个回合发起方（goal driver、job-wake、scheduled_messages、private_initiative、voice）没有被当作场所建模，因此没有统一的信任级与能力声明。
- persona 热编辑：当前回合冻结，下一回合原子切换代际并注入一次 `<memory-update>`；指纹拆为 `persona_compatibility_id` 与 `wire_prompt_hash`，指纹变化只算一次计划内冷启动（v1 曾因指纹变化删除历史，缺陷 C1）。

## 3 配置文件

### 3.1 位置与格式

- 主配置 `config/gqy.toml`，TOML 格式（**D-07 待定**；v1 为 JSONC，导入器负责转换，见 20）。权限 0600。

### 3.3 默认值的唯一来源

```rust
// 草案，以实现为准
#[derive(Clone, Debug, Serialize, Deserialize, JsonSchema, TS)]
#[serde(default, deny_unknown_fields = false)]
pub struct Config {
    pub daemon: DaemonConfig,
    pub timeouts: TimeoutsConfig,
    pub providers: BTreeMap<ProviderId, ProviderConfig>,
    // …
}

/// 每个字段的元数据，由 schema 生成器读取。
pub struct FieldMeta {
    pub apply: Apply,              // NextTurn | NewSession | Restart
    pub bounds: Option<Bounds>,    // 数值上下界（02 §6：可放宽到上限，不能关闭）
    pub secret: bool,              // 只允许 key_ref，不允许明文
}
```

- 每个配置结构体都实现 `Default`，并在结构体级别使用 `#[serde(default)]`。字段的默认值只出现在 `Default` 实现里，不出现第二处。
- 同一份 Rust 类型生成三样东西，全部由 `cargo xtask gen` 产出并由 CI 校验无漂移：
  1. **JSON Schema**（`schemars`）：带 `x-gqy-apply`、`x-gqy-bounds`、`x-gqy-secret` 扩展，经 `GET /api/v1/config/schema` 提供给 Web 设置页，页面据此渲染表单，不手写字段；
  2. **TS 类型**（`ts-rs`，01 §3 中 `gqy-protocol` 的 feature）；
  3. **带注释的默认配置**：`gqy config defaults` 打印，注释来自字段的文档注释。
- 校验在 `Config::validate()` 中集中进行：越界、引用不存在的 provider/persona、`key_ref` 指向不存在的 secret 等，都返回带路径的错误列表（`providers.openai.models[2]: expected non-empty string, got ""`）。

### 3.4 保存：单写者、原子写

- daemon 运行时，唯一写者是 daemon 内的 `ConfigService`（持有 `ArcSwap<Config>`，02 §8）。CLI 的 `gqy config set` 与 Web 设置页都通过 API 提交**修改操作**（路径 + 新值），而不是整份文件。
- daemon 未运行时，CLI 直接写文件，先对 `config/.lock` 加 `flock` 独占锁。
- 保存流程：
  1. 取锁；读取当前文件字节，计算 `revision = blake3(bytes)`；
  2. 请求携带的 `If-Match` 修订号与 `revision` 不同时返回 409（`ConfigConflict`），客户端重新读取；
  3. 用 `toml_edit` 在文档上应用修改操作，保留注释与未知键；
  4. 解析得到 `Config`，执行 `validate()`，失败则返回错误列表，文件不动；
  5. 写 `gqy.toml.tmp-<pid>`（0600）→ `fsync` → `rename` → `fsync` 目录；
  6. 替换 `ArcSwap`，广播 `config.changed { revision, changed_paths }`。
- 外部编辑（用户用编辑器改文件）：daemon 每 2 s 检查 mtime 与大小，变化时重新加载并校验；校验失败保留旧配置，广播 `config.invalid { errors }`，`gqy doctor` 显示。

### 3.5 热加载语义

每个字段在 schema 中声明生效时机：

| `apply` | 含义 | 例子 |
| --- | --- | --- |
| `NextTurn` | 下一个回合开始时的 `ConfigSnapshot` 生效（02 §4）；进行中的回合不受影响 | 超时、压缩阈值、记忆召回参数、供应商投放层（`keepalive`、`write_grace_ms`） |
| `NewSession` | 只影响之后新建的会话；已有会话的 Surface 快照不变（§7） | 默认 persona、默认模型绑定、`tools.loading_mode`、场所能力收窄 |
| `Restart` | 需要重启 daemon；`config.changed` 事件中标出 `restart_required` | 监听地址、数据目录、`[store]` 连接参数 |

会改变请求前缀字节的配置一律不是 `NextTurn`。这条规则由测试守护：把每个 `NextTurn` 字段逐一改成非默认值，mock 供应商断言下一轮请求仍然是上一轮的字节前缀延伸（04 门禁）。

## 4 密钥

- 配置中只允许出现**引用**：`key_ref = "secret:openai_main"`。`FieldMeta.secret = true` 的字段出现明文值时校验失败，并提示使用 `gqy secret set`。
- 存储后端（Q-12-1 待定）：
  - `file`（推荐首版默认）：`config/secrets.toml`，0600，键值对，单写者、原子写，流程同 §3.4；
  - `keychain`（可选）：macOS Keychain / Linux Secret Service，不可用时失败并提示，不回退到明文。
- 环境变量 `GQY2_SECRET_<NAME>` 可覆盖同名 secret，便于 CI 与容器环境（前缀见 D-01）。
- API 只提供写入与存在性查询：`PUT /api/v1/secrets/{name}`、`GET` 返回 `{ name, set: true, hint: "sk-…a1b2" }`，永不回传明文。
- 导出（10 §11）、备份清单、日志、`gqy doctor` 输出都不包含 secret 值；tracing 层对 `SecretString` 类型实现只输出 `***` 的 `Debug`。
- 多 key 轮转：`key_ref` 可以是数组，轮转与冷却逻辑见 06。

## 5 persona

### 5.1 目录格式

```text
personas/<persona_id>/
├── persona.toml       清单（必需）
├── prompt.md          私有版核心提示词（必需）
├── public.md          公开版核心提示词（可选；缺失时该 persona 不能用于 External 场所）
├── relations/         与特定 principal 的关系档案（可选，只在 privileged 场所注入）
│   └── <principal>.md
└── avatar.png         头像（可选）
```

`persona_id` 限定为 `[a-z0-9][a-z0-9_-]{0,31}`；显示名放在清单里。

### 5.2 清单

```toml
# 草案，以实现为准
id = "guqingying"
display_name = "顾清影"
description = "Companion persona for chat and daily help."
compatibility = 1                  # 手工递增：改变“人设语义”的大改时 +1

[enable]
subsystems = ["memory", "skills", "kb", "review"]   # 子系统启用集
toolsets   = ["core", "web", "media"]               # 工具集（07 定义工具集名称）
skills     = []                    # 空 = 全部已安装技能；写了就是白名单
mcp        = []                    # 同上，MCP 服务器 id
scripts    = []                    # 同上，脚本工具 id

[venues]
allow = ["tui", "web", "desktop", "cli", "connector"]  # 可以被哪些场所类别使用

[model]
tier = "standard"                  # 未绑定具体模型时的默认档位（06）
```

- 未知的子系统名、工具集名在校验时报错并列出合法值（v1 `PersonaManifest::validate` 的做法）。
- 退役名字（例如 v1 的 `deep_research`）由一张常量表声明，读到时给出 `warn` 而不是报错。

### 5.3 内置 persona

| id | 启用集 | 用途 |
| --- | --- | --- |
| `dev` | `subsystems = []`，`toolsets = ["core"]`（**core_only**） | 编码；取代 v1 的 `AgentMode::Dev` |
| `default` | 全部子系统，`toolsets = ["core", …已安装]` | 首次运行的默认 persona |

内置 persona 嵌入二进制；用户在 `personas/dev/` 下放同名目录即覆盖（整目录覆盖，不做字段合并）。

**不存在“模式”。** 代码中没有 `AgentMode` 或任何“dev 模式”布尔。切换到编码工作就是换用 `dev` persona，而换 persona 意味着新会话（§7.3）。守护见 §10。

### 5.4 代际（generation）

- `PersonaSnapshot { id, generation, compatibility, content_hash, manifest, prompt_private, prompt_public, relations }`。`content_hash = blake3(清单规范化字节 ‖ 各提示词文件字节)`。
- `persona_generations(persona_id, generation, content_hash, compatibility, created_at)` 追加型表（10 §7.6）：daemon 加载 persona 时，若 `content_hash` 与最新一行不同，就插入新行并使 `generation + 1`。
- 目录监视：每 2 s 检查 mtime；变化后重新加载并校验。校验失败时保留旧代际并发出 `persona.invalid`。

### 5.5 代际如何进入已有会话

会话在创建时冻结 `(persona_id, generation)`（§7）。persona 被编辑后：

| 时机 | 行为 |
| --- | --- |
| 进行中的回合 | 不受影响（02 §4 快照语义） |
| 已有会话的后续回合 | 仍使用冻结的代际，前缀不变 |
| 该会话下一次压缩（05） | 压缩本来就是唯一的前缀改写点；压缩时采用 persona 的最新代际重新渲染 system 段，并记 `context_rewrite reason=persona_generation` |
| 用户执行 `/persona reload` | 立即做一次计划内冷启动：重新渲染 system，记同样的日志；不删除任何历史（修正 v1 缺陷 C1） |
| 新会话 | 使用最新代际 |

`compatibility` 发生变化（人设大改）时，旧会话在下一回合前提示用户：继续使用旧代际，或 `/persona reload`。不自动切换。

v1 的做法是“下一回合原子切换并注入一次 `<memory-update>`”，它会在会话中段改写 system。v2 把切换点收敛到压缩与显式重载，见 Q-12-2。

### 5.6 公开版与私有版

- 会话创建时按场所选择提示词版本：`Trust::Owner` 或 `Member` 的私聊用 `prompt.md`；`External` 以及任何群聊场所用 `public.md`。没有 `public.md` 的 persona 不能绑定到这些场所，绑定时报错 `PersonaNotPublic`。
- `relations/<principal>.md` 只在 `privileged` 场所、且会话 principal 与文件名匹配时注入。
- 安全规则（谁能用哪些工具、群聊禁止宿主工具等）不写在任何提示词里，由 08 的代码判定（铁律 7）。提示词里的“你不能……”只是体验层的文字，不承担鉴权。

## 6 场所（Venue）

### 6.1 定义

```rust
// 草案，以实现为准（类型位于 gqy-core）
pub struct Venue {
    pub kind: VenueKind,
    pub trust: Trust,          // Owner | Member | External | Internal
    pub caps: VenueCaps,
    pub interactive: bool,     // 是否有人在场、能实时回答 Question
}

pub enum VenueKind {
    Tui, Web, Cli, Desktop,
    Connector { platform: PlatformId, conversation: ConversationKind /* Private | Group */ },
    Room { room: RoomId },       // 聊天室成员会话（16 §9）
    Timer, Job, Subagent, Review,
    Mesh { device: DeviceId },
}

/// 场所类别的调度与上下文声明；属于注册表常量（§6.2），不随请求变化。
pub struct VenueDecl {
    pub quota: QuotaClass,             // 场所配额类别（02 §3.1、03 §4）：Interactive | Connector | Timer | Internal
    pub supersede_on_new: bool,        // 新提交是否让会话代际 +1、覆盖旧运行（03 §5.2）
    pub coalesce: Option<CoalescePolicy>, // 队列合并策略（03 §5.1，细节归 16）
    pub context_profile: ContextProfile,  // Coding | Chat：压缩模板与尾巴预算（05 §5.1、§6.4）
}

pub struct VenueCaps {
    pub questions: bool,        // 能否展示并回答审批/提问（08）
    pub markdown: bool,
    pub images_out: bool,
    pub files_out: bool,
    pub streaming: bool,
    pub max_message_chars: Option<u32>,
}
```

### 6.2 注册表

每种场所类别的默认值集中在一张常量表中。配置 `[venues.<kind>]` 只能**收窄**能力，不能放宽（放宽会绕过 08 的判定前提）。

| VenueKind | trust 来源（代码判定） | interactive | questions | 说明 |
| --- | --- | --- | --- | --- |
| `Tui` | UDS：本地令牌（13 §8.1，主）+ 对端 uid = daemon uid（附加检查）→ Owner | 是 | 是 | |
| `Web` | 登录账号角色：owner → Owner，member → Member | 是 | 是 | |
| `Cli`（`gqy ask`） | 同 Tui | 默认否；`--interactive` 时是 | 同 interactive | 非交互时审批一律拒绝（08） |
| `Desktop` | 进程内 → Owner | 是 | 是 | |
| `Connector{platform, Private}` | owner 账号列表 → Owner；已授权 → Member；其余 → External | 是 | 仅 Owner | 平台昵称不参与判定 |
| `Connector{platform, Group}` | 同上，但宿主工具永远不可用（08） | 是 | 否 | 记忆可见性见 11 §3.2 |
| `Timer` | Internal，scope 继承创建者 | 否 | 否 | 替代 v1 scheduled_messages、alarm |
| `Job` | Internal，scope 继承创建者 | 否 | 否 | 替代 v1 job-wake、goal driver |
| `Subagent` | Internal，能力不超过父运行 | 否 | 否 | 03 |
| `Review` | Internal | 否 | 否 | 11 §8.2 |
| `Room{room}` | Internal；成员会话工具面为空 | 否 | 否 | 16 §9 |
| `Mesh{device}` | 按配对时授予的信任（17） | 视对端 | 视对端 | |

调度与上下文声明（`VenueDecl` 默认值，数值集中在 `gqy-config`；配置只能收窄）：

| VenueKind | 配额类别（默认活动回合） | `supersede_on_new` | 合并 | 上下文档案 |
| --- | --- | --- | --- | --- |
| `Tui`、`Web`、`Cli`、`Desktop` | Interactive（受全局 16） | 否 | 无 | Coding（05 的默认；persona 可声明 Chat） |
| `Connector{_, Private}` | Connector（8，02 §3.1） | **是**（16 §8） | 无 | Chat |
| `Connector{_, Group}` | Connector（8） | 否 | 合并同会话连续消息，上限 20 条（03 §5.1） | Chat |
| `Room{room}` | Connector（8） | 否 | 无 | Chat |
| `Timer` | Timer（4，03 §14） | 否 | 无 | 继承会话 |
| `Job`、`Subagent`、`Review` | Internal（子代理另有独立池，03 §9.3） | 否 | 无 | 继承会话 |
| `Mesh{device}` | Interactive | 否 | 无 | 继承会话 |

v1 的主动发言（private_initiative）与语音作为扩展回归时，必须先在这张表中登记场所类别，才能构造 `TurnRequest`（02 §3.3 要求每个 `TurnRequest` 带 `Venue`）。

## 7 Surface 快照

`principal` 的编码沿用 v1（10 §4.4，文本形式 `principal:<24hex>`），由网关按 `Caller` 推导（13 §8.4），随会话冻结。

### 7.1 会话创建时冻结什么

```rust
// 草案，以实现为准
pub struct SessionSurface {
    pub principal: Principal,
    pub venue: Venue,                    // 创建时的场所
    pub persona: PersonaRef,             // (id, generation, variant: Private|Public)
    pub tool_surface: Arc<ToolSurface>,  // 07：由 persona 启用集 × 场所能力 × 配置编译
    pub surface_hash: SurfaceHash,
    pub model: ModelBinding,             // 06
    pub system: SystemBytes,             // §8 渲染出的 system 段字节，存为 blob
    pub loading_mode: LoadingMode,
}
```

- 这些值写入 `sessions` 行（`WriteOnce` 列）与 `system_blob`（10 §7.2）。会话加载时**从库中读取**，不重新计算。
- 工具面编译函数的输入只有 `(PersonaSnapshot, Venue, ConfigSnapshot 中 NewSession 类字段, 工具注册表)`，是纯函数；同样的输入必须得到同样的 `surface_hash`。

### 7.2 跨入口继续同一会话

- Owner 在 TUI 创建的会话可以在 Web、桌面、CLI 中继续：这些入口都是本机 Owner 场所。每个回合的 `TurnRequest.venue` 反映**实际来源**，用于该回合的尾部 origin 信息（09）与审批能力（08）；会话的 Surface **不随入口重新计算**，工具面与 system 保持不变。
- 准入检查（03）：请求的 principal 必须等于会话 principal；场所 trust 不得低于会话创建时的 trust。不满足时返回 `VenueMismatch`，不会“降级执行”。
- 连接器会话只能从同一个 `session_bindings` 键进入（10 §7.2）。

### 7.3 什么时候换 Surface

只有三种情况：新建会话；压缩时采用新 persona 代际（§5.5）；用户显式执行 `/persona reload` 或 `/model` 切换（记入 `session_model_changes`，并作为计划内冷启动记日志）。换 persona 的 id（例如从 `default` 切到 `dev`）不在会话内进行，而是新建会话并以 `parent_session_id` 关联。

## 8 system 段组装

system 段在 Surface 快照时渲染一次，是请求前缀中 `[S]`（稳定）部分的一段（04 定义整体布局：tools[S] → system[S] → history[A] → 当前 user[E] → 不可信尾部[E] → 可信尾部[E] → runtime 尾部[E]）。本文只规定 system 内部的节与顺序：

| 顺序 | 节 | 来源 | 外壳 |
| --- | --- | --- | --- |
| 1 | `persona` | `prompt.md` 或 `public.md` | `<persona name="…">` |
| 2 | `audience` | 会话 principal 的受众策略：Owner、Member、External、群聊各一段内置英文模板；Owner 场所附 owner 档案 | `<audience>` |
| 3 | `relations` | `relations/<principal>.md`（仅 privileged） | `<relationship>` |
| 4 | `venue-policy` | 场所类别的内置英文策略（输出格式、消息长度、是否可提问） | `<venue-policy>` |
| 5 | `tool-guidelines` | 工具面中启用工具的使用准则（07），按工具名排序 | `<tool-guidelines>` |
| 6 | `skills-index` | 启用技能的名字与一行摘要（18），按名排序 | `<skills>` |
| 7 | `kb-index` | 启用的 kb 域与标题（11 §10.3） | `<knowledge-base>` |
| 8 | `environment` | 会话级静态感知：OS、架构、shell、工作区根（09 中会话内不变的部分） | `<environment>` |

规则：

- 每一节只有**一个**渲染函数（铁律 6），输入是 `SessionSurface` 的冻结值，输出确定的字节；节之间用固定的一个空行分隔；空节整节省略（不输出空外壳）。
- 回合级变化的信息（时间、cwd、发送者昵称、召回记忆、复盘提示）**永远不进 system**，只进尾部并化石化（04、11）。
- 顺序与外壳名称写成 `SystemSection` 枚举，渲染器按枚举顺序遍历；新增一节要改枚举并刷新形状夹具（07 的 shape 测试同样覆盖 system 字节）。

## 9 语言规则（i18n）

- **模型可见文本一律英文短句**：外壳标签与属性、内置模板（audience、venue-policy）、工具描述与参数说明、工具返回给模型的错误、注入的提示块（`<self-review>`、`<recalled-memories>` 的 note 属性等）。
- **用户撰写的内容不受限制**：persona 提示词、关系档案、记忆正文、kb 文档可以是任何语言。
- **界面文本走 i18n**：TUI 与 Web 使用各自的消息目录（`zh-CN`、`en`），键名在 `gqy-protocol` 中定义为常量；API 错误返回 `code` + 参数，不返回拼好的中文句子。界面语言由 `[ui].language` 决定，默认跟随系统区域设置。
- 守护：所有模型可见的字符串常量集中在各 crate 的 `model_text` 模块中；测试扫描这些模块，出现 CJK 字符即失败。

## 10 测试与守护

- **默认值单一来源**：生成的 JSON Schema、TS 类型、默认配置与仓库中提交的产物逐字节比对；在 Rust 中改一个默认值而不重新生成，CI 变红。
- **原子保存与并发**：两个客户端带同一修订号同时保存，一个成功、一个 409；成功后 `secrets.toml` 字节不变（v1 回滚 secret 的回归）。
- **写入中断**：在 rename 之前 kill 进程，原文件完好，残留的临时文件在下次启动时被清理。
- **热加载不改前缀**：§3.5 的逐字段测试。
- **明文 secret 拒绝**：配置中写 `api_key = "sk-…"`，校验失败并给出 `gqy secret set` 提示。
- **dev 不是特例**：把内置 `dev` persona 复制为 `foo`（启用集相同），两者编译出的 `surface_hash` 相同。代码中任何按名字 `"dev"` 分支的逻辑都会让测试变红。另有 xtask 规则禁止出现 `AgentMode` 标识符。
- **Surface 冻结**：会话创建后修改 persona 提示词与 `[venues]` 配置，后续 10 轮请求的 system 与 tools 字节不变；执行压缩后 system 更新为新代际，并有一条 `context_rewrite reason=persona_generation` 日志。
- **跨入口**：TUI 创建的会话从 Web 继续，`surface_hash` 不变；成员账号尝试提交到 owner 会话返回 `VenueMismatch`。
- **公开版**：没有 `public.md` 的 persona 绑定群聊场所时返回 `PersonaNotPublic`。
- **system 确定性**：同一 `SessionSurface` 渲染 100 次字节相同；节顺序与夹具一致。
- **英文扫描**：§9 的 CJK 扫描，附一个故意含中文的夹具证明规则生效。
