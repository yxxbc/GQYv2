# 01 · 总体架构

> 状态：【规划】。前置阅读：[00 设计理念](00-设计理念.md)。

## 1 一句话形态

**一个二进制、一颗内核、多个入口。** 核心产物是单一自包含可执行文件（共存期命令名见 D-06）。它按子命令长出不同角色。只有 daemon 执行回合，其余入口都是网关的客户端。外部平台（QQ、iMessage…）各是一个独立的连接器进程，经 `gqy-connector/1` 连到 daemon 进程内 `gqy-gateway` 的连接器端点；这个端点就是“中间网关”（协议边界：鉴权、ack、限速、帧上限、不可信输入隔离），暂不设独立网关进程，协议基于网络，以后可加独立中继而不改连接器（00 §5，16）。

```text
               ┌──────────── 入口（客户端）────────────┐
   终端 TUI     Web 控制台      桌面（Tauri）   gqy ask / 脚本   连接器（QQ / iMessage…）
      │            │                │               │                 │
      └─ UDS ──────┴── HTTP/SSE ────┴── in-proc ────┴── UDS ──────────┴── WS(gqy-connector)
                                   ▼
┌──────────────────────── gqy daemon（唯一执行回合的地方）────────────────────────┐
│  gqy-gateway：版本化 API、鉴权、SSE 事件总线、连接器端点                          │
│  gqy-engine ：Supervisor → 会话 actor → 回合状态机（工具循环、压缩、子代理）      │
│  能力：provider · ledger · tools · perception · memory · ext                   │
│  持久化：gqy-store（单写者线程 + 读连接池）  系统：gqy-sys（PTY/信号/沙盒/探测）  │
└──────────────────────────────────────────────────────────────────────────────┘
                 │                          │                        │
            模型供应商（HTTPS）          本机文件与进程（沙盒内）      其它设备（mesh，17）
```

## 3 crate 分层与依赖方向

规则：**一个 crate 只能依赖严格更低层的 crate，同层之间不互相依赖。** `cargo xtask arch` 读取 `cargo metadata`，逐条核对下表。不设白名单，违规就是 CI 红（铁律 4）。

| 层 | crate | 职责 | 允许的外部重依赖 |
| --- | --- | --- | --- |
| L0 基础类型 | `gqy-core` | ID 类型、`Clock` trait、规范化 JSON、错误分类 `ErrorKind`、安全文本切片、限额常量、`ContentPart`/`ToolSpec` 等领域数据类型；跨 L2 共享的纯值类型（`RequestPlan`、`LedgerEntry`、`StableSection`、`ContextPayload`、`ModelBinding`、`ProviderProfile` 等，04 §4.5）；`SubsystemHooks` trait 及其输入输出类型（`TailBlock`、`RequestView`、`HookCx`，18 §3） | serde、thiserror、blake3、tokio（仅 `rt`/`sync` 最小面，供 `blocking::run`）、tracing、jiff |
| L0 | `gqy-protocol` | 对外 API 的 DTO、事件信封、协议版本常量、连接器帧；可选 feature 生成 TS 类型 | serde、ts-rs（feature） |
| L1 系统与持久化 | `gqy-sys` | C/libc FFI：PTY、信号、进程组与资源限制、OS 探测、沙盒后端（Landlock / macOS） | libc、nix、landlock |
| L1 | `gqy-store` | SQLite 单写者线程、读连接池、迁移、仓储（repo）、内容寻址 blob 存储、备份 | rusqlite（bundled） |
| L1 | `gqy-config` | 路径（`GqyPaths`）、配置模式与默认值（唯一来源）、加载/校验/原子写、persona 清单解析 | toml、toml_edit |
| L2 基础能力 | `gqy-provider` | `Provider` trait、协议适配器（openai-chat / openai-responses / anthropic）、SSE 解析、能力画像、用量归一化、mock 供应商 | reqwest（rustls） |
| L2 | `gqy-ledger` | 账本条目模型、请求规划（`RequestPlan`）、化石化、前缀哈希链、工具面序列化 | — |
| L2 | `gqy-tools` | `Tool` trait、注册表、工具面编译、参数收口、内置核心工具（文件、编辑、补丁、搜索、命令、PTY） | globset、grep 系 crate |
| L2 | `gqy-perception` | Host / Workspace / Origin / Context 四维感知提供者 | — |
| L3 扩展能力 | `gqy-memory` | 记忆存取、整理、联想检索、知识库；以 `Tool` 与 `SubsystemHooks` 形式挂载 | — |
| L3 | `gqy-ext` | 技能、脚本工具、MCP 客户端、扩展包管理；全部适配为 `Tool` / 提示片段 | — |
| L4 引擎 | `gqy-engine` | Supervisor、会话 actor、准入、回合状态机、压缩、子代理、钩子调度、作业与定时器 | — |
| L5 服务 | `gqy-gateway` | axum 路由、自建 accept 循环（hyper-util）、中间件栈、鉴权与会话、限速、SSE、UDS、TLS、连接器端点、Web 静态资源内嵌 | axum、tower、tower-http、hyper、hyper-util、tokio-rustls（rustls 的 ring 后端）、rcgen、socket2、subtle、data-encoding、rust-embed |
| L5 | `gqy-client` | 协议客户端（UDS / HTTP），供 TUI、CLI、mesh 复用 | — |
| L5 | `gqy-mesh` | 设备发现、配对、能力委派、同步合并（17） | — |
| L5 | `gqy-connector-sdk` | 连接器共享客户端：WS 连接、握手、心跳、重连、`max_inflight` 窗口、水位推进（16 §4.1）；只依赖 `gqy-protocol` | tokio-tungstenite |
| L6 组装 | `gqy-daemon` | 唯一的 daemon 组装函数 `assemble_daemon(paths, cfg) -> DaemonHandle`：构造 store、provider、tools、memory、ext、engine、gateway、mesh，注册 `ToolSource`、`StorageDomain`、`SubsystemHooks`；库 crate，不创建 runtime | — |
| L7 入口 | `gqy`（apps/gqy） | 入口二进制：解析子命令；daemon 角色调用 `gqy-daemon` 组装，其余子命令作为客户端连接 | clap |
| L7 | `gqy-tui`（apps/tui） | 终端客户端 | ratatui、crossterm |
| L7 | `gqy-desktop`、连接器 | 桌面宿主（内嵌模式调用 `gqy-daemon`）、平台连接器（依赖 `gqy-connector-sdk`） | tauri 等 |

附加约束（同样由 `cargo xtask arch` 检查）：

- `gqy-tui`、连接器、`gqy-desktop` 的前端部分**不得**依赖 L1–L4 crate。它们只能通过 `gqy-client` / `gqy-connector-sdk` / `gqy-protocol` 访问运行时，确保入口不持有业务事实。
- 只有 `gqy-daemon` 可以同时依赖 `gqy-engine` 与 `gqy-gateway` 做组装；`apps/gqy` 与桌面宿主通过依赖 `gqy-daemon` 获得组装能力，不自己拼装。
- `gqy-connector-sdk` 只依赖 `gqy-protocol`（L0）与 WS 客户端库，不得依赖 L1–L4。
- 重依赖（reqwest、axum、ratatui、rusqlite）只允许出现在上表所列 crate 中，防止基础层被拖重。

### 3.1 为什么这样切

- v1 的 `llm → tools` 反向边，起因是适配器要读回合上下文。在 v2 中，`gqy-provider` 只拿到一个已规划好的 `RequestPlan` 与 `ProviderProfile`，根本看不见工具与回合（04、06）。
- v1 的 `tools → agent` 反向边，起因是子代理和知识库要回调回合引擎。在 v2 中，子代理是引擎自己的能力：工具层只产出“请求派生子回合”的效果（`ToolEffect::SpawnSubturn`），由引擎执行（03、07）。
- v1 的 `agent → platforms` 反向边，起因是引擎认识具体平台。在 v2 中，平台差异全部折叠进场所（`Venue`）声明与连接器协议，引擎只认 `Venue` 数据（12、16）。
- 账本与供应商分开：账本决定“发什么、按什么顺序”，适配器决定“怎么编码成字节”。两者都必须确定性输出，组合起来才构成字节契约（04）。二者同属 L2、互不依赖，所以它们之间传递的值类型（`RequestPlan`、`LedgerEntry`、`ModelBinding`、`ProviderProfile` 等）定义在 `gqy-core`（04 §4.5）。
- `SubsystemHooks` 由 `gqy-engine`（L4）调用、由 `gqy-memory` / `gqy-ext`（L3）实现，所以 trait 定义在 `gqy-core`；它的上下文不携带 store 句柄，子系统自己的存储句柄在组装处注入（18 §3.1）。
- 组装单独成层：`apps/gqy` 与桌面宿主都要组装 daemon，若把组装放在 `apps/gqy`，桌面宿主就得依赖同层入口；`gqy-daemon` 位于服务层之上、入口之下，两者都向下依赖它（原 Q-15-6）。

## 4 进程形态

| 子命令 | 常驻 | 职责 |
| --- | --- | --- |
| `gqy`（无参数） | 否 | 启动 TUI；若 daemon 未运行则按配置拉起（后台）后再连接 |
| `gqy daemon run` | 是 | 前台运行 daemon（服务管理器使用） |
| `gqy daemon start / stop / status / logs` | 否 | 生命周期管理（单实例锁 + UDS `ping`） |
| `gqy ask` | 否 | 一次性提问；输出 JSONL 事件或纯文本，退出码稳定（13） |
| `gqy doctor` | 否 | 打印感知矩阵中的 Host 能力、沙盒可用性、配置校验结果 |
| `gqy import-v1` | 否 | v1 数据导入（20） |
| `gqy connector install <name>` | 否 | 为某个连接器生成 launchd / systemd --user 服务文件（16 §4.1）；不拉起、不监管连接器进程 |
| `gqy config …`、`gqy persona …` | 否 | 配置与人格管理（通过网关，daemon 未运行时直接读写文件并加锁） |

- **单实例**：数据目录下 `run/daemon.lock` 用 `flock` 独占；同时写 `run/daemon.json`（pid、启动时间、协议版本、监听地址）。存活判断用锁 + UDS `ping`，不读 `/proc`，以保证跨平台。
- **连接器进程**：每个平台一个独立二进制（`apps/connectors/`），由操作系统服务管理器（launchd / systemd --user）拉起与监管，`gqy connector install <name>` 生成服务文件；daemon 不管理连接器生命周期，也不含任何平台代码（00 §5，16 §4）。
- **不自重生 worker**：v1 的渲染、嵌入、闹钟 worker 不再作为同一二进制的隐藏角色。长任务是 daemon 内的作业（03）；需要隔离的执行是沙盒内子进程（08）。确有独立进程需求时（如语音），作为扩展另行构建。
- **桌面宿主**：Tauri 进程调用 `gqy-daemon` 在进程内组装同一套 daemon（与 `gqy daemon run` 是同一个组装函数），同时是客户端和服务端（15 §10、17）；若检测到同一数据目录已有 daemon，则退化为纯客户端。

## 5 一个回合如何穿过系统

```text
入口 ──(API: POST /api/v1/sessions/{id}/turns)──▶ gateway
  gateway：鉴权 → 解析 Venue/principal → engine.submit(TurnRequest)
  engine ：Supervisor 找到会话 actor（按需加载）→ 准入（排队 / 拒绝 / 接受）
  actor  ：构造 TurnContext（会话快照 + 场所 + 感知 + 取消令牌 + 预算）
  回合状态机循环：
     ledger.plan(TurnContext) → RequestPlan
     provider.stream(RequestPlan) → 事件流（文本/推理/工具调用/用量）
     tools.dispatch(ToolCall, ToolContext) → ToolOutcome（审批、沙盒内执行）
     ledger.append(…)（经 store 单写者落库）→ 事件总线 → 各入口
  结束：回合终态（完成 / 失败 / 取消）落库；钩子 after_turn；可能触发压缩
```

所有步骤的数据都是显式参数，任何函数签名里都不存在“隐含的当前会话”。

## 6 工具链与工程基线

- Rust 2024 Edition。MSRV 在 P0 施工时按当时稳定版确定，写进 `rust-toolchain.toml` 与 workspace `rust-version`；不低于技术栈要求的 1.85。
- workspace 级 lints：`unsafe_code = "deny"`，只有 `gqy-sys` 可以以模块级 `allow` 使用 unsafe，且每处都要写 `// SAFETY:` 说明；clippy 开启 `unwrap_used`、`expect_used`、`panic`、`indexing_slicing`（非测试代码 deny）、`await_holding_lock`、`large_futures`。
- 每个库 crate 定义自己的 `Error`（thiserror），并实现 `gqy_core::ErrorKind` 分类；`anyhow` 只允许出现在 `apps/*` 与 `xtask`。
- 文件体积门禁：由 `cargo xtask size` 执行，阈值为 800/1500/2000（00 §3）。
- 前端：TypeScript + esbuild 独立二进制（只剥离类型），类型检查用原生 TypeScript 检查器二进制 `tsgo`（`--noEmit`）；两者的版本与校验和都固定在 `xtask`，零 Node（00 §5、15 §3）。

## 7 扩展一个能力要动哪些地方（接线目标）

| 要加的东西 | 动的地方 | v1 对照 |
| --- | --- | --- |
| 内置工具 | `gqy-tools/src/builtin/<name>.rs` 一个文件 + `builtin/mod.rs` 注册表一行；形状夹具刷新 | 23 个文件 |
| 供应商模板 | 配置文件一段（全字段有默认值）；新协议才需要新适配器文件 | 同 |
| 入口 / 场所 | 一个 `Venue` 声明 + 该入口自己的客户端代码 | 引擎认识平台 |
| 外部平台 | 一个连接器二进制（任意语言，遵守 gqy-connector 协议；Rust 连接器复用 `gqy-connector-sdk`） | 同，但 v1 用 Python |
| 子系统（如记忆） | 实现 `SubsystemHooks` 并在组装处（`gqy-daemon`）注册 | 引擎内写死调用 |
| 斜杠命令 | 命令表一行（驱动补全、帮助、分发、`GET /api/v1/commands`） | 同（v1 已有此样板） |
