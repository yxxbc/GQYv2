# 06 · 模型供应商适配

> 状态：【规划】。前置阅读：[00 设计理念](00-设计理念.md)（原则“普适层默认开，投放层默认关”“先读规范，再读代码，最后推理”）、[01 总体架构](01-总体架构.md) §3、[02 运行时与并发模型](02-运行时与并发模型.md) §6、[04 前缀缓存账本](04-前缀缓存账本.md)。本文的供应商行为描述均为 v1 实测或公开文档的转述，实现时必须按当时的官方文档与实测逐项核验。

## 1 目标

1. **一个 trait，三种协议**：`openai-chat`、`openai-responses`、`anthropic`。新增一个兼容已有协议的供应商只改配置，不写代码（全字段有默认值）。
2. **确定性编码**：同一个 `RequestPlan` 在同一 `encoding_version` 下永远编码为同一串字节（04 I-7）。
3. **原生信封保真**：assistant 回复按供应商原生结构存储与回放，推理内容、签名、不透明项不丢不改。
4. **能力显式建模**：每个差异点都是 `ProviderProfile` 的一个字段；未知能力默认不发送。
5. **失败可分类、重试单层有界**：所有错误进入封闭的分类；重试只在本层做一次决策循环（02 §6）。
6. **用量口径统一**：四个互斥桶，守恒校验，每请求一行绝对值账。

## 2 v1 教训

| v1 事实 | v2 对策 |
| --- | --- |
| 超时只作用于建连，没有流空闲超时，流可以永久挂起 | 四类超时（02 §6），SSE 注释与心跳也计入活动（§7） |
| 嵌套重试 3×3、无退避 | 单层重试、带抖动指数退避、封顶 30 s（§8） |
| Anthropic `stop_reason` 未解析 | `FinishReason` 统一归一化（§3.3） |
| `llm → tools` 反向依赖 18 处，起因是适配器要读回合上下文 | 适配器只拿 `RequestPlan` 与 `ProviderProfile`（01 §3.1） |
| token 口径漏算工具流水，偏差约 57 倍；`add_usage` 漏累加归一化后的 `cache_read` | 适配器内一次归一化，下游只读归一化结果（§14） |
| DeepSeek 工具调用轮必须回传 `reasoning_content`，否则报错 | `send_reasoning_content` 能力字段（§4、§5） |

| 多 key 逗号分隔轮转 + 冷却；`ProviderConfig` 全字段 `serde(default)`；内置 11 个模板 | 继承（§8.4、§16） |
| CLI 中转（claude-code / codex / antigravity / cline）续传靠前缀哈希链 `--resume`，失配整段重放 | 作为后续扩展保留设计位（§12） |

## 3 Provider trait 与流事件

### 3.1 trait

```rust
// 草案，以实现为准
pub trait Provider: Send + Sync {
    fn profile(&self) -> &ProviderProfile;

    /// 纯函数：RequestPlan → 线上请求。不做 IO，不读时钟。
    fn encode(&self, plan: &RequestPlan) -> Result<WireRequest, EncodeError>;

    /// 发送一次（不重试），把原生流解析为统一事件，结束时返回组装好的响应。
    fn send<'a>(
        &'a self,
        wire: &'a WireRequest,
        sink: &'a mut dyn StreamSink,
        cancel: CancellationToken,
    ) -> BoxFuture<'a, Result<ProviderResponse, ProviderError>>;
}

pub struct WireRequest {
    pub url: Url,
    pub headers: Vec<(HeaderName, HeaderValue)>,  // 顺序确定；密钥头在发送时注入，不参与 wire_hash
    pub body: Bytes,                              // §6 布局
    pub wire_hash: [u8; 32],                      // blake3(body)，写入请求记录（04 §10）
}

pub struct ProviderResponse {
    pub envelope: AssistantEnvelope,   // §5
    pub finish: FinishReason,
    pub usage: NormalizedUsage,        // §14
    pub timing: Timing,                // connect、first_byte、total
}
```

`gqy-provider` 另外提供 `ProviderClient`：持有 `Arc<dyn Provider>`、密钥池与重试策略，对外只有一个方法：

```rust
// 草案，以实现为准
impl ProviderClient {
    pub async fn run(&self, plan: &RequestPlan, events: EventSink, cancel: CancellationToken)
        -> Result<ProviderOutcome, ProviderError>;   // ProviderOutcome = ProviderResponse + attempts + key_id
}
```

回合引擎（03 §6.1）只调用 `ProviderClient::run`。`encode` 在一次 `run` 中只调用一次；重试与换钥重发的是同一个 `body`，只替换密钥头（§8）。

### 3.2 统一流事件

```rust
// 草案，以实现为准
pub enum StreamEvent {
    TextDelta { text: String },
    ReasoningDelta { text: String },
    ToolCallBegin { index: u32, id: String, name: String },
    ToolCallArgsDelta { index: u32, fragment: String },
    Usage(RawUsage),        // 可能在中途或末尾到达；以最后一次为准
    Finish(FinishReason),
}
```

`StreamSink` 把 `TextDelta` / `ReasoningDelta` 转成 `assistant.delta` / `reasoning.delta` 事件（03 §11），并记录“是否已转发过内容”，供重试判定（§8.2）。签名、不透明项等不产生流事件，只进入最终信封。

### 3.3 FinishReason 归一化

| 统一值 | openai-chat `finish_reason` | openai-responses | anthropic `stop_reason` |
| --- | --- | --- | --- |
| `Stop` | `stop` | `status=completed` 且无函数调用 | `end_turn`、`stop_sequence` |
| `ToolCalls` | `tool_calls`（及旧 `function_call`） | 输出含 `function_call` 项 | `tool_use` |
| `Length` | `length` | `incomplete_details.reason=max_output_tokens` | `max_tokens` |
| `ContentFilter` | `content_filter` | `incomplete_details.reason=content_filter` | `refusal` |
| `Other(String)` | 其他值原样保留 | 其他 | `pause_turn` 等 |

流结束却没有收到终止事件（`[DONE]`、`message_stop`、`response.completed`）时，判为 `ProviderError::Protocol(StreamIncomplete)`，不猜测为 `Stop`。

## 4 ProviderProfile：能力画像

```rust
// 草案，以实现为准
pub struct ProviderProfile {
    // 协议与端点
    pub protocol: Protocol,                    // OpenAiChat | OpenAiResponses | Anthropic
    pub base_url: Url,
    pub model: String,
    // 窗口与输出
    pub context_window: u32,                   // 默认 168000（v1 默认值）
    pub max_output_tokens: u32,                // 默认 8192
    pub vision: bool,                          // 默认 false
    // 角色与消息
    pub late_system_role: LateSystemRole,      // None（默认）| System | Developer —— 04 §4.4
    pub developer_role: bool,                  // 顶层 system 是否用 developer 角色；默认 false
    // 推理
    pub thinking_mode: ThinkingMode,           // None（默认）| Budget{tokens} | Effort{level} | Toggle
    pub signed_thinking: bool,                 // 回放必须带签名（Anthropic extended thinking）；默认 false
    pub interleaved_thinking: bool,            // 工具调用之间可有推理；默认 false
    pub send_reasoning_content: ReasoningReplay, // Never（默认）| ToolTurns | Always —— DeepSeek 需 ToolTurns
    // 工具
    pub parallel_tool_calls: Option<bool>,     // None：不发送该字段
    pub tool_choice_none: bool,                // 是否支持 tool_choice=none；默认 false
    // 流与用量
    pub stream_usage: bool,                    // openai-chat 是否发送 stream_options.include_usage；默认 false
    pub usage_dialect: UsageDialect,           // 按协议推断；DeepSeek 等可显式指定 §14
    // 缓存
    pub cache_semantics: CacheSemantics,       // Contract | BestEffort（默认）| PerRequest —— §9
    pub cache_control: CacheControlMode,       // None（默认）| Anthropic{ ttl, max_breakpoints } —— §11
    pub session_header_format: SessionHeader,  // None（默认）| PromptCacheKey | Header{ name }
    pub cache_block_tokens: u32,               // 缓存匹配粒度，默认 64（04 §14）
    pub cache_min_tokens: u32,                 // 可缓存的最短前缀，默认 1024
    // 超时（只能收窄或在 02 §6 上限内放宽）
    pub timeouts: TimeoutOverrides,
}
```

规则：

- 类型归属（00 §5 已定）：`ProviderProfile` 与 `ModelBinding` 定义在 `gqy-core`（账本的 `RequestPlan` 需要引用它们，而 `gqy-ledger` 与 `gqy-provider` 同层不得互相依赖，见 04 §4.5）。
- **未知即不发**：任何字段为默认值时，对应的请求字段、请求头都不出现。v1 曾因给不支持的网关发送 `developer` 角色或 `reasoning_content` 而报 400；默认保守，按实测逐项打开。
- `profile_hash = blake3(canonical_json(profile 中影响编码的字段))`，写入 `StableSection` 与请求记录。它变化意味着编码可能变化，按 `ModelBindingChange` 开新纪元（04 §9）。超时字段不参与哈希。
- 内置模板（§16）为已知供应商给出实测过的画像；用户条目只写与模板不同的字段。

## 5 原生信封保真

### 5.1 结构

```rust
// 草案，以实现为准
pub struct AssistantEnvelope {
    pub protocol: Protocol,
    pub items: Vec<EnvelopeItem>,      // 保持供应商给出的顺序
}

pub enum EnvelopeItem {
    Text { text: String },
    ToolCall { id: String, name: String, arguments_raw: String },   // 原始参数字节，不做任何清洗
    ReasoningContent { value: FieldPresence },   // openai-chat 系（DeepSeek 等）的 reasoning_content
    Thinking { text: String, signature: Option<String> },           // Anthropic
    RedactedThinking { data: String },                               // Anthropic
    Opaque { raw: Box<RawValue> },     // openai-responses 的 reasoning 项（含 encrypted_content）等，原样保存 JSON 字节
}

pub enum FieldPresence { Absent, Empty, Text(String) }   // 区分“无键”与“空串”
```

### 5.2 回放规则

- 同一协议下回放：逐项按原结构编码。`ReasoningContent` 按 `send_reasoning_content` 决定：`ToolTurns` 时只在含 `ToolCall` 的信封上回传，`Absent` 不写键、`Empty` 写 `""`。`Thinking` 在 `signed_thinking = true` 时带签名原样回传，顺序不变。`Opaque` 以原始 JSON 字节写回 `input` 数组。
- 工具调用参数回放使用 `arguments_raw`（模型原始字节）。原始参数不是合法 JSON 时：openai-chat 协议原样作为字符串回放；anthropic 协议要求 `input` 为对象，确定性地编码为 `{"_raw": "<原始字符串>"}`。执行时使用的是注册表收口后的参数（07），与回放无关。
- 工具调用 `id` 缺失（部分网关）：在流组装时按 `call_<run 前 8 hex>_<request_seq>_<index>` 生成，写入信封后固定。

### 5.3 跨协议回放（换模型后）

会话换到另一协议是计划内冷启动（04 §9）。旧信封按降级规则编码：保留 `Text` 与 `ToolCall`；丢弃 `Thinking`、`RedactedThinking`、`Opaque`、签名；`ReasoningContent` 丢弃。降级是确定性的，因此新纪元内依然满足前缀延伸。

## 6 确定性编码

1. **单一路径**：每种协议一个编码模块（`encode/openai_chat.rs`、`encode/openai_responses.rs`、`encode/anthropic.rs`），每种条目在每种协议下只有一个编码函数（04 I-7）。
2. **规范 JSON**：使用 `gqy_core::canonical_json` 的写出器。线上类型只用有序结构（struct 字段顺序或 `Vec<(K, V)>`），禁止 `HashMap`；数字最短往返表示；字符串不做 Unicode 规范化、非 ASCII 原样输出；无多余空白。
3. **请求体布局**：所有非消息字段在前，按固定顺序写出（`model`、采样参数、`tools`、`tool_choice`、`system` / `instructions`、会话缓存字段、`stream`…），**消息数组（`messages` 或 `input`）是最后一个键**。这使得 04 §12.1 的“去掉 `]}` 后是前缀”判定成立。
4. **消息映射**：一个 `Context` 条目编码为一条线上消息，**适配器不合并相邻同角色条目**。唯一的分组是：紧跟在同一 assistant 信封之后的一批 `ToolResult` 条目，在 anthropic 协议下编码为一条 `user` 消息中的多个 `tool_result` 块（协议要求）。这批条目总是在同一次请求间隙一起追加（03 §6.2），所以分组稳定。
5. **`encoding_version`**：常量。任何改变既有条目编码字节的修改都必须升级它（04 §9.3）；`tests/fixtures/request-shapes/` 夹具会在忘记升级时变红。
6. **与账本的分工**：适配器不重排、不增删条目，不插入时间或随机值。它只把 `RequestPlan` 翻译成字节，附加的只有由 `CacheHints` 与画像决定的确定性内容（会话缓存键、`cache_control` 断点，§11）。

## 7 流式解析与超时

### 7.1 SSE 解析

- 按 WHATWG EventSource 规则逐行解析：`data:` 多行拼接、`event:` 事件名（anthropic 与 responses 使用）、以 `:` 开头的注释行、空行分派事件。
- UTF-8 在网络块边界被切断时缓存残字节，不做有损替换。
- 上限：单行 1 MiB、单事件 4 MiB、单响应累计 64 MiB；超出即 `Protocol(Oversized)`。
- `data: [DONE]`（openai-chat）、`message_stop`（anthropic）、`response.completed` / `response.incomplete` / `response.failed`（responses）为终止事件。
- 流中错误事件（anthropic 的 `event: error`，如 `overloaded_error`；responses 的 `response.failed`）按 §8.1 分类。
- 工具调用参数增量按 `index` 累积；anthropic 的 `input_json_delta` 按内容块索引累积。

### 7.2 四类超时

数值与上限见 02 §6：建连 10 s、首字节 120 s、流空闲 90 s、单次请求总时长 20 min。适配器侧的细则：

- **流空闲**计时在收到任意字节时复位，包括 SSE 注释行与供应商心跳事件（如 anthropic `ping`）。长推理期间供应商通常发心跳；不发心跳的供应商在推理模型上可通过画像 `timeouts.stream_idle` 放宽（上限 600 s）。
- **首字节**指收到 HTTP 响应头之后的第一个 SSE 事件。
- 超时触发时关闭连接（02 §5 要求取消后 1 s 内停读）。
- 压缩摘要请求使用收窄的总时长（05 §6.5）。

## 8 错误分类、重试与多密钥

### 8.1 分类

```rust
// 草案，以实现为准
pub enum ProviderErrorKind {
    Auth,              // 401 / 403
    QuotaExhausted,    // 402 或供应商明确的余额不足
    RateLimited { retry_after: Option<Duration> },   // 429
    Overloaded,        // 529、503、流中 overloaded_error
    Server,            // 其他 5xx
    ContextOverflow,   // §8.3
    BadRequest,        // 其他 400 / 404 / 422
    ContentFilter,
    ConnectTimeout, FirstByteTimeout, StreamStalled, TotalTimeout,
    Transport,         // 连接重置、TLS、DNS
    Protocol(ProtocolError),   // SSE / JSON 畸形、流无终止事件、超限
    Cancelled,
}
```

`ProviderError` 带 `status`、供应商错误原文（前 2 KiB）、`key_id`（密钥指纹，不含密钥本身）、`attempt`。原文作为取证保留，分类只基于状态码与结构化字段，字符串匹配仅用于 §8.3 的溢出识别。

### 8.2 重试策略（单层）

| 类别 | 可重试 | 换钥 | 密钥处置 |
| --- | --- | --- | --- |
| `RateLimited` | 是 | 有其他健康密钥则立即换 | 冷却 `retry_after`，缺省 60 s |
| `Overloaded`、`Server` | 是 | 否 | 不冷却 |
| `ConnectTimeout`、`FirstByteTimeout`、`Transport` | 是 | 否 | 不冷却 |
| `StreamStalled`、`TotalTimeout` | 仅当尚未转发内容 | 否 | 不冷却 |
| `Auth` | 仅换钥重试 | 是 | 禁用到配置重载，发 `provider.key_disabled` |
| `QuotaExhausted` | 仅换钥重试 | 是 | 冷却 1 h |
| `ContextOverflow`、`BadRequest`、`ContentFilter`、`Protocol`、`Cancelled` | 否 | 否 | — |

- 总尝试次数默认 4（首发 + 3 次重试），总重试墙钟不超过 3 min。
- 退避：`min(30 s, 1 s × 2^n)` 的全抖动（`[0, 上限]` 均匀取值）；`retry_after` 不超过 30 s 时按它等待，超过 30 s 且没有其他健康密钥时不等待，直接以 `RateLimited` 失败并在错误中给出建议等待时间。
- **已转发内容后不重试**（03 §8）：`StreamSink` 一旦转发过 `TextDelta` / `ReasoningDelta`，任何错误直接上抛。
- 每次重试发 `request.retrying { attempt, kind, delay_ms }`。
- 重试等待可被取消令牌打断。

### 8.3 溢出识别

`ContextOverflow` 的判定（05 §9 消费）：

1. **排除优先**：错误文本含 `rate limit`、`too many requests`、`throttl`（不区分大小写）时，不判溢出（v1 教训：Bedrock 的 “Too many tokens, please wait” 会误命中）。
2. **匹配核心特征**（不区分大小写）：`context_length_exceeded`、`maximum context length`、`exceeds the context window`、`prompt is too long`、`context size`（DeepSeek：`prompt has N tokens, but the configured context size…`）、`too many tokens`、`token limit exceeded`、`input is too long`。
3. 状态码 400 / 413 且响应体为空：仅当按 `RequestPlan` 本地估算的输入 ≥ 0.9 × 窗口时判溢出，否则判 `BadRequest`。
4. 无报错溢出（`length` 且零输出且输入 ≥ 0.99 窗口；`stop` 且输入 > 窗口）由 05 §9 基于归一化用量判定，不在本层。

特征表放在 `gqy-provider` 一处常量中，每条都有来源注释和一个夹具用例。

### 8.4 多密钥与选择

- 配置 `key_ref` 为密钥引用列表（只允许 `secret:<name>` 引用，不允许明文，12 §4；v1 为逗号分隔的明文字符串，导入器负责拆分并移入 `secrets.toml`，20 §5.5）。
- **选钥策略** `key_selection`：
  - `session_sticky`（默认）：`index = blake3(session_id) mod n`，在健康密钥中选；失败换钥后，该会话粘在新密钥上直到它不健康。理由：部分供应商的缓存按账号隔离，粘性选钥从不比轮转差，同时仍把不同会话分散到不同密钥。
  - `round_robin`：每请求轮转（v1 行为），适合明确跨密钥共享缓存或按次计费的供应商。
- 辅助请求（04 §11）使用 `round_robin`，不占用会话粘性。
- 密钥健康状态存内存（`KeyPool`，每供应商一个，actor 化或原子状态），冷却到期自动恢复；不持久化（重启后全部视为健康）。

## 9 缓存语义三类与两层投放

### 9.1 三类

| 类别 | 例子（v1 实测或文档） | 特征 | 默认策略 |
| --- | --- | --- | --- |
| `Contract` | Anthropic `cache_control`（写入 1.25–2×）、OpenAI prompt caching、Kimi | 付费或明确承诺的缓存；append-only 字节流即可稳定命中 | 普适层 + 断点规划（§11） |
| `BestEffort` | DeepSeek 官方 | 免费、无承诺；命中随集群负载与流量形态变化 | 普适层；投放层可选开启 |
| `PerRequest` | opencode zen 等按次计费网关 | 缓存不省钱（最多省延迟）；多发请求是负收益 | 普适层；投放层禁止开启（配置校验报错） |

### 9.2 普适层（默认开，不可关）

字节纯度、append-only、化石化、stub 工具面（04、07），以及：

- **会话缓存标识**：画像 `session_header_format` 不为 `None` 时，主链请求携带由 `SessionId` 派生的稳定键（`PromptCacheKey` 写入请求体 head，`Header{name}` 写入请求头）。辅助请求不携带。
- **粘性选钥**（§8.4）。

### 9.3 投放层（默认关）

**保温 ping `keepalive`**

- 行为：会话主链最后一次请求完成后，若会话空闲，每 `interval`（默认 20 s）把最后一次请求的 body 原样重发一次，只把 head 中的 `max_tokens` 改为 1、`stream` 改为 false（head 不参与服务端前缀匹配；消息部分逐字节相同）。
- 停止条件：会话有新请求、空闲超过 `max_idle`（默认 5 min）、连续 2 次保温失败、daemon 停机。
- 记录：`RequestPurpose::Auxiliary(Keepalive)`，不写账本，写用量账（便于核算成本）。
- 适用条件（写进配置注释）：仅对 `BestEffort` 且实测热窗口短于你的典型回合间隔的供应商有收益。【v1 实测】DeepSeek 65 s 空闲后跨轮命中 28% → 94.9%，净省约三分之二输入成本；mimo 97.2% → 97.3%，零收益。`PerRequest` 上禁止开启。

**写入宽限 `write_grace_ms`**

- 行为：同一会话主链上一次请求结束不到 `write_grace_ms` 就要发下一次时，等待剩余时间再发（可取消，上限 5000 ms）。
- 默认 0（关）；DeepSeek 建议值 2500。【v1 实测】DeepSeek 写入异步，1.5 s 内跟进会 miss，6 s 后稳定。
- 只影响工具循环中紧挨着的请求；不影响用户可见的首个请求。

## 10 模型绑定、档位与旁路角色

```rust
// 草案，以实现为准
pub struct ModelBinding {
    pub provider_id: String,
    pub model_id: String,
    pub tier: ModelTier,                 // Lite | Cheap | Standard | Flagship

    pub profile_hash: [u8; 32],
```

- 会话创建时冻结 `ModelBinding`（02 §4）；用户换模型是 `ModelBindingChange` 冷启动（04 §9）。
- 每个配置的模型声明一个档位。旁路角色按档位解析到“第一个健康的该档位模型”：

| 角色 | 默认档位 | 说明 |
| --- | --- | --- |
| `Title`、`Selection` | lite | |
| `Judge` | cheap | |
| `Organizer`、`Review` | standard | 记忆整理、聊后复盘（11） |
| `Vision` | 第一个 `vision = true` 且档位 ≥ cheap 的模型 | |

## 11 Anthropic `cache_control` 断点规划

仅当 `cache_control = Anthropic{…}` 时生效。断点是编码层的叠加物：它不改变 `RequestPlan`，只在编码时给若干内容块加 `"cache_control":{"type":"ephemeral"}`（TTL 为 1 h 时附 `"ttl":"1h"`）。

默认规划（最多使用 3 个，协议上限 4）：

1. **稳定断点**：`system` 最后一个块（覆盖 tools + system）。
2. **尾部断点**：本次请求最后一条消息的最后一个内容块（写入本次前缀）。
3. **读取断点**：当上一次请求的尾部（`CacheHints.prev_request_end`）距本次尾部超过 20 个内容块时，在上一次尾部的内容块上再放一个断点，确保服务端的回溯窗口能找到已写入的前缀（例如一次并行 25 个工具结果）。

规则：

- 断点位置由 `(RequestPlan, profile)` 确定性计算。
- 字节门禁对 anthropic 协议先剥离 `cache_control` 再比较前缀（04 §12.1），另有测试断言断点位置符合本节规则。
- TTL 默认 5 min；`ttl = "1h"` 写入成本更高，只在回合间隔经常超过 5 min 的场景由用户开启。
- 前缀短于 `cache_min_tokens` 时不放断点。
- v1 计划首版只放 1 个 system 断点，另两个为数据触发项；v2 把尾部与读取断点作为默认的理由是工具循环（多次请求、每次追加）是主要负载，只有 system 断点时历史部分每次都全价。见 Q-06-2。

## 12 CLI 中转（后续扩展）

【后续扩展，不在 P02 范围】v1 支持以本机 CLI（claude-code、codex、antigravity、cline）作为“供应商”。v2 预留设计位：

- 协议 `cli-relay`，画像字段 `relay = "claude-code" | "codex" | …`、`binary`、`args`；子进程经 `gqy-sys` 在沙盒策略下启动（08）。
- GQY 的工具面通过本地 MCP 桥暴露给 CLI；CLI 原生工具调用的足迹同样进入 `ToolOutcome.footprint`（05 §7.2，v1 曾因只在本地执行分支采集而恒为空）。
- 续传键为 04 §10 的 `prefix_hash`：链头一致则 `--resume`，失配则整段重放。
- 压缩统一由 GQY 执行（v1 用户裁定），不向 CLI 传自压缩阈值；要求 GQY 的 `context_window` 不大于 CLI 的真实窗口。
- 缓存语义与用量由 CLI 报告质量决定，默认按 `PerRequest` 处理。

是否纳入内核还是作为扩展（18）见 Q-06-3。

## 13 mock 供应商

`gqy-provider` 在 `mock` feature 下提供 `MockServer`，供单元测试、04 字节门禁、03/05 场景测试、端到端测试共用：

- 在 `127.0.0.1` 随机端口启动真实 HTTP 服务，走真实的 reqwest 与 SSE 解析路径（不是进程内替身）。
- 同时实现三种协议的端点与流格式。
- 按 `MockScript` 应答：每条脚本项是一次响应，可包含文本、推理、签名、不透明项、工具调用（含并行）、`finish_reason`、用量（含缓存字段）。
- 故障注入：`Delay{ first_byte }`、`StallAfter{ events }`、`Status{ code, body, retry_after }`、`Overflow{ style }`（各供应商的溢出文案）、`MalformedUsage`、`DropConnection`、`NoTerminalEvent`、`Oversized`、限速输出（`tokens_per_sec`，用于 05 的慢模型验收）。
- 记录每个请求的方法、路径、请求头（密钥打码）、body 原始字节与到达时间，供断言。
- 缓存模拟（可选）：按 `cache_block_tokens` 粒度模拟前缀命中并在用量中返回 `cache_read`，用于验证用量账与 `miss_suspect` 逻辑。
- 与注入的 `Clock` 配合，超时测试在暂停时钟下确定性运行（02 §10）。

## 14 用量归一化

### 14.1 口径

```rust
// 草案，以实现为准
pub struct NormalizedUsage {
    pub input_uncached: u32,
    pub cache_read: u32,
    pub cache_write: u32,
    pub output: u32,              // 含推理
    pub reasoning_output: Option<u32>,   // output 的子集，供展示
    pub input_total: u32,         // = input_uncached + cache_read + cache_write
    pub reported: UsageSource,    // Reported | Estimated（流中无用量时由本地估算）
    pub malformed: bool,
}
```

四个桶互斥：`input_uncached`、`cache_read`、`cache_write`、`output`。

### 14.2 映射

| 协议 / 方言 | input_total | cache_read | cache_write | input_uncached |
| --- | --- | --- | --- | --- |
| openai-chat（OpenAI 口径） | `prompt_tokens` | `prompt_tokens_details.cached_tokens` | 若有 `cache_write_tokens` 字段则取，否则 0 | total − read − write |
| openai-chat（DeepSeek 口径） | `prompt_cache_hit_tokens + prompt_cache_miss_tokens`（与 `prompt_tokens` 交叉校验） | `prompt_cache_hit_tokens` | 0 | `prompt_cache_miss_tokens` |
| openai-responses | `input_tokens` | `input_tokens_details.cached_tokens` | 0 | total − read |
| anthropic | 三项之和 | `cache_read_input_tokens` | `cache_creation_input_tokens` | `input_tokens` |

`output` 取 `completion_tokens` / `output_tokens`；推理子项取 `completion_tokens_details.reasoning_tokens` / `output_tokens_details.reasoning_tokens`。

### 14.3 守恒校验

- `cache_read + cache_write > input_total`，或任一字段为负、缺失关键字段：`malformed = true`。**不做饱和减法掩盖**；原始用量 JSON 一并保存到请求记录供取证。
- malformed 的用量不作为占用锚点（05 §4.1），在用量账中照常记录并计数。
- 流中未收到用量（未开启 `stream_usage` 等）：用本地估算填充，`reported = Estimated`，同样不作为锚点。

## 15 用量与成本记录

每次请求（含重试后的最终结果、fork、辅助、保温）在同一个写作业里写两张表（10 §7.5）：`llm_requests` 存 04 §10 `RequestRecord` 的字节契约字段与下列元数据，`usage_records` 存用量四桶与成本（保留与汇总见 10 §9.3、19 §3.3）。字段为 04 §10 `RequestRecord` 加上：

- `provider_id`、`model_id`、`protocol`、`purpose`、`key_id`（密钥指纹前 8 hex）；
- `NormalizedUsage` 全部字段与原始用量 JSON；
- `finish`、`attempts`、`timing`（connect / first_byte / total 毫秒）、`error_kind`（失败时）；
- `cost`：配置了价格表时按桶计算（`input_uncached × p_in + cache_read × p_read + cache_write × p_write + output × p_out`），否则为空。不推测价格。

同时打 04 §14 的 `prompt_cache_accounting` 日志行。**不记录请求与响应正文**。`/usage` 与 Web 用量页从请求记录聚合，展示绝对值与金额。

## 17 边界与失败模式

| 风险 | 对策 |
| --- | --- |
| 网关声称兼容 OpenAI 但拒绝未知字段 | 未知即不发；画像逐项打开 |
| 供应商修改服务端模板 | 客户端无法感知；用量账 `miss_suspect` 提示 |
| 供应商流中途改变用量字段位置 | 以最后一次 `Usage` 事件为准；缺失判 `Estimated` |
| 推理模型长时间无输出 | 心跳复位空闲计时；画像可放宽到上限 600 s |
| 所有密钥被禁用 | 运行 `Failed(ProviderAuth)`，错误写明各密钥指纹与状态 |
| 签名推理跨协议 | 降级回放（§5.3），计划内冷启动 |
| 用量 malformed | 不作锚点，不掩盖，记录原文 |
| 保温在按次计费上烧钱 | 配置校验禁止 |

## 18 测试与守护

- **编码确定性**：同一 `RequestPlan` 编码 1000 次字节相同；随机打乱内部集合构造顺序后仍相同。
- **布局**：三协议下消息数组都是 body 最后一个键（解析 JSON 键顺序断言）。
- **信封保真**：每协议的往返夹具（原生响应 → 信封 → 回放编码），断言 `reasoning_content` 的 `Absent` / `Empty` 区分、签名与不透明项字节不变；去掉 `FieldPresence` 区分，测试红。
- **SSE**：跨块切断的 UTF-8、多行 `data:`、注释行复位空闲计时、无终止事件判错、超限判错。
- **超时**：暂停时钟下四类超时各一例；心跳存在时不触发空闲超时。
- **重试**：429 带 `retry_after=5` 等待 5 s；已转发内容后流中断不重试；尝试次数上限；`Auth` 换钥且原钥禁用；取消打断退避等待。去掉“已转发不重试”判定，界面重复文本测试红。
- **溢出识别**：每条特征一个夹具；限流文案不误判；空 body 400 在低占用时判 `BadRequest`。
- **用量映射**：四种方言各一个夹具；`read + write > total` 判 malformed；v1 “漏累加 cache_read” 回归用例。
- **断点**：anthropic 断点数量与位置规则；间隔 > 20 块时出现读取断点。
- **投放层**：`PerRequest` 上开启保温，配置校验失败；保温请求消息部分与最后一次主链请求逐字节相同。
- **选钥**：同一会话在健康状态不变时始终选同一密钥；换钥后粘在新密钥。
