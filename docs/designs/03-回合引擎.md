# 03 · 回合引擎

> 状态：【规划】。前置阅读：[00 设计理念](00-设计理念.md)、[01 总体架构](01-总体架构.md)、[02 运行时与并发模型](02-运行时与并发模型.md)。本文依赖 [04 前缀缓存账本](04-前缀缓存账本.md) 的 `RequestPlan` 与化石化规则、[05 上下文与压缩](05-上下文与压缩.md) 的压缩入口、[06 模型供应商适配](06-模型供应商适配.md) 的流事件与错误分类。

## 1 目标

1. 一个回合（Turn）从准入到终态只有一条代码路径：TUI、Web、`gqy ask`（共存期命令名 `gqy2`，见 D-06；下文统一写 `gqy`）、连接器、定时器、作业唤醒、子代理，全部走 02 §3.3 的 `Supervisor::submit`。
2. 回合状态机的每个状态都可观察（事件）、可持久化（崩溃后能判定停在哪里）、可取消（02 §5）。
3. 工具循环在任何失败路径上都保持 `tool_call` / `tool_result` 配对完整，账本只追加（04）。
4. 子代理、后台作业、定时器都是“普通回合 + 显式来源”，不存在第二条执行路径。
5. 所有循环都有上界：请求数、工具调用数、墙钟时间、子代理深度与并发。

## 2 v1 教训

| v1 事实 | 后果 | v2 对策 |
| --- | --- | --- |
| actor 只串行准入、不串行执行；一会话一回合靠 `agent/control.rs` 三个 Drop 守卫 | 闩锁分散，评审说不清谁持有执行权 | 执行权由 `SessionActor` 独占持有，状态机是唯一推进者（§3） |
| 入口表外还有 5 个 `StartTurn` 发起方（goal driver、job-wake、scheduled_messages、private_initiative、voice） | 无法按场所做准入与配额 | 所有发起方都必须构造带 `Venue` 的 `TurnRequest`（§4） |
| 子代理走 `store.pinned().start_turn()` 绕过 actor | 跳过了哪些闩锁无人说得清 | 子代理是带 `parent_run` 的普通回合（§9） |
| 每次 StartTurn 前两次 `recover_stale_turns` | 恢复逻辑与热路径耦合 | 恢复只在 daemon 启动时做一次（§13） |
| daemon 内存定时器，重启即丢，开机不补跑 | 闹钟丢失 | 定时器持久化到主库，启动时按策略补跑（§10.2） |
| 长命令 300 s 超时直接杀进程，整轮丢失 | 编译、测试类任务不可用 | 软超时转后台作业，硬上限才终止（§10.1） |
| 嵌套重试 3×3、无退避 | 故障时请求放大 9 倍 | 重试只在供应商层单层进行，回合层不重试（§8） |
| Anthropic `stop_reason` 未解析 | 截断无法识别 | 统一 `FinishReason`，`length` 规则见 §7 |
| 工具面内唯一的并行是 ≥2 个 subagent 调用 | 只读工具串行执行，浪费墙钟 | 按效果类别分组并行（§6） |

## 3 回合状态机

### 3.1 状态

```rust
// 草案，以实现为准
pub enum RunState {
    Queued,            // 在会话队列中等待；尚未占用执行权
    Planning,          // 构造 TurnContext、冻结工具面、检查预算与占用、生成 RequestPlan
    Compacting,        // 回合内压缩（预检触发、强制档或溢出恢复），见 05 §8
    Streaming,         // 一次供应商请求在途（含供应商层内部重试）
    AwaitingApproval,  // 有待回答的 Question；不占全局回合配额（02 §6）
    ExecutingTools,    // 执行本批工具调用（含子代理等待）
    // 终态
    Completed,
    Failed(RunFailure),
    Cancelled(CancelReason),   // CancelReason 见 02 §5
    Interrupted,               // 仅由启动恢复写入（§13）
}
```

`Queued` 不是 `RunTask` 的状态：排队中的请求由 actor 持有，出队时才 spawn 运行任务。但它有 `RunId`，并且会落库（§5.3），所以在事件与查询里与其他状态统一表示。

### 3.2 转移表

| 从 | 事件 | 到 | 说明 |
| --- | --- | --- | --- |
| （无） | 准入：会话空闲 | Planning | 发 `run.started` |
| （无） | 准入：会话忙且队列未满 | Queued | 发 `queue.enqueued` |
| Queued | 前一运行进入终态 / 独占操作结束 | Planning | 发 `queue.dequeued`、`run.started` |
| Queued | 被新代际覆盖、TTL 到期、用户撤销 | Cancelled | 原因 `Superseded` / `Timeout` / `User` |
| Planning | 占用 ≥ 触发线（05 §4） | Compacting | 回合开始前的预检压缩 |
| Planning | 计划完成 | Streaming | 发 `request.started` |
| Planning | 预算耗尽 | Cancelled(Budget) | 见 §7 |
| Compacting | 压缩成功或被闸门跳过 | Planning | 重新规划 |
| Compacting | 压缩失败且无法降级 | Failed(ContextOverflow) | 自动路径通常降级为占位摘要，不走这里（05 §7） |
| Streaming | 流结束，无工具调用 | Completed | 发 `run.completed` |
| Streaming | 流结束，有工具调用 | ExecutingTools 或 AwaitingApproval | 审批在执行前发生 |
| Streaming | 溢出错误且本回合未恢复过、尚无任何输出 | Compacting | 一次屏障（05 §9） |
| Streaming | 不可恢复的供应商错误 | Failed | 分类见 §12 |
| AwaitingApproval | 全部问题已回答 | ExecutingTools | 拒绝的调用写入“被拒绝”结果 |
| ExecutingTools | 本批结果全部落账 | Planning | 下一次请求 |
| 任意非终态 | 取消令牌触发 | Cancelled(reason) | 补写配对结果（§3.3） |

实现要求：转移函数是纯函数 `fn next(state, event) -> Result<(RunState, Vec<Effect>), IllegalTransition>`，与 IO 分离。非法转移返回错误，不 panic；单元测试用穷举表覆盖所有 `(状态, 事件)` 组合。

### 3.3 终态的账本收尾

进入任何非 `Completed` 终态时，运行任务在同一个 store 事务里完成三件事：

1. 本批中已发出但没有结果的工具调用，写入合成结果（按效果类别措辞，见 §13 表）；
2. 追加一条 `Context` 通道的 `TurnAborted` 注记（system-late 角色，04 §4.4）：`<turn-aborted reason="user|timeout|budget|error"/>`。它在下一回合被逐字节回放，告诉模型上一回合没有正常结束；
3. 被中断的那次流式输出：已流出的文本只写 `Display` 通道并带 `partial=true`，**不进入** `Context` 通道。理由：半截的 assistant 信封可能缺签名或缺工具参数，按原生协议回放会被拒绝（06 §5）；而该次请求本身没有进入账本，所以下一次请求仍是上一次已发送请求的字节延伸（04 §3 I-2）。

## 4 准入与 TurnRequest

```rust
// 草案，以实现为准
pub struct TurnRequest {
    pub session: SessionTarget,        // 已有会话 / 新建（带 persona 与场所）
    pub venue: Venue,                  // 12；决定信任级、能力、交互性、配额类别
    pub principal: Principal,          // 入口的真实身份；会话已有则必须一致
    pub input: TurnInput,              // 用户原文 + 附件 + 不可信尾巴字段（16）
    pub mode: InputMode,               // §5.4
    pub parent: Option<ParentLink>,    // 子代理：parent_run、parent_call、depth
    pub budget: Option<TurnBudget>,    // 为空时取场所默认
    pub idempotency_key: Option<String>, // 连接器事件 id 等，重复提交返回原结果
}

pub enum Admission {
    Started { run: RunId },
    Queued { run: RunId, position: u16 },
    Steered { into: RunId },           // mode = Steer 且当前运行接受了插话
    Rejected(RejectReason),            // QueueFull / PrincipalMismatch / VenueQuota / ShuttingDown / Duplicate…
}
```

准入顺序（actor 内，纯状态转移，不做 IO）：幂等键查重 → principal 与会话冻结值比对（不一致即 `PrincipalMismatch`）→ 场所配额（02 §3.1）→ 按 `mode` 与会话状态决定 Started / Queued / Steered / Rejected。

全局回合许可（`Semaphore`，默认 16）在 `Planning` 开始时获取，在 `AwaitingApproval` 期间释放、回答后重新获取，在终态释放。子代理使用独立的子代理池（§9.3），避免父运行持有许可等待子运行而死锁。

## 5 排队、代际与插话

### 5.1 会话队列

- 每会话一个有界 FIFO，默认容量 8；满时返回 `Rejected(QueueFull)`（02 §7 的“拒绝”策略）。
- 场所可以声明合并策略 `CoalescePolicy`：连接器群聊把队列中同一会话的连续消息合并为一个回合的输入（上限 20 条，超出部分留在队列）。合并在出队时发生，合并后的原文顺序与到达顺序一致。合并规则的细节归 16。
- 独占操作（压缩、回退、分叉）进行中时，新提交一律排队，操作结束后按序出队。

### 5.2 代际（generation）

会话持有单调递增的 `generation: u64`。以下动作使其加一：

- `mode = Interrupt` 的提交；
- 场所声明 `supersede_on_new = true`（例如连接器私聊：用户连发时只回复最新语境）时的每次提交。

代际加一时：队列中代际更旧的排队项以 `Cancelled(Superseded)` 结束；当前运行若代际更旧，同样以 `Superseded` 取消。运行在终态时比较自己的代际与会话当前代际，**过期运行的对外投递（连接器发送、通知）一律抑制**，并发 `generation.superseded`。账本记录照常保留（取消不回滚，02 §5）。

### 5.3 队列持久化

排队项写入主库 `turn_queue` 表（字段：`run_id`、`session_id`、`venue_json`、`generation`、`enqueued_at`、`input` 摘要与 blob 引用、`idempotency_key`；表草案见 10 §7.4）。这样连接器消息不会因 daemon 重启而丢失。启动恢复时的处理见 §13。

### 5.4 输入模式：排队、插话、打断

```rust
pub enum InputMode { Queue, Steer, Interrupt }
```

| 模式 | 当前运行存在时的行为 | 默认使用方 |
| --- | --- | --- |
| `Queue` | 进入会话队列，当前运行结束后开始新回合 | 所有场所的默认值 |
| `Steer` | 写入当前运行的插话收件箱（有界，8 条）；在下一个安全点作为 `user` 条目追加进账本，本回合继续 | TUI / Web 的显式“插话”操作 |
| `Interrupt` | 代际加一，当前运行以 `Cancelled(User)` 结束，新输入排到队首 | TUI 的打断键、Web 的“停止并发送” |

**安全点**：本批工具结果全部落账之后、下一次 `Planning` 之前。插话永远不会插在 `tool_call` 与 `tool_result` 之间，也不会插在 `[E]` 区段中间，所以不破坏配对，也不违反 append-only（04 §3）。若运行在安全点之前就以“无工具调用”完成，收件箱中剩余的插话转成队首的新回合，模式降为 `Queue`，并发 `queue.enqueued{from: "steer"}`。

## 6 工具循环

### 6.1 主循环

```rust
// 草案，以实现为准
async fn run_turn(ctx: Arc<TurnContext>, deps: &EngineDeps) -> RunOutcome {
    loop {
        // Planning
        ctx.budget.check_before_request()?;                 // §7
        if deps.meter.needs_compaction(&ctx, Stage::Preflight) {
            deps.compactor.run_in_run(&ctx, Trigger::Auto).await?;   // Compacting，05 §8
        }
        let plan = deps.ledger.plan(&ctx)?;                  // 04：只读账本，产出 RequestPlan
        deps.ledger.fossilize_pending(&ctx, &plan).await?;   // 发送前落库，04 §6
        // Streaming
        // 06：只传 plan、事件出口与子取消令牌，适配器看不到 TurnContext；单层重试在内部
        let envelope = match deps.provider.run(&plan, ctx.events.clone(), ctx.cancel.child_token()).await {
            Ok(env) => env,
            Err(e) if e.is_overflow() && ctx.overflow_barrier.try_take() => {
                deps.compactor.run_in_run(&ctx, Trigger::Overflow).await?;
                continue;
            }
            Err(e) => return RunOutcome::failed(e.into()),
        };
        deps.ledger.append_assistant(&ctx, &envelope).await?;
        let calls = match envelope.finish {
            FinishReason::Length if envelope.has_tool_calls() => reject_truncated(&ctx, &envelope, deps).await?, // §7
            _ => envelope.tool_calls(),
        };
        if calls.is_empty() { return RunOutcome::Completed; }
        // AwaitingApproval / ExecutingTools
        let results = deps.dispatcher.execute_batch(&ctx, calls).await;    // §6.2
        deps.ledger.append_tool_results(&ctx, results).await?;             // 按调用顺序
        deps.ledger.append_steers(&ctx, ctx.steer_inbox.drain()).await?;   // 安全点
    }
}
```

- 每一步的 `?` 都把错误映射为 `RunFailure`（§12），不存在“静默兜底”分支。
- 回合内强制档压缩（占用 ≥ 0.9）在 `Planning` 的同一检查点触发，参数为 `Stage::InLoop`（05 §4）。

### 6.2 并行工具执行规则

模型在一次响应里给出的工具调用顺序是**规范顺序**。执行可以并发，落账必须按规范顺序。

1. **分组**：从左到右把调用切成最大连续组。一个调用是“可并行”的，当且仅当其效果类别为 `ReadOnly` 或 `Presentation`，且工具没有声明 `parallel_safe = false`（07）。`Writes`、`Exec`、`Network` 类调用各自单独成组，构成屏障。子代理调用（`ToolEffect::SpawnSubturn`）在组内可以彼此并行，受 §9.3 的并发 4 约束。
2. **组内并发上限**：默认 8。
3. **审批先于执行**：一个组内需要审批的调用，按规范顺序依次发 `question.asked`，全部得到回答后整组才开始执行（状态为 `AwaitingApproval`）。被拒绝的调用写入合成结果 `Denied by user.`（或策略拒绝的原因），组内其他调用照常执行。
4. **失败不连坐**：组内一个调用失败，不取消兄弟调用；失败作为该调用的结果返回给模型。只有运行级取消会取消整组。
5. **超时**：每个调用各自受 02 §6 的前台工具超时约束；`Exec` 类调用的软超时行为见 §10.1。
6. **落账原子性**：一个组的结果在同一个 store 事务里追加；全部组完成后才进入安全点。

### 6.3 参数收口与未知工具

- 参数按 schema 还原（字符串 `"1"` → 整数等）在注册表分发处完成（07）。落库的 assistant 信封保留模型原始参数字节，还原后的值只用于执行。
- 模型调用了工具面中不存在的名字：返回结果 `Unknown tool "<name>". Available tools are listed in the tools array.`，不中止回合。
- stub 工具被直接调用但参数不满足完整 schema：返回校验错误，并提示先调用 `load_tools`（07）。

## 7 预算与 `finish_reason=length`

```rust
// 草案，以实现为准
pub struct TurnBudget {
    pub max_requests: u32,        // 默认 100；子代理 50
    pub max_tool_calls: u32,      // 默认 400；子代理 200
    pub max_wall: Duration,       // 默认 2 h；子代理 30 min；上限 12 h
    pub max_length_rejections: u8,// 默认 2（连续）
}
```

- 预算在每次 `Planning` 检查；耗尽时运行以 `Cancelled(Budget)` 结束，按 §3.3 收尾。v2 首版不做“耗尽前再发一次收尾请求”，原因是收尾请求需要改变工具可用性，会引入工具面或参数差异；是否增加见 Q-03-1。
- 审批等待时间不计入 `max_wall`（等待本身无超时但可取消，02 §6）。
- **`finish_reason=length` 规则**（v1 实测继承）：若本次响应因输出上限被截断且含工具调用，则**全部**工具调用都不执行（参数可能是截断的 JSON，执行任何一个都不安全），每个调用写入合成结果：`Rejected: the response was truncated (finish_reason=length) before this call was complete. Re-issue the call with shorter arguments, or split the work.`，然后继续循环。连续发生 `max_length_rejections` 次后运行以 `Failed(OutputTruncated)` 结束。
- 若被截断的响应不含工具调用：运行 `Completed`，`run.completed` 事件带 `truncated: true`，界面据此提示“输出被截断”。不自动续写。

## 8 重试的边界

- **唯一的重试层在供应商适配器**（06 §8），单层、指数退避、有总次数上限。回合引擎不重试请求，工具分发器不重试工具调用。
- 供应商层只在“尚未向上游转发任何内容事件”时重试。一旦发出过 `assistant.delta` 或 `reasoning.delta`，后续失败直接上抛，由状态机按 §3.3 收尾，避免界面重复文本。
- 用户侧的“重试”是一个新运行（新 `RunId`），输入与上一个失败运行相同，照常走准入。账本中失败运行的注记保留。

## 9 子代理

### 9.1 形态

子代理由工具产出 `ToolEffect::SpawnSubturn(SubturnSpec)`，由引擎执行（01 §3.1）。它就是一个普通回合：

```rust
// 草案，以实现为准
pub struct SubturnSpec {
    pub prompt: String,
    pub tier: Option<ModelTier>,          // lite / cheap / standard / flagship（06 §10）
    pub profile: SubagentProfile,         // 例：General、Dev（对应 v1 的 dev 参数）
    pub background: bool,                 // true：立即返回作业句柄（§10）
    pub resume: Option<SessionId>,        // 续接之前的子代理会话
}

pub struct ParentLink { pub parent_run: RunId, pub parent_call: CallId, pub depth: u8 }
```

- 子会话是隐藏的审计会话（`SessionKind::Subagent`），有自己的账本、自己的前缀链（04 §10）与自己冻结的工具面。
- 场所：`Venue { kind: Subagent, trust: 父场所 trust, caps: 父 caps ∩ 子代理档案 caps, interactive: false }`。信任级与能力**只能收窄不能放大**；principal 继承父会话。
- 模型绑定：按 `tier` 在同一供应商配置中解析（06 §10）；未指定时与父会话相同。
- 子代理工具描述是常量字节（v1 继承），不随配置插值，避免父会话工具面抖动。

### 9.2 生命周期与结果

1. 父运行的 `ExecutingTools` 组中遇到 `SpawnSubturn`：构造 `TurnRequest{ parent: Some(ParentLink), venue: Subagent, mode: Queue }` 调用 `Supervisor::submit`（没有旁路）。
2. 子运行的取消令牌是父工具调用令牌的子令牌：父运行取消 → 子运行取消。
3. 子运行进入终态后，其最后一条 assistant 文本作为父调用的工具结果，附带 `subagent_session` 与终态；超长时按 05 §10 的写入期截断规则处理。子运行失败时，工具结果写明失败分类，不让父运行失败。
4. 子代理的问题（审批）：若父场所可交互，则转发到父会话的问题通道，并标注来源子会话；否则按子代理档案的策略直接拒绝（08）。
5. `background = true`：立即返回 `Job started: <JobId>`，子运行作为作业继续（§10）。

### 9.3 深度、并发与审计

| 项 | 默认 | 上限 | 超出时 |
| --- | --- | --- | --- |
| 嵌套深度 `max_subagent_depth` | 1（子代理不能再派生子代理） | 3 | 工具返回 `Subagent depth limit reached (max N).` |
| 每个父运行的并发子代理 | 4 | 8 | 多出的调用在组内排队等待 |
| 全局子代理池 | 8 | 32 | 子运行在 `Queued` 等待池许可 |
| 子代理审计保留 `subagent_trace_days` | 7 天 | — | 到期由维护作业删除子会话（事件 `session.expired`）；被用户固定的除外 |

审计轨迹：父账本中的工具调用条目记录 `child_session` 与 `child_run`；子会话元数据记录 `parent_run`、`parent_call`、`depth`。`GET /api/v1/runs/{id}/tree` 可以还原整棵运行树（13）。

## 10 后台作业与持久化定时器

### 10.1 作业

```rust
// 草案，以实现为准
pub enum JobKind { Command, Subturn, Script }
pub enum JobState { Running, Succeeded, Failed, Cancelled, TimedOut, Lost }

pub struct JobRecord {
    pub id: JobId, pub session: SessionId, pub origin: (RunId, CallId),
    pub kind: JobKind, pub state: JobState,
    pub started_at: Timestamp, pub hard_deadline: Timestamp,
    pub pid_start: Option<(u32, u64)>,      // pid + 进程启动时间，用于恢复时判定
    pub output: OutputRef,                  // 尾部 64 KiB 存库，全文存 blob，上限 8 MiB
    pub exit: Option<ExitInfo>,
    pub wake: WakePolicy,
}
```

- **长命令转作业**：`Exec` 类工具超过前台软超时（02 §6，默认 120 s）后不终止进程，而是把它登记为 `JobKind::Command`，工具立即返回：`Command still running after 120s; moved to background as job <id>. Use job_status / job_wait / job_output.` 硬上限默认 2 h（可配，最大 24 h），到期按 02 §6 的终止流程处理，状态 `TimedOut`。
- 作业相关工具（`job_status`、`job_wait`、`job_output`、`job_cancel`）归 07（07 §10）；`job_wait` 单次等待上限 120 s。
- 并发上限：每会话 8 个运行中作业，全局 32 个；超出时新作业创建失败并如实报告。
- **唤醒**：`WakePolicy::OnFinish` 时，作业结束且发起它的运行已经结束，引擎提交一个 `Venue{kind: Job}` 的回合，输入是一条 system-late 通知（`<job-finished id=… state=… exit=…>` + 输出尾部）。发起运行仍在进行时不唤醒，由模型自己轮询。后台子代理与转入后台的命令默认 `OnFinish`；其他默认 `Never`。

### 10.2 持久化定时器

```rust
// 草案，以实现为准
pub enum TimerSpec { Once { at: Timestamp }, Every { interval: Duration, anchor: Timestamp }, Daily { at: LocalTime, tz: Tz } }
pub enum CatchUp { Skip, RunOnceIfWithin(Duration) }   // 默认 RunOnceIfWithin(6 h)

pub struct TimerRecord {
    pub id: TimerId, pub session: SessionId, pub principal: Principal,
    pub venue_template: VenueTemplate, pub spec: TimerSpec, pub catch_up: CatchUp,
    pub payload: String, pub next_due: Timestamp, pub last_fired: Option<Timestamp>,
    pub state: TimerState,   // Active / Paused / Done / Cancelled
}
```

- 定时器存主库 `timers` 表（草案见 10 §7.4），调度器是引擎内一个任务：内存里只保留按 `next_due` 排序的最小堆，睡眠到最近到期时刻（经注入的 `Clock`，便于测试）。增删改经调度器的有界命令通道。
- 到期：提交 `Venue{kind: Timer}` 的回合，信任级取创建者当时的信任级，但不高于 `Member`（定时器输入由模型或用户在过去写下，不代表此刻的授权；需要 `Owner` 能力的动作在执行时仍走审批，08）。
- 周期定时器按 `spec` 从“现在”计算下一次到期，**不补跑积压的多次**。
- 启动补跑见 §13。时钟跳变（系统时间回拨超过 5 分钟）时，调度器重新从库加载，并记 `timer.clock_jump` 日志。

## 11 事件

事件信封与 schema 以 13 为准。回合引擎发出下列类型（全部带 `run`）：

| 类别 | 类型 |
| --- | --- |
| 运行 | `run.started`、`run.state`（每次状态转移）、`run.completed`、`run.failed`、`run.cancelled`、`run.interrupted` |
| 队列与代际 | `queue.enqueued`、`queue.dequeued`、`queue.dropped`、`generation.superseded`、`steer.accepted`、`steer.applied` |
| 请求 | `request.started`、`request.retrying`（06）、`request.finished`（含归一化用量） |
| 流 | `assistant.delta`、`reasoning.delta`、`assistant.message` |
| 工具 | `tool.preparing`、`tool.started`、`tool.progress`、`tool.output`、`tool.finished` |
| 问题 | `question.asked`、`question.answered`、`question.closed`（`reason = dismissed \| run_ended \| expired \| cancelled`）、`question.unanswerable` |
| 上下文 | `context.compact_started`、`context.compact_finished`、`context.compact_skipped`、`context.compact_failed`、`context.notice` |
| 子代理 | `subagent.started`、`subagent.finished` |
| 作业与定时器 | `job.created`、`job.progress`、`job.finished`、`timer.fired`、`timer.missed` |
| 会话 | `session.expired`（子代理审计会话到期删除，§9.3） |
| 供应商 | `provider.key_disabled`（06 §8.2） |

上表所有类型都登记在 13 §6.2 的事件目录中，哪些落库、哪些只广播以该目录的“持久化”列为准（例如 `request.started`、`tool.progress` 只广播）；落库的事件都先落库再广播（02 §7）。增量事件以批（默认 50 ms 或 4 KiB）合并落库为可重建摘要，完整内容以 `assistant.message` 与账本为准（13 §6.3）。

## 12 失败分类

```rust
// 草案，以实现为准
pub enum FailureKind {
    ProviderAuth,          // 所有密钥认证失败
    ProviderRateLimited,   // 重试耗尽
    ProviderUnavailable,   // 5xx / overloaded，重试耗尽
    ProviderBadRequest,    // 400 类，非溢出
    ContextOverflow,       // 溢出且一次屏障已用
    StreamStalled,         // 流空闲超时，且已有输出（不可重试）
    RequestTimeout,        // 首字节 / 总时长超时，重试耗尽
    ProviderProtocol,      // SSE 或 JSON 畸形、流无终止事件
    ContentFiltered,
    OutputTruncated,       // §7 连续 length 拒绝
    StoreUnavailable,      // StoreBusy 等（02 §6），不静默丢写
    SandboxUnavailable,    // 仅当回合级要求沙盒而无法生效（08，失败关闭）
    Internal,              // 非法状态转移等不变量破坏
}

pub struct RunFailure { pub kind: FailureKind, pub detail: String, pub request_seq: Option<u32>, pub provider: Option<ProviderErrorInfo> }
```

- `detail` 写真正知道的事实（期望值、实际值、HTTP 状态、供应商原文前 2 KiB），不写猜测的原因（00 §3）。
- 每个 `FailureKind` 映射到 `gqy_core::ErrorKind`，并对应 `gqy ask` 的退出码（13）。
- 工具失败不是运行失败：它以工具结果回到模型。

## 13 启动恢复

只在 daemon 启动、网关开始接受请求之前执行一次（02 §9）。步骤：

1. **非终态运行**：`Planning`、`Compacting`、`Streaming`、`AwaitingApproval`、`ExecutingTools` 全部标为 `Interrupted`，按 §3.3 收尾。已发出但无结果的工具调用写入合成结果：

   | 效果类别 | 合成结果 |
   | --- | --- |
   | `ReadOnly`、`Presentation` | `Interrupted by daemon restart before completion.` |
   | `Writes`、`Exec`、`Network` | `Interrupted by daemon restart; the call may have partially taken effect. Verify the current state before retrying.` |

2. **回合内压缩中断**：压缩提交是单事务（05 §7），未提交即等于没发生；记录 `context.compact_failed{reason: "interrupted"}`。
3. **待回答问题**：标为关闭，发 `question.closed{reason: expired}`。
4. **作业**：`Running` 的作业，若 `pid_start` 对应进程仍存活（pid 与启动时间都匹配），按 02 §6 终止整个进程组；统一标为 `Lost`，发 `job.finished{state: Lost}`。v2 首版不重新接管孤儿进程的输出管道。
5. **队列**：`turn_queue` 中的排队项，交互式场所（Tui、Web、Cli）的一律丢弃（客户端连接已断，发 `queue.dropped{reason: restart}`）；非交互式场所（Connector、Timer、Job）的，入队时间在 `queue_restart_ttl`（默认 30 min）内的按原顺序重新准入，超时的丢弃并记录。
6. **定时器**：`next_due < now` 的定时器按 `CatchUp` 处理：`RunOnceIfWithin(d)` 且 `now − next_due ≤ d` 时补跑一次（`timer.fired{late_by}`），否则记 `timer.missed`；周期定时器随后按 §10.2 计算下一次。
7. 恢复摘要写入日志一行：`recovery interrupted_runs=… lost_jobs=… requeued=… dropped=… timers_fired=… timers_missed=…`。

## 14 边界与失败模式

- **执行权唯一**：会话同一时刻至多一个非终态、非 `Queued` 的运行，或一个独占操作。这由 actor 状态保证，不依赖锁。
- **审批无超时**：等待可以无限长，但不占全局许可；取消令牌依然有效。
- **子代理死锁**：父运行持有全局许可等待子运行，子运行从独立池取许可，所以不会互等。子代理深度默认 1，进一步排除递归放大。
- **插话与压缩**：回合内压缩只折叠当前回合之前的回合（05 §5 的当前回合保护），插话收件箱不受影响。
- **定时器风暴**：同一时刻大量到期时，定时器回合同样受场所配额约束（Timer 类别默认 4）。
- **不做的事**：回合级自动重试、工具级自动重试、孤儿进程重新接管、定时器积压多次补跑。

## 16 测试与守护

每条都要求“去掉对应实现后会红”（铁律 10）。

- **状态机穷举**：对所有 `(RunState, Event)` 组合断言转移表；删掉任意一行转移，测试红。
- **配对完整性属性测试**：随机注入取消、超时、流错误、daemon 崩溃（在任意 await 点），断言账本中每个 `tool_call` 都恰有一个 `tool_result`。去掉 §3.3 第 1 步，测试红。
- **并行落账顺序**：mock 工具让第 1 个调用最慢，断言结果按规范顺序落账；把落账改成按完成顺序，测试红。
- **屏障**：一次响应含 `[read, write, read]`，断言 `write` 在两个 `read` 之间独占执行（用时间戳区间不重叠判定）。
- **length 规则**：mock 供应商返回 `finish_reason=length` + 两个工具调用，断言零执行、两条合成结果；连续 2 次后 `Failed(OutputTruncated)`。
- **插话安全点**：在工具执行中途插话，断言插话条目位于该批全部工具结果之后；并跑 04 的字节前缀门禁。
- **代际**：连续 3 次 `supersede` 提交，断言只有最后一个运行对外投递。
- **子代理**：深度超限返回固定文案；父取消后 1 秒内子运行终止；全局许可占满时子代理仍能完成（死锁回归）。
- **长命令转作业**：`sleep 200` 在第 120 s（暂停时钟）返回作业句柄，进程仍存活；硬上限到期后进程组全部退出。
- **定时器补跑**：停机跨越一个到期点，重启后补跑一次；跨越超过 `catch_up` 窗口则记 `missed`；周期定时器积压 5 次只补 1 次。
- **启动恢复**：在 `ExecutingTools` 中杀 daemon，重启后运行为 `Interrupted`，`Exec` 类合成结果使用“may have partially taken effect”文案。
- **唯一入口**：`cargo xtask arch` 检查 `SessionActor::new` 与运行任务构造不可从 `gqy-engine` 外部访问（02 §3.3）。
