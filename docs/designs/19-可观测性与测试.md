# 19 · 可观测性与测试

> 状态：【规划】。前置阅读：[00 设计理念](00-设计理念.md)（铁律 1、6、9、10；§3 文件体积；§5 平台范围与施工流程）、[01 总体架构](01-总体架构.md)（§6 工程基线）、[02 运行时与并发模型](02-运行时与并发模型.md)（§10 测试与守护）。

## 1 目标

1. **出了问题能定位。** 任何一次失败都能从日志里按 `request_id` / `session` / `run` 串起来，且日志不含正文与密钥。
2. **缓存与用量可核对。** 每次模型请求一行绝对数日志；每次上下文改写一行原因日志（铁律 9）。
3. **每次测试都有反馈。** 技术栈文档要求“每次测试都能显示出反馈，从而知道哪些地方出错需要修复和改进”。`cargo xtask test` 输出可读摘要，失败定位到文件行号与期望/实际值，同时产出 JSON 报告。
4. **门禁可执行、有区分能力。** 每条铁律都有机器检查；每条检查都证明过“违规时会红”（铁律 10）。
5. **本地与 CI 同一实现。** CI 工作流只调用 `scripts/` 与 `cargo xtask`，本地能原样复现（scripts/CLAUDE.md）。

## 2 v1 教训

- `usage-history.jsonl` 不轮转、每次全量读；token 口径漏算 tool_flow，偏差约 57 倍【v1 实测】。
- 每请求一行绝对数日志、不记正文、保留 14 天，以及所有上下文改写记 `context_rewrite reason=`——这是 v1 做对的地方，v2 继承。
- 共享进程级缓存导致测试偶发失败；`refactor-check.sh` 因 `set -u` 从未跑到后三道门禁；联网路径无夹具；无浏览器自动化【v1 实测】。
- 测试计数门禁：数 passed + failed，不得低于已提交的基线；有意删测试时同一提交更新基线【v1 实测，CI `test-count` 作业】。
- 一次“修复”用恒为绿的测试验证：不加修复也是 0 行 stderr，用户装上后噪声照旧。结论：**先证明不修时会红**（v1《理念》）。
- 门禁脚本是 Python（`arch_dep_check.py` 等），与“运行时与测试一律 Rust”冲突。

## 3 日志与追踪

### 3.1 span 层级

```text
daemon{version, pid}
 ├─ http{request_id, method, route, caller_kind}          # 网关每个请求
 ├─ session{session}                                      # actor 生命周期
 │   └─ run{run, turn, venue_kind, parent_run?}
 │       ├─ request{req_seq, provider, model}             # 一次模型请求
 │       ├─ tool{call, name, effect}                      # 一次工具调用
 │       │   └─ proc{pid, pgid}                           # 子进程
 │       └─ compact{trigger}
 ├─ store.writer{batch_id}                                # 单写者批次
 ├─ blocking{label}                                       # gqy_core::blocking::run（02 §2）
 └─ connector{platform, account, connection} / mesh{peer}
```

- span 字段只放 ID 与枚举，不放正文。`#[instrument(skip_all, fields(...))]` 是默认写法，由 xtask 规则检查 `#[instrument]` 必须带 `skip_all`（防止把参数整体 Debug 打进日志）。
- 所有 ID 类型实现 `Display` 为稳定短格式，便于 grep。

### 3.2 输出与文件

| 输出 | 格式 | 内容 |
| --- | --- | --- |
| stderr（前台运行 / `daemon run`） | 人读紧凑格式 | 级别 ≥ `info` |
| `logs/daemon.YYYY-MM-DD.jsonl` | JSON 行 | 级别 ≥ `info`（`GQY2_LOG` 可调，语法同 `RUST_LOG`） |
| `logs/requests.YYYY-MM-DD.jsonl` | JSON 行 | 只含 target `gqy::usage` 与 `gqy::context_rewrite`（§3.3、§3.4） |

- **轮转**：按日；单文件超过 256 MiB 时当日滚动为 `.1`、`.2`。
- **保留**：14 天。清理在 daemon 启动时与每日零点由保留作业执行（10 §9.3 的 `work_items`），不依赖外部 logrotate。审批与权限审计不写日志文件，唯一来源是主库 `audit_log` 表（08 §9.1，保留 180 天，10 §9.3）。
- **写入不阻塞回合**：日志写入走 `tracing-appender` 式的非阻塞写线程与有界队列（容量 8192）；满时丢弃 `debug`/`trace` 级别并计数，`info` 以上等待至多 50 ms 后丢弃并计数，丢弃计数每分钟报一行 `warn`。这是 02 §7 允许的“降级”类别（日志不是用户数据）。
- 目录布局归 10（`logs/`），级别与路径可在 12 的配置中覆盖。

### 3.3 每请求缓存用量日志

每次模型请求结束（成功、失败、取消都写）写一行，target `gqy::usage`，**只有绝对数，不记正文**：

```text
{"ts":"…","session":"…","run":"…","req_seq":3,"epoch":3,"purpose":"main|compact_fork|aux:title|aux:judge|…",
 "provider":"deepseek","model":"deepseek-chat","protocol":"openai-chat","cache_semantics":"best_effort",
 "input_uncached":1302,"cache_read":38211,"cache_write":0,"output":417,"input_total":39513,
 "hit_ratio":0.967,"prefix_hash":"…","prefix_bytes":152033,"prev_prefix_extends":true,
 "prev_input_total":39100,"expected_read_floor":39040,"miss_suspect":false,
 "ttfb_ms":812,"elapsed_ms":6420,"finish":"stop|length|tool_calls|error|cancelled","estimated":false,"retry":0}
```

- 四桶互斥：`input_uncached / cache_read / cache_write / output`（06）。`cache_read + cache_write > input_total` 时记 `malformed_usage` 并保留原始值，不修正（报错说它真正知道的）。
- `prev_prefix_extends`：本次请求字节是否为同会话上一请求的字节前缀延伸（04 的在线判定）。为 `false` 且不是计划内事件时额外写一行 `warn target=gqy::prefix`，用于发现前缀漂移。
- 辅助请求以 `purpose` 区分（取值即 04 §11 的 `RequestPurpose`：`main`、`compact_fork`、`aux:<kind>`），独立统计（v1 教训：fork 摘要命中曾漏记）。`prev_input_total`、`expected_read_floor`、`miss_suspect` 的定义见 04 §14。
- **单一路径**：这一行与数据库 `llm_requests` + `usage_records` 表（10 §7.5）由同一个 `UsageRecord` 值产生：`record_usage(&UsageRecord)` 先经 store 在一个写作业里写入两表，再发 tracing 事件，再发 `request.finished` 事件（13）。不存在第二处计算用量的代码。`GET /api/v1/usage` 只读这张表。

### 3.4 上下文改写日志

所有改变“下一次请求前缀”的动作写一行，target `gqy::context_rewrite`：

```text
{"ts":"…","session":"…","reason":"compaction|compaction_undo|surface_change|persona_generation|model_binding_change|layout_version|device_handoff|overflow_recovery|v1_import",
 "from_seq":120,"to_seq":388,"watermark_before":0,"watermark_after":388,"tokens_before":151200,"tokens_after":18400,
 "bytes_before":…,"bytes_after":…,"recover_ref":"blob:<hash>","planned":true}
```

- `reason` 取值即 04 §9.1 `ColdStartReason` 的 snake_case，不另立名单。
- `recover_ref` 指向可恢复的原文（折叠原文 blob，05），满足铁律 9“留下日志和可恢复的原文”。
- 同时发 `context.rewrite` 事件（13 §6.2）。
- `planned: false` 的改写不应出现；出现即 `error` 级别，并由集成测试断言 mock 长会话中计数为 0。

### 3.5 密钥与正文

- 密钥类型 `Secret<T>`（`gqy-core`）：`Debug`/`Display` 输出 `***`，不实现 `Serialize`（写配置文件走专门路径）。
- 请求/响应正文不进日志，`debug` 级别也不进；需要排查字节问题时，用 `gqy doctor dump-request <run> <req_seq>` 从账本重建请求字节到本地文件（04），而不是开日志。
- 守护：集成测试用含已知假密钥 `sk-test-CANARY…` 的配置跑一个完整回合（含失败重试与供应商错误），然后扫描 `logs/` 下全部文件与 stderr 捕获，断言不出现该字符串与用户正文中的标记词。去掉 `Secret` 的 `Debug` 实现改为派生后此测试必红。

### 3.6 运行时指标

第一版不引入 Prometheus 等外部系统。`GET /api/v1/daemon/status`（13 §5.1）提供：活动运行数、各信号量占用、store 写队列深度与 p99 排队时间、blocking 池占用、事件订阅数与 lagged 次数、日志丢弃计数。TUI/Web 的诊断页读取它。

### 3.7 性能预算矩阵

全局性能预算的唯一定量清单（14 §11 的 TUI 表是其中一节的细化）。预算都是**设计初值**，第一次实测后照实校准并写回；预算**不是** CI 失败条件（§4.2：基准只作警告），但超过预算的 PR 必须附说明。

量法三条（参考 gqy 23-性能预算 的教训）：启动分“第一帧 / 能打字 / 能提交第一轮”三点、冷热分开报；内存按进程分开报 PSS 与私有匿名内存，空会话与大会话（约 8 MB、300+ 条消息）各量一次、空闲后再量一次；原始数据随代码入库。

| 指标 | 预算（初值） | 量法 / 出处 |
| --- | --- | --- |
| 冷启动到能打字（daemon 未运行） | ≤ 150 ms（p95） | 三点法 |
| 热启动到首帧 | ≤ 50 ms（p95） | 同上 |
| 热启动到能提交第一轮 | ≤ 200 ms（p95） | 含会话载入（10 §4.3） |
| 按键到上屏 | ≤ 16 ms（p99） | criterion `tui/frame`（14 §11） |
| store 一次写作业（含同步） | ≤ 20 ms（p99，SSD） | “先落盘后回复”直接影响手感（10 §4.2） |
| daemon 空闲 PSS | ≤ 30 MB | 空会话、无活动回合、空闲 10 分钟后 |
| 每个活动会话增量 | ≤ 5 MB | 大会话 |
| 会话打开（10k 条目，冷路径） | ≤ 100 ms | 投影缓存未命中 |
| 120k 上下文 TTFT | ≤ 1.2 s（观测目标） | 与供应商和网络相关，只作回归对照，不作门禁 |
| release 二进制体积 | ≤ 50 MB（stripped，linux x86_64，初值） | 打包那一步校准 |

- 长驻进程的分配器纪律（glibc arena 上限、空闲 trim）等**实测**显示有明显收益时再引入；没有测量不调优（AGENTS.md“朴素优先于巧妙”）。

## 4 测试分层

| 层 | 位置 | 工具 | 约束 |
| --- | --- | --- | --- |
| 单元 | 各 crate `src/**` 的 `#[cfg(test)]` | `cargo test`、`proptest` | 纯函数优先；不碰网络与真实文件系统（用内存实现） |
| crate 集成 | `crates/*/tests/` | `tempfile`、`wiremock`、mock 供应商 | 每个测试自己的临时数据目录 |
| 端到端 | 仓库根 `tests/` | 启动真实 daemon 组装（进程内或子进程）、`gqy-client` | mock 供应商；真实供应商用例默认 `#[ignore]` |
| 形状 / 字节 | `crates/gqy-ledger/tests/`、`crates/gqy-tools/tests/` | 夹具（sha256） | 夹具刷新走 `cargo xtask fixtures refresh`，差异需在 PR 说明 |
| 浏览器 | `tests/web/` | WebDriver（15 §9） | 无 driver 时显式“跳过” |
| 基准 | `crates/*/benches/` | `criterion` | 不作为 CI 失败条件；结果写入报告供对比 |

### 4.1 共同规则

- **数据目录隔离**：所有测试的数据目录都来自 `TestHome::new()`（10 §3：`tempfile::TempDir` + `GqyPaths::at`，不依赖环境变量）；需要启动子进程 daemon 的 e2e 测试再把 `GQY2_HOME`（D-01 定名前的暂用名）设为同一临时目录。测试 harness 在进程启动时断言该变量不指向 `~/.gqy` 或 `~/.gqy2`，否则立即 panic（测试代码允许 panic；非测试代码的 `GqyPaths` 只返回错误，不 panic）。
- **无共享进程级状态**：禁止测试依赖全局缓存（v1 偶发失败的根因）；02 §8 的“禁止可变全局”规则本身就覆盖测试代码之外，测试中若需要共享夹具，用 `OnceLock` 只读值。
- **确定性时间**：超时类测试用 `#[tokio::test(start_paused = true)]` + 注入 `Clock`（02 §10）；断言结果，不断言耗时。
- **mock 供应商**：统一使用 `gqy-provider` 的 `MockServer`（06 §13：`127.0.0.1` 真实 HTTP、三种协议、脚本化响应、故障注入），不另建进程内替身；需要录制真实供应商字节时再用 `wiremock` 夹具。联网路径全部有夹具（修 v1 缺口）。
- **真实环境用例**：需要真实供应商、真实平台账号或特定操作系统的用例标 `#[ignore = "needs: <env>"]`，由 `cargo xtask test --include-ignored=<tag>` 选择性运行。属性形式固定为 `#[ignore = "needs:<tag>"]`（单标签，`tag` 用小写字母/数字/连字符，如 `webdriver`、`openai`、`macos`）；xtask 扫描测试源码建立“用例 → 标签”映射（扫描器有单测），运行时把**其它** ignored 用例列入 `--skip`，单个 `--include-ignored` 调用即可；出现名字子串冲突时改为逐用例运行并提示改名。实现落在测试运行器那一步（2026-09-28 定）。

### 4.2 关键基准（criterion）

| 基准 | 测什么 | 用途 |
| --- | --- | --- |
| `ledger/plan_request` | 1k / 10k 条目会话的请求规划耗时 | 防止前缀规划随会话长度超线性增长 |
| `ledger/prefix_hash_chain` | 追加一条后的哈希链更新 | |
| `provider/sse_parse` | 每秒解析 SSE 事件数 | 吞吐 |
| `gateway/event_fanout` | 1 个会话 × 32 订阅者的事件扇出 | 背压设计验证 |
| `tui/frame` | `update + layout + draw`（14 §11） | 按键到上屏预算 |
| `e2e/mock_long_session` | mock 供应商 50 轮长会话的前缀命中率（`cache_read / input_total`） | 前缀契约回归的量化指标 |

## 5 测试日志：`cargo xtask test`

### 5.1 行为

```text
cargo xtask test [--workspace | -p <crate>] [--filter <pat>] [--include-ignored=<tag>] [--no-count-gate]
  1. 运行 cargo test（--no-fail-fast），逐行捕获 libtest 输出并同时透传到终端
  2. 解析结果：每个测试二进制的 passed / failed / ignored / 耗时；每个失败的名称、panic 位置、断言信息
  3. 打印摘要（下）；写 JSON 与 Markdown 报告
  4. 运行测试计数门禁（§6.1 第 11 项）
  5. 退出码：任一失败或门禁不过 → 1；解析失败 → 2（报告里写明哪一行无法解析）
```

- 解析对象是 libtest 稳定的文本输出（`test <name> ... ok|FAILED|ignored`、`test result:`、`---- <name> stdout ----` 与 `panicked at <file>:<line>:<col>:`）。libtest 的 JSON 输出格式需要 nightly，不采用。备选是 `cargo-nextest`（JUnit 输出），见 Q-19-1。
- 解析器自身有夹具测试：真实 libtest 输出样本（成功、失败、panic、doc 测试、`should_panic`、编译失败）→ 期望的结构化结果。

### 5.2 终端摘要（示例格式）

```text
══ 测试报告 ══ 2026-10-03 14:02:11  commit 1a2b3c4  平台 macos-aarch64  用时 48.2s
crate               通过   失败   跳过   用时
gqy-core             212      0      0   1.1s
gqy-ledger           341      2      0   6.4s
gqy-gateway          118      0      3   9.8s   (跳过: needs:webdriver ×3)
合计                 671      2      3
── 失败 ──
1) gqy-ledger::plan::tests::tail_order_is_stable
   位置  crates/gqy-ledger/src/plan/tests.rs:88:9
   期望  [System, History, User, UntrustedTail, TrustedTail, Runtime]
   实际  [System, History, UntrustedTail, User, TrustedTail, Runtime]
   复跑  cargo test -p gqy-ledger plan::tests::tail_order_is_stable -- --exact
── 最慢 5 个 ──  …
── 门禁 ──  测试计数 671 ≥ 基线 669 ✔（高于基线，请在本提交更新基线）

```

- 失败信息的“期望/实际”来自断言输出本身：项目约定用 `assert_eq!`/`pretty_assertions` 或自定义断言宏，失败消息必须包含期望值、实际值与相关 ID。解析器只做提取，不猜测。
- “复跑”一行给出可直接复制的命令。

### 5.3 JSON 报告

```rust
// 草案，以实现为准（xtask）
pub struct TestReport {
    pub schema: u32,                 // 1
    pub started_at: String, pub elapsed_ms: u64,
    pub commit: Option<String>, pub platform: String, pub toolchain: String,
    pub suites: Vec<SuiteResult>,    // 每个测试二进制
    pub totals: Totals,              // passed, failed, ignored, executed = passed + failed
    pub failures: Vec<Failure>,      // name, crate, file, line, message, rerun
    pub skipped: Vec<Skipped>,       // name, reason（如 needs:webdriver）
    pub gates: Vec<GateResult>,      // name, ok, detail
}
```

CI 把 `target/gqy-test-report/` 作为构件上传（保留 14 天），并把 `report.md` 写入作业摘要（`$GITHUB_STEP_SUMMARY`）。

## 6 门禁

### 6.1 门禁清单

`cargo xtask check` 依次运行下列检查；每项也可单独运行。“守护的铁律/原则”一列说明它存在的理由。

| # | 门禁 | 命令 | 守护 | 生效阶段 |
| --- | --- | --- | --- | --- |
| 1 | 格式 | `cargo fmt --all --check` | — | 门禁那几步 |
| 2 | clippy | `cargo clippy --workspace --all-targets -- -D warnings`；workspace lints 含 `unwrap_used`、`expect_used`、`panic`、`indexing_slicing`（非测试 deny）、`let_underscore_must_use`、`unused_result_ok`、`await_holding_lock`、`large_futures`、`disallowed_methods`（`Runtime::new`、`block_on`、`unbounded_channel`，02） | 1.5、铁律 5 | 门禁那几步 |
| 3 | rustdoc 文档完整 | lints `missing_docs = "deny"`（库 crate 公开项）、`clippy::missing_errors_doc`、`clippy::missing_panics_doc`（deny）；`RUSTDOCFLAGS="-D rustdoc::broken_intra_doc_links -D rustdoc::private_intra_doc_links" cargo doc --workspace --no-deps` | AGENTS.md“注释写详细” | 门禁那一批 |
| 4 | 层序 | `cargo xtask arch`：按 01 §3 表核对 `cargo metadata` 依赖图；无白名单 | 铁律 4 | 门禁那几步 |
| 5 | 静态规则 | `cargo xtask arch` 附带：`task_local!`、可变全局 `static`、`#[instrument]` 无 `skip_all`、TUI 绕过帧缓冲（14 §4.1）、`deny_unknown_fields`（13 §10） | 铁律 3、6 | 随各阶段加入 |
| 6 | 文件体积 | `cargo xtask size`：`.rs`/`.ts`/`.css` 800 警告、1500 需施工单说明、2000 红 | 00 §3 | 门禁那几步 |
| 7 | 字节前缀 | mock 供应商长会话集成测试：第 N 轮请求是第 N−1 轮的字节前缀延伸（计划内改写除外，且必须有 `context_rewrite` 行） | 铁律 1 | P03 |
| 8 | 形状夹具 | 每个工具面逐工具规范化 JSON 的 sha256 与夹具一致（07） | 铁律 1 | P06 |
| 9 | 迁移只增 | `cargo xtask migrations`：已发布迁移文件的 blake3 清单不可变；新迁移只允许 `CREATE TABLE`、`CREATE INDEX`、`ALTER TABLE … ADD COLUMN`；禁止 `DROP`、`RENAME`、无条件 `UPDATE`/`DELETE`（10） | 铁律 9 | P01 |
| 10 | 协议兼容 | `gqy-protocol` 夹具只增不改 + 反序列化测试；`cargo xtask gen-ts --check` | 13 §10 | P05 |
| 11 | 测试计数 | `cargo xtask test` 内：实际执行数（passed + failed，不含 ignored）≥ 平台基线 `xtask/baselines/test-count.<os>.txt`；降低 → 红；升高 → 警告并提示同提交更新基线 | 铁律 10 | 门禁那几步 |
| 12 | Web 分层与类型 | `cargo xtask web check`（15 §4.2、§3.2） | 铁律 6 | P10 |
| 13 | 模型可见文本英文 | 扫描提示词与工具描述资源文件，禁止 CJK 字符（persona 侧文本与 i18n 目录除外） | 00 §3 | P06 |
| 14 | 供应链 | `cargo deny check`（许可证、重复版本、禁用源、advisories）；`cargo audit`（与 deny 的 advisories 二选一，Q-19-3） | — | 出现 `Cargo.lock` 之后 |
| 15 | 提交与 PR | 已有：`scripts/check-commit-subject.sh`、`scripts/check-pr-standards.sh` | 仓库护栏 | 已有 |

- `no-unwrap` 由第 2 项的 clippy lints 实现，不另写扫描器。测试代码通过 `#[cfg(test)]` 模块级 `allow` 放开。
- **不许吞错误**（00 §3）：`let _ = result` 由 `let_underscore_must_use` 拦；`result.ok();` 这种“看起来处理了、其实只是压掉 `#[must_use]` 警告”的写法由 `unused_result_ok` 拦（Clippy 1.82+，restriction）。确需丢弃时必须写 `#[expect(…, reason = \"…\")]`，把理由留在代码里（2026-09-28 定，00 §5）。
- 每一项门禁在引入它的施工单中附带“违规样例”测试：构造一个违规输入（临时 crate、临时迁移文件、临时 TS 文件），断言门禁报红。去掉门禁中的规则后，这个样例测试必须变红——门禁自身也要有区分能力。

### 6.2 测试计数基线为什么按平台

`cfg(target_os)` 使三个平台执行的测试集合不同（例如 Landlock 只在 Linux）。基线按 `linux`、`macos`、`windows` 分别记录；Windows 只跑单元测试（§8），其基线只统计单元测试。

## 7 验证纪律：先红后绿

- **修 bug**：先写复现测试并提交到分支（或在 PR 描述中贴出它在修复前的失败输出），再修复。PR 模板（`.github/pull_request_template.md`，P00 新增）有必填项“修复前失败的证据”。
- **新功能**：守护测试写完后，临时注释掉被守护的实现（或将关键常量改错），确认测试变红，再恢复。PR 描述写明“去掉了什么、哪条测试变红”。
- **变异测试（周期性）**：对 `gqy-ledger`、`gqy-provider` 的解析与规划模块、`gqy-tools` 的参数收口、08 的策略函数，每周用 `cargo-mutants` 跑一次（非阻塞 CI 作业）。存活的变异体列入报告，由维护者决定补测试或登记为等价变异。
- “修完之后现象没了”不构成验证；验收步骤必须包含“不修时能复现”的对照（v1《理念》）。

## 8 CI 与分支流程

### 8.1 流程

- 每张施工单一个工作树与分支：`step/Pxx-NN-<短名>`，检出到 `.worktrees/Pxx-NN-<短名>/`（仓库根 `AGENTS.md`；00 §5 施工流程决策）。
- 分支上的提交推到远端跑 CI；CI 全绿是验收的一部分。验收通过后整理成正式提交，经 PR 合入 `main`，由 `pr-standards` 等必需检查把关；不在本地快进推送 `main`。
- 必需状态检查（required checks）、分支保护、绕过权限属于 GitHub 仓库设置，需要仓库管理员配置，不能由本地 YAML 自动完成（scripts/CLAUDE.md）。

### 8.2 工作流形态（P00 新增 `.github/workflows/ci.yml`）

```text
on: pull_request, push(main), workflow_dispatch
permissions: {}（各作业只授予 contents: read）
所有 action 按 commit SHA 固定（与现有 security-review.yml 一致）；checkout 设 persist-credentials: false

jobs:
  checks       (ubuntu-latest)       scripts/ci-checks.sh      → cargo xtask check 的第 1–6、9、10、13 项
  test-linux   (ubuntu-latest)       scripts/ci-test.sh        → cargo xtask test（全量：单元 + 集成 + e2e + doc）
  test-macos   (macos-latest, arm64) scripts/ci-test.sh        → 同上
  test-windows (windows-latest)      scripts/ci-test.sh --unit → cargo build --workspace + 仅单元测试（--lib --bins）
  docs         (ubuntu-latest)       scripts/ci-docs.sh        → 第 3 项 rustdoc 门禁
  web          (ubuntu-latest)       cargo xtask web build + web check；浏览器测试在 P10 后加入
  supply-chain (ubuntu-latest)       cargo deny check —— 仅在 Cargo.lock 存在后添加
  mutants      (schedule weekly, 非阻塞)  cargo mutants --in-diff 或指定 crate
每个测试作业：上传 target/gqy-test-report/ 为构件；report.md 写入作业摘要
```

- **平台矩阵**（00 §5 平台范围）：Linux 与 macOS（Apple 芯片）跑全部检查与测试；Windows 只要求编译通过与单元测试通过，缺失的能力（沙盒、PTY 等）在 `gqy-sys` 中报告为不可用并失败关闭，相应测试以 `cfg` 排除。
- `scripts/ci-*.sh` 是薄封装：`set -euo pipefail`、定位仓库根、调用 `cargo xtask …`，保证本地与 CI 同一实现（scripts/CLAUDE.md）。Windows 作业用 Git Bash 运行同一脚本。
- 现有 `security-review.yml` 的说明“Cargo 清单未出现前不添加 Rust 审计步骤”继续有效：`supply-chain` 作业与 `cargo deny` 配置（`deny.toml`）在第一个 `Cargo.lock` 入库的同一施工单中加入。
- 缓存：`Swatinem/rust-cache`（固定 SHA）按 `Cargo.lock` 与工具链缓存；缓存不影响正确性，失效时只变慢。

### 8.3 本地快速检查

| 场景 | 命令 |
| --- | --- |
| 提交前 | `cargo xtask check --fast`（fmt、clippy、arch、size） |
| 改了某个 crate | `cargo xtask test -p <crate>` |
| 推送前 | `cargo xtask check && cargo xtask test` |
| 复现 CI | `scripts/ci-test.sh`（与 CI 同一脚本） |

## 9 边界与失败模式

| 情况 | 行为 |
| --- | --- |
| 日志磁盘写满 | 写线程报错计数，daemon 不因日志失败而停止；`/daemon/status` 显示日志降级 |
| libtest 输出格式变化导致解析失败 | `cargo xtask test` 退出码 2，报告指出无法解析的行；不把“解析失败”当成“通过” |
| 测试被 `#[ignore]` 大量标记以躲过失败 | 测试计数只数执行的用例，被忽略的用例会让计数下降而报红 |
| 基准波动 | 基准不作为失败条件 |
| 真实供应商用例 | 默认跳过，报告中单列“跳过（needs: …）”，不计入通过 |
