# 20 · v1 数据导入

> 状态：【规划】。前置阅读：00（铁律 9、D-01、D-06、D-07）、[10 存储与数据演进](10-存储与数据演进.md)、[11 记忆与知识库](11-记忆与知识库.md)、[12 人格、配置与场所](12-人格配置与场所.md)。账本条目类型见 04。本文定义 `gqy import-v1`：把 v1（gqy-agent v0.7.x）的数据目录单向导入到一个全新的 v2 数据目录。共存期命令名为 `gqy2 import-v1`（D-06 待定），下文用 `gqy` 指代。

## 1 目标与原则

1. **源只读，永不修改。** v1 的 `~/.gqy` 在导入前后逐字节不变（按文件 blake3 与 mtime 验证）。回退 v1 只需要不再使用 v2。
2. **预演 → 核对 → 应用**（00 §5 已定决策）。默认只预演；应用前必须核对通过。
3. **目标必须是新目录。** 应用阶段在临时目录中构建完整的 v2 数据目录，核对通过后一次 `rename` 到位。失败或放弃时删除临时目录即可回滚，不存在“导了一半”的目标。
4. **不静默丢数据。** 所有不导入的内容都在报告中逐项列出（路径、行数、原因）；它们仍然留在 v1 目录里。
5. **确定性。** 同一份源数据导入两次，得到的目标数据（除导入时间戳外）完全相同。

## 3 命令

```text
gqy import-v1 [--from <v1 dir>] [--to <v2 dir>] [--apply] [--include <set>] [--exclude <set>]
              [--report <dir>] [--sample <n>] [--seed <u64>]
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--from` | `$GQY_HOME`（v1 的变量），否则 `~/.gqy` | v1 数据目录 |
| `--to` | `GqyPaths` 的根（`~/.gqy2`，D-01） | 必须不存在或为空目录 |
| `--apply` | 否 | 不带时只做预演与核对，不创建目标 |
| `--include` / `--exclude` | 见 §5 默认集合 | 可选类别：`sessions,memory,kb,personas,config,extensions,files,artifacts,usage,history,platform` |
| `--sample` | 20 | 抽样对比的会话数 |
| `--seed` | 0 | 抽样种子，保证报告可复现 |

退出码：`0` 成功（预演无阻断问题 / 应用完成）；`1` 核对失败；`2` 参数或环境错误；`3` 源被占用（v1 daemon 在运行）；`4` 目标非空。

## 4 流程

```text
discover ─▶ snapshot ─▶ plan ─▶ (dry-run 报告，结束)
                           └─▶ build(staging) ─▶ verify ─▶ commit(rename) ─▶ 报告
                                                     └─ 失败：删除 staging，报告，退出 1
```

### 4.1 discover（发现）

- 识别布局标记与各库位置；读取每个 SQLite 的 `user_version` 与表清单。
- 检查 v1 daemon 是否在运行：沿用 v1 自己的判定（`state/gqy/core.sock` 可连接，或 `core.lock`/`starter.lock` 被持有）。运行中则退出码 3，提示先 `gqy daemon stop`（v1）。
- 对源目录中将要读取的每个文件记录 `(路径, 大小, mtime, blake3)`，作为“源未被修改”的基线。

### 4.2 snapshot（快照）

- 源库一律**不直接打开**。每个 SQLite 连同 `-wal`、`-shm` 三件套一起复制到 staging 的 `source-snapshot/`（10 §9.1 的三件套规则；v1 08-21 的事故就是单独复制活库）。复制后在副本上执行检查点与 `PRAGMA quick_check`，然后只读打开副本。
- 快照期间再次检查 v1 daemon 未启动；结束后重算源文件 blake3，与基线不一致就中止（说明有进程在写）。

### 4.3 plan（规划）

- 逐类别生成导入计划：每张源表的行数、将生成的目标行数、跳过的行及原因、将要复制的文件与总字节、配置转换结果。
- 预演到此为止：写出报告（§9），不创建目标目录。报告中阻断级问题（例如库完整性检查失败、目标非空）会让退出码为 1 或 4。

### 4.4 build（构建）

- 在 `--to` 的同级目录创建 `.<name>.importing-<ts>/`，按 10 的布局初始化一个全新的 v2 数据目录（执行全部迁移）。
- 通过 `gqy-store` 的写接口写入（后台车道，大批量事务，每 1000 行一个事务），不绕过 10 的触发器与约束。
- 文件复制优先使用 reflink / `clonefile`（同文件系统时），否则普通复制；复制后校验 blake3。

### 4.5 verify（核对）

在 staging 目录上执行，全部通过才进入 commit：

| 检查 | 方法 |
| --- | --- |
| 行数 | 每个映射对：源行数 = 目标行数 + 报告中的跳过数 |
| 内容哈希 | 每个会话：按回合顺序对 v1 `user_content`、`assistant_content` 计算 blake3 链；对 v2 对应 `Channel::Raw` 条目重算，二者相等 |
| 记忆 | 每个 persona：`(content, kind, visibility, owner_principal)` 多重集合的哈希一致 |
| 文件 | 每个复制的文件：blake3 一致 |
| 抽样对比 | 按 `--seed` 抽取 `--sample` 个会话，渲染 v1 回放文本与 v2 账本文本的统一 diff，写入报告；差异必须全部落在 §7.3 列出的“允许差异”类别中 |
| 字节回放 | 对每个导入会话调用 v2 请求规划（04）两次，两次字节必须相同；并断言首个 v2 请求带有计划内冷启动标记 |
| 完整性 | 目标库 `integrity_check`、`foreign_key_check`，blob 引用全部存在 |
| 源未改 | 重算源文件 blake3，与 discover 基线一致 |

### 4.6 commit（提交）

- `rename(staging, --to)`，然后 `fsync` 父目录。目标库 `meta` 表写入 `imported_from = v1:<源路径>`、`imported_at`、`importer_version`、源清单哈希。
- 报告复制到目标的 `import/v1-<ts>/`。
- **回滚**：v2 尚未使用时，删除整个 `--to` 目录即可；v1 目录从未被修改。

## 5 映射表

### 5.1 会话（conversation.db → `gqy.db`）

每个 `home/<user>/conversation.db` 以及旧位置 `state/conversation.db` 都导入同一个 `gqy.db`，用 principal 区分归属（10 §10）。

| v1 | v2 | 规则 |
| --- | --- | --- |
| `accounts` | `accounts` | `role` 超级管理员 → `owner`，其余 → `member`；`password_hash` 若为 v2 支持的算法则保留，否则置为需重设（报告列出） |
| `home/<user>` 身份 | principal | owner 身份 → 本机 owner principal；成员 → `principal("web", install_id, account_id)` |
| `sessions` | `sessions` | `session_id` → 新 `SessionId = "ses_" + ULID(时间=created_at, 随机部分=blake3("v1", home, v1_id) 截断)`，保证确定性；`kind`：`user`/`subagent`/`room`/`room-member` 对应映射；`persona` 空串 → `default`；`workspace` → `workspace_root`；`name` → `title`；`model_override`、`sort_key`、`last_request_at` 不导入 |
| `sessions` 的冻结 Surface | `venue_json`、`persona_generation`、`surface_hash`、`system_blob` | 按导入时的 v2 persona 与 `Venue{kind: Tui, trust: Owner}`（成员会话为 `Web/Member`；平台会话由 `platform_session_bindings` 推出 `Connector`）现算一次并冻结 |
| `turns` | `turns` + `ledger_entries` | 见 §5.2 |
| `turn_tool_reports`、`turns.tool_reports`、`tool_reports_archive` | `ledger_entries(kind=LegacyToolReport)` | 仅在该回合没有 `tool_flow` 时使用（v20 之前的回合）；原始 JSON 作为 blob 保留取证 |
| `question_exchanges` | `questions(kind='ask', status='answered')` | 历史记录 |
| `image_assets`、`artifact_assets`、`user_attachments`（`data` 列或 `state/attachments/<id>/<name>` 文件）、`turn_inline_media` | `blobs` + `attachments` / `artifacts` | 按 blake3 去重；`turn_inline_media` 同时生成对应位置的账本条目，保持回放顺序 |
| `session_reviews` | `session_reviews` | `delivered_entry_seq` 置空；不重新投递 |
| `platform_session_bindings` | `session_bindings` | `binding_key = platform/account/kind/conversation/participant/persona` |
| `platform_access_grants`、`platform_access_audit` | 16 的 `connector_grants`、08 的 `audit_log` | 审计标记 `imported=1`，只读 |
| `turns.status='running'` | `turns.status='interrupted'` | 并为未配对工具调用补写取消结果（02 §9 同规则） |

### 5.2 回合 → 账本条目

v1 的“三份内容分离”与 v2 的通道一一对应：`raw_content`（v1 列名 `user_content`）→ `Channel::Raw`；`display_content` → `Channel::Display`；`context_messages` → `Channel::Context`。

| v1 回合字段 | v2 条目（按顺序） |
| --- | --- |
| `user_content` | `UserMessage`，Raw |
| `display_content`（与原文不同时） | `UserDisplay`，Display |
| `context_messages`（JSON 数组，化石尾巴） | 每个元素一条 `Fossil`，Context，**载荷为该元素的原样 JSON 字节** |
| `tool_flow`（v20 起：原生 tool_calls 与工具输出） | 交替的 `AssistantToolCalls` / `ToolResult` 条目；参数保留模型原样字节 |
| `tool_flow` 为空时的 `tool_reports` | `LegacyToolReport`（渲染为 v1 的扁平备忘文本） |
| `assistant_content`、`assistant_reasoning` | `AssistantMessage`（reasoning 作为同条目的独立字段；v1 未保存签名，见 §7.2） |
| `is_summary = 1` 的回合 | `Checkpoint` 条目 + `ledger_watermarks` 一行，`covers_through` 为 `compact_hidden_json` 中最后一个被隐藏回合的最后一条目；`compact_extras`（压后回灌文件）作为 Context 条目跟在 checkpoint 后 |
| `hidden = 1` 的回合 | 正常导入，位于水位以下（仍可被 `search_evicted_context` 检索，11 §6.5） |
| `token_context_end`、`generation_tokens`、`generation_ms`、`assistant_provider_id`、`assistant_model` | `turns` 对应列或条目元数据 |
| `token_prompt`、`token_cache_read`、`token_total` | 不生成 `usage_records`（那是逐请求明细，v1 只有回合汇总）；写入 `turns` 的导入统计字段 |
| `tool_footprint` | 条目元数据，供 05 的 footprint 合并 |
| `replay_journal` | 若存在，作为该回合的 Display 转录 |

### 5.5 配置转换（JSONC → TOML）

- 解析 JSONC（去注释、容忍尾逗号），按 v1 `AppConfig` 的字段逐项映射到 12 §3.2 的段。映射表是导入器中的一张常量表，每一项写明 v1 路径、v2 路径、转换函数。
- **密钥分离**：v1 字段名匹配 `api_key|key|token|secret|password` 的值，以及 `providers[].api_key`（逗号分隔的多 key）写入 `secrets.toml`，配置中改为 `key_ref`。报告只显示 `sk-…a1b2` 形式的提示。
- v1 的投放层设置（`cache.keepalive`、`write_grace_ms`）若用户打开过，则保留为打开：这是用户基于自己供应商实测做出的选择。
- 数值超出 v2 边界的按边界截断，并在报告中列出原值与新值。
- 无法映射的键（包括 v1 的 `extra` 映射）逐项列出；值若像密钥则打码。
- 生成的 `gqy.toml` 带注释：顶部注明“由 gqy import-v1 从 <路径> 生成”。

## 6 不导入的内容及原因

| 内容 | 原因 |
| --- | --- |
| `queued_prompts` 中未消费的排队消息 | 运行时状态；已消费的内容已在回合中 |
| `session_loaded_items` | stub 工具的加载状态由 v2 账本中的 `load_tools` 结果体现 |
| `turn_journal_*`、`turn_redo_*`、`subagent_trace`、`state/subagent-checkpoints` | 运行中间态与短期审计（v1 本身只保留 7 天） |
| `app_state`、`state/web-sessions.json`、`state/web-passwords/`、`invites` | 登录态与一次性邀请码；导入后重新登录 |
| `goals` | 目标循环不在内核范围（00 §4） |
| `sponsor_records`、`home/*/ledger/ledger.db`（记账） | 伴侣类功能，后续以扩展回归（00 §4）；数据留在 v1，扩展落地后另行导入 |
| `platform_plugin_kv`、`platform_meme_refs`、`data/memes/`、`meme.db` | 插件状态与表情包库，属于扩展 |
| `shared_files`、`home/*/shares`、`data/shared` | 分享链接与托管副本，v2 重新分享 |
| `room_participants`、`room_messages` | 聊天室依赖 16 的设计；16 定稿前不导入 |
| `evicted_context.db` | 内容与 conversation.db 中 `hidden=1` 的回合重复；导入器统计重复率写入报告，非重复行数 > 0 时标为警告 |
| `memory_embeddings`、`semantic_index.db`、`evicted_embeddings` | 向量与模型绑定，v2 首版不做向量（D-05） |
| `pending_events`（记忆待处理）、`skill_records` | 派生状态；未整理的短期日记已作为 `short_term` 导入，会被 v2 整理器处理 |
| `state/compact/`（折叠原文 fold-*.md）、`prompt-fingerprints`、`persona-hints`、`prompt.sha256` | 缓存与指纹，v2 自行生成 |
| `cache/`、`backups/`、`bin/`、`github/`、`state/models`、`state/relay` | 可重建或与数据无关 |
| `config/shell/`、`webui-theme*.css` | 与 v2 的 shell 集成与前端不兼容；报告提示手动迁移 |

## 7 化石与字节回放

### 7.1 为什么不追求“与 v1 字节相同”

v2 的 tools 数组、system 段结构、尾部外壳都与 v1 不同。无论如何导入，每个会话在 v2 中的第一个请求都与 v1 最后一个请求的前缀不同，供应商缓存必然冷启动一次。因此目标定义为：

1. **语义保真**：模型在 v2 中看到的历史内容与 v1 最后一次看到的相同，包括化石中的旧时间戳、旧的召回块、群聊元数据（`context_messages` 原样导入）。
2. **v2 内部字节稳定**：导入完成后，这些条目的字节就固定了；v2 之后每一轮都逐字节回放它们（04 门禁对导入会话同样成立）。
3. **计划内冷启动只发生一次**：每个导入会话的首个 v2 请求开启新纪元，原因 `ColdStartReason::V1Import`（04 §9.1），记 `context_rewrite reason=v1_import`；导入的 v1 条目用 `EntryKind::Legacy(..)`（04 §4.2）。

### 7.2 已知无法保真的部分

| 情况 | 处理 |
| --- | --- |
| v20 之前的回合没有 `tool_flow` | 渲染为 `LegacyToolReport` 扁平文本，与 v1 当时的回放方式一致 |
| v1 未保存 Anthropic thinking 签名 / Responses 不透明条目 | 导入的历史回合不带签名 thinking；v2 回放时按供应商规则省略历史 thinking（06）。只影响已完成的回合，不影响工具循环中的当前回合 |
| v1 `context_messages` 的 JSON 结构与 v2 `Message` 不完全一致 | 载荷保存原样字节；v2 适配器把 `Fossil` 条目按 v1 的角色与文本渲染，渲染函数只有一个（铁律 6），并有夹具测试 |
| v1 会话超过 v2 模型的上下文窗口，且没有摘要 | 首个 v2 回合按正常规则触发压缩（05），不在导入时压缩 |

### 7.3 抽样对比中允许的差异类别

`legacy_tool_report_render`、`thinking_omitted`、`display_only_markup`、`timestamp_precision`（v1 TEXT 时间转毫秒）。其他任何差异都让核对失败。

## 8 幂等与重跑

- **确定性**：新 ID 由源键派生（§5.1），时间戳来自源数据，遍历顺序按源主键排序；导入时间只写进 `meta` 与报告。守护测试：同一源导入两次到两个临时目录，`gqy export --canonical`（10 §11）的输出逐字节相同。
- **重跑**：目标必须为空，所以重跑 = 删除目标后重新执行，结果与上一次相同。
- **增量导入**（共存期继续使用 v1，之后再把新增内容补进 v2）：首版不支持，见 Q-20-1。报告会记录源清单哈希；对已导入过的目标再次运行时，导入器比对哈希并提示“源自上次导入后有 N 个会话变化”。
- **中断**：任何阶段中断（Ctrl-C、断电），只会留下 `.importing-*` 临时目录；下次运行时检测到后提示删除，不会继续使用半成品。

## 10 边界与失败模式

| 情形 | 行为 |
| --- | --- |
| v1 daemon 运行中 | 退出码 3，不做任何读取之外的操作 |
| 源库 `quick_check` 失败 | 该库标为阻断；`--exclude` 掉对应类别后才能继续 |
| 源库 `user_version` < 2（无 sessions 表） | 提示先用 v1 ≥ 0.7 打开一次完成 v1 自身迁移 |
| 源库版本高于 39 | 按列存在性探测读取（按列名读，未知列忽略），报告标注“未知的新版本” |
| 目标非空 | 退出码 4 |
| 磁盘空间不足 | plan 阶段估算所需空间（库 + 文件 × 1.1），不足时预演即报告阻断 |
| 构建或核对中任一失败 | 删除 staging，报告失败项，退出码 1 |
| 源在导入过程中被修改 | 基线哈希不一致，中止并报告 |

## 11 测试与守护

- **夹具**：`tests/fixtures/v1/` 下放若干最小 v1 数据目录（由 v1 仓库的测试工具生成，脱敏），覆盖 conversation.db v12、v20、v25、v39 四个版本，含摘要回合、隐藏回合、运行中回合、附件、多身份、多 persona 记忆、JSONC 配置（含注释与多 key）。
- **源不变**：导入前后对夹具目录做完整哈希树比较；故意让导入器以读写方式打开源库时测试变红。
- **测试隔离**：源与目标都放在 `tempfile` 临时目录，`GQY2_HOME` 指向临时目标（10 §3）。
- **映射完整性**：对每张 v1 表，断言它出现在 §5 映射表或 §6 不导入清单之一中（常量表驱动）；v1 夹具出现未登记的表时测试失败。
- **核对有区分能力**：在构建阶段注入一个故障（丢弃一条回合、篡改一个字节、漏复制一个附件），verify 必须失败并指出具体会话与检查项。
- **确定性**：§8 的双次导入比较。
- **回放门禁**：导入会话在 mock 供应商上连续跑 3 轮，第 2、3 轮请求分别是前一轮请求的字节前缀延伸（04）；首轮带 `v1_import` 冷启动标记。
- **密钥**：导入后的 `gqy.toml` 中不含任何夹具中的密钥明文；`secrets.toml` 权限为 0600（`cfg(unix)`）。
- **principal 连续性**：v1 夹具中某条 `principal` 可见性记忆，在 v2 中用同一平台身份的 scope 能召回，换一个身份不能召回。
