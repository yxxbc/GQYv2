## 1 为什么重写：v1 的底层坏在哪里

v1（本地 gqy-agent，v0.7.0，约 30.9 万行 Rust、1288 次提交）证明了“长会话、本机执行、多入口”的本地 Agent 可以运行。它的问题不是方向不对。2026-09-15 代码评审的原话是：“方向是对的，纪律罕见地好；问题不在分层，在接线。”但接线的问题已经下沉到底层，靠打补丁收不住。下面每一条都有 v1 的代码或事故作证据。

### 1.1 并发模型错位（最致命）

v1 的主程序是 `#[tokio::main(flavor = "current_thread")]`：所有会话的回合都挤在同一个线程的 `LocalSet` 上跑。只要有一处同步阻塞，所有会话就一起冻住。实例如下：

- 压缩持有全局锁，做 30 秒的阻塞 HTTP；
- MCP 读 stdout 没有超时，一旦卡住就永久占住执行线程；
- 在锁内同步写 SQLite；
- 2026-09-09，压缩在 actor 主循环里直接 await，把全部会话拖死了四分半。

之后的补救是 4 处临时 runtime、17 处 `block_on`、71 处 `spawn_blocking`。这是用补丁对抗模型，补丁跟不上调用点的增长。

**v2 的回答**：使用多线程 runtime，每个会话由一个 actor 持有状态，阻塞 IO 走专用线程池，SQLite 由单一写者线程负责。每一次等待都必须有超时、能取消、有上界（见 02）。

### 1.2 回合上下文是隐式的

v1 的回合上下文靠 9 个 `task_local` 传递（工作区、会话、是否子代理、来源终端、平台发送者、来源、桥深度、模型、生图额度），再加上沙盒的 `SANDBOX`。任何函数都能偷偷读这些值，于是出现两个后果：

- 为了读 task_local，`llm` 层反向依赖了 `tools` 层；
- 子代理绕过 actor 直接启动回合，评审时已经说不清它跳过了哪些闩锁。

**v2 的回答**：`TurnContext` 是显式参数，禁止用 task_local 传业务上下文。依赖方向由 crate 边界在编译期强制（见 01、02）。

### 1.3 只有接线，没有抽象

v1 的规模和抽象程度不成比例：

- 全库只有 5 个 trait，没有 LLM trait、Tool trait、Memory trait，也没有子系统钩子；
- 加一个工具要改 23 个文件，其中 9 处是纯接线；
- `Agent` 结构体有 43 个字段；
- `AgentMode` 与 persona 清单是两个并存的真相源，前者有 336 处引用。它迁到一半就停了，原因是一动就会改变提示词的字节。

评审里有一句话：“半成品重构比不改更贵——不改只有一个概念，改一半有两个。”

**v2 的回答**：先定能力边界的 trait，每个概念只有一个真相源。加一个内置工具只动一个文件，外加一行注册（见 07）。

### 1.4 存储碎片化，“只追加”没守住

- 同一个用户的数据分散在多个地方：每个身份一份 `conversation.db`、每个 persona 一份 `memory.db` 和 `evicted_context.db`，另有独立的账本库、两个知识库，以及一堆 JSON/JSONL；
- 规则写的是“只追加迁移”，39 条迁移（`LATEST_VERSION = 39`；白皮书按 09-26 快照写的是 37）里却有 DROP TABLE、批量 UPDATE 置空和 drop 后重建；
- 有一次直接 `fs::copy` 活库，丢了锁，数据库损坏。

**v2 的回答**：一个主库加一个内容寻址的 blob 目录。迁移只允许增量，由测试钉住。备份只用 `VACUUM INTO`（见 10）。

### 1.5 错误、超时与失败模式缺位

- 错误全用 `anyhow`，非测试代码里有 2432 处 `unwrap/expect`；失败分类只能靠字符串穿透 context；
- 超时只作用于建连，没有流空闲超时，流可以永久挂起；
- 重试嵌套成 3×3 次，且没有退避；
- daemon 只监听 SIGINT，收到 SIGTERM 时跳过优雅停机；
- 有一整个“静默兜底”家族，例如 `_ => ("", "")`，以及位置索引导致某个界面永远进不去。

**v2 的回答**：每个 crate 用 `thiserror` 定义带分类的错误；clippy 禁止非测试代码 `unwrap`；超时分为建连、首字节、流空闲、总时长四类；停机协议写进设计（见 02、19）。

### 1.6 跨语言胶水与外部依赖

v1 仓库里有 332 个 `.py`，包括 iMessage 桥（Python LaunchAgent 加一个 C 启动器，启动器里编进了绝对路径）、架构门禁、e2e 测试。前端的配置默认值是从 Rust 手抄过去的。运行时还依赖 PATH 上的一串外部命令。

**v2 的回答**：运行时和测试一律用 Rust。前端类型由 Rust 类型生成。外部命令变成可选的“增强”，缺失时明确降级，不能静默失败（见 13、15、16、19）。

### 1.7 两条路径口径不一

09-24 TUI 验收的 10 个问题都出自同一个根因：同一个东西有两条渲染或计算路径，而且各自的口径不同。缓存工程里“序列化路径必须唯一”说的也是这件事。

**v2 的回答**：把“单一路径”提升为全局铁律（见 §2 第 6 条）。

## 2 铁律

铁律是不可协商的约束。违反铁律的设计必须先修改本文并经用户确认。每条都要有机器可执行的守护，由 19 与施工单负责落地。

1. **前缀即契约。** 相同的会话状态必须产生逐字节相同的请求前缀。上下文按 append-only 追加；发送过的瞬态内容一律化石化，逐字节回放。压缩（及其撤销）是唯一的前缀改写点，采用纪元模型：水位记录只追加，每次压缩开启一个新纪元；撤销压缩也是开启新纪元、恢复旧视图（一次计划内冷启动），历史条目与已写的水位记录永不改写（04 §9、05 §11）。守护：mock 供应商断言“同一纪元内第 N 轮请求是第 N−1 轮请求的字节前缀延伸”（04）。
2. **执行归属唯一。** 同一会话同一时刻只有一个推进者，所有发起回合的来源（终端、网页、平台、定时器、子代理）都走同一个准入入口。守护：准入是唯一的 `pub` 入口，由类型系统保证（02、03）。
3. **上下文显式。** 回合所需的一切通过 `TurnContext` 值传递，不用 task_local 或全局可变状态传业务数据。守护：lint 加架构检查（01）。
4. **依赖只向下。** crate 分层由 Cargo 依赖图强制，xtask 检查层序，不设豁免白名单（01）。
5. **每一次等待都有上界。** 所有 IO、通道、锁、子进程都要有超时、可以取消、容量有界。不允许无界通道，不允许在异步上下文里做同步阻塞 IO（02）。
6. **单一路径、单一事实来源。** 同一个概念只有一个真相源，同一种输出只有一条渲染或序列化路径。配置默认值、API 类型、命令表都要从一处生成。
7. **权限由代码判定。** 提示词里的任何文字都不承担鉴权。principal 来自入口的真实身份，并随会话冻结。不可信文本与可信字段走不同通道（08、12、16）。
8. **失败关闭，边界诚实。** 沙盒或策略无法生效时拒绝执行，不降级裸奔。能力不能覆盖的范围要在文档里写明，例如“沙盒不管网络”（08）。
9. **用户数据不静默丢失。** 迁移只增不删；导入先预演、再核对、最后应用；任何上下文改写都要留下日志和可恢复的原文（05、10、20）。
10. **验证必须有区分能力。** 修复前测试必须是红的，修复后是绿的；只在修复后跑绿不算验证。每次测试都要输出可读的反馈日志（19）。

## 3 设计原则（可权衡）

原则指导取舍。与铁律冲突时，以铁律为准。

- **先立边界，后扩能力。** 依赖顺序是 FFI、沙盒、存储、账本，然后才是工具和扩展。
- **决定构造什么，而不是装上再关。** persona 与场所决定工具面，在会话创建时快照并冻结（12）。
- **数据结构先行，能力用 trait 暴露。** 低层只暴露类型和 trait，由上层组装。trait 至少要有一个真实实现，外加一个测试替身；只为“将来可能”准备的 trait 不写。
- **普适层默认开，投放层默认关。** 在任何供应商上都只有收益的优化默认打开；收益取决于供应商行为的优化默认关闭，并在配置注释里写明适用条件（06）。
- **报错说它真正知道的。** 错误信息写出期望值和实际值，不写猜测的原因。落库保留原始输入，作为取证链。
- **模型可见文本用英文短句**，界面文本走 i18n。
- **文件体积**：目标 ≤ 800 行，上限 1500 行，超过 2000 行 CI 报红。超过上限要在施工单里写明拆分计划。
- **先读规范，再读代码，最后推理。** 供应商行为以实测为准，文档只作参考（06）。

## 4 范围与非目标

**范围**（已由用户确认，2026-09-28）：“内核先行，伴侣后置”。

- 设计文档覆盖全部领域。
- 施工顺序：工程地基 → 存储与类型 → 供应商 → 账本 → 回合引擎 → 生产级网关 → 工具 → 权限与沙盒 → 压缩 → TUI → Web → 人格与配置 → 记忆 → 扩展 → 连接器 → 设备共享 → 导入与发布。
- 语音、记账、玄学、游戏查询、各类日用查询**不进内核**，放到最后以扩展（技能 / 脚本 / MCP / 扩展包）的形式提供。

**非目标**：

- 不引入必须依赖的中心服务器。服务器只是可选的设备角色（17）。
- 不引入 Python / Node.js 运行时依赖。Node 也不能作为构建依赖；前端只在构建期用 esbuild 独立二进制（15）。
- 平台范围按 §5 的决策执行：Linux 与 macOS 完整成立，Windows 只保证能编译、能跑单元测试。在此之外不承诺更细的平台清单，只描述“某平台暴露哪些能力、缺少时怎样失败”（09）。
- 不做多租户 SaaS。GQYv2 面向个人及其设备；外部联系人通过连接器以不可信身份接入。
- 不自称解决模型内生的长期记忆问题。GQYv2 维护的是模型之外的连续性。

## 7 术语表

| 术语 | 含义 |
| --- | --- |
| 回合（Turn） | 一次用户输入引发的全部推进：若干次模型请求与工具执行，直到模型给出最终回复、失败或被取消 |
| 请求（Request） | 回合内的一次模型 API 调用 |
| 运行（Run） | 一次回合执行的实例，有 `run_id`；重试、续跑会产生新的 run |
| 会话（Session） | 一条连续的对话与账本；同一时刻至多一个活动回合 |
| 账本（Ledger） | 会话的 append-only 条目序列，是请求字节的唯一来源（04） |
| 化石（Fossil） | 已经发出的瞬态内容，落进账本后逐字节回放 |
| 水位（Watermark） | 某个纪元的视图起点（压缩覆盖到哪里）。水位记录只追加：压缩写一条新记录并开启新纪元；撤销压缩也写新记录、开启新纪元并恢复旧视图。已写的记录与账本条目永不改写（04 §9、05 §7、§11） |
| 纪元（Epoch） | 一段满足“逐次字节前缀延伸”的连续请求；每次计划内冷启动（压缩、撤销、换模型等，04 §9.1）开启新纪元，纪元号单调递增 |
| 工具面（Tool Surface） | 会话内对模型可见的 tools 数组；会话内字节恒定 |
| stub | 工具面中的懒工具形态：真名 + 一行摘要 + 宽松参数壳 |
| 场所（Venue） | 回合的来源入口，例如 TUI、Web、QQ 群、定时器、子代理；它声明信任级与能力 |
| principal | 发起者的稳定身份标识，由入口的真实身份派生，随会话冻结。编码沿用 v1：对 `(platform, account_id, user_id)` 做长度前缀拼接后取 blake3 前 24 hex，文本形式 `principal:<24hex>`（10 §4.4） |
| persona | 配置单位：提示词 + 启用集，决定构造哪些工具与子系统 |
| 感知矩阵 | 把“系统知道什么”与“模型看到什么”拆成 Host / Workspace / Origin / Context 四维 |
| 网关（Gateway） | daemon 对外的 HTTP/SSE/WS/UDS 门面 |
| 连接器（Connector） | 外部平台 I/O 进程，通过 gqy-connector 协议接入网关 |
| 普适层 / 投放层 | 默认开启、处处有益的优化 / 默认关闭、依赖供应商的优化 |
| 施工单（Work Order） | `docs/construction/` 下一个 PR 大小的实施单元 |
